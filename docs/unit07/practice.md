# 单元 7 课后练习

本单元的核心是**把页面拆成有清晰接口的组件**。所以练习的重点不是“功能做出来”，
而是“**接口设计得对不对**”。

**三道必做题，一道选做题。**

## 必做题

### 练习 1 · 把活动列表页拆成至少三个组件

拿你之前写的活动列表页（没有的话按下面的字段自己写一个），拆成至少三个组件：

| 组件 | 职责 |
| --- | --- |
| `SearchBar` | 关键词输入、状态筛选、搜索与重置按钮 |
| `ActivityTable` | 表格展示：标题、类型、组织者、报名截止时间、状态、操作 |
| `StatusTag` | 活动状态标签：状态到文案与颜色的映射 |

**具体要求**

1. **列表页只负责“数据和请求”**，展示与交互交给子组件。
2. 每个组件写出**属性表**与**事件表**，写在组件文件的顶部注释里，格式如下：

```js [接口注释示例]
/**
 * 活动列表表格
 * 属性：
 *   activities  Array   必填，活动列表数据
 *   loading     Boolean 可选，默认 false，是否显示加载态
 * 事件：
 *   row-click   (activity) => void  点击某一行
 *   edit        (activity) => void  点击“编辑”
 */
```

3. 状态标签组件要能处理四种状态（草稿、报名中、报名截止、已结束），
   并给未知状态一个兜底显示。

**验收标准**

| 项目 | 要求 |
| --- | --- |
| 拆分数量 | 至少三个组件，且每个都能用一句话讲清职责 |
| 属性数量 | **每个组件的属性不超过 5 个**；超过的要说明为什么 |
| 接口注释 | 每个组件都有完整的属性表与事件表 |
| 单向数据流 | 子组件没有直接修改 `props`（包括数组成员与对象属性） |
| 命名与目录 | 组件名至少两个单词；基础件与业务件分开放 |
| 可运行 | 页面能正常显示列表、搜索、切状态 |

::: warning 这一题最容易被扣分的地方
**属性堆太多。** 常见的是给 `ActivityTable` 传一堆回调：

```js
// ✗ 每个操作一个事件，属性表爆炸
:on-edit、:on-delete、:on-offline、:on-view-signups、:on-export
```

先想一想：这些操作能不能合并成一个语义化的事件？

```js
// ✓ 一个事件带上“动作”与“数据”
emit('action', { type: 'edit', activity })
```

两种设计都能用，但**接口的可读性差别很大**。选一种并说明理由。
:::

### 练习 2 · 写一个可复用的分页器组件

需求：分页器自己不持有页码，**页码与总数由父组件通过属性传入**，
用户翻页时通过事件通知父组件。

```vue [目标用法]
<Paginator
  :total="total"
  :current-page="page"
  :page-size="pageSize"
  @change="onPageChange"
/>
```

**具体要求**

1. 属性：`total`（总数，必填）、`currentPage`（当前页）、`pageSize`（每页条数）。
2. 事件：`change`，参数是新的页码。
3. 页数由 `total` 与 `pageSize` 算出（用 `computed`），**不要另传一个 `pageCount`**。
4. 上一页 / 下一页按钮在边界时禁用。
5. 页码按钮在页数很多时要做省略（比如显示 `1 2 3 ... 12 13`），
   不要一次渲染 100 个按钮。
6. 给属性加类型校验与默认值，**数组和对象类型的默认值要写成函数**。

**验收标准**

| 项目 | 要求 |
| --- | --- |
| 单向数据流 | 分页器不修改 `currentPage`，只发事件 |
| 计算逻辑 | 页数、页码列表都用 `computed`，不用 `watch` 手动同步 |
| 边界处理 | 第一页禁用“上一页”，最后一页禁用“下一页” |
| 页码省略 | 页数多时不会渲染出上百个按钮 |
| 参数校验 | `total` 用 `required`；`pageSize` 有默认值（比如 10） |

::: tip 边界情况要一个一个想
写这种组件时，先把边界情况列出来，再写代码：

- `total` 是 0（列表为空）→ 分页器显示什么？建议**整个隐藏**，由父组件控制，或者组件内部返回空。
- 只有 1 页 → 要不要显示分页器？
- `currentPage` 超出范围（比如数据刷新后从第 5 页变成了第 2 页）→ 谁负责纠正？
- `total` 变化导致页数变少 → 当前页要不要自动回到最后一页？

**这四个问题的答案应该在组件的注释里写清楚。** 不写清楚，用的人就会踩。
:::

### 练习 3 · 可清空的搜索输入框

用 `v-model` 实现一个搜索输入框组件，功能是：

1. 输入框右侧有一个“清空”按钮，**只在有内容时显示**。
2. 点清空按钮，值变为空字符串，并让输入框重新获得焦点。
3. 按 Esc 也能清空。
4. 父组件用 `v-model` 绑定值。

```vue [目标用法]
<SearchInput v-model="keyword" placeholder="搜索活动名称" />
```

**具体要求**

1. 组件内部**不能直接改 `props.modelValue`**，要通过 `emit` 通知父组件。
2. 清空后自动聚焦 —— 需要用到模板引用，说明你用的是 `useTemplateRef` 还是 `ref(null)`，以及为什么。
3. `placeholder` 用带默认值的属性传。
4. **不要用 `defineModel` 写第一版**，先手写一遍属性与事件；
   写完再加一个 `defineModel` 的版本做对比。

**验收标准**

| 项目 | 要求 |
| --- | --- |
| 事件声明 | 声明了 `update:modelValue`，并在输入时触发 |
| 清空逻辑 | 清空时既改值又聚焦，两件事都做了 |
| 按钮显示 | 值为空时清空按钮不显示 |
| 两版对比 | 能在注释里说出两版代码量的差别与各自的适用场景 |
| 密码框复用 | 组件同时支持 `type` 为 `text` 与 `password`（加分项） |

::: warning 一个容易写错的地方
清空之后要聚焦，但**聚焦不能写在事件处理里紧接着执行**。原因是清空会改变 DOM
（按钮消失了、输入框的值变了），必须等 DOM 更新之后再聚焦。

提示：回顾[6.5 生命周期](/unit06/05-lifecycle)里的 `nextTick`，
以及[案例 05 里插入语法后设置光标](/unit06/06-case-markdown)的做法。
:::

## 选做题

### 练习 4 · 评论楼中楼（递归组件）

用递归组件实现一个“评论楼中楼”结构，用在活动详情的讨论区。

数据结构：

```js
const comments = [
  {
    id: 1,
    author: '林小雨',
    content: '请问这个活动需要自带器材吗？',
    createdAt: '2026-03-01 10:20',
    replies: [
      {
        id: 2,
        author: '陈志远',
        content: '同问，我也没有球拍',
        createdAt: '2026-03-01 10:25',
        replies: []
      }
    ]
  }
]
```

**具体要求**

1. 递归组件展示评论，层级缩进。
2. 每一层最多显示 3 条回复，超出的部分显示“展开更多回复（还有 5 条）”。
3. 每条评论有“回复”按钮，点击后在它下面展开一个输入框，
   提交后**追加到这条评论的 `replies` 里**。
4. 只允许回复到第二层（第三层及以后的“回复”按钮都指向第二层的父评论）——
   这条规则怎么写，说明你的思路。

**验收标准**

| 项目 | 要求 |
| --- | --- |
| 递归命名 | 递归组件用 `defineOptions({ name })` 显式命名 |
| 缩进 | 层级缩进明显，且层数变化不影响代码 |
| 状态 | “哪条评论正在回复”用单值表达，不是每条评论一个 `isReplying` |
| 单向数据流 | 子组件不直接改 `comments`，通过事件上抛，由页面改数据 |
| 深度限制 | 能说明第三层回复被折叠到第二层的处理方式 |

::: tip 第 3 条与第 4 条的思路
第 3 条的做法和[案例 09 的编辑态](/unit07/06-case-editable-table)是一样的：
用一个 `replyingId` 表示“正在回复哪条”，进入与退出都只改这一个值。

第 4 条有一个简洁的做法：递归时把“可回复的目标 id”一起往下传。
到了第二层再把目标改成自己，往下就不变了。**想想这个“祖先 id”是怎么一层层传下去的**
—— 这和[案例 03 里传 `level`](/unit07/05-case-tree)是同一种手法。
:::

## 自检标准

做完之后逐条自查：

- [ ] 每个组件都能用一句话说清职责
- [ ] 每个组件的属性不超过 5 个，超出时有明确理由
- [ ] 每个组件都有属性表与事件表，写在文件顶部
- [ ] 子组件没有直接修改 `props`（含数组与对象的内部成员）
- [ ] 对象与数组类型的属性默认值写成了函数
- [ ] 递归组件用了 `defineOptions({ name })` 显式命名
- [ ] 分页器不持有页码，只通过事件通知
- [ ] 可清空搜索框用了 `v-model`，并能在清空后正确聚焦

## 常见问题

::: details 拆分的时候，页面里还剩什么
页面（`views/` 下的组件）剩下三件事：

1. **数据**：`ref` 出来的列表、加载状态、错误信息。
2. **请求**：调用接口、处理成功与失败。
3. **编排**：哪个子组件在什么时候显示、收到事件后怎么改数据。

**模板部分应该很短** —— 如果页面的 `<template>` 还是超过 50 行，说明还有该拆的没拆。
:::

::: details 子组件需要父组件的某个方法，该传回调还是发事件
优先发事件。原因：

- 事件是**声明式的接口**，写在 `defineEmits` 里，用的人一看就知道有哪些；
- 传回调函数时，父组件要写 `:on-xxx="..."`，属性表会混进“行为”，不好维护；
- 事件的名字能表达“发生了什么”，回调的名字往往只能表达“要做什么”。

**只有在“需要把子组件当函数用”的极少数场景**（比如列表渲染的插槽），才考虑传函数。
:::

::: details 递归组件传属性太啰嗦怎么办
如果递归时每一层都要重复写五六个属性，说明这些属性**是“全局上下文”**，
每一层都需要但和层级无关。

这种情况应该改用[依赖注入](/unit08/02-provide-inject)：在顶层 `provide` 一次，
每层 `inject` 拿。递归组件里传属性和依赖注入的取舍标准是：

- 属性**每一层都可能不同**（比如 `level`、`node`）→ 用属性传。
- 属性**每一层都一样**（比如 `selectedId`、`expandedKeys`、`keyword`）→ 用依赖注入。
:::

::: details 分页器做完了，但父组件怎么知道该请求第几页
父组件监听 `change` 事件，改自己的 `page`，然后**在 `watch` 里发请求**：

```js
watch(page, () => loadList())
```

或者直接在事件处理函数里发：

```js
function onPageChange(next) {
  page.value = next
  loadList()
}
```

两种都行。**注意不要两处都发** —— 既 `watch` 又在事件里发，会请求两次。
:::

::: details 为什么我的组件在别的页面复用不了
三个常见原因：

1. **属性里塞了业务数据**：比如 `ActivityTable` 的属性叫 `activities`，
   它只能渲染活动。改成 `rows` 加 `columns` 就通用了。
2. **组件内部写死了接口调用**：它在 `onMounted` 里自己拉数据，别处用就会请求错误的接口。
   必须把数据来源交给使用方。
3. **样式里用了父组件的类名**：拆出去之后样式失效，或者反过来污染了别处。

**复用的前提是“它不知道自己被谁用”。**
:::
