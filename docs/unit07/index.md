## 先看一个 400 行的页面

活动详情页的第一版是这样的：一个 `ActivityDetailView.vue`，**400 行**。里面装着：

- 顶部活动标题、状态标签、操作按钮（编辑、下架、导出报名名单）
- 中部的活动信息表（类型、组织者、报名截止时间、名额、已通过人数）
- 报名进度条
- 场次与场地列表
- 报名记录表格（带搜索、状态筛选、分页）
- 底部的审核记录时间线

这个页面能跑，也能交付。问题出在**第二次改需求**的时候：

> 需求一：活动列表页也要显示“报名进度条”。
> 需求二：审核页也要用“报名记录表格”，但那边不显示“导出”按钮。
> 需求三：场次列表在另一个页面（场次管理）也要用。

三个需求意味着三处改动，而每次改动都要在 400 行里找到对应的那段，还要小心别碰坏旁边的逻辑。
第二次、第三次之后，没人敢动这个文件了。

**这就是组件化要解决的问题。** 这个单元教你两件事：**怎么拆**，以及**拆完之后父子之间怎么说话。**

## 组件化的收益来自“接口”，不是来自“文件数”

先把一个常见的误区说清楚：**拆成组件不等于变好。**

如果拆完之后，父组件需要给子组件传八个属性才能让它工作，或者子组件里到处读父组件的数据，
那你只是把一个 400 行的文件变成了五个互相纠缠的文件，**总复杂度反而上升了**。

真正带来收益的是**清晰的接口**。所谓接口，就是两句话：

> 这个组件**需要**什么？（属性，props）
> 这个组件**会告诉外面**什么？（事件，emits）

有了这两句话，组件才是一个“能独立讲清楚的东西”。别人用你的组件时，不需要读它的内部实现，
只需要看它的接口。

## 这次课的 4 学时怎么用

| 环节 | 时长 | 做什么 |
| --- | --- | --- |
| 检查预习 | 0.3 学时 | 抽问：把一个页面拆成组件，判断依据是什么？`props` 为什么不能改？ |
| 讲解 | 1.4 学时 | 重点讲 7.1 的拆分依据与 7.2 的单向数据流；7.3 讲清事件名的书写规则 |
| 现场任务 | 1.8 学时 | 两人一组，把自己作业里的活动列表页拆成至少三个组件，并画出接口表 |
| 复盘 | 0.5 学时 | 挑两组对比：拆得多的是不是更好？哪些属性其实不该传？ |

::: warning 这次课最容易做偏的两件事
1. **为了拆而拆** —— 把 20 行的模板拆成 4 个组件，父组件传 10 个属性。
   判断标准是“这个组件能不能独立讲清楚”，不是“文件数够不够多”。
2. **改 props** —— 子组件里写 `props.list.push(item)`，数据看起来变了，但父组件的数据也跟着被改了，
   控制台还会给警告。这是本单元必须彻底搞清楚的一条。
:::

## 这个单元的两个产出

**一、自研卡片组件**

不是用 UI 库的 `Card`，而是自己写一个：

| 要求 | 说明 |
| --- | --- |
| 可复用 | 至少在两个页面里用过 |
| 有接口 | 属性不超过四个，事件不超过两个 |
| 有默认值 | 不传属性时也能正常显示 |
| 能装内容 | 主体区域可以放任意内容（这个能力在[单元 8 的插槽](/unit08/01-slots)里正式学） |

**二、可自定义单元格的表格组件**

这是本单元的核心产出。要求：

| 项目 | 要求 |
| --- | --- |
| 数据通过属性传入 | 表格组件自己不持有数据源 |
| 列配置通过属性传入 | 列宽、标题、对齐方式由使用方决定 |
| 操作通过事件上抛 | 点击某一行、点某个按钮，都通过事件通知父组件 |
| 至少两种单元格形态 | 比如文本、状态标签、操作按钮 |

::: tip 为什么是“表格”
因为它是最能暴露接口设计问题的场景：**表格组件要足够通用，
就必须把所有“这块怎么显示、点了做什么”的决定权交回给使用方。**

你会在 7.2 和 7.3 里反复回到这个问题。
:::

## 读完之后

这个单元结束时，你应该能拿着一个组件，用三句话介绍它：

1. 它**需要**什么属性，每个属性是什么类型、有没有默认值。
2. 它**会发出**哪些事件，每个事件带什么数据。
3. 它**不管**什么 —— 也就是哪些决定权在使用方手里。

能说清这三句，你的组件就具备了被复用和交接的基础。下一单元
[单元 8：组件进阶与逻辑复用](/unit08/)会在此基础上讲插槽、依赖注入与组合式函数。
