# 7.1 单文件组件与拆分依据

## 一个 400 行的文件

前面提到的活动详情页，结构大致是这样：

```text [src/views/ActivityDetailView.vue（约 400 行）]
<template>
  ├── 标题与状态标签            （约 30 行）
  ├── 顶部操作按钮组            （约 25 行）
  ├── 活动信息表                （约 50 行）
  ├── 报名进度条                （约 20 行）
  ├── 场次与场地列表            （约 70 行）
  ├── 报名记录表格（含搜索、筛选、分页）（约 140 行）
  └── 审核记录时间线            （约 40 行）
</template>

<script setup>
├── 5 个接口请求
├── 8 个 ref 状态
├── 12 个事件处理函数
└── 3 个 computed
</script>
```

400 行不算很长，一个文件也能维护。真正的问题在**交接**和**复用**：

- 新同学要改“报名记录表格”，必须先读懂上面那六块是干什么的。
- 想在审核页复用表格，只能整段复制 —— 改了一个 bug，另一个地方忘改。
- 报名进度条的两个数字（已通过人数、名额）在列表页也要用到，但算法只写在这里。

所以这个页面该拆。**问题是怎么拆。**

## 先搞清楚一个 `.vue` 文件里有什么

拆之前，得先知道单个文件的三个组成部分各自负责什么。

```vue [src/components/ActivityStatusTag.vue]
<script setup>
// 一、逻辑：数据、计算、事件处理
import { computed } from 'vue'

const props = defineProps({
  status: { type: String, required: true }
})

// 状态 → 显示文案
const STATUS_TEXT = {
  draft: '草稿',
  enrolling: '报名中',
  closed: '报名截止',
  finished: '已结束'
}

// 状态 → 样式类名
const STATUS_CLASS = {
  draft: 'is-draft',
  enrolling: 'is-enrolling',
  closed: 'is-closed',
  finished: 'is-finished'
}

const text = computed(() => STATUS_TEXT[props.status] ?? '未知')
const cls = computed(() => STATUS_CLASS[props.status] ?? '')
</script>

<template>
  <!-- 二、结构：这一段决定了渲染出什么 -->
  <span class="status-tag" :class="cls">{{ text }}</span>
</template>

<style scoped>
/* 三、样式：只作用于这个组件的元素 */
.status-tag {
  padding: 2px 8px;
  border-radius: 10px;
  font-size: 12px;
}
.is-enrolling {
  color: #0a7d32;
  background: #e7f7ec;
}
.is-closed {
  color: #8a6d1f;
  background: #fdf4e0;
}
</style>
```

三块的分工很直白：

| 块 | 作用 | 一句话 |
| --- | --- | --- |
| `<script setup>` | 数据与逻辑 | 这个组件“能做什么” |
| `<template>` | 结构与绑定 | 这个组件“长什么样” |
| `<style scoped>` | 样式 | 这个组件“看起来如何” |

::: tip 三块的顺序不固定
`<script setup>` 写在 `<template>` 前面或后面都可以，Vue 都能编译。
但**团队要统一**。本课程统一为 `script` → `template` → `style`，
因为这样打开文件第一眼看到的是这个组件要什么属性、会发什么事件。

`<template>` 里内容多的时候，把 `style` 放最后也方便快速跳到底部改样式。
:::

### 为什么用单文件组件，不用字符串模板

在 [4.1](/unit04/01-declarative) 里见过用 `template` 字符串定义组件的写法。
单文件组件（SFC，Single-File Component）相比它有三个实际好处：

| 好处 | 具体表现 |
| --- | --- |
| 编译期检查 | `<template>` 里的语法错误在构建时就报出来，字符串模板要到运行时才知道 |
| 工具支持 | 编辑器里有语法高亮、自动补全、跳转定义 |
| 样式隔离 | `<style scoped>` 让样式默认只作用于本组件，字符串模板做不到 |

代价是**必须经过构建工具处理**（`@vitejs/plugin-vue`）。这也是为什么
[单元 2](/unit02/04-vite)要在写 Vue 之前先把构建工具配好。

## `<style scoped>` 到底隔离了什么

`scoped` 这个名字容易让人以为“样式被完全隔离了”。其实它做的事更朴素：**给选择器加一个属性选择器。**

### 原理：加一个 `data-v-xxxxxx` 属性

写这样的代码：

```vue [src/components/ActivityCard.vue]
<style scoped>
.card {
  padding: 16px;
}
</style>
```

构建后大致变成：

```css [构建后的 CSS（示意）]
.card[data-v-a1b2c3d4] {
  padding: 16px;
}
```

同时，这个组件模板里渲染出的元素会被加上 `data-v-a1b2c3d4` 属性。**选择器多了一个条件：
元素必须带这个属性。** 其他组件的元素没有这个属性，自然匹配不上。

::: warning 它不是真正的隔离
它靠的是“属性对得上”。所以有两类情况会“漏”：

1. **子组件的根元素**会同时带上父组件的 `data-v` 属性（Vue 有意这么设计的）。
   于是父组件的 `scoped` 样式**能**作用到子组件的根元素上。
2. **`v-html` 插入的内容**是运行时生成的，不会带上 `data-v` 属性，所以样式一律不生效。

这两条在下面的“常见坑”里有具体例子。
:::

### 遇到子组件内部元素，用 `:deep()`

如果确实需要从父组件给子组件**内部**的元素加样式（比如调一下第三方组件的间距），
用 `:deep()` 穿透：

```vue [src/views/ActivityDetailView.vue]
<style scoped>
/* 父组件想调整子组件内部的表格行高 */
.signup-table :deep(.row) {
  height: 44px;
}

/* 想给子组件根元素加样式，直接写就行，不需要 :deep() */
.signup-table {
  margin-top: 16px;
}
</style>
```

::: danger `:deep()` 用得越多，说明接口设计得越差
`:deep()` 是“绕过封装”的后门。偶尔用一次可以，但如果一个父组件里出现了十条
`:deep()`，说明它在**替子组件决定内部长什么样**。

更好的做法是让子组件自己暴露一个属性（比如 `size="compact"`），由子组件内部决定怎么调样式。
**父组件管“要什么效果”，子组件管“怎么实现”。**
:::

## 该拆哪几处，不该拆哪几处

回到那个 400 行的页面。逐个部分判断：

| 页面里的部分 | 拆不拆 | 理由 |
| --- | --- | --- |
| 活动状态标签 | **拆** | 列表页、审核页、场次页都要用，而且“状态到颜色的映射”是一条独立规则 |
| 报名进度条 | **拆** | 它自己算“已通过 / 名额”的比例，逻辑自成一体；列表页也要用 |
| 场次与场地列表 | **拆** | 场次管理页也要用，而且那边还带编辑按钮，正好用属性控制 |
| 报名记录表格 | **拆** | 审核页要复用，但那边不显示“导出”按钮 —— 用属性区分 |
| 活动信息表 | 不拆 | 只是把已有数据列成几行，拆出去要传 6 个属性，且只在这一页用 |
| 审核记录时间线 | 不拆 | 只在这一页出现，数据来自页面已经拿到的结果，拆出去反而要多传一层 |
| 顶部操作按钮组 | 不拆 | 每个按钮点了都调用本页面的方法，拆出去要传 4 到 5 个事件监听 |
| 标题与副标题 | 不拆 | 纯布局文字，拆出去只增加文件数 |

注意判断的标准不是“这段代码长不长”，而是**它有没有独立的职责、会不会被别处用到**。

## 拆分的三个信号与两个反信号

把上面的判断提炼成可复用的标准。

### 三个“该拆”的信号

| 信号 | 判断问题 | 例子 |
| --- | --- | --- |
| **被复用** | 别的地方也用得到吗？ | 报名记录表格在审核页也要用 |
| **独立变化** | 它的改动会不会经常和周边代码无关地发生？ | 状态标签的颜色规则随设计稿变，但页面其他部分不变 |
| **逻辑自成一体** | 它能不能独立讲清楚自己的输入和输出？ | 进度条只需要两个数字，算完显示一个百分比 |

**三个信号满足任意一个就值得拆。** 满足两个以上基本可以确定要拆。

### 两个“不该拆”的反信号

这两个是最实用的边界判断：

::: danger 反信号一：拆完之后，父组件要传 8 个属性
这说明**这个组件的“输入”太多，边界没划清**。要么是它承担的职责太多，
要么是它其实应该读取更上层的数据（比如用[依赖注入](/unit08/02-provide-inject)），
而不是靠一堆属性喂进去。

**判断标准**：属性超过 5 个就该停下来想一想。不是硬性上限，
但超过这个数往往说明边界有问题。
:::

::: danger 反信号二：拆完之后，子组件仍然要读父组件的上下文
举个例子：子组件里写着 `props.activity.status`、`props.activity.organizer.name`、
`props.currentUser.role`，然后自己根据这些做判断。

这说明它**没有自己的边界**，只是父组件代码的“搬运工”。要么把需要的数据整理好再传，
要么干脆别拆 —— 留在父组件里反而更清楚。
:::

::: tip 一个更本质的判断方法
问自己：**“这个组件我能用一句话介绍清楚吗？”**

- ✓ 可以：“报名进度条，传已通过人数和名额，显示比例。”
- ✗ 不行：“活动详情头部，传活动对象、当前用户、几个回调，它负责显示标题、
  根据状态决定显示哪些按钮、还要处理下架确认弹窗。”

第二句话说明它做了至少三件事，**应该是三个组件，或者干脆不拆**。
:::

## 命名与目录约定

拆出来的组件，名字和位置也要有规矩，否则半年后没人找得到。

### 组件命名：至少两个单词

| 规则 | 好的例子 | 不好的例子 | 原因 |
| --- | --- | --- | --- |
| 用 PascalCase 命名文件 | `ActivityCard.vue` | `activity-card.vue` | 与 Vue 生态一致，编辑器导入时提示正确 |
| 至少两个单词 | `ActivityCard.vue` | `Card.vue` | 单单词容易和 HTML 元素或其他库的组件重名 |
| 名字说明“是什么” | `SignupTable.vue` | `Table1.vue` | 看名字就知道用途 |
| 与父组件配套的用父名前缀 | `ActivityDetailHeader.vue` | `Header.vue` | 一搜就能找到它属于谁 |

**唯一的例外是基础组件的统一前缀。** 比如所有基础组件都以 `Base` 开头：
`BaseButton.vue`、`BaseCard.vue`、`BaseEmpty.vue`。这个前缀本身就在说“我是通用件”。

### 目录组织：基础组件与业务组件分开

```text [src 目录结构]
src/
├── components/
│   ├── base/                    基础组件：与“校园活动”无关，换个项目也能用
│   │   ├── BaseButton.vue
│   │   ├── BaseCard.vue
│   │   └── BaseEmpty.vue
│   └── business/                业务组件：带校园活动业务语义
│       ├── ActivityStatusTag.vue
│       ├── ActivityCard.vue
│       ├── SignupProgress.vue
│       └── SignupTable.vue
└── views/                       页面组件：一个路由对应一个
    ├── ActivityListView.vue
    ├── ActivityDetailView.vue
    └── SignupReviewView.vue
```

判断一个组件放 `base` 还是 `business`，问一句：

> **把它复制到另一个完全不同的项目里，还能直接用吗？**

- 能 —— 它不知道任何校园活动的事，放 `base`。
- 不能 —— 它认识“活动”“报名”“审核员”这些概念，放 `business`。

::: warning 不要建太深的目录层级
见过这样的结构：`components/activity/detail/header/ActivityHeader.vue`。
四层目录，为了找一个组件要点开四次。

**`components` 下面两层就够了**（`base` / `business`，或者按领域分一层）。
层级深不代表组织得好，只代表更难找。
:::

## 小结

- 单文件组件由三块组成：`<script setup>` 管逻辑、`<template>` 管结构、`<style scoped>` 管样式；
  顺序团队统一，本课程按 `script` → `template` → `style`。
- `<style scoped>` 的原理是**加 `data-v-xxxx` 属性选择器**，不是真隔离；
  子组件根元素会被父组件样式影响，`v-html` 生成的内容拿不到样式。
- 要影响子组件内部元素用 `:deep()`，但用多了说明接口设计有问题。
- 拆分的三个信号：**被复用、独立变化、逻辑自成一体**，满足一个就值得拆。
- 拆分的两个反信号：**拆完要传八个属性、拆完仍要读父组件上下文**。
- 组件名至少两个单词；基础组件统一加 `Base` 前缀，与业务组件分开放；
  目录两层就够。

## 常见坑

::: details 坑 1：以为 `scoped` 能完全隔离，结果父组件样式漏进了子组件
**现象**：给父组件里的 `.activity-card` 加了 `margin-bottom`，子组件的根元素也跟着有了外边距。

**原因**：Vue 会让子组件的**根元素**同时带上父组件的 `data-v` 属性。
父组件里针对这个元素的 `scoped` 样式会生效。

**处理**：这是有意设计的行为，用好了很方便（父组件可以控制子组件的外边距）。
如果不想要，就在父组件里用一个包裹元素：

```vue
<div class="card-wrapper">
  <ActivityCard />
</div>
```
:::

::: details 坑 2：`v-html` 的内容样式不生效
**现象**：预览区里的 `h2`、`code` 完全没有样式。

**原因**：`v-html` 插入的元素是运行时生成的，**不带 `data-v` 属性**，
`scoped` 样式匹配不上。

**处理**：用 `:deep()`：

```vue
<style scoped>
.preview :deep(h2) {
  font-size: 20px;
}
</style>
```
:::

::: details 坑 3：拆完发现子组件要改父组件的数据
**现象**：子组件里写了 `props.list.push(item)`，数据变了，但控制台出现警告，
父组件的数据也被改了。

**原因**：`props` 是**单向数据流**，子组件不应该修改它。引用类型的属性被改，
父组件的数据会跟着变，行为不可预测。

**处理**：子组件通过 `emit` 通知父组件，由父组件来改。
这条是下一节 [7.2](/unit07/02-props)的核心内容。
:::

::: details 坑 4：为了“看起来整洁”把 20 行模板拆成 4 个组件
**现象**：一个简单的活动信息表被拆成 `InfoRow.vue`、`InfoLabel.vue`、`InfoValue.vue`，
父组件要传一堆属性，读代码要来回跳四个文件。

**原因**：把“文件行数少”当成了目标。

**处理**：**拆分的目的是降低理解成本，不是减少行数。**
判断标准回到那句话：“这个组件能一句话讲清楚吗？”如果一句话讲的是
“它就是活动信息里的一行”，那它不值得单独存在。
:::

::: details 坑 5：`.vue` 文件不加后缀导入
**现象**：`import ActivityCard from '@/components/business/ActivityCard'` 报模块找不到。

**原因**：`.vue` 文件不在 Vite 默认的自动补全后缀列表里。

**处理**：导入时**一律写全 `.vue` 后缀**。这也是 Vue 官方风格指南的建议 ——
统一写后缀，避免大小写和路径解析带来的歧义。
:::

## 课后练习

::: details 练习 1：判断这些部分该不该拆
下面是一个“活动报名审核页”的组成部分。逐条判断并写理由：

1. 顶部的“待审核 12 条”统计条
2. 报名记录表格（含批量通过、批量驳回）
3. 每行里的“学生信息”小卡片
4. 页面底部的“操作日志”折叠面板
5. 审核时弹出的“驳回理由”输入框

**参考思路**：对每一部分问三个问题：别处用得到吗？它会独立变化吗？
能一句话讲清输入输出吗？第 3 条要想一想 —— 它只在这个表格里用，
但它有明确的输入（一条报名记录）和清晰的展示职责，判断时要权衡。

:::

::: details 练习 2：数一数属性
假设你要把一个表格组件拆出来，需要这些属性：

```text
rows、loading、columns、selectable、showExport、exportFileName、
rowKey、emptyText、pageSize、currentPage、total、onRowClick
```

回答两个问题：

1. 其中哪几个**不应该**是属性？
2. 怎么改能让属性数量降下来？

**参考思路**：`onRowClick` 是事件不是属性，应该用 `emits`。
分页相关的四个属性（`pageSize`、`currentPage`、`total`、以及分页事件）其实属于
另一个组件 —— 分页器。先把职责分开，属性数量自然会降。

:::

::: details 练习 3：给自己的作业做一次拆分
拿出你之前写的一个超过 200 行的页面，做四件事：

1. 画出它的结构树（哪些部分、各占多少行）。
2. 用三个信号逐个判断，标出“该拆”和“不该拆”。
3. 对每个要拆的组件，写出它的**属性表**和**事件表**（先只写名字和类型）。
4. 按 `base` / `business` 决定它放在哪个目录。

**参考思路**：第 3 步是关键。如果你发现某个组件的属性表超过 5 行，
回去重新想边界，不要硬拆。这份练习的产出会在
[7.2](/unit07/02-props)和[7.3](/unit07/03-emits)里继续用。

:::
