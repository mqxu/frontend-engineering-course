# 单元 8 · AI 协作：状态放错位置，最容易出多实例共享的坑

这一章讲复用：插槽、依赖注入、内置组件、组合式函数、自定义指令。目标都是同一个 —— 把一段东西抽出来，让多处能共用。

AI 特别擅长“抽”。你把一段重复了三次的代码贴给它，它几秒钟就能给出一个 `useXxx` 函数。但它抽的时候有一个惯性：**把状态写在函数外面。**

这个惯性是有原因的 —— 写在函数外面，状态只创建一次，看起来“更省”；而且它见过的示例代码里，模块级变量常被当作缓存或单例来用。问题在于，**组件的状态一旦放到函数外面，就变成了所有实例共享的。** 同一个组件在页面上出现两次，两边会互相影响。

而这个 bug 最难查的地方是：它不报错，而且单看一个组件时完全正常。

## 这一章哪些活能交给 AI

判断标准：**“抽”这件事可以交，“状态放哪一层”这件事不能交。**

| 任务 | 能交给 AI 吗 | 为什么 |
| --- | --- | --- |
| 把一段重复逻辑抽成组合式函数 | 可以 | 抄写加改名，机械工作 |
| 生成通用函数的初稿 | 可以 | 有固定套路，改改就能用 |
| 检查有没有状态被写在模块作用域 | 可以 | 它有固定的核对办法，但要你确认组件会不会被用两次 |
| 审自定义指令的钩子写全了没 | 可以 | 机械核对 |
| 解释 `provide` / `inject` 的响应性规则 | 可以 | 讲到能判断对错就够 |
| 解释 `KeepAlive` 的 `activated` / `deactivated` | 可以 | 触发时机它讲得清楚 |
| 决定某个状态该放函数内还是函数外 | **不能直接信** | 它默认往外放，理由是“共享”和“避免重复创建” |
| 决定该用 `provide` / `inject` 还是 props | **不能直接信** | 它偏向用 `inject`，因为写起来少一层 |
| 决定全局通知、模态框的状态放哪 | **不行** | 取决于你的应用结构，也取决于要不要被跨路由复用 |

中间那两行是这一章的重点。这两个判断都不难，但需要你先想清楚一件事：**"这个状态是有几份？"**

## 提示词怎么写

### 1. 让它把逻辑抽成组合式函数，并说明状态的归属

```text
这段逻辑在三个组件里都写了，请帮我抽成一个组合式函数：

[粘贴三段代码]

要求：
1. 抽完之后，逐项列出函数里每一个 ref 或 reactive，说明它为什么放在
   函数内部，而不是写在函数外面
2. 如果某个状态你认为应该放在函数外部（模块作用域），说明理由，
   并告诉我“这个函数被两个组件同时使用时，会发生什么”
3. 函数返回什么、参数收什么，列出完整的签名
4. 函数名按 use 开头，说明为什么取这个名字
```

**为什么这么写**：第 1 点是这段提示词的核心。让它**逐项解释每个状态为什么放在函数内**，它就必须正面回答归属问题 —— 而不是顺手把 `const list = ref([])` 写在文件顶部。

第 2 点是在给它留出“确实可以放外面”的空间，但要求它回答“被两个组件同时使用会发生什么”。**这个问题的答案就是判断标准**：如果答案是“两边会互相影响”，那就不能放外面；如果答案是“没关系，它就是设计成共享的”（比如全局通知），那放外面是对的。

### 2. 让它检查有没有多实例共享的状态

```text
这是我的组合式函数：

[粘贴完整文件]

请做两件事：

一、把这个文件里的所有 ref、reactive、普通变量按位置分类：
| 变量名 | 定义位置（函数内 / 模块作用域） | 如果放模块作用域，多实例会怎样 |
（函数内的也列出来，写“不涉及”）

二、指出哪些状态如果被多个组件同时使用会互相影响。

另外说明：这个函数现在会被几个组件用到？如果某处状态本来就是设计成全局的，
说明它为什么可以全局。
```

**为什么这么写**：把“有没有问题”换成“按定义位置分类”，你就能一眼看到模块作用域那几个变量，逐个判断。要求把函数内的也列出来，是为了让表格完整 —— 只看异常项容易漏。

最后一句很重要：**模块作用域不等于错。** 全局通知、全局模态框这类状态本来就该只有一份（[案例 06](/unit08/06-case-modal)里的模块级 `ref` 就是这么设计的）。加这一句是防止它矫枉过正，把该全局的也改成函数内的。

### 3. 让它审一个自定义指令的生命周期

```text
这是我的自定义指令：

[粘贴完整代码]

请逐一检查：
1. 用到了哪几个钩子，分别是 mounted / updated / beforeUnmount / unmounted 中的哪几个
2. 每个钩子里注册或修改的东西，有没有在对应的卸载钩子里撤销
3. 指令的绑定值变化时会发生什么（考虑 value 或 arg 变了的情况）
4. 如果我把这个指令用在 v-for 生成的一百个元素上，会有什么问题
```

**为什么这么写**：第 4 点最有用。**自定义指令的 bug 在单个元素上通常看不出来，在列表里才会暴露。** 比如一个防抖指令，如果每次 `updated` 都新建一个定时器而不清掉上一次的，一个元素上只是“有点迟钝”，一百个元素上就是卡顿。

第 3 点也常被漏掉：指令的绑定值变了之后，`mounted` 不会再跑，只有 `updated` 会。它写指令时经常只考虑第一次。

## AI 在这一章容易错什么

### 把状态写在模块作用域，导致多实例共享

**现象**：它抽出来的组合式函数长这样：

```js
// ✗ 状态在函数外面
const list = ref([])
const loading = ref(false)
const error = ref('')

export function useActivityList() {
  async function load() {
    loading.value = true
    try {
      list.value = await fetchActivities()
    } finally {
      loading.value = false
    }
  }
  return { list, loading, error, load }
}
```

**原因**：写在函数外面，状态只创建一次，看起来“更省内存”；而且它把这种写法理解成“共享缓存”，觉得是优点。

**后果很好辨认**：这个函数被两个组件同时使用时，两个组件的 `list` 是同一份 —— **在 A 页面筛选出的结果，切到 B 页面还在。** 而 B 页面的代码里根本没有 `list` 的赋值语句，你会去 B 页面找 bug，方向完全错了。

**怎么处理**：判断标准一句话 —— **问“这个状态应该有几份”。**

| 这个状态应该有几份 | 放哪 | 例 |
| --- | --- | --- |
| 每个使用它的组件各一份 | **函数内** | 列表数据、加载状态、筛选条件 |
| 整个应用只有一份 | 模块作用域或 Pinia | 全局通知队列、当前登录用户 |

改法是把它挪进函数内：

```js
// ✓ 状态在函数内，每个组件各一份
export function useActivityList() {
  const list = ref([])
  const loading = ref(false)
  const error = ref('')

  async function load() {
    loading.value = true
    try {
      list.value = await fetchActivities()
    } finally {
      loading.value = false
    }
  }
  return { list, loading, error, load }
}
```

记住一句话：**“整个应用只有一份”的状态，本来就该考虑用 Pinia（[单元 10](/unit10/)），而不是靠模块级变量偷偷共享。** 用 Pinia 的好处是它出现在 store 目录里，别人一眼能看到它是全局的；而模块级变量藏在某个组合式函数的文件里，没人知道它被共享了。

### 组合式函数里注册了监听或定时器，但没有清理

**现象**：函数里 `onMounted` 加了 `window.addEventListener`，但没写 `onUnmounted`。或者在函数里 `setInterval` 之后只返回了一个 `clear` 函数给调用方，指望调用方记得调用。

**原因**：它把“清理”当成了使用者的责任，而不是函数自己的责任。

**怎么处理**：一个原则 —— **谁注册，谁清理。** 函数自己注册的副作用，就在函数自己的 `onUnmounted` 里清掉，不要往外抛。

```js
export function useWindowSize() {
  const width = ref(window.innerWidth)
  function onResize() { width.value = window.innerWidth }

  onMounted(() => window.addEventListener('resize', onResize))
  onUnmounted(() => window.removeEventListener('resize', onResize))  // 自己清

  return { width }
}
```

注意 `onResize` 提成了具名函数 —— `removeEventListener` 必须传**注册时的同一个函数引用**，写成 `() => {...}` 是无效的，而且不报错。

只有在一种情况下才往外抛清理函数：**清理时机不由组件决定**。比如一个“轮询”函数，调用方可能想中途停下来再重新开始，这时返回一个 `stop` 是合理的，但**组件卸载时的兜底清理仍然要留在函数里。**

### 滥用 `provide` / `inject`

**现象**：它把本该用 props 传一层的东西也写成了 `provide` / `inject`，理由是“避免 prop 层层传递”。

**原因**：`inject` 用起来少写一层，看起来更简洁。而“避免 prop drilling”是个正当理由，它用起来没有心理负担。

**怎么处理**：`provide` / `inject` 是有代价的 —— **数据来源变得不明显。** 你读一个深层组件的代码，看到 `inject('activityContext')`，得往上翻好几层才知道这个东西是谁提供的。props 虽然啰嗦，但来源写在标签上，一眼可见。

判断用哪个，看两层：

| 情况 | 用什么 |
| --- | --- |
| 只跨一层 | props 加一个事件，最清楚 |
| 跨多层，但只给某一个子树 | `provide` / `inject`，在最近的那个父级提供 |
| 跨多层，而且是整个应用共享 | Pinia |
| 只是为了让某个深层组件拿到回调 | 还是 props，或者用插槽把内容交给父级 |

顺带一条本项目的约定：`provide` 的键**用 `Symbol` 而不是字符串**。字符串键容易和别的库撞上，而撞上之后是静默失效 —— 注入到的是别人的东西。

### 自定义指令只写 `mounted`

**现象**：指令只实现了 `mounted(el, binding) { ... }`，`updated` 和 `unmounted` 都不写。

**原因**：第一次挂载是最好想的场景，后面的更新和卸载它不主动补。

**怎么处理**：对照这张表，缺哪个补哪个。

| 钩子 | 什么时候跑 | 不写会怎样 |
| --- | --- | --- |
| `mounted` | 元素挂到页面上 | 指令完全不生效 |
| `updated` | 组件更新、且绑定值或所在组件的状态变了 | 绑定值变了界面不跟着变 |
| `beforeUnmount` | 元素即将被移除 | 有些清理可以放在这里 |
| `unmounted` | 元素已移除 | 注册的监听、定时器、观察器全都留着 |

实践上有个偷懒但有效的做法：**把“建立”和“更新”合并到一个函数里。** 比如一个“根据权限决定元素显示与否”的指令，`mounted` 和 `updated` 里的逻辑完全一样，那就抽出来两个钩子都调：

```js
function apply(el, binding) { /* 根据 binding.value 决定显示或移除 */ }

export const vPermission = {
  mounted: apply,
  updated: apply,
  unmounted: (el) => { /* 清理 */ }
}
```

::: details 还有一类错误：用了 `KeepAlive` 却不处理失活
**现象**：它给你加上 `<KeepAlive>` 做缓存，但组件里的定时器、轮询、监听还在一直跑。

**原因**：`KeepAlive` 缓存组件时，组件**不会被卸载** —— 所以 `onUnmounted` 不会触发。它加 `KeepAlive` 时往往只想着“保住滚动位置和表单内容”，想不到这一层。

**怎么处理**：被 `KeepAlive` 缓存的组件，要知道两个额外的钩子：

| 钩子 | 什么时候跑 |
| --- | --- |
| `onActivated` | 组件被显示出来时（包括第一次挂载之后） |
| `onDeactivated` | 组件被缓存起来、切走时 |

判断该不该在这两个钩子里做事，看这个副作用**有没有必要在组件不可见时继续跑**：

| 副作用 | 切走时该怎样 |
| --- | --- |
| 轮询接口刷新数据 | 停掉，回来再开 |
| 播放的动画 | 停掉 |
| 一个“未保存”的标志位 | 留着，这本来就是它存在的意义 |
| 长连接的推送 | 看业务，多数要留着 |

**只写 `onUnmounted` 的清理逻辑，在 `KeepAlive` 下是失效的。** 这是这一章里“写对了但不生效”的典型 —— 代码看着没问题，因为 `onUnmounted` 确实写得对，只是它根本不会被调用。
:::

## 怎么验收 AI 的产出

这一章的产出是组合式函数和自定义指令。验收的核心是**位置的正确性**，因为放错位置不报错。

- [ ] 组合式函数里的每个 `ref` / `reactive` 都在函数内部，除了你明确认定该全局的
- [ ] 每个全局状态你都能说出“为什么它只能有一份”
- [ ] 函数自己注册的副作用，都在同一个函数里清了，而且清的是同一个函数引用
- [ ] 返回给外部的清理函数（如果有）只是额外手段，不是唯一的清理途径
- [ ] `provide` 的键用的是 `Symbol`；用 `inject` 的地方，你向上翻得清数据是谁提供的
- [ ] 自定义指令的 `mounted` / `updated` / `unmounted` 都写了，或者说明了为什么不需要
- [ ] 用 `KeepAlive` 的组件，清理逻辑写在 `onDeactivated` 里而不是只写在 `onUnmounted` 里
- [ ] **同一个组件在同一页面上放两次，互相不影响**

最后一条是这一节最有效的验收动作，而且一分钟就能做。做法：把你要检查的组件在页面上连着写两个，看它们是不是各自独立。

## 练习

### 故意写一个“两个组件互相影响”的 bug，让 AI 找出来

**任务**：写一个组合式函数（比如 `useActivityList`），**故意把状态写在模块作用域**，然后在同一个页面上用两次，让它出现互相影响的现象。再让 AI 找出来。

**要求**：记录里必须包含这四项：

| 项 | 要求 |
| --- | --- |
| 埋的 bug | 写清哪个变量放在了函数外 |
| 现象描述 | 写清做了什么操作、看到什么结果（要具体到数据） |
| AI 有没有找出来 | 找出来了就粘它的定位过程；没找出来就写你换了什么问法 |
| 改法与验证 | 改完之后同样的操作看到了什么不同 |

::: details 验收标准与参考思路
**为什么值得埋这个 bug**：它是这一章唯一一个“不靠读代码、单靠跑页面也能看出问题”的 bug，也是最容易被带到综合项目里去的那种。你在练习里埋一次，比在项目里被它坑一次划算得多。

**思路提示**：

- 现象要设计得容易描述。比如两个“活动筛选列表”放在同一页，在左边选“进行中”，右边的列表也跟着变空了 —— 一句话就能说清。
- **先问笼统的问题**：“这个页面有什么 bug？”看它能不能定位到模块作用域。它很可能只会在页面代码里找。
- 再换第 2 个提示词模板（要求“按定义位置分类”）。对比两种问法的结果，记下来。**同一个问题、两种问法、两倍效果**，这是这一节要反复建立的直觉。
- 改完顺手加一个“同一个组件用两次”的验收动作到你的检查习惯里。这条从这一周开始，一直用到综合项目。

**不合格的写法**：

> 让 AI 看了一遍，它说是响应式的问题，我改了改好了。

“响应式的问题”是个筐，什么都能往里装。真正的原因是数据被两个组件共享了 —— 这跟响应式没关系，`ref` 在这里工作得完全正常，它忠实地把“一份数据”的变化同步到了两个地方。

**合格的写法**：

> 我把 `list` 和 `loading` 留在了函数外面。页面上放两个筛选列表，
> 在左边选“进行中”，右边本来显示“全部”的列表也跟着变成只有进行中的 —— 两边显示的是同一份数据。
> 第一次问它“这个页面有什么 bug”，它说是“可能缺少 loading 状态”，没找到真正的原因。
> 换成第 2 个提示词模板后，它列出的分类表里 `list` 和 `loading` 标着“模块作用域”，
> 并指出“两个实例会共享”。定位到了。
> 改法是把两个变量都挪进函数内。同样的操作，两边现在互不影响。
> 我把它记成了一条验收习惯：**新写的组合式函数，先看状态在不在函数内。**

差别在于：后者不但找到了原因，还改变了下次的做法。**这一章的知识点不难，难的是形成“先看位置”的习惯。**
:::
