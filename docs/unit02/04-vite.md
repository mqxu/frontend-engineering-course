# 2.4 构建工具与 Vite

## 浏览器看不懂我们写的文件

在 `src/App.vue` 里写下第一个组件之后，你可能会想：**能不能不用 Vite，直接双击
`index.html` 打开？**

试试看。把 `index.html` 里的 `<script type="module" src="/src/main.js"></script>`
保持不变，直接用浏览器打开这个文件，控制台会给你一串报错：

```text [浏览器控制台]
Failed to load module script: Expected a JavaScript module script but the server
responded with a MIME type of "text/html".

GET http://127.0.0.1:5500/src/App.vue net::ERR_ABORTED
Uncaught TypeError: Failed to resolve module specifier "vue".
```

三个报错对应三个问题：

| 报错 | 原因 |
| --- | --- |
| `MIME type of "text/html"` | 用 `file://` 打开时，`/src/main.js` 被当成路径找文件，找不到就返回了 HTML |
| `Failed to resolve module specifier "vue"` | 浏览器不认识裸模块名，`import 'vue'` 不知道该去哪个文件找 |
| `App.vue` 加载失败 | **浏览器根本不认识 `.vue` 文件** |

第三行最关键。`.vue` 文件是一种自定义格式，里面有 `<template>`、`<script>`、
`<style>` 三块，浏览器没有对应处理器。同样的问题还有：

| 我们写的 | 浏览器认不认 |
| --- | --- |
| `.vue` 单文件组件 | ✗ 不认识 |
| `.scss` / `.sass` 样式文件 | ✗ 不认识 |
| `.ts` 类型标注 | ✗ 不认识 |
| `import 'vue'` 裸模块名 | ✗ 不知道去哪找 |
| `@/components/Foo.vue` 别名 | ✗ 不知道 `@` 是什么 |
| 可选链之外更新的语法 | 部分不支持 |

**构建工具的存在理由就是这一件事：把我们写的、浏览器看不懂的代码，翻译成浏览器能看懂的代码。**

## 构建工具做的三件事

不管叫什么名字（Vite、Webpack、Rspack、Rollup），构建工具都在做三件事：

| 阶段 | 做什么 | 例子 |
| --- | --- | --- |
| 转换 | 把不可识别的格式换成标准 JS / CSS | `.vue` → `.js`、`.scss` → `.css` |
| 解析 | 把裸模块名和别名换成真实路径 | `import 'vue'` → `./node_modules/.pnpm/vue@3.5.42/.../vue.runtime.esm-bundler.js` |
| 打包 | 把成百上千个模块合并、压缩、拆分 | 产物放进 `dist/` |

第一件事回答“浏览器不认识什么”，第二件事回答“文件在哪”，第三件事回答
“交付给用户的是哪些文件”。

## Vite 最特别的地方：开发态和生产态走两条路

其他构建工具在开发时和生产时做的事情差不多，都是“把所有代码打包成几个文件”。
Vite 不一样，它把这两件事**分开做**：

| 对比项 | 开发态（`pnpm dev`） | 生产态（`pnpm build`） |
| --- | --- | --- |
| 底层 | 浏览器原生 ES Module + esbuild 转换 | Rollup 打包 |
| 是否打包 | **不打包**，按需编译 | 打包成少量文件 |
| 产物在哪 | 不写磁盘，在内存里 | `dist/` 目录 |
| 启动速度 | 秒级，与项目规模关系不大 | 几秒到几十秒，与项目规模相关 |
| 目标 | 改代码后立刻能看到 | 给真实用户下载，体积和性能优先 |

为什么开发态可以不打包？因为**现代浏览器原生支持 ES Module**。浏览器自己能处理
`import '/src/App.vue'` 这种请求 —— 只要服务器返回的是一段合法的 JS。

于是 Vite 的开发服务器变成了一个“**按需翻译**”的服务：

```text [Vite 开发服务器的处理过程]
浏览器请求 /src/main.js
  → Vite 读到文件，把里面的裸模块名和别名改写成浏览器能请求的路径
  → 返回改写后的 JS

浏览器接着请求 /src/App.vue
  → Vite 用 @vitejs/plugin-vue 把 .vue 编译成普通 JS
  → 返回编译结果

浏览器再请求 /src/style.css（由 .scss 编译而来）
  → Vite 编译 sass，返回 CSS
```

关键点：**只有浏览器请求到的文件才会被编译**。你有 200 个页面组件，
但首页只用到 5 个，那启动时只编译这 5 个。这就是为什么一个几百个文件的项目
也能秒级启动。

## 为什么冷启动快：依赖预构建

开发态不打包，那 `node_modules` 里那几百个依赖怎么办？总不能每个都让浏览器单独请求一次 ——
`element-plus` 一个库就有上千个模块，浏览器要发上千个请求，页面会卡半天。

Vite 在第一次启动时会先做一次**依赖预构建**：

```bash [终端输出（第一次 pnpm dev 时）]
VITE v8.3.0  ready in 412 ms

  ➜  Local:   http://localhost:5173/
  ➜  Network: use --host to expose
  ➜  press h + enter to show help
```

如果你删掉 `node_modules/.vite` 再启动，会先看到这样一段，然后才是 ready：

```text [缓存目录]
node_modules/.vite/deps/
├── _metadata.json
├── vue.js
├── element-plus.js
└── ...
```

### 依赖预构建解决三个问题

| 问题 | 具体表现 | 预构建怎么解决 |
| --- | --- | --- |
| 模块数量太多 | `element-plus` 有上千个内部模块，浏览器要发上千个请求 | 用 esbuild 把上百个模块合成一个文件，请求数降到个位数 |
| 格式不统一 | 很多 npm 包还是 CommonJS 格式，浏览器只认 ES Module | 统一转成 ES Module |
| 每次启动都重复处理 | 依赖很少变，每次都重新处理是浪费 | 结果缓存在 `node_modules/.vite/deps`，只有依赖变了才重新构建 |

对比一下“处理”的对象就能明白 Vite 的设计取向：

| 对象 | 处理方式 | 理由 |
| --- | --- | --- |
| 依赖（`node_modules`） | 启动时一次性预构建，然后缓存 | 内容不常变，数量多，适合批量处理 |
| 你的源码（`src/`） | 每次请求时按需编译，不缓存 | 内容常变，数量少，逐个处理最省时间 |

::: warning `node_modules/.vite` 什么时候要删
这个缓存目录偶尔会出问题。典型现象是：改了依赖版本，但开发服务器还是在用旧版本；
或者报错信息里出现的代码和你的源码对不上。

处理方式：

```bash [终端]
rm -rf node_modules/.vite
pnpm dev
```

**注意是 `node_modules/.vite`，不是 `node_modules`。** 前者是缓存，删了不心疼；
后者要重装依赖，能不动就不动。
:::

## HMR：改代码之后页面为什么能局部刷新

HMR 是 Hot Module Replacement（模块热替换）的缩写。它解决的问题是：
**改一行代码，不想丢掉当前页面状态。**

想象一下你在调试活动报名审核弹窗：填了一半的表单、展开的下拉框、滚到了第三屏。
如果没有 HMR，你一保存代码页面就整页刷新，所有状态清零，又得从头点到那个位置。

Vite 的 HMR 大致是这样工作的：

```text [HMR 的大致流程]
1. 你在编辑器里保存 src/views/ActivityListView.vue
2. Vite 开发服务器通过 WebSocket 告诉浏览器：“这个文件变了”
3. 浏览器里的 HMR 运行时收到消息，问：“这个模块能热替换吗？”
4. 能 —— 只重新加载这个模块，页面其他部分和状态都不动
   不能 —— 往上找到最近一个能热替换的模块
   一路找到底还不能 —— 整页刷新
```

第 4 步里“能不能热替换”是由**模块自己声明的**。`.vue` 文件由插件处理，
组件相关的部分默认支持热替换；纯 JavaScript 文件需要手动声明（一般不用管）。

### 热更新失效的常见现象

| 现象 | 可能原因 | 怎么处理 |
| --- | --- | --- |
| 改代码后页面完全不动 | 开发服务器断了，或 WebSocket 被代理拦了 | 看终端有没有报错，刷新页面看是否恢复 |
| 每次都整页刷新，状态总丢 | 改的文件不支持热替换（比如路由配置文件） | 属于正常行为，改路由结构本来就需要重新初始化 |
| 改了样式没反应 | 样式写在了 `index.html` 的内联 `<style>` 里 | 把样式挪进 `src/assets/` 或组件内 |
| 改了依赖没反应 | 依赖被预构建缓存了 | 删 `node_modules/.vite` 重启 |
| 页面白屏，终端一堆报错 | 你写的代码本身有语法错误 | 先修语法错误，HMR 会恢复 |

::: tip 一个判断技巧
**页面自动刷新了 vs 页面没反应**，这两种情况指向完全不同的原因。

自动刷新说明“变了但没法局部替换”，通常是正常的；没反应说明“根本没收到变化通知”，
要查连接。分清楚这两类，排查能省一半时间。
:::

## 生产态为什么必须用 Rollup 打包

开发态不打包，代价是浏览器要发几十上百个请求。这在本地无所谓（服务器就在本机），
但到了线上就不可接受：

| 因素 | 开发态（不打包） | 生产态（打包） |
| --- | --- | --- |
| 请求数量 | 每个模块一个请求 | 合并成几个文件 |
| 网络延迟 | 本机，几乎为 0 | 每个请求都有真实往返延迟 |
| 代码体积 | 保留注释、空格、完整变量名 | 压缩混淆，删掉调试代码 |
| 兼容性 | 假定现代浏览器 | 可以按目标浏览器降级语法 |
| 缓存 | 无所谓 | 文件名带哈希，可长期缓存 |

所以 `pnpm build` 走的是另一条路：用 Rollup 把所有模块分析一遍，
从入口开始顺着 `import` 关系收集，打成一个依赖图，然后输出到 `dist/`：

```bash [终端]
pnpm build

# 输出类似
vite v8.3.0 building for production...
✓ 128 modules transformed.
dist/index.html                   0.46 kB │ gzip:   0.30 kB
dist/assets/index-DiwygxGE.css   12.34 kB │ gzip:   3.21 kB
dist/assets/index-B7xK2pQm.js   186.72 kB │ gzip:  62.45 kB
✓ built in 3.42s
```

这一页输出的每一行都值得读：文件名、原始体积、gzip 之后的体积。
**第 11 周做综合项目时，这份输出就是“产物构成分析”的原始数据。**

## 和 Webpack 比，差在哪

Webpack 是上一代的主流选择，现在很多公司仍在用。对比不是为了分好坏，
而是让你知道各自的取向。

| 对比项 | Vite | Webpack |
| --- | --- | --- |
| 配置文件量 | 少，常见配置二三十行 | 多，几十到几百行常见 |
| 开发服务器启动 | 秒级，与项目规模基本无关 | 十秒到几分钟，与规模强相关 |
| 底层实现 | 开发态用原生 ESM，生产态用 Rollup | 全程自己做打包 |
| 生态 | 较新，常用插件都有 | **最成熟**，几乎没有找不到的插件 |
| 老项目兼容 | 需要一些适配 | 天然适合 |
| 学习曲线 | 平缓，配置直观 | 陡峭，概念多（loader、plugin、chunk 等） |

Webpack 慢的根本原因在于**它必须先打包再启动**：项目越大，要处理的模块越多，
启动就越慢。Vite 把这个顺序反了过来：**先启动，用到什么再编译什么。**

::: tip 学哪一个是“够用”的
本课程用 Vite。但要知道 Webpack 的存在，因为两类场景会碰到它：

1. 接手老项目 —— 很多 2020 年前后的项目还是 Webpack，你得能看懂配置。
2. 特殊需求 —— 少数场景 Vite 的生态还不够，需要退回 Webpack。

**理解了“转换 / 解析 / 打包”这三件事，换工具只是换配置写法。**
:::

## 小结

- 构建工具的存在理由是：浏览器不认识 `.vue`、`.scss`、裸模块名和路径别名。
- 构建工具做三件事：转换格式、解析模块路径、打包输出。
- Vite 的开发态不打包，用浏览器原生 ES Module 按需编译；生产态用 Rollup 打包。
- 冷启动快的原因是依赖预构建（esbuild，结果缓存在 `node_modules/.vite/deps`）+ 源码按需编译。
- HMR 只重新加载改动的模块，保住页面状态；失效时先分清“自动刷新”还是“没反应”。
- 生产态必须打包，因为请求数量、体积、缓存、兼容性四方面都要求这么做。
- 与 Webpack 的差别主要在启动速度与生态成熟度，核心概念是相通的。

## 常见坑

::: details 坑 1：改了 vite.config.js 却不生效
**现象**：明明改了配置，行为却和改之前一样。

**原因**：配置文件只在启动时读一次。别名、插件这类改动不会热更新。

**处理**：`Ctrl + C` 停掉开发服务器，重新 `pnpm dev`。

**判断方法**：改 `server.port` 这种配置，如果端口没变，就是没重启。
:::

::: details 坑 2：删了 node_modules 之后启动特别慢
**现象**：重装依赖后第一次 `pnpm dev` 卡了好几秒。

**原因**：`node_modules/.vite/deps` 是跟着 `node_modules` 一起被删掉的，
所以要做一次完整的依赖预构建。

**处理**：这是正常现象，等它跑完就好。**不要以为“Vite 变慢了”。**
第二次启动就恢复正常水平了。
:::

::: details 坑 3：路径大小写不一致，本地能跑线上报错
**现象**：本地 `pnpm dev` 正常，`pnpm build` 后在服务器上某个组件加载失败。

**原因**：macOS 与 Windows 的文件系统默认**不区分大小写**，
`import ActivityList from './activityList.vue'` 能找到 `ActivityList.vue`。
Linux 服务器区分大小写，就找不到了。

**处理**：让 import 的路径和真实文件名**完全一致**。排查时用：

```bash [终端]
# 列出真实文件名，逐个核对 import 写法
ls src/views
```

**这类问题必须在 `pnpm preview` 阶段发现**，不要等部署之后。
:::

::: details 坑 4：在 dev 里用 process.env 读环境变量
**现象**：`console.log(process.env.VITE_API_BASE)` 输出 `undefined`。

**原因**：Vite 的客户端代码里没有 `process` 这个对象（那是 Node 环境才有的），
环境变量要通过 `import.meta.env` 读。

**处理**：改成 `import.meta.env.VITE_API_BASE`。详见
[2.5 环境变量与常用配置](/unit02/05-env-config)。

**特殊情况**：`vite.config.js` 是跑在 Node 里的，那里可以用 `process.env`，
但拿不到 `.env` 里定义的值 —— 除非用 `loadEnv()` 显式加载。
:::

::: details 坑 5：以为 dist 可以直接双击打开
**现象**：`pnpm build` 之后直接双击 `dist/index.html`，页面一片空白。

**原因**：产物里引用的资源路径是 `/assets/xxx.js`，绝对路径以根目录为起点。
用 `file://` 打开时根目录变成了本地磁盘根，找不到文件。

**处理**：用 `pnpm preview` 启动一个本地服务器访问。如果确实需要能双击打开的产物，
在 `vite.config.js` 里把 `base` 设成 `'./'`（相对路径）—— 但这是特殊情况，
正常项目保持默认。

**记住：`dist` 不是给人双击的，是给服务器托管的。**
:::

## 课后练习

::: details 练习 1：对比 dev 与 preview 的网络请求
分别在 `pnpm dev` 和 `pnpm preview` 打开的页面上，用浏览器开发者工具的
Network 面板看请求数量。

回答：

1. 两种模式下，页面加载发出的 JS 请求大概各有多少个？
2. 生产态的文件名有什么特征？开发态的又是什么样？
3. 为什么生产态的请求数少这么多？

**参考思路**：开发态你会看到几十上百个请求，路径直接对应 `src/` 下的文件；
生产态只有几个，文件名带一串哈希。原因就是这一节讲的“开发态不打包，生产态打包”。

**顺手做一件事**：把两个模式下的总体积对比一下，记在笔记里。
第 12 周做构建优化时会用到这个基线数字。
:::

::: details 练习 2：观察依赖预构建的缓存
步骤：

1. 删掉 `node_modules/.vite`，记录 `pnpm dev` 从启动到 ready 用了多久。
2. 停掉，再启动一次，记录时间。
3. 打开 `node_modules/.vite/deps`，看看里面有哪些文件。

回答：为什么第二次更快？缓存目录里为什么只有 `vue.js`、`element-plus.js` 这种
合并后的文件，而不是几百个小文件？

**验收点**：能说出“依赖预构建把多个模块合并成一个文件，结果缓存在磁盘上”这一句。
:::

::: details 练习 3：复现一次热更新失效
任务：制造一次“改了代码但页面没反应”，然后定位原因。

思路（选一种）：

- 在 `index.html` 里加一段内联 `<style>`，改它，看样式是否跟着变。
- 修改 `vite.config.js` 的 `server.port`，看端口有没有变。
- 在浏览器里手动断开网络一小会儿，改代码，看是否有更新。

**验收点**：要能分清三种情况 —— **整页刷新（正常，模块不支持热替换）**、
**完全没反应（异常，连接或配置问题）**、**报错后白屏（你自己的代码有语法错误）**。
写清楚你遇到的是哪一种，依据是什么。
:::

::: details 练习 4：给同学讲清“为什么需要构建工具”
不看这一节，用三句话解释：

1. 为什么浏览器不能直接跑 `.vue` 文件？
2. 为什么开发时可以不打包，生产时必须打包？
3. 为什么 Vite 启动比 Webpack 快？

**参考思路**：三句话各自的落点应该是 —— **格式不认识**、**请求数与体积的代价不同**、
**先启动后编译 vs 先编译后启动**。

**检验方法**：找一个没上这门课的同学，讲一遍，看他能不能复述出大意。
讲不清的地方，就是你没真正理解的地方。
:::
