# 3.5 自动构建流水线

## 一个反复出现的傍晚

周三下午你和搭档各自提交了几次代码，各自本地都跑得通。周四上午老师要看进度，
你打开项目准备演示，先顺手跑一下构建 —— 报错了。

```text [终端]
[vite]: Rollup failed to resolve import "@/shared/utils/format" from
"src/features/activity/ActivityListView.vue".
```

你查了一下，搭档把 `format.js` 移到 `features/activity/utils/` 去了，
但没改引入路径。他本地能跑是因为**他的 `node_modules` 里还留着旧的缓存** ——
删掉重装就复现了。

真正的问题不在于这个错误本身，而在于：**这个问题在你发现之前，已经躺在主分支上
快一天了。**

如果每一次推送都自动跑一遍“安装依赖 → 检查 → 构建”，这个问题会在搭档推送后
一分钟内就被发现，而且反馈直接出现在他的合并请求里 ——
他当时就能改，不用等你周三晚上才发现。

这就是流水线要解决的事。这一节讲怎么配一条，以及为什么它比“提醒大家提交前跑一下”有效。

## 流水线是什么

一句话：**在别人的机器上，自动把你的代码跑一遍。**

```text [流水线的四个部分]
触发条件  →  运行环境  →  一串步骤  →  结果反馈
什么时候跑   在哪跑     做什么       成功了没

推送到分支    一台干净的   安装依赖     合并请求上显示
发起合并请求  Linux 机器   执行检查     绿勾或红叉
                         构建产物
```

关键在“**一台干净的机器**”。你的电脑上有缓存的 `node_modules`、
有全局装过的工具、有 `.env.local`、有这些年积累的编辑器配置。
流水线上什么都没有 —— 每次都是从零开始。

所以流水线其实在回答一个问题：

> 一个新同学克隆我的仓库，在一台什么都没配的机器上，能跑起来吗？

**本地能跑不算数，流水线能过才算数。**

## 四个阶段

不管用什么平台，一条前端流水线基本都分为四个阶段：

| 阶段 | 做什么 | 对应命令 | 失败说明什么 |
| --- | --- | --- | --- |
| 拉取 | 从仓库检出代码 | 平台自动完成 | 分支或权限有问题 |
| 安装 | 装 Node、装依赖 | `pnpm install --frozen-lockfile` | 依赖声明或锁文件有问题 |
| 检查 | 跑代码检查 | `pnpm lint` | 代码有规范问题 |
| 构建 | 产出构建结果 | `pnpm build` | 代码有真实错误 |

顺序不能换。安装失败就没法检查，检查失败就没必要构建 ——
**早点停下来，反馈更快。**

::: tip 为什么“检查”要放在“构建”前面
两者都会失败，但失败的信息价值不同：

- 检查失败告诉你“第 42 行有个 `==`”。
- 构建失败可能只告诉你“打包出错”。

**把便宜且信息明确的步骤放前面**，能省下大量等待时间。
这也是为什么有的团队在安装之后先跑一遍 lint，再跑构建。
:::

### 以云效 Flow 为例

云效的流水线是图形化配置的，界面上就是“阶段 + 任务 + 步骤”三层。

| 阶段名 | 任务 | 步骤 | 关键命令 |
| --- | --- | --- | --- |
| 拉取代码 | 代码源 | 选择仓库与分支 | 平台自动完成 |
| 安装依赖 | Node 构建 | 安装 Node 24 → 安装依赖 | `pnpm install --frozen-lockfile` |
| 执行检查 | Node 构建 | 代码检查 | `pnpm lint` |
| 构建产物 | Node 构建 | 构建 | `pnpm build` |

每个节点都能选“失败后是否继续”。建议：

| 节点 | 失败后 |
| --- | --- |
| 安装依赖 | 立即停止（后面都做不了） |
| 执行检查 | 立即停止（问题要马上修） |
| 构建产物 | 立即停止 |
| 上传产物 | 继续（产物上传失败不影响代码质量结论） |

图形化配置也能切换成 YAML 模式，整体结构大致是这样（不同平台字段名会不同，
看的是结构而不是具体字段）：

```yaml [流水线配置（结构示意）]
name: 前端构建与检查
trigger:
  push:
    branches: [main]
  pull_request: true
stages:
  - stage: 安装依赖
    steps:
      - run: pnpm install --frozen-lockfile
  - stage: 执行检查
    steps:
      - run: pnpm lint
  - stage: 构建产物
    steps:
      - run: pnpm build
    artifacts:
      - dist/**
```

如果你用的是 GitHub，对应的配置文件是这样：

```yaml [.github/workflows/ci.yml]
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 12

      - uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: pnpm

      - name: 安装依赖
        run: pnpm install --frozen-lockfile

      - name: 代码检查
        run: pnpm lint

      - name: 构建
        run: pnpm build
```

无论哪种写法，四个阶段和三条命令都是一样的。

::: warning 一定要加 `--frozen-lockfile`
这个参数的含义是“**只按锁文件安装，如果锁文件和 `package.json` 不一致就直接失败**”。

不加的话，流水线可能会自己更新锁文件、装上和你本地不一样的版本。
于是出现一种最难查的问题：**流水线能过，你本地过不了**（或反过来）。

**它失败的时候其实是在提醒你：锁文件忘了提交。** 这是好事。
:::

## 本地能过、流水线不过的六个原因

这是新手最困惑的一类问题。按出现频率从高到低列出来，每条都给出判断方法。

### 一、Node 版本不一致

| | 你本地 | 流水线 |
| --- | --- | --- |
| Node | 24.9.0（手动装的） | 18.x（平台默认） |

平台默认版本通常比较旧。表现是各种语法错误或 `ERR_PNPM_UNSUPPORTED_ENGINE`。

**判断方法**：流水线日志里搜 `node -v` 的输出，和你本地的比。
**处理**：在流水线配置里显式指定 Node 版本，并且在 `package.json` 里写 `engines`。

### 二、环境变量缺失

`.env.local` 是本地文件，**不会提交到仓库**，所以流水线上没有它。

表现是构建时报 `undefined`，或者产物里的接口地址是空的。

**判断方法**：看 `.gitignore` 里忽略了哪些 `.env` 文件，
这些文件的值流水线上一定拿不到。

**处理**：把“构建时需要”的环境变量配置到流水线的环境变量设置里
（平台一般都有这个入口）。**不要把密钥写进仓库来图方便。**

### 三、锁文件没提交

表现是 `--frozen-lockfile` 报错，或者依赖版本和本地不同。

**判断方法**：`git status` 看 `pnpm-lock.yaml` 有没有未提交的改动。

**处理**：本地 `pnpm install` 之后把锁文件一起提交。

### 四、大小写敏感

| 文件系统 | 行为 |
| --- | --- |
| macOS（默认）、Windows | 不区分大小写 |
| Linux | **区分** |

`import X from './ActivityList.vue'` 在本地能找到 `activityList.vue`，
在 Linux 上找不到。

**判断方法**：把引入路径和真实文件名逐字符比对。

```bash [终端]
# 列出真实文件名
ls src/features/activity/components/
```

**处理**：引入路径与文件名完全一致。**顺便养成文件名大小写不混用的习惯。**
这条其实和 3.3 的命名约定是同一个问题。

### 五、跳过了提交钩子

有人用 `git commit --no-verify` 提交了不合规的代码，本地钩子没拦，
流水线的检查就会失败。

**判断方法**：检查失败的规则，看是不是“提交钩子本该拦下的”。
**处理**：让流水线和钩子用同一套配置 —— 都是 `pnpm lint`，
这样两边结论一致，不会出现“钩子过了流水线不过”。

### 六、依赖装错位置

某个包放在 `devDependencies` 里，但它被业务代码 import 了。

本地能跑，因为开发时所有依赖都在。流水线上如果只装生产依赖
（`pnpm install --prod`），这个包就没了。

**判断方法**：本地删掉 `node_modules`，用生产依赖装一次再构建：

```bash [终端]
rm -rf node_modules
pnpm install --prod
pnpm build
```

**处理**：把它移到 `dependencies`。判断方法还是那一句：
**构建产物里需不需要它。**

::: tip 排查流水线问题的通用方法
不要在本地反复试，**直接看流水线日志**。

日志里有三样东西是你必须找的：

1. 失败的是哪一步（安装 / 检查 / 构建）。
2. 那一步的完整输出（不是最后一行错误，往上多看几行）。
3. 环境信息（Node 版本、pnpm 版本、工作目录）。

**本地能过而流水线不过时，差异一定在“环境”和“文件”两处。**
把这两处逐个核对，问题自然会暴露。
:::

## 把检查接进流水线之后

前面几节配的检查，都在“你自己的机器上”：编辑器提示、提交钩子拦截。

| 位置 | 依赖什么 | 能不能被绕过 |
| --- | --- | --- |
| 编辑器 | 你保存了文件 | 能（用别的编辑器） |
| 提交钩子 | 你本地钩子装好了 | 能（`--no-verify`） |
| 流水线 | 平台设置的规则 | **不能** |

**这就是流水线不可替代的地方。** 前两道防线靠自觉，第三道不靠。

配好之后实际发生的三个变化：

| 变化 | 具体表现 |
| --- | --- |
| 问题在合并之前被发现 | 合并请求上直接显示红叉，评审人不用自己跑构建 |
| 反馈时间大幅缩短 | 推送后一分钟内知道结果，不用等到演示前才发现 |
| 评审的关注点转移 | 不用再讨论“你有没有跑过构建”，直接讨论业务逻辑 |

第三条最容易被低估。**当“代码能不能构建”由流水线保证之后，
评审时间可以全部用在业务逻辑上** —— 这正是 [3.1](/unit03/01-why-lint) 讲的：
能机械判断的事，不该由人来做。

### 把流水线设成合并的门禁

最后一步很重要：**在平台的合并请求设置里，勾上“流水线通过才允许合并”。**

不设这一步的话，流水线只是个“提醒”；设了这一步，它才是“门禁”。

| 设置 | 效果 |
| --- | --- |
| 只跑流水线 | 红叉显示出来，但谁都能点合并 |
| 流水线 + 合并门禁 | 红叉时合并按钮不可用 |

::: danger 门禁第一次跑通常会红
因为历史代码里可能本来就有一堆告警。这时候有两种处理方式：

- **把规则关掉** —— 三周后你会发现规则全被关光了。
- **只检查本次改动** —— 让历史问题保持原样，新代码必须合规。

选第二种。具体做法有两种：一是流水线里只对改动文件跑检查；
二是把历史问题记成待办，规则先设成 `warn`，逐周清理。

**门禁的目标是“不让问题变多”，不是“立刻让所有问题归零”。**
:::

## 小结

- 流水线是在一台干净的机器上自动跑一遍代码，回答“新同学能跑起来吗”。
- 四个阶段：拉取 → 安装 → 检查 → 构建，顺序不能换。
- 安装用 `pnpm install --frozen-lockfile`，锁文件不同步时直接失败。
- 本地能过流水线不过，六个常见原因：Node 版本、环境变量、锁文件、大小写、跳过钩子、依赖装错位置。
- 编辑器与提交钩子都能被绕过，流水线是唯一不靠自觉的一道。
- 把流水线设成合并门禁，它才是“门禁”而不是“提醒”。
- 门禁的目标是阻止问题变多，历史问题逐周清理，不要一次性归零。

## 常见坑

::: details 坑 1：流水线报错只看了最后一行
**现象**：日志最后一行是 `Error: Process completed with exit code 1`，看不出原因。

**原因**：最后一行只是“这一步失败了”的通用提示，真正的原因在上面。

**处理**：往上翻，找**第一条**报错信息。比如：

```text [日志（从下往上看）]
Error: Process completed with exit code 1          ← 通用提示，没用
✖ 1 problem (1 error, 0 warnings)                  ← 汇总，有用
  42:11  error  Expected '===' and instead saw '==' ← 真正的原因
```

**记住：日志从下往上读，第一条具体报错才是入口。**
:::

::: details 坑 2：本地成功的构建，流水线里超时
**现象**：安装依赖这一步卡住不动，最后超时。

**原因**：流水线在境外或异地网络环境下拉 `registry.npmjs.org` 很慢。

**处理**：在流水线的环境变量或 `.npmrc` 里配置镜像源。
如果公司有内网镜像，用内网的。

**注意**：镜像配置要放在**流水线的环境设置**里，而不是提交到项目里 ——
不然团队里用别的镜像的人会受影响。

**另一个可能**：忘了配缓存。配了缓存之后，第二次跑只要几秒。
:::

::: details 坑 3：流水线每次都重新装一遍依赖，很慢
**现象**：每次跑要三到五分钟，大部分时间在装依赖。

**原因**：没配缓存，或者缓存键写得不对（比如用了每次都会变的值）。

**处理**：大多数平台都支持按锁文件做缓存。GitHub Actions 上就是
`cache: pnpm` 那一行；云效上在任务设置里勾选缓存目录，缓存的键用锁文件的哈希。

**验证方法**：连续跑两次，第二次的“安装依赖”耗时应该明显短于第一次。
:::

::: details 坑 4：检查和构建用了不同的规则
**现象**：提交钩子通过了，流水线却报一样的错。

**原因**：钩子只检查改动文件（`lint-staged`），流水线检查全部文件。
如果改动文件之外的老文件有问题，就会这样。

**处理**：这不是 bug，是设计。理解两者的分工：

| 位置 | 检查范围 | 目的 |
| --- | --- | --- |
| 提交钩子 | 只检查改动文件 | 快速反馈 |
| 流水线 | 全部文件 | 保证整体质量 |

**如果希望两边一致**，就在流水线里也只检查改动文件（用 `git diff --name-only`）。
但本课程建议流水线跑全量 —— 全量才能真正代表仓库的状态。
:::

::: details 坑 5：产物的路径写死在别处
**现象**：流水线里上传 `dist/` 报“目录不存在”。

**原因**：`vite.config.js` 里改了 `outDir`，或者构建根本没成功。

**处理**：先确认构建这一步是成功的，再看 `outDir` 的值。
**流水线配置和 `vite.config.js` 两处必须一致。**

**顺手做一件事**：产物路径不要写死两遍，可以用环境变量或者约定 ——
默认就用 `dist`，别改。
:::

::: details 坑 6：把密钥放进流水线配置文件并提交
**现象**：为了方便，把接口密钥直接写在 `.github/workflows/ci.yml` 里。

**原因**：以为仓库是私有的就安全。

**处理**：**永远不要把密钥提交到仓库**，用平台的“密钥管理”功能，
在流水线里以环境变量注入。

**为什么**：仓库权限会变、可能被误设为公开、可能被克隆到别处。
密钥一旦进入 Git 历史，即使后来删掉，历史里依然能翻出来。
:::

## 课后练习

::: details 练习 1：画出一条流水线的四个阶段
给你要配的流水线画一张图，标出：

1. 触发条件（什么情况下跑）。
2. 运行环境（什么系统、什么 Node 版本）。
3. 四个阶段各自的命令。
4. 每个阶段失败之后是停止还是继续。
5. 结果反馈到哪里（合并请求 / 通知）。

**验收点**：触发条件要能回答“每次推送都跑吗？
只推了文档也要跑吗？” —— 这个问题没有标准答案，
但你要能说出自己的选择理由。
:::

::: details 练习 2：配一条流水线并让它跑绿
在你们的项目仓库里配一条完整的流水线。

**要求**

| 项目 | 要求 |
| --- | --- |
| 触发 | 推送到功能分支和发起合并请求时触发 |
| 安装 | 显式指定 Node 24，用 `--frozen-lockfile` |
| 检查 | 跑 `pnpm lint` |
| 构建 | 跑 `pnpm build` |
| 缓存 | 配好依赖缓存 |
| 失败可见 | 在合并请求页面上能看到流水线状态 |

**验收标准**

| 场景 | 预期结果 |
| --- | --- |
| 正常推送 | 流水线全绿 |
| 故意提交一个格式错误 | 检查阶段失败，合并请求上显示红叉 |
| 改好后再次推送 | 流水线恢复绿色 |
| 连续跑两次 | 第二次的安装阶段明显更快（缓存生效） |

**截图留证**：绿色状态一次、红色状态一次、两次耗时的对比。
:::

::: details 练习 3：制造一次“本地能过、流水线不过”
从这一节讲的六个原因里挑一个，故意制造出来，然后修好。推荐两个：

**方案 A —— 大小写**

```bash [终端]
# 1. 把某个文件重命名成只改大小写的形式
git mv src/features/activity/ActivityCard.vue src/features/activity/Activitycard.vue
# 2. 但引入路径写成 ActivityCard.vue（大小写不一致）
# 3. 推送到流水线，看是否报 Failed to resolve import
```

**方案 B —— 环境变量**

1. 在构建时用到的一个环境变量，只在 `.env.local` 里定义。
2. 确认 `.env.local` 在 `.gitignore` 里。
3. 推送，看流水线的构建阶段是否失败。

**验收点**：报告里要写清“现象 → 日志里的关键行 → 原因 → 修法”，
并且指出**这类问题为什么在本地发现不了**。

**这个练习的价值在于**：你自己制造过一次，下次看到类似报错能立刻想到原因。
:::

::: details 练习 4：把流水线设成合并门禁
在平台的仓库设置里：

1. 找到合并请求设置，把流水线设为合并前的必要条件。
2. 用一个不合规的提交测试：确认“合并”按钮不可用，并截图。
3. 修好之后确认按钮恢复可用。

**验收标准**

| 项目 | 要求 |
| --- | --- |
| 门禁生效 | 流水线红时合并按钮不可用（有截图） |
| 恢复 | 修好并推送后按钮可用 |
| 有记录 | 写一段说明：为什么把流水线设成门禁，而不是只当提醒 |

**参考思路**：最后一段的落点应该是“**不依赖人的自觉**” ——
提醒会被忽略，门禁不会。
