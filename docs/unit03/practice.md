# 单元 3 课后练习

本单元的练习和前面两周不一样：**它们不是“做完交上来”，而是“以后一直用”。**

**四道必做题，一道选做题。** 练习 1 和 2 在同一份代码上做，
练习 3 和 4 需要两人配合、需要远程仓库。四道题做完，你手上的东西就是
第 11 周综合项目的起点。

::: warning 开始之前
需要三样东西：

- 一个能构建的项目（第 2 周练习 1 修好的那个）。
- 一套可用的检查配置（3.2 配好的）。
- 一个远程仓库，加上一个能配合你的搭档。

**练习 3 没有搭档做不了**，先找好人再开始。
:::

## 必做题

### 练习 1 · 给“满屏告警”的代码做规范治理

下面这个组件是一个真实项目里被提交上来的版本。功能勉强能跑，
但一旦接上检查，终端会刷出十几条告警。

```vue [src/views/ActivityListView.vue（待治理）]
<script setup>
import { ref, computed } from 'vue'
import dayjs from 'dayjs'
import { formatCapacity } from '../../shared/utils/format'
import { formatDeadline } from '../../shared/utils/format'

const list = ref([])
const keyword = ref('')
const currentStatus = ref(null)
let loading = false

const filteredList = computed(() => {
  return list.value.filter(item => {
    if (keyword.value != '' && item.title.indexOf(keyword.value) == -1) {
      return false
    }
    if (currentStatus.value != null && item.status != currentStatus.value) {
      return false
    }
    return true
  })
})

function loadList() {
  loading = true
  fetch('/api/activity/list').then(res => res.json()).then(data => {
    list.value = data.data
    loading = false
  })
}

function formatTime(t) {
  if (t == null) return '-'
  return dayjs(t).format('YYYY-MM-DD HH:mm')
}
</script>

<template>
  <div class="activity-list">
    <input v-model="keyword" placeholder="搜索活动" />
    <div v-for="item in filteredList" :key="item.id" class="activity-item">
      <span>{{ item.title }}</span>
      <span>{{ formatCapacity(item.enrolled, item.capacity) }}</span>
    </div>
  </div>
</template>

<style scoped>
.activity-list {
  margin: 0px;
  color: #FFFFFF;
}
</style>
```

#### 你要做的事

**第一步：接入检查，统计治理前的告警数。**

```bash [终端]
pnpm lint 2>&1 | tail -20
pnpm lint:style 2>&1 | tail -20
```

把数量记录下来，**不要立刻开始改**。

**第二步：给每条告警分类。**

| 告警 | 属于哪一层 | 能自动修吗 | 该怎么改 |
| --- | --- | --- | --- |
| | | | |

**第三步：分批修。**

1. 先跑 `pnpm lint:fix` 和 `pnpm lint:style:fix`，让工具处理能自动修的部分。
2. 再手动处理剩下需要判断的。
3. **顺手改掉那些检查发现不了、但你会写出 bug 的地方**（提示：那个 `loading`）。

**第四步：再统计一次告警数，做前后对比。**

#### 验收标准

| 项目 | 要求 |
| --- | --- |
| 前置统计 | 治理前的告警数有具体数字，按规则名分类列出 |
| 分层正确 | 每条告警都能说出属于格式层还是语义层 |
| 治理完成 | `pnpm lint` 与 `pnpm lint:style` 输出零问题 |
| 前后对比 | 有一张“治理前 / 治理后”的数量对照表 |
| 额外发现 | 指出至少一处检查发现不了、但确实会出 bug 的写法，并说明现象 |

::: details 参考思路
**第一步的预期结果**（具体条数取决于你配的规则集，量级一致）：

| 来源 | 大致条数 | 典型规则 |
| --- | --- | --- |
| ESLint | 6 到 10 条 | `eqeqeq`、`no-unused-vars`、`vue/require-v-for-key` 之外的用法 |
| Stylelint | 2 到 3 条 | `length-zero-no-unit`、`color-hex-length` |

**第三步的分类**：

| 告警 | 层 | 能自动修 | 怎么改 |
| --- | --- | --- | --- |
| `item.status != currentStatus.value` | 语义 | 能 | `!==` |
| `keyword.value != ''` | 语义 | 能 | `!==` |
| `formatDeadline` 未使用 | 语义 | 不能 | 删掉 import（或补上使用） |
| 两行从同一文件分别 import | 语义 | 不能 | 合并成一行 |
| 缩进、引号 | 格式 | 能 | 交给 Prettier |
| `margin: 0px` | 格式 | 能 | `0` |
| `#FFFFFF` | 格式 | 能 | `#fff` |

**第四步里“检查发现不了的问题”**：`let loading = false` 不是响应式的。
接口慢的时候，页面上的加载状态**永远不会显示出来** —— 因为改一个普通变量
不会触发重新渲染。

正确写法是用 `ref`：

```js [✓ 正确写法]
const loading = ref(false)
// 使用时：loading.value = true
```

**这个练习最重要的一点是**：检查工具能拦住一部分问题，
但“变量该不该是响应式的”这类问题它管不了 —— 还是得靠你理解框架。

另外 `fetch` 没有处理失败情况，接口报错时 `loading` 会一直停在 `true`
（如果改成了 `ref` 的话）。这类问题也属于“检查发现不了”。
:::

### 练习 2 · 故意提交一次不合规的代码

#### 要求

按下面的顺序做，每一步都把终端输出记录下来。

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 | 提交一个格式有问题的文件 | `pre-commit` 拦下 |
| 2 | 修掉格式问题，提交信息写“改了一下” | `commit-msg` 拦下 |
| 3 | 换一个不合规的类型，比如 `update: xxx` | 仍被拦下 |
| 4 | 写成 `feat(activity): 活动列表支持按状态筛选` | 提交成功 |
| 5 | 用 `git log --oneline -3` 看结果 | 提交记录格式统一 |

#### 验收标准

| 项目 | 要求 |
| --- | --- |
| 截图完整 | 四次拦截/成功的终端输出都有记录 |
| 报错看懂 | 每次被拦下时，能指出是哪条规则、哪一行 |
| 提交记录 | `git log` 里的三次提交信息都符合格式 |
| 记录反思 | 写一句：如果没有钩子，这三个问题会在什么时候被发现 |

::: details 参考思路
**第 1 步的关键**：故意写一个格式问题（比如缩进 4 个空格 + 双引号）。

```js [src/features/activity/tmp.js（临时文件）]
const  statusList = ["报名中", "已结束"]
```

提交时会看到 `pre-commit` 的输出，里面包含 ESLint 的报错和规则名。
**注意：Prettier 可能直接把它格式化好了，所以这一步不一定失败。**
如果没失败，说明你的 `lint-staged` 配置里 Prettier 排在 ESLint 之后 ——
那就改成一个 ESLint 一定报的语义问题，比如 `status == 0`。

**第 2 步会看到这样的输出**：

```text [终端]
⧗   input: 改了一下
✖   subject may not be empty [subject-empty]
✖   type may not be empty [type-empty]
```

**顺序不能颠倒**：`pre-commit` 在 `commit-msg` 之前跑。
如果 `pre-commit` 就失败了，你根本看不到 commitlint 的报错。

**最后一句反思的落点**：如果没有钩子，这三个问题会在**代码评审**时被发现
（占用别人的时间），或者在**流水线**上被发现（等待更久），
最坏的情况是在**演示时**被发现。
:::

### 练习 3 · 两人一组实现功能并互相评审

#### 要求

两人配合完成一次完整的协作流程，**每个人都要经历“作者”和“评审人”两个角色**。

**功能范围建议**（两人各选一个，都改到同一批文件才能出现有价值的讨论）：

| 角色 | 功能 | 主要文件 |
| --- | --- | --- |
| A | 活动列表按状态筛选 | `ActivityListView.vue`、`features/activity/api.js` |
| B | 活动列表按关键词搜索 | 同上 |
| 可选 C | 报名截止时间的格式化 | `ActivityListView.vue`、`shared/utils/format.js` |

**每个人的操作清单**

1. 从 `main` 切功能分支，命名符合 `<类型>/<描述>`。
2. 至少 3 次提交，每次只做一件事。
3. 推送，开合并请求，填写说明（做了什么、怎么验证）。
4. 评审搭档的合并请求，**至少留 2 条评论**，其中至少 1 条提出问题或建议。
5. 处理搭档给你的评论，说明采纳或不采纳的理由。
6. 流水线跑绿后合并。

#### 验收标准

| 项目 | 要求 |
| --- | --- |
| 分支 | 命名规范，从最新的 `main` 切出 |
| 提交 | 信息符合格式，粒度合适，没有 `wip` 残留 |
| 合并请求 | 有说明，不能只写“改了一下” |
| 评审 | 双向评审：每个人至少留 2 条评论 |
| 评论质量 | 说清“改什么”和“为什么”，不只给结论 |
| 合并 | 合并前流水线是绿的 |

::: warning 评审评论的质量是这道题的重点
数量容易凑，质量不容易。对照 [3.4 的评审标准](/unit03/04-git-flow#代码评审看什么不看什么)自查：

| ✗ 低质量评论 | ✓ 高质量评论 |
| --- | --- |
| 这里可以优化 | 第 58 行：筛选和过滤写在一个 computed 里，拆成两个可读性更好，也方便单独测试 |
| 加个注释 | 这段名额计算的边界（通过人数等于上限）没有注释，建议补一句说明为什么不关闭入口 |
| 这样写不好看 | 第 42 行用了 `indexOf` 判断包含，改成 `includes` 更直观 |

**判断方法：把你的评论遮住结论，对方能不能自己判断该改什么。**
:::

::: details 参考思路
**怎么让冲突真的出现**（这道题的价值一半在这里）：

- 两人都改 `ActivityListView.vue` 里同一个计算属性。
- 一个人加筛选逻辑，另一个人把 `filter` 的参数名从 `a` 改成 `item`。

两人都提交之后，后合并的那个会遇到冲突。**冲突的处理过程要记录下来**：

| 记录项 | 内容 |
| --- | --- |
| 冲突文件 | |
| 冲突标记原文 | |
| 两边的意图分别是什么 | |
| 最终选了哪个 / 怎么合并的 | |
| 判断依据 | |
| 解决后怎么验证的 | |

**如果没出现冲突也不要紧**，但要在报告里说明为什么没冲突 ——
大概率是两人改的文件本来就分散，这本身就是 [3.3 按功能分目录](/unit03/03-modules-structure) 的收益。
:::

### 练习 4 · 配一条自动构建流水线

#### 要求

| 项目 | 要求 |
| --- | --- |
| 触发条件 | 推送到功能分支时触发；发起合并请求时触发 |
| 环境 | 显式指定 Node 24 |
| 安装 | `pnpm install --frozen-lockfile` |
| 检查 | `pnpm lint` |
| 构建 | `pnpm build` |
| 缓存 | 配好依赖缓存 |
| 门禁 | 流水线通过才允许合并 |

#### 验收标准

| 场景 | 预期结果 |
| --- | --- |
| 正常推送 | 全绿 |
| 故意提交格式错误 | 检查阶段失败，合并按钮不可用 |
| 修好后推送 | 恢复绿色，按钮可用 |
| 连跑两次 | 第二次安装阶段明显更快 |

**截图留证**：绿色一次、红色一次、两次耗时对比、门禁生效时的界面。

::: details 参考思路
**第一次跑红是正常的**，处理顺序：

1. 先看**第一条**具体报错（从日志底部往上翻）。
2. 判断属于哪一类：环境问题（Node 版本、环境变量）还是代码问题（检查、构建）。
3. 环境问题改流水线配置；代码问题改代码。

**缓存怎么验证生效**：

| 次数 | 安装依赖耗时 | 说明 |
| --- | --- | --- |
| 第一次 | 约 1 分钟 | 全部重新下载 |
| 第二次 | 十几秒 | 命中缓存 |

**如果第二次没变快**，检查缓存的键是不是用了会变的值（比如时间戳）。
正确的做法是用锁文件的哈希当键 —— 锁文件没变，缓存就一直有效。

**门禁那一步**：在仓库设置的合并请求规则里勾选“流水线必须通过”。
如果平台不支持这个功能，就在报告里说明，并写成“由评审人确认流水线状态”。
:::

## 选做题

### 练习 5 · 写三条适合本团队的额外 ESLint 规则

结合 [3.1 的“三遍规则”练习](/unit03/01-why-lint#课后练习)，
给你们的项目提三条新的检查规则。

**要求**

每条都填完整：

| 规则名 | 等级 | 理由 | 会拦下什么 | 什么情况下会误报 | 怎么处理误报 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

**候选方向**

| 方向 | 可能的规则 | 说明 |
| --- | --- | --- |
| 调试代码 | `no-console`、`no-debugger` | 只留 `warn` 和 `error`，控制台输出要清理 |
| Vue 组件写法 | `vue/component-name-in-template-casing` | 模板里组件名统一用 PascalCase |
| 属性顺序 | `vue/attributes-order` | 模板属性按固定顺序排 |
| 异步处理 | `no-floating-promises` 类规则 | 不允许裸的 Promise 调用 |
| 命名 | `camelcase` | 变量名统一风格 |

**验收点**：“什么情况下会误报”这一栏必须填。
答不出来就不合适现在加 —— **一条今天就会误报的规则，今天就会被关掉。**

::: tip 为什么只要求三条
规则加得越多，误报的机会越多，被绕过的概率越大。

**三条规则如果能稳定执行一个学期，比三十条执行三天有价值得多。**
:::

## 自检标准

做完之后，逐条自查：

- [ ] 治理前后的告警数量有具体数字对比，且治理后为零
- [ ] 能说清每条告警属于格式层还是语义层
- [ ] 指出至少一处检查发现不了但会出 bug 的写法
- [ ] 提交钩子的拦截效果有截图，四种情况都验证过
- [ ] 完成了双向评审，每个人至少留了 2 条有理由的评论
- [ ] 冲突（如果有）的处理过程有完整记录
- [ ] 流水线在正常推送时全绿，在有问题时变红
- [ ] 流水线设成了合并门禁，并验证过按钮状态
- [ ] 工程模板能被别人克隆后跑起来（找一个人试一遍）

全部打勾，这个单元过关。**这份工程模板就是第 11 周综合项目的起点。**

## 常见问题

::: details 没有搭档怎么办
三个办法：

1. 找隔壁组的同学互换评审 —— 互相帮忙看一下，双方都受益。
2. 请老师或助教当评审人。
3. 自己用两个分支模拟：用 `feat/a` 和 `feat/b` 两个分支同时改同一个文件，
   先后合并，人为制造一次冲突。

**第 3 种办法能做出冲突，但体会不到“评审时该怎么想”** ——
所以只作为备用方案。评审能力是这道题真正的考点。
:::

::: details 流水线一直红，改不动了
按这个顺序分诊：

| 失败阶段 | 大概率是 | 先做什么 |
| --- | --- | --- |
| 安装依赖 | 锁文件没提交、Node 版本不对 | `git status` 看锁文件，对照 `engines` 查版本 |
| 代码检查 | 规则太严或历史代码有问题 | 先只保证“本次改动文件”通过 |
| 构建 | 路径大小写、导入错误、环境变量缺失 | 本地删掉 `node_modules` 重装再构建一次 |

**不要为了让它变绿而关规则。** 如果确实需要临时放行，
把那条规则设成 `warn`，并在 `TODO` 里记下来 —— **放行要留痕。**
:::

::: details 我们的平台不支持合并请求门禁
两种替代方案：

1. **靠流程**：在团队的合并请求说明里固定一条“合并前确认流水线为绿色”，
   由评审人核对。
2. **靠平台的其他功能**：有些平台支持“保护分支”，禁止直接推送到 `main`，
   这也是一种门禁（推不上去，就必须走合并请求）。

**在报告里写清你用的是哪种，以及它的局限在哪里。**
:::

::: details 三个人一起做可以吗
可以，但要注意功能不要重叠太多 —— 三个人都改同一个文件会很难收场。

建议的分工方式：**一个人负责一个页面或一个功能**，
评审时两两交叉（A 评 B、B 评 C、C 评 A），这样每个人都能看到两种不同的写法。

**评审面越广，学到的东西越多。** 只评跟自己写法差不多的那份合并请求，收益有限。
:::
