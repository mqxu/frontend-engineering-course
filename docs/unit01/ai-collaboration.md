# 单元 1 · AI 协作：用 AI 做调研和排错，结论得自己核

这一章你还没开始写业务代码，AI 在这里的用处不是“帮你写”，是**帮你把看不懂的东西看懂，把找不到的线索找出来**。

但这一章也是 AI 最容易把你带偏的地方：它给的命令、包名、版本号，都可能是不存在的。

## 这一章哪些活能交给 AI

判断标准先立起来：**能让你更快理解一件事的活可以交，需要你自己做判断的活不能交。**

| 任务 | 能交给 AI 吗 | 为什么 |
| --- | --- | --- |
| 解释一个陌生概念 | 可以 | 它见过的解释比教程多，换个说法往往就通了 |
| 把报错信息翻译成人话 | 可以 | 报错原文是给工具看的，不是给人看的 |
| 根据你的情况列环境自检清单 | 可以 | 它知道一个前端工程通常要装什么 |
| 对比两个工具的区别 | 可以 | 能快速给你一张对比表当起点 |
| 判断你该先学什么、走哪个方向 | **不行** | 它不了解你的基础、时间、目标，这是你要自己定的 |
| 给出安装命令和版本号 | **不能直接信** | 后面的“容易错什么”专讲这一节 |
| 决定你的目录结构 | **不行** | 取决于你的项目实际，它看不到 |

最后三行是这一章的重点。**AI 在这一章的作用是“把信息整理清楚”，不是“替你做决定”。**

## 提示词怎么写

### 1. 让它把概念讲成人话

```text
用一句话解释 [概念] 是什么、解决什么问题、什么时候不该用。

然后举一个校园活动管理后台里的例子，说明如果没有它会遇到什么麻烦。

不要展开讲原理，我要的是判断标准。
```

**为什么这么写**：“一句话”是硬约束，能挡掉长篇大论。要求用**你自己的项目**举例，是因为泛泛的例子你看了不会往心里去 —— 换成活动管理后台的场景，你立刻能对上号。最后一句防的是它一上来就讲实现细节。

### 2. 让它帮你读报错

```text
我在装环境时遇到这个报错：

[完整粘贴报错，不要只贴一句]

我的系统是 [Windows 11 / macOS 15]，用的是 [Node 24 LTS]，
在此之前我执行的操作是 [装 fnm 并切换版本]。

请回答：
1. 这个报错最可能的原因是什么，按可能性排序
2. 为了确定是哪一种，我下一步该跑什么命令、看什么
3. 每种原因的解决步骤

你确定的地方直接说结论，不确定的地方明确说不确定。
```

**为什么这么写**：报错排查最耗时间的不是“不知道原因”，是“不知道下一步看什么”。第 2 点逼它给出可执行的下一步，而不是笼统的“建议重装”。最后一句很关键 —— 让它敢说“不确定”，比拿到一个语气笃定但其实错了的答案强得多。

### 3. 让它列环境清单

```text
我是软件工程技术专业的学生，要在一台 [Windows 11] 电脑上搭前端开发环境，
之后要学 Vue 3、用 Vite 构建、用 Git 提交代码。

请列一份环境自检清单：每项要装什么、怎么确认装好了、装错会有什么表现。
用表格，三列。
```

**为什么这么写**：把“你要干什么”讲清楚，清单才不会是通用的。要求给“装错的表现”，是因为环境问题最难的地方就是**装错了但不报错** —— 比如 Node 装了但 PATH 没配好。

## AI 在这一章容易错什么

### 编造一个不存在的包名或命令

**现象**：它给你的安装命令里有个包名，格式完全正常，看起来很像真的，但装的时候报 `404 Not Found` 或 `package not found`。

**原因**：它并不是“查了官方仓库发现没有”，而是根据见过的成百上千个包名，按命名规则拼了一个出来。这种行为有个名字叫“幻觉依赖”。同一个问题也会出现在命令上 —— 比如让你执行某个工具里并不存在的子命令。

**怎么处理**：装之前先确认存在。

```bash
# 查 npm 上的包是否存在、最新版本是多少
curl -s https://registry.npmjs.org/vue/latest | head -c 200

# 包名里带斜杠的，斜杠要转义成 %2F
curl -s https://registry.npmjs.org/@vue%2Fuse%2Fcore/latest | head -c 200
```

返回 `{"error":"Not found"}` 就是不存在。命令的话，用 `command -v 命令名` 看有没有。

### 给一个过时的安装方式

**现象**：它让你 `npm install -g` 全局装某个工具，或者让你用一个已经废弃的工具。

**原因**：它的知识有截止时间，而前端工具链的推荐做法两三年就会换一轮。比如包管理器从全局安装转向了版本管理工具，很多老教程里的做法现在已经不推荐。

**怎么处理**：安装方式以**官方文档**为准。判断方法很简单：搜一下工具名加“官方文档”，看首页的 Getting Started 里写的是什么。另外，看到 `-g` 要警惕 —— 全局安装的包会污染系统环境，不利于版本切换，现在的推荐做法基本都不用全局安装。

### 按主流环境给你答案，忽略你的实际情况

**现象**：你在 Windows 上，它给的命令是 macOS 的；或者反过来。

**原因**：它默认按训练数据里出现最多的环境回答。你的系统、Shell、已有版本这些信息，它不看你的电脑是不知道的。

**怎么处理**：**每次提问都把环境说清楚。** 一句话的事：`我的系统是 Windows 11，用 PowerShell`。上面第 2 个提示词模板里特意留了系统这一项，就是为了这个。

::: details 还有一类错误：把“能跑”说成“没问题”
**现象**：你问“这个配置对不对”，它回答“配置正确，可以正常使用”。你按它说的做了，结果启动不起来。

**原因**：它没有运行环境，无法真正验证。它判断“对不对”的依据是这段配置看起来符不符合规范。

**怎么处理**：把问题从“对不对”改成“怎么验证”。例如不要问“我这个 PATH 配得对吗”，改问“我该怎么确认 PATH 配好了，给我一条能直接跑的命令”。**能跑的验证命令比“应该没问题”可靠得多。**
:::

## 怎么验收 AI 的产出

这一章的产出大多是**信息**，不是代码，所以验收动作也不一样。逐条过：

- [ ] 它给的每一个包名，都在 `registry.npmjs.org` 上查到了
- [ ] 它给的每一个命令，都用 `command -v` 或官方文档确认过存在
- [ ] 它给的每个版本号，都在官方渠道核实过（npm registry 或 nodejs.org）
- [ ] 安装方式与官方文档的 Getting Started 一致，没有出现 `-g`
- [ ] 提问时说明了你的操作系统和 Shell，它的回答没有假设错环境
- [ ] 问到“对不对”时，它给的是可执行的验证命令，而不是“应该没问题”
- [ ] 你不能确定的地方，已经动手试过一遍，而不是直接写进环境自检报告

前四条对应“信息真不真”，中间一条对应“针不针对我”，最后两条对应“有没有真的验证”。**这七条过完，AI 在这一章的产出就可以用了。**

## 练习

### 用 AI 把一份报错查清楚

**任务**：故意制造一个环境报错，然后用 AI 把它查清楚，写成一份记录。

制造报错的几个办法（挑一个）：

1. 故意把 `package.json` 里的 `"type": "module"` 删掉，再运行 `pnpm dev`。
2. 故意写一个不存在的依赖名，执行 `pnpm install`。
3. 把 Node 版本切到一个很老的版本，再跑一个新项目。

**要求**：记录里必须包含这四项，顺序不能变：

| 项 | 要求 |
| --- | --- |
| 报错原文 | 完整粘贴，不许删减，不许只写“报错了” |
| AI 的第一版回答 | 按可能性排序的原因列表 |
| 你实际验证的结果 | 哪些原因被排除、用什么命令排除的 |
| 最终原因与解决 | 现象 → 原因 → 解决 → 怎么预防下次 |

::: details 验收标准与参考思路
**为什么要“故意制造报错”**：等报错自己找上门，你只会手忙脚乱地试；主动造一个，你才有余力观察是哪一环出的问题。而且你知道正确答案，正好能验证 AI 说得对不对。

**思路提示**：

- 提问时一定要贴**完整报错**，尤其别删掉最后那几行 —— 真正的原因往往在最后一行。
- 让 AI 给出“下一步该看什么”，然后你真的去看。这一步是重点，别跳过。
- 如果 AI 的第一版原因猜错了，**把它猜错的这一条也记下来**，写清你是怎么排除的。这类记录在后续单元会一直用。
- 环境类报错的排查顺序可以从这里切入：先确认命令本身存在 → 再确认 Node 版本对得上 → 再确认依赖装上了 → 最后才怀疑代码。

**不合格的写法**：

> AI 说是 Node 版本问题，我换了版本就好了。

这句话没有信息量：换到什么版本？为什么原版本不行？怎么确认就是版本问题而不是碰巧好了？

**合格的写法**：

> 报错是 `SyntaxError: Unexpected token 'export'`。AI 给了三个原因，第一个是 `package.json` 里缺 `"type": "module"`。
> 我用 `node -e "console.log(require('./package.json').type)"` 查到返回 `undefined`，确认了这一条。
> 补上 `"type": "module"` 后报错消失。原因是 Node 默认把 `.js` 当 CommonJS 处理，
> 而 Vite 的配置文件用的是 ESM 语法。预防办法：以后新建工程先确认这三个字段 ——
> `type`、`engines`、`packageManager`。

差别在于：后者**能复现、能验证、能迁移到别的场景**。
:::
