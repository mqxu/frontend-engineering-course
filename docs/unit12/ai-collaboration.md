# 单元 12 · AI 协作：优化建议先验证，再采纳

最后一章的内容是三件事：联调、优化、部署，最后交材料。AI 在这三件事上都能帮上忙，但它的建议有一个共同的性质：

**它是假设，不是结论。**

它说“加上路由懒加载首屏会快很多”—— 这句话在大多数项目上成立，但在你的项目上是不是成立，得测完才知道。它说“这段代码没人用，可以删掉”—— 它是从“代码里没有引用”推出来的，而懒加载进来的路由在代码里本来就看不到静态引用。

这一章要建立的最后一个习惯是：**没有测量就没有优化。** 这条习惯的价值不止在课程里 —— 它决定了你以后是“照着 AI 的建议改一堆东西”还是“改一处、量一次、留下确实有效的那几处”。

## 这一章哪些活能交给 AI

判断标准：**列出可能性可以交，判断“值不值得做”不能交 —— 后者需要测量数据，它没有。**

| 任务 | 能交给 AI 吗 | 为什么 |
| --- | --- | --- |
| 审 Nginx 配置，指出漏项 | 可以 | 配置项是有限的，它能核全 |
| 解释每条配置防的是什么问题 | 可以 | 配置的语义它讲得清 |
| 列出这个项目可以优化的方向 | 可以 | 当清单用，采纳哪条由测量决定 |
| 给每条优化配一个测量办法 | 可以 | 这一条它会做得不错，只要你要求 |
| 起草 README 与交付文档的结构 | 可以 | 结构有固定套路 |
| 审答辩稿的逻辑有没有前后矛盾 | 可以 | 这类一致性检查它做得快 |
| 判断“这个优化值不值得做” | **不能直接信** | 它只看“理论上更快”，看不到你的实测数据 |
| 判断“这段代码可以删吗” | **不能直接信** | 它看不到动态引用与懒加载 |
| 决定交付材料包含哪些 | **不行** | 取决于课程要求 |
| 决定部署方式 | **不行** | 取决于学校或企业给的服务器条件 |

**倒数第三行是这一章的核心。** 优化建议它永远给得出来，而且听起来每条都有道理。你的任务不是挑出“哪条有道理”，而是**测出哪条在你的项目上真的有效。**

## 提示词怎么写

### 1. 让它审部署配置，每条都要说清防的是什么

```text
这是我的 Nginx 配置：

[粘贴完整配置]

请分两部分回答。

第一部分：逐条说明
| 配置项 | 防的是什么问题 | 漏了会怎样 |
（我写了什么就列什么，不要补充我没写的）

第二部分：缺了什么
这个项目是 Vue 单页应用，用的是 history 路由模式，
接口走 /api 前缀转发给后端。按这些前提，我的配置里
还缺哪几项？每项说明漏了之后会出现什么现象。
```

**为什么这么写**：分两部分是关键。**第一部分限定“只说我写了的”，第二部分才让它补充。** 合在一起问，它会把“应该有的”和“你已有的”混成一张表，你分不清哪些是你已经配好的、哪些是它建议加的。

第二部分要写清前提（单页应用、history 模式、`/api` 前缀），这些前提决定了哪些配置项是必需的。不写前提，它给的清单会变成一份通用的最佳实践，跟你项目的实际对不上。

这个配置里最容易漏的三处，你可以先自己核一遍：

| 漏什么 | 现象 |
| --- | --- |
| `try_files $uri $uri/ /index.html` | 刷新子路由就 404，直接输地址进不去 |
| `index.html` 的不缓存头 | 前端发版后，用户拿到的还是旧页面（引用了已经不存在的旧文件，白屏） |
| `/api/` 那一处 `proxy_pass` 后面加了斜杠 | `location` 前缀被替换掉，`/api/activities` 变成 `/activities`，后端 404 |

### 2. 让它给优化建议，每条必须带测量办法

```text
这是我的项目情况：
- 构建产物总大小：[数值]，首屏加载的 JS：[数值]
- 页面数量：[数值]
- UI 库：Element Plus
- 路由：已开启懒加载 / 未开启（选一个）

请列出可以优化的方向。

要求：
1. 每条给三个信息：改什么、预期改善多少、**怎么测量**
2. “怎么测量”要具体到操作步骤，比如“跑 pnpm build 看 dist 总大小”
   或者“用浏览器开发者工具的网络面板，看首屏 JS 的传输大小”
3. 按“改动量小收益大”排序
4. 说明哪些优化之间会互相影响（做了 A 会影响 B 的效果吗）
```

**为什么这么写**：第 1 点里“怎么测量”是必须要求的一项。不要求它就只说前两项 —— 而前两项你没法验证。

第 4 点很实用：**优化之间会互相影响。** 比如“分包”和“按需引入”都作用在同一个产物体积上，两个一起做，各自的收益会比单独做时小。它不主动说这件事，你就会以为是两个收益相加。

拿到清单之后，你的动作是**挑一条、改、测、记，然后再挑下一条。** 一次改五条，测不出是哪条起了作用 —— 这正好是[12.2](/unit12/02-build-optimize)里“先测，再改”那一步的要求。

### 3. 让它审答辩材料里的“难点”是不是真难点

```text
我的答辩稿里“遇到的难点与解决”这一节写的是：

[粘贴这一节的内容]

请逐条判断：这一条算不算真的难点。
判断标准：
- 是真的解决了一个技术问题，还是只是“照着文档做了一遍”？
- 解决问题时有没有做过取舍？取舍是什么？
- 有没有可以出示的证据（日志、代码对比、测量数据）？

对每条给出“算 / 不算 / 说不好”和理由。
最后：如果我要把“不算”的那几条改写成真实情况，给我改法。
不要帮我把它们包装成难点。
```

**为什么这么写**：最后一句是这一段的关键。**不加这句话，它的默认行为是帮你想怎么把小事写得像大事** —— 这正好是答辩里最容易被问穿的地方。老师追问一句“这里你具体解决了什么”，包装过的内容立刻露馅。

判断标准里那三条是实用工具。“有没有可以出示的证据”尤其好用 —— **能拿出日志或测量数据的，才是真做过的。**

## AI 在这一章容易错什么

### 建议删掉“看起来没人用”的代码

**现象**：它说“这段 `src/components/StatCard.vue` 在项目里没有被引用，可以删掉”，或者“这个 `v-permission` 指令没有地方在用”。

**原因**：它靠的是**静态引用检索** —— 在代码里搜这个文件名或函数名。而通过懒加载引入的路由、通过动态注册挂上去的组件和指令，在代码里本来就没有静态引用。它看不到这一层。

**后果很直接**：删了之后页面白屏，或者某个按钮的权限控制失效了。而且你很可能要等到演示前才想起来打开那个页面。

**怎么处理**：**删除代码这件事，永远自己确认，不要照它说的做。** 判断一个文件或指令是不是真的没人用，用这几个动作：

```bash
# 1. 按文件名搜（包括不带扩展名的写法）
grep -rn "StatCard" src/

# 2. 按注册方式搜 —— 懒加载的路由通常写成 () => import
grep -rn "import(" src/router/

# 3. 全局组件和指令是注册上去的，搜注册名
grep -rn "app.component\|app.directive" src/

# 4. 模板里的写法可能和文件名不一样（kebab-case）
grep -rn "stat-card\|statCard" src/
```

四条都搜不到，再考虑删除。本项目的 AGENTS.md 里有一条禁止事项就是这件事：**不要删除你没有确认过引用位置的代码，删除前先给出检索结果。** 这条约定就是为了防这类问题。

**一个更稳的做法**：不删，先注释掉，跑一遍所有页面，确认没问题了再删。多花五分钟，换一个不会在演示时翻车的把握。

### Nginx 配置漏项或者写反

**现象**：它给的配置里有 `location /api/ { proxy_pass http://127.0.0.1:8080/; }`（多了一个斜杠），或者没有 `try_files`，或者给 `index.html` 也设了 `expires 1y`。

**原因**：这些都是“看起来合理”的写法。`proxy_pass` 后面加斜杠符合直觉（一个地址当然以斜杠结尾），给 `index.html` 设缓存也符合“静态资源都该缓存”的思路。

**怎么处理**：记住这三处的正确写法与后果。

```nginx
# ① history 模式必需
location / {
    try_files $uri $uri/ /index.html;
}

# ② 带哈希的资源可以缓存一年
location /assets/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}

# ③ 入口 html 必须不缓存 —— 少了这条，② 就成了麻烦
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}

# ④ proxy_pass 后面不要加斜杠
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
```

②和③要一起记：**带哈希的文件可以缓存一年，入口 html 必须每次都检查。** 只做②不做③，用户会拿着缓存的旧 `index.html` 去加载已经不存在的旧文件 —— 现象是白屏，而且你自己刷新几十次都复现不了（因为你的浏览器可能是新的）。

还有一处小细节：`gzip_types` 里**不要加 `text/html`**。Nginx 默认就对 HTML 压缩，加进去会有一条警告。

### 优化建议不给测量办法

**现象**：它给你一段“优化建议”，每条都写着“可以显著提升首屏速度”“能有效减少体积”，但没有一条告诉你改完怎么确认。

**原因**：这类表述在性能文章里到处都是，它照着这个层次写。而且它没有你的项目可跑，本来也给不出实测数据。

**怎么处理**：**把“有没有测量办法”当作采纳建议的第一道门槛。** 一条建议如果给不出测量办法，就直接不采纳 —— 不是因为它一定错，而是因为你没法知道它有没有用。

常用的测量办法其实就几个动作：

| 测什么 | 怎么测 |
| --- | --- |
| 产物总大小 | `pnpm build` 之后看输出的各文件体积 |
| 首屏加载的 JS 有多大 | 浏览器开发者工具的网络面板，刷新一次看加载了哪些文件、传输了多少 |
| 某个页面的加载时间 | 网络面板里的瀑布图，看最后一个请求什么时候结束 |
| 分包有没有生效 | 构建输出里有没有生成额外的 chunk 文件 |

**改前测一次、改后测一次，把两个数记下来。** 只有一组数据的话，你没法区分“变快了”和“本来就快”。

顺带一个判断：**如果一条建议的收益在测量单位的量级以下，就不值得做。** 比如用 gzip 把产物从 900 KB 压到 300 KB，是显著改善；某个优化把 12 KB 压到 11 KB，在你的项目规模上没有任何意义。**优化要有终点，不能无限做下去。**

### 建议清理文件，把交付材料删了

**现象**：你说“帮我清理一下仓库”，它列出一堆“可以删除”的文件 —— 里面可能包含交付文档、你的笔记、答辩用的截图、`.env.example` 之类的示例配置文件。

**原因**：它判断标准是“这个文件在构建流程里有没有用”。对构建没用的，它就归到可删的那一类。而交付材料当然对构建没用。

**怎么处理**：**清理仓库和删除代码是同一类操作，都要你逐条确认。** 分两步走：

1. **先让它列清单，不让它动手。** 明确说“只列出来，不要删除任何文件”。
2. **拿清单对照交付要求逐项确认。** 交付材料、`.env.example`、`README.md`、`LICENSE`、`.gitignore` —— 这些都在可删清单里出现过，但都是要交的。

判断一个文件该不该删，问一句：**“删了之后，别人克隆下来能不能跑起来、能不能看懂？”** 答案是“不能”，就别删。

::: details 还有一类错误：把没解决的难点写成亮点
**现象**：你让它帮你改答辩材料，它建议把“尝试了某个方案但没成功”这一段删掉，或者改写成一个“攻克了难题”的故事。

**原因**：它的默认目标是“让材料看起来更好”。而“看起来更好”和“写得真实”在答辩这个场景里是冲突的 —— 答辩的评审会追问。

**怎么处理**：让它审材料时，明确要求它**不要美化**。

有一个判断很有用：**真正的难点，一定伴随着取舍和一个明确的理由。** 拿这条过一遍你的材料：

| 写法 | 算不算难点 |
| --- | --- |
| “用了 Pinia 做状态管理” | 不算 —— 照着文档做了一遍 |
| “用了 Pinia，但 token 的持久化没放进去，因为担心 XSS” | 算 —— 有取舍，有理由 |
| “排查了跨域问题” | 说不好 —— 要看有没有定位过程 |
| “接口 401 后自动跳登录，但跳转时丢了原来要去的页面。后来在守卫里带了 redirect 参数，同时校验它不会跳到站外” | 算 —— 有问题、有方案、有安全考虑 |

右边这一列的共同点：**能说出“为什么这么做”和“为什么不那么做”。** 答辩时能讲出这两句，比罗列十个功能有用得多。

顺便说一个反向用法：把已经解决的难点改成“已知问题”。有些问题你确实没解决完，写在“已知问题”里是诚实的，而且老师通常会问“你打算怎么解决”—— 你答得上来，比假装解决了更得分。
:::

## 怎么验收 AI 的产出

这一章的产出是部署配置、优化改动、交付材料。验收动作全部围绕“测过没有”。

- [ ] Nginx 配置里有 `try_files`，有 `index.html` 的不缓存头，`proxy_pass` 后面没有斜杠
- [ ] 配置用 `nginx -t` 测过语法，再 `reload`（不是 `restart`）
- [ ] 每一条采纳的优化，都有改前改后的两组测量数据
- [ ] 没有采纳任何“给不出测量办法”的优化建议
- [ ] 它建议删除的代码，你逐条搜过引用（含懒加载与动态注册），确认过再删
- [ ] 仓库里没有 `MOCK_`、`console.log`、硬编码的本机地址
- [ ] 交付材料齐全：README、交付文档、答辩材料、AI 参与声明
- [ ] 从零克隆下来，照 README 能做起来

前两条对应“配置对不对”，中间三条对应“改动有没有依据”，后三条对应“交付完整不完整”。**最后一条是整个课程里最实在的一条验收 —— 能做到这一条，说明你的项目是“交出去了”而不是“做完了”。**

## 练习

### 拿一份部署配置让 AI 挑问题，逐条验证哪些是真问题

**任务**：用你在[12.3](/unit12/03-deploy)里写的 Nginx 配置（或者从同学那里借一份），让 AI 挑问题，然后**逐条动手验证哪些是真问题、哪些是它多虑了**。

**要求**：记录里必须包含这四项：

| 项 | 要求 |
| --- | --- |
| 你的配置 | 完整保留 |
| AI 挑出来的问题 | 逐条记录 |
| 逐条验证结果 | 每条写清“怎么验证的”“结论是真是假” |
| 修订后的配置 | 只改验证为真的那几条，并说明为什么没改其余的 |

::: details 验收标准与参考思路
**为什么重点在“验证”**：让 AI 挑问题很容易，它一定能挑出一堆。**这一节要练的是“判断哪条该改”** —— 全部照改，你会把配置改得越来越复杂；全部不理，你可能会漏掉真问题。判断依据只能来自实测。

**思路提示**：

- 验证 `try_files` 那一条：**打包部署后，直接在地址栏输一个子路由地址回车。** 有回退就正常显示，没有就 404。这个动作十秒钟就能做完。
- 验证 `index.html` 缓存那一条要稍微绕一下：改一次代码、重新构建、部署，然后**强行刷新（`Ctrl+Shift+R` 或 `Cmd+Shift+R`）** 看能不能拿到新版本；再等一段时间不刷新看一次。测出来才有结论。
- 验证 `proxy_pass` 斜杠那一条：把两种写法各试一次，看后端收到的路径是什么（后端日志里能看到，或者在前端网络面板看响应的 404）。
- **它挑出来的问题里，一定有“理论上有道理但你的场景下不影响”的。** 比如它会建议加 `client_max_body_size`，但你的项目没有文件上传，这一条就不必改。这类“不改”的决定要写清理由 —— **这也是这段记录里最有价值的部分。**
- 顺手把“验证办法”整理进部署文档。下次部署换一台服务器，照着做一遍就行。

**不合格的写法**：

> AI 挑出了五条问题，我全部改了，现在配置更完善了。

“全部改了”意味着你没有判断。那五条里如果有两条是你项目里用不到的，现在你的配置里就多了两段没人懂的东西 —— 半年后要改的人（可能是你自己）得先去弄明白它们为什么要写在那里。

**合格的写法**：

> AI 挑了五条。三条是真问题，两条不是。
> 【真问题一】它说缺 `try_files`。我在服务器上直接输 `/activities` 回车，得到 404，
> 确认是真的。加上之后同样的地址能正常显示了。
> 【真问题二】`index.html` 没有不缓存头。我改了一次代码重新部署，
> 用普通刷新（F5）看到的是旧页面，强行刷新才更新。确认是真的。
> 【真问题三】`proxy_pass` 结尾有斜杠导致接口 404。我看后端日志，
> 请求路径变成了 `/activities` 而不是 `/api/activities`，确认是真的。
> 【不是问题】它建议加 `client_max_body_size`。我们的项目没有文件上传，
> 最大的请求体是一个表单，几十 KB。不改。
> 【不是问题】它建议给 `/assets/` 加 `immutable`。我查了一下我原来的配置，
> 已经写了 `Cache-Control "public, immutable"`，它没读到。不改。
> 三条改动我都记进了部署文档，附上验证办法。

差别在于：后面这份记录里的每一条结论都有**一个具体的验证动作**。“不是问题”的那两条也写清了为什么不改 —— 这比改动本身更能说明你真的理解了这份配置。
:::
