# 综合项目 · AI 协作规范

这一页是综合项目的**执行约定**，和需求规格、接口约定同级。它规定三件事：仓库里要放什么、一次任务怎么让 AI 参与、交付时要声明什么。

::: tip 为什么单独写一页
因为“用 AI 写代码”这件事最容易失控的地方不是工具，是**没有约定**。全班三十个人各用各的方式让 AI 生成代码，最后交付出来的东西命名五花八门、接口约定各写一套、谁也不知道哪段代码是谁写的、有没有被审过。

这一页就是把这些不确定性消掉。
:::

## 一、仓库根目录的 AGENTS.md

### 要放什么

在仓库根目录新建一个 `AGENTS.md`，与代码一起提交。它是给 AI 读的“项目说明书”，也顺便帮新加入的组员理解项目。

下面这份是**本项目的模板，可以照着改**。不要直接抄 —— 里面的每条约定你都要确认和你们组实际的写法一致，写完对不上就是假的。

```md [AGENTS.md]
# 校园活动服务平台 · 管理端

学生会使用的活动管理后台。Vue 3 单页应用，对接后端 REST 接口。

## 常用命令

- 装依赖：pnpm install
- 开发：pnpm dev
- 构建：pnpm build
- 代码检查：pnpm lint
- 格式：pnpm format

改完代码先跑 lint，再提交。

## 技术栈

Vue 3.5（组合式 API，script setup）+ Vite 8.3 + Vue Router 5.3 +
Pinia 4.0 + Element Plus 2.14 + axios 1.20。

包管理统一用 pnpm，不要用 npm 或 yarn，也不要提交 package-lock.json。

## 目录约定

- src/views/       页面组件，一个路由一个文件，文件名用 kebab-case
- src/components/  通用组件，只有被两处以上复用时才移进来
- src/api/         接口函数，按业务模块分文件（activity.js、signup.js…）
- src/stores/      Pinia store，一个业务模块一个文件
- src/domain/      纯函数形式的业务规则，不依赖 Vue
- src/utils/       工具函数

不要在 views 下建二级子目录放同一个模块的组件，组件按复用范围放 components。

## 接口约定

- 后端响应格式统一为 { code, message, data }
- 成功码是 0，不是 200
- 前端字段用驼峰，后端返回下划线，转换在 src/api 层做，页面里不要出现下划线字段
- 业务错误码是四位数字，2005 表示名额已满，2006 表示已过报名截止时间
- 分页参数是 page 与 pageSize，返回结构是 { list, total, page, pageSize }

## 业务规则

- 活动状态：DRAFT → SIGNING → SIGNUP_CLOSED → FINISHED
- 下架是独立的布尔标记 offShelf，不是一种状态，不要把它写进状态判断
- 名额只统计审核通过（APPROVED）的报名记录，待审核和已驳回都不占名额
- 时段冲突判断：同场地的两个时段，只要一个的结束时间小于等于另一个的开始时间就不算冲突

业务规则的实现统一放 src/domain/activity-rules.js，不要散落在页面里。

## 代码风格

- 组件统一用 script setup 的写法（组合式 API），不用选项式 API
- 变量和函数用驼峰，组件文件名用大驼峰，其他文件名用 kebab-case
- 不写 console.log 提交，调试完删掉
- 不写 var，用 const，需要重新赋值才用 let

## 禁止事项

- 不要修改 src/utils/request.js 里的拦截器逻辑，那里处理业务码和登录失效
- 不要在任何文件里写密钥、token、真实账号密码
- 不要删除你没有确认过引用位置的代码，删除前先给出检索结果
- 不要改动 src/domain/ 下的规则函数签名，页面依赖它们
- 不要引入新的 UI 库或状态管理库

## 提交规范

提交信息用 <type>(<scope>): <subject> 格式，type 取 feat、fix、docs、
style、refactor、chore。一次提交只做一件事，不要一次提交二十个文件。
```

### 逐段说明

几个地方值得单独说清，因为它们是这份文件真正起作用的部分。

**“常用命令”放在最前面。** AI 最常见的错误之一是编造命令，把命令写在最前面能大幅减少这类错误。写完要自己跑一遍确认命令都对。

**“禁止事项”是最有价值的部分。** 有分析发现，在真实项目的 AGENTS.md 里，最有效的指令往往是最简单的边界说明，比如“不要提交密钥”。上面的五条禁止事项都对应本项目里真实容易出问题的地方：

| 禁止事项 | 对应的问题 |
| --- | --- |
| 不改拦截器 | AI 容易“顺手优化”，把业务码处理逻辑改掉，导致页面里 `e.code === 2005` 全部失效 |
| 不写密钥 | 2026 年 3 月已出现通过提示注入攻击劫持 AI 编码代理窃取密钥的案例 |
| 不删未确认引用的代码 | 看起来没人用的组件可能是路由懒加载进来的，删了直接白屏 |
| 不改 domain 函数签名 | 改签名会让所有调用点静默出错 |
| 不加新依赖 | 避免一个项目里出现两套 UI 库 |

**篇幅控制在 100 到 200 行。** 这份模板约 80 行，是合适的量。不要把所有文档都塞进来 —— 需要细节时用链接指向别的文档，这个做法叫“渐进式披露”。

### 前端目录可以再放一份

项目变大以后，可以在前端工程目录下再放一份更细的 AGENTS.md。AI 处理某个目录下的文件时，**就近的文件覆盖上层的**，所以子目录那份可以只写和这个目录相关的约定，比如组件命名规则、样式规范。

## 二、从需求到实现：五份文档就是规格

本项目的规格不是额外写的东西 —— **你要写的这五份文档本身就构成规格**：

```
① 需求规格说明          做什么、为什么做、有哪些字段
        ↓
② 业务规则与状态流转     名额怎么算、冲突怎么判、状态怎么变
        ↓
③ 接口约定              路径、参数、返回结构、错误码
        ↓
④ 目录结构与命名约定     文件放哪、怎么命名
        ↓
⑤ 页面清单与任务清单     拆成一次能做完的小任务
```

前四份在[项目规格](/project/)里已经给出，第五份要你自己拆。

这套流程对应业界说的**规格驱动开发**，核心主张是：把“要建什么、为什么建”先写成可审阅的规格，代码是规格的落地。GitHub 的 Spec Kit 把这套流程做成了工具链，它的命令顺序是：项目原则 → 规格（只写做什么、为什么，不写技术栈）→ 澄清模糊点 → 质量清单 → 技术计划 → 任务清单 → 跨产物一致性检查 → 执行实现。

**你不必用这个工具，手写 Markdown 走同样的流程效果一样。** 本节要你练的就是这个顺序。

### 页面清单怎么写

拿[需求规格](/project/requirements)里的功能列表，按这个格式拆：

```md [页面清单.md]
## 活动管理模块

### 页面 4 · 活动列表
- 路由：/activities
- 角色：组织者看自己的，审核员看全部
- 接口：GET /api/activities
- 页面上有：
  - 筛选区：关键词、活动类型、状态、时间范围
  - 表格列：标题、类型、组织者、报名截止时间、已报名/名额、状态
  - 操作列：查看、编辑、下架/上架、删除（按接口返回的 canEdit / canDelete / canOffShelf 决定是否显示）
- 四态：加载中显示骨架、空数据显示引导文案、出错显示重试按钮、无权限显示提示

### 页面 5 · 活动详情
（同上格式）
```

**每个字段的来源都要写清**：是从接口拿的、还是自己算的、还是从路由参数拿的。写到这一步，AI 才可能生成对的东西。

### 接口清单怎么写

从页面清单倒推，把每个页面用到的接口列成一张表：

| 接口 | 方法 | 用在哪个页面 | 传什么 | 拿什么 |
| --- | --- | --- | --- | --- |
| `/api/activities` | GET | 活动列表 | 筛选条件、分页 | `list` / `total` |
| `/api/activities/:id` | GET | 活动详情、编辑回填 | 路径参数 id | 活动完整对象 |
| `/api/activities` | POST | 新增活动 | 表单字段 | 新建的活动对象 |

这张表的用处是：AI 生成接口层时**只允许用这张表里的接口**。表里没有的，它就不能编。

## 三、一次任务的完整示范

拿“活动列表页”走一遍，你会看到这套方法的实际手感。

### 第一步：自己写清规格

不要直接问 AI。先花十分钟把下面这些写下来（可以直接接着前面的页面清单往下写）：

```md [任务 04-活动列表.md]
## 目标
实现活动列表页 /activities，能从接口拿数据、能筛选、能分页。

## 约束
- 复用 src/components 里已有的 PageTable 组件
- 筛选条件变化后自动回到第 1 页
- 操作列按 canEdit / canDelete / canOffShelf 决定显示哪些按钮
- 成功码是 0，错误提示统一走 request.js 的拦截器，页面不要重复弹提示

## 不做
- 不做批量操作
- 不做导出
- 不做列的自定义显示

## 完成标准
- 筛选项清空后能恢复全量数据
- 删除最后一页最后一条后，停留在上一页而不是空白页
- 后端关闭时页面显示错误态而不是一直转圈
```

注意最后一段“不做”和“完成标准”。**“不做”比“要做”更能约束 AI 的产出范围。**

### 第二步：给 AI 的提示词

```text
先读根目录的 AGENTS.md 和 docs/页面清单.md 里“页面 4 · 活动列表”一节。

按照 docs/任务/04-活动列表.md 的要求实现这个页面。

要求：
1. 只创建 src/views/activity-list.vue 和 src/api/activity.js 两个文件，
   不要修改其他已有文件
2. 接口只用 docs/接口清单.md 里列出的，不要新增接口
3. 用 script setup，Options API 不要用
4. 字段名在 api 层转成驼峰，页面里不要出现下划线字段
5. 完成后告诉我：你改了哪些文件、每个文件做了什么、有哪些地方
   你不确定、需要我确认

先不要写代码，先把你的实现计划讲一遍，我确认后再写。
```

这段提示词里有几个关键动作：

- **让它先读 AGENTS.md 和页面清单** —— 项目和任务的上下文都有了。
- **限定文件范围** —— 不加这条，它可能顺手改掉五个你没让它动的文件。
- **限定只能用清单里的接口** —— 防止编造接口。
- **要求先讲计划再写代码** —— 计划看错比代码写错便宜得多，改一次计划只要一分钟。

### 第三步：验收

代码生成完，按顺序做三件事。

**第一件，三句话检查。** 挑出改动里最关键的两三处，不看 AI 的说明，自己回答：

1. 它做了什么？（输入是什么、输出是什么）
2. 为什么这么写？（关键决定是什么，比如为什么用 `computed` 而不是 `watch`）
3. 如果这里出错会怎么表现？（说出一个具体现象）

**第二件，跑起来试。** 按你写的“完成标准”逐条试：

- [ ] 筛选条件清空后恢复到全量数据
- [ ] 删掉最后一页的最后一条，停在上一页
- [ ] 关掉后端，页面显示错误态
- [ ] 报名人数显示的是通过审核的人数，不是报名总数
- [ ] 下架的活动显示“上架”而不是“下架”
- [ ] 审核员登录时能看全部活动，组织者只看到自己的
- [ ] 控制台没有报错和警告

**第三件，对照 AGENTS.md 逐条核。** 成功码是不是 0、字段名有没有下划线漏出来、有没有引入新依赖、有没有 `console.log` 没删。

### 第四步：记录

在 `docs/开发记录.md` 里加一条：

```md
## 2026-10-08 · 活动列表页

- **AI 参与**：页面骨架与接口层由 AI 生成，筛选的防抖逻辑自己写的
- **澄清过程**：第一次没说清“筛选变化要回到第 1 页”，生成的是留在当前页，
  重新说明后修正
- **发现的错误**：AI 把报名人数写成了 list.total，实际是接口返回的
  approvedCount 字段；另外它默认成功码是 200，读 AGENTS.md 后改正
- **自己判断的部分**：删除后的翻页处理没让 AI 写，因为依赖我们这个表格组件
  的分页事件顺序，AI 看不到组件内部实现
```

这条记录后面要改写进 AI 参与声明，也是答辩时最容易被问到的内容。**它是加分项，不要省。**

## 四、AI 参与声明

项目交付时提交一份 `docs/ai-usage.md`，模板如下：

```md [ai-usage.md]
# AI 参与声明

## 用了哪些工具

- 工具名称与版本：
- 大致使用时间范围：

## 哪些部分用了 AI

| 模块 / 文件 | AI 参与程度 | 说明 |
| --- | --- | --- |
| src/views/activity-list.vue | 生成骨架后人工修改 | 表格与筛选由 AI 生成，删除后的翻页逻辑自己写 |
| src/api/ | 生成 | 按接口清单生成，逐条核对过返回字段 |
| src/domain/activity-rules.js | 未使用 AI | 规则较细，自己写更快 |

参与程度从下面三档里选：
- **生成**：AI 产出后基本未改
- **生成后修改**：AI 产出骨架，关键逻辑人工改写
- **仅辅助**：用 AI 解释概念或排查报错，代码自己写

## 关键澄清

列出为了让 AI 产出可用结果，你补充说明过哪些信息。至少三条。

## 发现并修正的 AI 错误

| 现象 | 为什么是错的 | 怎么发现的 | 怎么改的 |
| --- | --- | --- | --- |
| 默认成功码写成 200 | 本项目约定成功码是 0 | 跑起来发现所有请求都进错误分支 | 在 AGENTS.md 里写明约定，重新生成 |
| 删除后列表空白 | 删掉最后一页最后一条没有回退页码 | 手动测试时试到 | 自己补了页码回退 |

这一栏是声明的重点。至少三行，每行都要能对上真实的代码改动。

## 判断不交给 AI 的部分

说明哪些活你判断不适合交给 AI，理由是什么。

## 声明

本人确认：本项目中提交的所有代码，我都读过并能解释其作用；
所有密钥、账号信息未出现在与 AI 的对话中。
```

### 这份声明怎么打分

| 项 | 权重 | 看什么 |
| --- | --- | --- |
| 完整性 | 30% | 覆盖了所有主要模块，没有隐瞒 |
| “发现的错误”一栏 | 40% | 至少三行，且能与代码改动对应上 |
| “判断不交给 AI”一栏 | 20% | 理由具体，不是“感觉不合适” |
| 声明真实性 | 10% | 抽查问答时能对上 |

**“发现的错误”一栏占 40%，是全表最高的。** 原因很直接：这一栏为空只有两种可能 —— 要么你没审就交了，要么你把审出来的问题都算成了自己的功劳。两种都不合格。

## 五、合并前的评审清单

每次把自己的分支合并到主分支之前，逐条过一遍：

- [ ] 我读过这次改动的每一行，能解释它在做什么
- [ ] 三句话检查做过（做了什么、为什么这么写、出错会怎样）
- [ ] `pnpm lint` 通过
- [ ] 页面在浏览器里实际跑过，不只是编译通过
- [ ] 接口返回的字段名都对上了，页面里没有下划线字段漏出来
- [ ] 成功码用的是 0
- [ ] 加载中、空数据、出错三种状态都显示正常
- [ ] 没有 `console.log` 残留
- [ ] 没有密钥、token、真实账号
- [ ] 没有引入 AGENTS.md 里禁止的依赖
- [ ] 没有删除任何未经确认的代码
- [ ] 改动范围和我打算提交的一致，没有顺手改别的文件
- [ ] 提交信息写清了这个提交做了什么

::: warning 一条容易被跳过但最要紧的
最后一条“改动范围”。AI 生成的改动经常包含你没让它动的地方，比如顺手重排了某个文件的导入顺序、改了一个函数的参数默认值。**提交前用 `git diff` 看一眼改动的文件清单**，多出来的要么理解它为什么改，要么回退掉。
:::

## 六、禁止事项

这几条不要做，做了按未完成计：

| 禁止 | 原因 |
| --- | --- |
| 提交没读过的代码 | 答辩会被问住，出问题也排查不了 |
| 把密钥、token、真实账号密码贴进对话 | 已有提示注入攻击窃取密钥的公开案例 |
| 让 AI 判定权限 | 前端的一切判断都能被绕过，权限必须在服务端每个接口上做 |
| 让 AI 直接给出删除代码的结论就执行 | 必须自己先搜引用位置，动态导入的代码看起来就是没人用 |
| 用 AI 生成的内容替换真实的测试结果 | 声称测试通过但没跑，属于造假 |
| 把 AI 生成的设计文档当自己的分析直接交 | 文档里要有取舍与代价分析，这是评分项 |

## 七、这套规范怎么落到评分里

回到[评分维度](/project/)，AI 协作影响其中三项：

| 评分维度 | 权重 | AI 协作带来的影响 |
| --- | --- | --- |
| 工程质量 | 25% | 有 AGENTS.md 且与实际写法一致，加分；命名和约定混乱，扣分 |
| 工程化实践 | 20% | 提交历史清晰、每次提交范围明确，加分；大量“update”提交和大杂烩提交，扣分 |
| 答辩表现 | 10% | 能讲清“我发现的 AI 错误”和“我判断不交给 AI 的部分”，明显加分 |

注意这里没有一条是“用了 AI 就扣分”或“不用 AI 就加分”。**评分看的是你有没有形成可重复的工作方式，以及你能不能对自己的代码负责。**
