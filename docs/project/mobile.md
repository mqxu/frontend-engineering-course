# 用户端需求规格

这一页是用户端（uni-app 写的学生端）的**需求规格**。它和管理端的[需求规格说明](/project/requirements)是同级的文档，对应的是同一个后端、同一批数据。

**两份规格文档不要混着看。** 管理端那份讲的是组织者和审核员看到的界面；这一份讲学生看到的界面。**同一个活动，两种人看到的东西差别很大。**

## 一、这一端的目标

**让学生用手机完成一件事：看到有什么活动，报名参加，知道审核结果。**

只做这一件事。**不做的事也写清楚**，免得越做越大：

| 不做 | 为什么 |
| --- | --- |
| 签到、核销 | 需要现场扫码，超出这一端的范围 |
| 活动评价、打分 | 可选功能，会拖长周期 |
| 消息推送、订阅通知 | 需要额外的后端能力与平台申请，课时不够 |
| 组织者视角的功能 | 那是管理端的事，两端不要互相渗透 |

**这条边界要守住。** 学生端最容易被加功能 —— “顺手再加个签到吧”“能不能评论” —— 加到最后这一端变得和管理端一样大，而它的核心价值只是“看一眼、报个名”。

## 二、谁在用

只有一个角色：**学生**。

| 属性 | 说明 |
| --- | --- |
| 身份 | 在校学生，用微信或浏览器打开 |
| 使用场景 | 课间、宿舍、走在路上；**单手操作，可能只给三秒钟注意力** |
| 技术水平 | 会用微信小程序，但不会为了报名去研究一个界面 |
| 登录意愿 | 低。**能先看就不要强制登录** |
| 数据归属 | 只看得到自己的报名记录，看不到别人的 |

**“登录意愿低”这一条决定了整个信息架构。** 活动列表和详情不登录也能看，只有点“报名”才要求登录。反过来做（一进来就登录），大部分学生会直接关掉。

**用户在 `user` 表里的角色是 `STUDENT`。** 这是本端要新增的一个角色值 —— 管理端原来只有 `ORGANIZER` 和 `AUDITOR`。

## 三、页面清单

**一共 5 个页面，其中 3 个在底部 tabBar 里。**

| 页面 | 路由 | 在 tabBar | 需要登录 | 职责 |
| --- | --- | --- | --- | --- |
| 活动列表 | `pages/activity/list` | 是 | 否 | 浏览、搜索、筛选活动 |
| 活动详情 | `pages/activity/detail` | 否 | 否 | 看详情、决定要不要报 |
| 报名表单 | `pages/signup/form` | 否 | 是 | 填资料、提交报名 |
| 我的报名 | `pages/signup/my` | 是 | 是 | 看审核状态、取消报名 |
| 我的 | `pages/user/index` | 是 | 是 | 个人信息、退出登录 |

**启动页是活动列表，不是登录页。** 这是刻意的：先让人看到内容。

### 拆分依据

**依据一：列表和详情分开。** 详情要展示长文本的活动说明和场次信息，列表页塞不下。**列表只给决策需要的信息**：标题、类型、截止时间、还剩多少名额。

**依据二：报名单独成页。** 报名要填四个字段，放不进详情页。而且报名是个有后果的动作，**单独一页能让用户意识到“我正在提交东西”**，比在详情页底部弹个层更不容易误触。

**依据三：登录不单独成页（在“我的”里）。** 登录是去报名的路上顺手完成的一步，不该让用户提前准备。所以“我的”页里放登录入口，报名按钮发现未登录时也跳过去。

## 四、数据字段

**活动、报名、用户的字段定义以[需求规格说明](/project/requirements)的第四章为准，这一节只讲学生端特有的部分。**

### 列表项（活动列表用的字段）

比管理端的列表**少**，这是刻意的：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 主键 |
| `title` | string | 标题，单行超出省略 |
| `type` | enum | 活动类型，用来显示彩色标签 |
| `organizerName` | string | 主办方，学生需要知道是谁办的 |
| `quota` | number | 名额上限 |
| `approvedCount` | number | 已通过人数 |
| `signupDeadline` | string | 报名截止时间 |
| `status` | enum | 活动状态 |
| `coverUrl` | string \| null | 封面图，**可能为空** |

**列表里没有 `description`。** 活动说明可能几百字，二十条带下来响应体会大好几倍。说明只在详情接口里返回。

**前端要自己算两个派生值**，不要指望后端加字段：

```js
// 剩余名额
const remaining = computed(() => activity.quota - activity.approvedCount)
// 是否可报名
const canSignup = computed(() =>
  activity.status === 'SIGNING' && remaining.value > 0
)
```

**为什么不让后端返回 `remaining`？** 因为 `remaining` 是可以从两个已有字段算出来的，**多一个字段就多一处可能不一致的地方**。这条和管理端的约定一致（看板的 `quotaUsageRate` 是例外，因为它的算法需要明确约定）。

### 详情（活动详情多返回的字段）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `offShelf` | boolean | 下架标记 |
| `description` | string | 活动说明，**HTML 字符串** |
| `coverUrl` | string \| null | 封面图 |
| `mySignupStatus` | enum \| null | 我对这个活动的报名状态，`null` 表示没报过 |
| `sessions` | array | 已安排的场次 |

**`mySignupStatus` 是这一端最关键的字段。** 它决定了详情页底部那个按钮显示什么。没有它，详情页要多发一次请求才能知道“我报过没有”。

**`description` 是 HTML，不是纯文本。** 学生端用 `<rich-text>` 渲染，这个组件只认基础标签（`p`、`div`、`span`、`strong`、`img`、`a`），**复杂样式和 CSS 类名会丢**。所以后端给的说明要克制。

### 报名记录（我的报名用的字段）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 报名记录 id |
| `activityId` | number | 关联活动 |
| `activityTitle` | string | 活动标题 |
| `activityStatus` | enum | **关联活动的状态** |
| `activityStartTime` | string \| null | 活动开始时间 |
| `venueName` | string \| null | 场地名称 |
| `status` | enum | 报名状态 |
| `remark` | string | 自己填的备注 |
| `rejectReason` | string \| null | 驳回理由，仅 `REJECTED` 时有值 |
| `auditorName` | string | 审核人 |
| `auditedAt` | string \| null | 审核时间 |
| `createdAt` | string | 报名时间 |

**`activityStatus`、`activityStartTime`、`venueName` 这三个是学生端特意要的。** 学生打开“我的报名”时，最想知道的是三件事：**过了没有、什么时候办、在哪儿办。** 这三个字段能一次性回答完，不用再点进详情页。

### 报名状态

| 状态 | 含义 | 学生能做什么 |
| --- | --- | --- |
| `PENDING` | 已提交，等审核 | 可以取消 |
| `APPROVED` | 审核通过 | 可以取消（会释放名额） |
| `REJECTED` | 被驳回 | 看理由，可以重新报（如果还在报名期） |
| `CANCELLED` | 自己取消的 | 可以重新报 |

**注意 `CANCELLED` 的记录不会消失。** 它还在列表里，显示成灰色的“已取消”。**删掉的话，学生会以为自己从没报过这个活动，然后再报一次，然后又被拒** —— 保留记录可以避免这一类困惑。

## 五、界面要求

移动端的界面要求和桌面端不同，**最核心的差异是“一屏能放多少东西”。**

### 活动列表

| 元素 | 呈现方式 |
| --- | --- |
| 布局 | **卡片列表，不是表格**。一屏大约 3 到 4 张卡片 |
| 标题 | 单行，超出省略 |
| 类型 | 彩色标签，用字典里的颜色 |
| 报名进度 | “还剩 N 个名额”；**名额为 0 时显示“名额已满”并用红色** |
| 截止时间 | 已过期的用灰色显示，并加“已截止”的标记 |
| 封面图 | 有就显示（固定高度，`aspectFill` 裁切），**没有就不留空位** |
| 交互 | 点击整张卡片进详情 |

### 活动详情

| 区域 | 呈现方式 |
| --- | --- |
| 顶部 | 封面图（或默认图），上面叠活动标题与类型标签 |
| 基本信息 | 主办方、截止时间、剩余名额，用信息行排列 |
| 场次信息 | 有场次就列出时间和场地，**没有场次显示“待安排”** |
| 活动说明 | `<rich-text>` 渲染，限制最大高度并允许展开 |
| 底部固定栏 | **始终可见**的报名按钮，含安全区留白 |

**底部按钮的文案由状态决定**，这是这一端最容易写漏的地方：

| 活动状态 | 我的报名状态 | 按钮文案 | 可点 |
| --- | --- | --- | --- |
| 任意 | `PENDING` / `APPROVED` / `REJECTED` | 查看我的报名 | 是 |
| `SIGNING` | 无或已取消，名额未满 | 立即报名 | 是 |
| `SIGNING` | 无或已取消，名额已满 | 名额已满 | 否 |
| `SIGNUP_CLOSED` | 无或已取消 | 报名已截止 | 否 |
| `FINISHED` | 无或已取消 | 活动已结束 | 否 |

**判断顺序是“先看报没报过，再看活动状态”。** 一个已经报名的学生应该看到“查看我的报名”，而不是“报名已截止”。

### 报名表单

| 字段 | 呈现方式 |
| --- | --- |
| 姓名 | 输入框，**从登录信息预填**，可改 |
| 学号 | 数字键盘，10 位，**从登录信息预填** |
| 班级 | 输入框，选填 |
| 备注 | 多行文本，最多 200 字，带字数统计 |
| 提交按钮 | 固定在底部，**提交中显示加载态且不可重复点** |

### 我的报名

| 元素 | 呈现方式 |
| --- | --- |
| 筛选 | 顶部分段器：全部 / 待审核 / 已通过 / 已驳回 |
| 状态 | 彩色标签 |
| 驳回理由 | **在卡片内单独一块高亮显示**，不能藏进详情页 |
| 时间地点 | 已通过的要显示活动时间与场地 |
| 操作 | 可取消的状态才显示“取消报名”按钮；点击时要二次确认 |
| 空状态 | “还没有报名记录”，并给一个“去看看活动”的按钮 |

### 提示与反馈

| 场景 | 用什么 | 不用什么 |
| --- | --- | --- |
| 提交成功 | **弹窗**，说明接下来会发生什么 | 一闪而过的提示 |
| 名额已满 | 轻提示 | 全屏弹窗 |
| 网络错误 | 轻提示 | 页面内嵌一块错误区域 |
| 取消报名 | **二次确认弹窗** | 直接执行 |
| 页面加载 | 骨架屏 | 空白等待 |

**第一次成功提交后用弹窗而不是轻提示**，因为用户需要知道“组织者会审核，你可以去我的报名看结果” —— 这个信息一句话说不完。

## 六、非功能要求

### 弱网下的表现

学生用手机在校园里，网络不一定好。**三条硬要求：**

1. **每个请求都要有加载态**（骨架屏或转圈），不能点完什么都不发生
2. **每个请求都要有失败态**，并给“重新加载”的入口
3. **触底加载失败时，页码要回退**，不能跳过一页数据

### 机型与平台适配

| 项 | 要求 |
| --- | --- |
| 小屏 | iPhone SE 这类 320px 宽的屏幕上不出现横向滚动 |
| 大屏 | 平板上内容不至于被拉伸变形 |
| 安全区 | 底部固定元素不被 iOS 的横条遮挡 |
| 软键盘 | 输入框不被键盘挡住 |
| 两端一致 | **H5 与微信小程序端都要验证**，不能只看一端 |

### 性能

| 项 | 目标 |
| --- | --- |
| 首屏 | 活动列表 10 条数据，3 秒内出现 |
| 图片 | 活动封面用 `aspectFill` 并限制高度，**不打原图** |
| 包体积 | 小程序端主包不超限（超了要分包） |

## 七、验收方式

| 序号 | 验收项 | 怎么验 |
| --- | --- | --- |
| 1 | 未登录能浏览 | 清空 storage，打开活动列表和详情，都能正常显示 |
| 2 | 未登录点报名 | 提示先登录并跳登录页，登录后能回到报名流程 |
| 3 | 报名的四道拦截 | 分别造“活动已结束”“已过截止”“名额已满”“已报过名”四种情况，提示各不相同 |
| 4 | 按钮状态机 | 按第五章那张表逐行切换验证，五种文案都正确 |
| 5 | 报名后可查 | “我的报名”里出现新记录，状态是待审核 |
| 6 | 驳回可见 | 用管理端把一条报名驳回，学生端能看到理由 |
| 7 | 取消释放名额 | 取消已通过的报名，详情页的名额数字增加 |
| 8 | 两端一致 | 上述七项在 H5 与微信小程序端各跑一遍 |

**第 3 项是重点。** 正常流程谁都能走通，**答辩时老师问的往往是这四种异常情况。**

## 八、与管理端的边界

| 项 | 管理端 | 用户端 |
| --- | --- | --- |
| 接口前缀 | `/api/auth`、`/api/activities` 等 | `/api/student/*` |
| 数据范围 | 组织者看自己的，审核员看全部 | 只看已发布未下架的，只看自己的报名 |
| 登录方式 | 账号密码 | 账号密码加微信小程序登录 |
| 技术栈 | Vue 3 加 Element Plus | uni-app 加 Wot UI |
| 部署 | Nginx 静态站点 | H5 站点加微信小程序 |

**两端共用同一个后端与同一套接口约定。** `code` 加 `message` 加 `data` 的响应结构、业务码、分页结构、鉴权方式，全部一致 —— 见[接口约定](/project/api)。

**这就意味着：用户端不需要重新设计数据流。** 请求层怎么封装、状态怎么分四种、错误码怎么映射，管理端已经趟过一遍，用户端照着做。

## 小结

- 用户端只有一个角色（学生），**只做一件事：看活动、报名、看结果**
- **启动页是活动列表，浏览不要求登录**，只有报名才要求
- 5 个页面，3 个在 tabBar；登录不单独占一个页面
- **列表不返回活动说明**，详情才返回；`mySignupStatus` 决定详情页的按钮
- 详情页的按钮是**状态机**，判断顺序是先看报没报过
- **驳回理由要在列表里就显示**，那是学生最想看的信息
- 弱网和异常路径是验收重点：**四种拦截、五种按钮状态，两端都要跑**
