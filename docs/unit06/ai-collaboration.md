# 单元 6 · AI 协作：表单校验要写全，副作用要清干净

表单是 bug 最集中的地方，这一章的知识点也最密：事件、修饰符、表单绑定、校验、生命周期清理。AI 在这一章的产出量会明显变大 —— 它能帮你把校验规则、错误文案、防重复提交这些东西一次写出来。

但它有一个固定的偏差：**它写的表单通常只有“顺利填完并提交成功”这一条路径。** 校验失败的提示、重复点击的保护、组件卸载时的清理，这三样它经常漏。

这一章讲的是**怎么让它把“不顺利的那几条路径”也写出来，以及怎么检查它有没有清干净副作用。**

## 这一章哪些活能交给 AI

判断标准：**机械规则和清单式检查可以交；涉及“这条规则该由谁管”的判断不能交。**

| 任务 | 能交给 AI 吗 | 为什么 |
| --- | --- | --- |
| 起草一组校验规则（纯函数形式） | 可以 | 规则本身是机械的，写完你逐条对业务 |
| 生成错误提示文案 | 可以 | 一句话的事，你挑一条改改就行 |
| 检查副作用有没有清理干净 | 可以 | 它对着钩子清单比人快 |
| 解释事件与修饰符的触发时机 | 可以 | 但要它给能观察到的例子 |
| 设计防重复提交的分层防护 | 可以 | 当起点，层次要你确认 |
| 判断“这条规则该不该由前端来管” | **不能直接信** | 它容易把前端校验说成够用了 |
| 判断“校验做完了就安全了吗” | **不能直接信** | 见下面“容易错什么”第三条 |
| 决定校验失败时的交互方式 | **不行** | 取决于用户习惯，也和你们组的约定有关 |

中间那两行合起来是一件事：**前端校验挡的是手误，不挡恶意请求。** 这句话 AI 不一定说错，但它默认不提，你不问它就不讲。

## 提示词怎么写

### 1. 让它写一组校验规则

```text
我要给“创建活动”表单写校验，字段有：活动名称、报名开始时间、
报名截止时间、名额上限。

项目约定：校验规则写成一组纯函数，放 src/domain/ 下，
每个函数接收值（需要多个字段时接收整个表单对象），
返回错误信息字符串或空字符串。不依赖 Vue。

请按这个约定写。要求：
1. 每个规则单独一个函数，函数名说清它检查什么
2. 时间类规则注意这两个：截止时间必须晚于开始时间；
   报名开始时间不能早于当前时间
3. 名额上限要求是 1 到 500 之间的整数
4. 每写完一条，说明“什么情况下它会误判”（合法输入被判为非法）

如果你发现有哪条规则必须查后端才能判断，单独列出来，不要硬写成同步规则。
```

**为什么这么写**：第 4 点是最有价值的一句。**校验规则最容易出的问题不是漏判，是误判** —— 比如“报名开始时间不能早于当前时间”这条，如果用户现在就在填，时间秒级对不上就会误判。让它自己说出误判场景，比你自己想全要省力。

最后一句也很关键：有些规则（比如“名额不能超过场地容量”）必须查后端，硬写成同步规则会让代码结构扭曲。让它主动标出来，你才知道哪些该放到异步校验里。

### 2. 让它检查副作用有没有清干净

```text
这是我的组件：

[粘贴完整代码]

请做一件事：把代码里所有的副作用列出来，逐个说明它在哪里被清理、清理得对不对。

副作用包括但不限于：定时器、事件监听（window、document、元素）、
请求、订阅、手动创建的 DOM 节点。

输出用表格，四列：
副作用 / 在哪注册的 / 在哪清理的 / 有没有问题。

没问题就写“无”，不要为了显得认真而硬找问题。
```

**为什么这么写**：把“检查一下”拆成“列出来 → 逐个落到清理位置”，它就必须对着代码逐行核对，而不是回一句“整体看起来规范”。表格里“在哪清理的”这一列是核心 —— 这一列空着的，就是漏掉的。

最后那句“不要硬找问题”是必要的。这类检查请求太宽泛时，它会为了显得有用而编几条问题，反而增加你的核对成本。

### 3. 让它解释事件与修饰符的触发时机

```text
请解释这几个东西的触发时机差别，每个都用一个“在浏览器里能观察到”的例子说明：

1. input 事件与 change 事件
2. v-model 与 v-model.lazy
3. .stop 与 .self

要求：每个例子写清“做什么操作 → 控制台会输出什么”，
我要能照着做一遍验证。不要只讲定义。
```

**为什么这么写**：触发时机这类知识，定义背下来没用，必须在真实操作里对上号。要求它给“做什么操作 → 看到什么”，你就有了三个能亲手验证的小实验。这三个里 `.stop` 与 `.self` 最容易混 —— 差别在于拦的是“所有冒泡上来的事件”还是“只拦目标是自己触发的那些”。

## AI 在这一章容易错什么

### 把 `v-model` 修饰符讲成“只是个小优化”

**现象**：它介绍 `.lazy` 时说“减少触发次数，性能更好”，介绍 `.number` 时说“自动转成数字”。你要是只按这两句话理解，会写出有问题的代码。

**原因**：这类“修饰符是什么”的解释，在各类教程里都停在这个层次，它照着这个层次讲，不会主动补边界。

**怎么处理**：两个修饰符各记一条边界。

`.lazy` 改的是**数据更新的时机**，不是触发频率：

| 你可能以为 | 实际上 |
| --- | --- |
| 值照样实时更新，只是少了些事件 | 输入过程中值**根本不变**，失焦才更新 |

后果：别处依赖这个值做实时预览的地方，加上 `.lazy` 之后会“卡住不动”，直到输入框失焦。所以**不要为了省请求随手加它**。

`.number` 转不了会**保留原字符串**，而且它内部的转换逻辑是“能读多少读多少”：

| 用户输入 | `v-model.number` 得到的值 |
| --- | --- |
| `50` | 数字 `50` |
| 空字符串 | 字符串 `''` |
| `abc` | 字符串 `'abc'` |
| `12abc` | 数字 `12` |

最后一行最危险：输入 `12abc` 拿到数字 `12`，**“格式不对”这件事被悄悄吞掉了**。所以**校验不能只看类型，必须校验值本身**。这一条在[6.4 表单校验](/unit06/04-validation)里有完整处理。

### `input` 与 `change` 的触发时机说反

**现象**：它说“`change` 在输入时触发，`input` 在失焦时触发”，或者把两者说成一回事。

**原因**：这两个事件名起得不直观 —— `input`（输入）听起来像“输入完成”，实际是“每敲一次”；`change`（改变）听起来像每次变化，实际是“值定了而且变了”。

**怎么处理**：用一组操作把它对上号。

| 操作 | `input` | `change` |
| --- | --- | --- |
| 敲第一个字符 | 触发 | 不触发 |
| 继续敲 | 每敲一次都触发 | 不触发 |
| 失焦 | 不触发 | 触发（值变过才触发） |
| 输入后又改回原值再失焦 | 触发 | **不触发**（值没变） |

最后一行是 `change` 的准确含义：**值确实发生变化时才触发。** 所以在需要“用户改了就立刻处理”的地方用 `input`，需要“用户确定了再处理”的地方用 `change`。

### 只做了前端校验就宣称“安全了”

**现象**：你问它“这样校验够不够”，它回答“已经很完善了，可以防止非法数据提交”。

**原因**：它判断“够不够”的依据是“校验规则覆盖了哪些情况”，而它看不到一个事实：**用户可以绕过你的页面直接发请求。**

**怎么处理**：记住这条边界 ——

> **前端校验挡的是手误，不挡恶意请求。真正的边界在服务端。**

这不是说前端校验没用，而是说它解决的是**体验问题**：立刻告诉用户哪里填错了，不用等一次往返。它的价值在体验，不在安全。

所以判断规则该放哪，看这条：**“如果这个校验被绕过，会不会造成实际损失？”** 会，就必须在服务端也做一遍。比如“名额上限不能超过场地容量”“截止时间之后不能再报名”这两条，前端做是为了体验，后端做才是真的挡住了。

这个判断在[单元 9](/unit09/ai-collaboration)和[单元 10](/unit10/ai-collaboration)里还会接着用。

### 忘记清理副作用

**现象**：它在 `onMounted` 里注册了 `window.addEventListener` 或 `setInterval`，但没写对应的 `onUnmounted`。或者在 `onUnmounted` 里写了，但清的不是同一个东西。

**原因**：它的注意力集中在“让功能跑起来”，`onMounted` 是功能，`onUnmounted` 是收尾。收尾这件事在生成代码时不显眼。

**怎么处理**：现象很好辨认 —— **在页面之间来回切换几次，如果日志越来越多、定时器越来越多、请求越来越密，就是没清。**

| 副作用 | 在哪清 | 清的是什么 |
| --- | --- | --- |
| `setInterval` | `onUnmounted` | 用注册时拿到的 id 调 `clearInterval` |
| `window.addEventListener` | `onUnmounted` | 同一个函数引用 + 同样的事件名 |
| 事件监听绑在元素上 | `onUnmounted` | 同上 |
| 请求 | 视情况 | 用取消令牌，或用一个标志位丢弃过期的响应 |

第三条有个常见坑：`removeEventListener` 必须传**同一个函数引用**。写成 `removeEventListener('resize', () => {...})` 是无效的 —— 那是一个新函数，跟注册的那个不是同一个。这个问题不报错，只是悄悄没起作用。

::: details 还有一类错误：请求发出去了，不管组件还在不在
**现象**：它在 `onMounted` 里发请求，回调里直接给状态赋值。你在请求还没回来时切到了别的页面，控制台开始报错，或者数据被写进了一个已经不在的组件。

**原因**：它默认请求一定会成功、而且用户一定会等。这两件事在真实环境里都不成立。

**怎么处理**：区分两种后果，因为它们要分开解决。

**后果一：竞态** —— 连续两次请求，先发的后回来，把新结果覆盖了。典型场景是搜索框边输边查。解决办法是给请求编号，只认最后一次：

```js
let seq = 0
async function search(keyword) {
  const current = ++seq
  const data = await fetchList(keyword)
  if (current !== seq) return   // 已经有更新的请求发出，这次的结果丢弃
  list.value = data
}
```

**后果二：卸载后写状态** —— 组件已经不在，回调还在给它赋值。解决办法是在卸载钩子里立一个标志位：

```js
let alive = true
onUnmounted(() => { alive = false })

onMounted(async () => {
  const data = await fetchList()
  if (!alive) return
  list.value = data
})
```

判断用哪一种：**看这个请求会不会被连续触发。** 搜索、筛选、分页这类会连续触发的，要处理竞态；只在进入页面时发一次的，立标志位就够。
:::

## 怎么验收 AI 的产出

这一章的产出是表单相关的代码。验收时按“不顺利的路径 → 副作用 → 修饰符边界”的顺序过：

- [ ] 校验规则写成了纯函数，没有依赖 Vue 的响应式 API
- [ ] 每条规则你都能说出一个“什么输入会被误判”的场景
- [ ] 校验失败的提示能落到具体字段，不是一条笼统的错误
- [ ] 提交时做了防重复：按钮置灰、提交中标志、请求层面至少有一层
- [ ] 代码里每一处副作用，都有对应的清理，且清的是同一个东西
- [ ] 用了 `.lazy` 的地方，确认没有别处依赖实时值
- [ ] 用了 `.number` 的地方，校验的是值本身而不只是类型
- [ ] 你没有因为 AI 说“校验已经很完善”就跳过后端的校验设计

前四条对应“不顺利的路径写全了没”，中间两条对应“有没有留下垃圾”，最后两条对应两个边界。**这八条过完，这个表单才算能交出去。**

## 练习

### 给一个带实时校验的表单，故意留一个没清理的定时器

**任务**：写一个带实时校验的表单（比如“创建活动”），**故意在组件里留一个没清理的定时器或事件监听**，然后让 AI 找出来。找到之后自己改对，并说明为什么必须清。

**要求**：记录里必须包含这四项：

| 项 | 要求 |
| --- | --- |
| 故意埋的副作用 | 写清埋的是什么、埋在哪一段 |
| 不清理时的现象 | 写清怎么观察到的（切页面几次？看什么？） |
| AI 有没有找出来 | 找出来了就粘它的定位过程；没找出来就写你换了什么问法 |
| 改完的验证 | 写清改完之后同一个观察办法看到了什么不同 |

::: details 验收标准与参考思路
**为什么是“故意埋”**：等副作用问题自己暴露出来，通常要等到项目快交付的时候，而且现象是“页面越用越卡”这种没法定位的描述。主动埋一个，你知道它在哪，就能专心观察“不清理会表现成什么样”—— 这个认识比知道“要清理”有用得多。

**思路提示**：

- 埋什么建议挑这两个之一：`setInterval` 每秒更新一个“剩余时间”，或者给 `window` 加一个 `resize` 监听。这两个的现象都容易观察。
- 观察办法：在页面之间来回切 5 次，如果定时器没清，控制台的输出会变成 5 倍频。**用输出次数来判断，比用眼睛猜准确。**
- 如果 AI 没找出来，**先换问法再下结论**。用第 2 个提示词模板（要求“逐个列出、落到清理位置”），比问“有没有内存泄漏”有效得多。记录下两种问法的差别，这本身就是这一节要教的东西。
- 顺手试一下那个“同一个函数引用”的坑：故意写成 `removeEventListener('resize', () => {})`，看 AI 能不能指出来。**这是这一章最隐蔽的一个坑，因为它不报错。**

**不合格的写法**：

> 让 AI 检查了一下，它说没有内存泄漏，我就没再管。

AI 说“没有”的时候，你要看它是怎么得出结论的。它逐行对照过每个副作用的注册与清理位置吗？还是只看了代码“像不像有清理”？

**合格的写法**：

> 我埋了一个 `setInterval`，每秒更新“报名倒计时”，写在 `onMounted` 里，没有 `onUnmounted`。
> 观察办法：在活动列表和详情页之间切换 5 次，控制台每秒输出 5 行 —— 说明 5 个定时器同时在跑。
> 第一次问 AI“有没有内存泄漏”，它回答“代码结构合理，未发现明显问题”，没找出问题。
> 换成第 2 个提示词模板后，它列出的副作用表里，`setInterval` 那一行“在哪清理的”是空的，
> 这才定位到。说明**笼统地问它只会给笼统的回答。**
> 加上 `onUnmounted` 清理之后，同样的切换操作只输出 1 行/秒。
> 另外我试了 `removeEventListener('resize', () => {})`，它没指出来 —— 这个坑得靠自己记。

差别在于：后者不但找到了问题，还发现了**自己的提问方式才是问题的一部分**。这一条经验在后面的单元会一直用到。
:::
