# 案例总览

## 案例库是做什么的

前面 12 个单元按知识点组织：一个单元讲清一类能力，每节配一个小示例。这样安排的好处是每条线都清楚，
但真实项目不会按知识点出题 —— 一个页面往往同时用到列表渲染、表单绑定、接口请求和状态管理。

案例库补的就是这一段：**把多个知识点装进一个完整页面，从数据结构一路写到可运行的代码。**

每个案例都是独立成篇的完整实现，不是单元内容的缩写版。你可以把它当成一份“参考实现 + 讲解”：
先看要做什么，然后自己动手写，卡住了再回来对照。

::: tip 案例里的业务都来自综合项目
全部 10 个案例都用 **校园活动服务平台 · 管理端** 的实体：活动、报名记录、场次、场地、学生、
组织者、审核员。你在案例里写过的数据结构，后面做综合项目时可以继续用。
:::

## 每个案例长什么样

所有案例页都用同一套骨架，方便你跳读：

| 段落 | 里面有什么 | 建议怎么读 |
| --- | --- | --- |
| 案例要做什么 | 业务场景 + “用到的知识点 → 对应章节”表 | 先读，读完停下 |
| 数据结构与接口设计 | 先定数据长什么样，再写代码 | 想清楚字段再往下 |
| 实现步骤 | 分 3 到 6 步，每步一段可运行代码 | 跟着写 |
| 完整代码 | 可以直接复制进项目的完整文件 | 对照自己的版本 |
| 常见坑 | 每条“现象 → 原因 → 怎么处理”，默认折叠 | 报错时回来查 |
| 扩展练习 | 给思路不给答案，默认折叠 | 写完基础版再做 |

“完整代码”那一段看起来最长，但它只是把前面几步拼起来，不是另写一套。**如果你前面每步都写过了，
这一段应该是用来核对的，不是用来抄的。**

## 怎么用这套案例（三步法）

### 第一步：只读前半段，读完就停

读“案例要做什么”和“数据结构与接口设计”，**不要往下翻**。读到“用到的知识点”表时，自己判断一下：
表里这些章节我是不是都学过？有哪一条一看就想不起来？

### 第二步：自己写一版，允许写得很丑

先让它跑起来，再想怎么变好看。这一阶段的目标不是写出和参考实现一样的代码，而是
**遇到具体卡点**：数组怎么增删不会错、`computed` 该怎么联、请求取消写在哪儿。

### 第三步：对照“完整代码”和“常见坑”

对照时重点看三件事：

1. 我的写法和参考实现差在哪，差别是“习惯不同”还是“我漏了一种情况”。
2. “常见坑”里有没有我刚刚踩到的，如果有，把原因写进自己的笔记。
3. “扩展练习”挑一道做，这一步才是把案例真正变成自己能力的地方。

::: warning 不要跳过第二步
直接看完整代码看起来很快，但你会发现合上页面什么也没留下。案例的价值不在代码本身，
而在 **你卡住的那几分钟**。
:::

## 难度分级说明

| 星级 | 名称 | 判断依据 | 需要先掌握 |
| --- | --- | --- | --- |
| ★☆☆ | 入门 | 单页面，没有异步请求，不需要拆组件 | 模板语法、`ref`、`v-for`、`v-model` |
| ★★☆ | 进阶 | 有异步请求，或者要拆组件、要做多层数据派生 | 生命周期、`computed`、`watch`、props 与 emits |
| ★★★ | 综合 | 多个模块协作，需要自己设计状态和数据流 | 路由、状态管理、自定义指令、组合式函数 |

星级只代表“这个案例需要多少前置知识”，不代表“有多难写对”。★☆☆ 的案例同样有值得琢磨的地方，
比如键值怎么选、空状态怎么处理 —— 这两件事很多人做了两年还在犯错。

## 案例和单元怎么配合

案例不是“单元课后练习的升级版”，它和单元是两种不同的读法：

| 维度 | 单元章节 | 案例页 |
| --- | --- | --- |
| 组织方式 | 按知识点 | 按完整功能 |
| 读法 | 顺序读，每节独立 | 先自己写，再对照 |
| 代码形态 | 片段，够说明问题就行 | 完整文件，能直接复制运行 |
| 主要作用 | 建立概念 | 建立手感 |

如果时间紧，可以按下面的顺序走：先跟着单元学知识点，每学完一个单元，挑一个对应该单元的案例做一遍。

| 学完这些单元 | 建议做 |
| --- | --- |
| 单元 4、5、6 | 案例 01 → 案例 02 |
| 单元 7、8 | 案例 03 → 案例 05 → 案例 06 |
| 单元 9、10 | 案例 04 → 案例 10 |
| 单元 11、12 | 案例 07、08、09 全部做一遍 |

## 完成一个案例的验收标准

写完一个案例，用这张表自查。五条全过，才算真的做完。

- [ ] 页面能跑起来，控制台没有报错和警告。
- [ ] 空数据、加载失败这两种情况都有对应的界面，不是一片空白。
- [ ] 列表渲染用了稳定的键值，没有拿数组下标当键。
- [ ] 所有需要用户等待或确认的操作都有反馈（按钮禁用、二次确认、提示文案）。
- [ ] 能用自己的话讲清这个案例里“最麻烦的一个点”是什么，以及为什么这样处理。

## 案例里统一的几个约定

10 个案例由不同的章节引出，但写法上保持一致，这样你在案例之间跳读时不用重新适应：

| 项目 | 约定 | 原因 |
| --- | --- | --- |
| 组件写法 | `<script setup>` + 组合式 API | 与 Vue 3.5 的推荐写法一致 |
| 组件命名 | 文件名用大驼峰，如 `SignupGrid.vue` | 模板里可以直接用 `<SignupGrid />` |
| 样式 | `<style scoped>`，只写满足功能的最少样式 | 避免样式问题盖过知识点 |
| 界面元素 | 用原生标签，不引入 UI 组件库 | 少一层依赖，代码能直接看懂 |
| 数据来源 | 本地假数据或本地 mock，接口形状按真实约定写 | 现在就能跑，接后端时改动最小 |
| 注释 | 只写在“为什么这样做”的地方 | 代码本身已经说明了“做了什么” |

::: tip 关于“不引入 UI 组件库”
综合项目里会用 Element Plus，那样开发更快。但案例的目的是让你看清实现过程 ——
如果一个表格的排序逻辑被组件库封装成一行 `:sortable`，你就学不到 `computed` 怎么分层。
**先用原生写一遍，再用组件库，你会知道组件库替你做了什么。**
:::

## 常见问题

::: details 案例代码可以直接用在综合项目里吗
可以，但要改两处：

1. **数据来源**。案例为了让代码能直接运行，多数用本地假数据或本地 mock；综合项目里要换成
   真实的接口调用，参考[案例 04](/cases/04-fetch)里的 api 分层写法。
2. **样式**。案例的样式只保证能用，没有做主题变量和响应式；项目里建议把颜色、间距抽成
   CSS 变量，具体做法在[单元 2 的样式部分](/unit02/04-vite)。

直接复制不改，最常见的结果是：案例能跑，项目里报一堆样式冲突。
:::

::: details 一个案例要花多久
不要按时间规划，按“卡点数量”规划。一个 ★☆☆ 案例通常只有两三个真正的卡点，
★★★ 的案例可能有七八个。**卡点解掉就是有效学习时间，抄代码不算。**

如果某个案例你已经能在不看参考实现的情况下一次写完，说明这个知识点已经掌握，直接跳过下一个。
:::

::: details 案例里的写法和我看到的不一样
可能是三种情况，需要分别对待：

1. **风格差异**：比如用 `computed` 还是 `watch` 都能实现，都能跑。这种情况看哪种更容易讲清数据流。
2. **版本差异**：本课程基线是 Vue 3.5.42，网上大量文章还在讲 Vue 2 的 `this`、`$set`，
   那些写法在组合式 API 里已经不适用。
3. **案例写错了**：如果确实有 bug，按[案例 04](/cases/04-fetch)里“竞态”那一节的思路验证一遍，
   能复现就能定位。

判断标准只有一条：**哪种写法更能说清数据从哪来、到哪去。**
:::
