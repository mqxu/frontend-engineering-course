# 单元 5 · AI 协作：让它把四种状态补齐

这一章的核心是一件事：**数据页面必须把加载中、出错、空数据、有数据四种状态都写出来。** 而这件事恰好是 AI 最容易漏的地方 —— 它生成的页面，通常是“成功路径 + 一个 `v-if`”，看起来模板写得挺整齐，可惜漏掉的三种状态正好是页面上真会出现的三种。

还有一种情况更隐蔽：它把四态写全了，但 `v-for` 的 `key` 用了数组下标。页面平时好好的，直到你删掉中间一条数据，才会看到某个输入框里的内容串到了别处。

这一节讲的是**怎么让它把该写的状态写全，以及怎么检查它写的派生逻辑有没有重复。**

## 这一章哪些活能交给 AI

判断标准：**结构性的、有固定套路的东西可以交；涉及“这一页真实会出现什么情况”的判断不能交。**

| 任务 | 能交给 AI 吗 | 为什么 |
| --- | --- | --- |
| 按四态规范补一个页面的模板 | 可以 | 四态是固定结构，它基本不会漏项 |
| 解释计算属性的缓存什么时候失效 | 可以 | 它能把依赖关系讲清楚 |
| 判断 `key` 该取哪个字段 | 可以 | 但数据的唯一性要你自己确认 |
| 检查有没有“派生数据被重复存” | 可以 | 这个错它有固定的识别办法 |
| 给筛选 → 排序 → 分页设计派生链 | 可以 | 当起点用，最后要自己收口 |
| 判断“这一页还缺了哪种状态” | **不能直接信** | 它容易把“没有数据”和“请求出错”当成一回事 |
| 决定空状态该给什么引导动作 | **不行** | 引导动作取决于业务流程，比如“去创建第一个活动” |
| 决定要不要缓存这段派生数据 | **不行** | 取决于这段数据有多贵、变化有多频繁 |

中间那两行是这一章的重点。**四态里最容易被合并的是“空数据”和“出错”** —— 界面上的区别只是一个图标加一行字，但用户该做的事完全不同：一个是去创建数据，一个是重试。

## 提示词怎么写

### 1. 让它按四态规范补齐一个页面

```text
这是我的活动列表页，目前只有“有数据”一种状态：

[粘贴模板部分]

项目约定：数据页面必须按固定顺序写四种状态 ——
加载中 → 出错 → 空数据 → 有数据，用 v-if / v-else-if / v-else 串起来。

请补齐另外三种，要求：
1. 加载中用骨架结构，不要只写一个“加载中”
2. 出错态要给重试入口，说清重试按钮触发哪个函数
3. 空状态按两种情况分开：一种是真的没有活动，一种是有筛选条件但没匹配到。
   前者的引导是“创建活动”，后者是“清空筛选条件”
4. 改完把四态的完整模板再输出一次，不要只给 diff
```

**为什么这么写**：第 3 点是这段提示词的关键。**默认让它补四态，它多半只给一个空状态。** 但列表页的空其实有两种，用户该做的动作完全不同 —— 没数据要去创建，筛选没匹配到要去清条件。把它明说出来，它才会分开写。

第 4 点要求输出完整模板，是因为它给 diff 的时候经常省略上下文，四态的顺序对不对你得自己拼。让它整段输出，[5.5](/unit05/05-four-states) 里讲的“顺序不能颠倒”才验得出来。

### 2. 让它审一段 `v-for` 的 `key`

```text
这是我的 v-for 部分：

[粘贴模板]

数据是这样的：

[说明每一条有哪些字段、哪个字段唯一、列表会不会被增删或排序]

请回答：
1. 我现在的 key 会不会有问题，会的话在什么操作下暴露
2. 如果没有问题，说明为什么
3. 如果有问题，给我正确的写法，并说明选这个字段的理由

不要只回答“用 id 最好”，要说清在这个场景下用别的字段会怎样。
```

**为什么这么写**：`key` 这件事有很多“正确答案”式的说法，但它是对场景敏感的。要判断用得对不对，得知道列表会不会被排序、删除、插入。所以第 1 点问“在什么操作下暴露”，把问题从“这个写法好不好”变成“这个写法什么时候会坏”—— 后者才能验证。

最后一句是在拦它给“用 `id` 最好”这种没有信息量的回答。你需要知道的是“用下标在删除中间项时会串数据”这类具体后果。

### 3. 让它检查派生数据有没有重复存

```text
这是我的 script setup 部分：

[粘贴]

我担心同一份数据被存了两遍，改一处忘了改另一处。

请检查：
1. 哪些数据是从别处派生出来的，却被单独存成了 ref
2. 每一处这样写的后果是什么，在什么操作下会不一致
3. 改成计算属性的写法

如果某处确实该单独存（比如它是用户可编辑的），说明为什么不该改。
```

**为什么这么写**：这个错 AI 特别容易犯 —— 它写代码时习惯“先把结果算出来存起来”，因为那样后面用起来方便。但存起来就意味着两份数据，两份数据就可能不一致。第 3 点要求给改法，第 4 点主动留出“确实该单独存”的空间 —— 因为可编辑的输入框确实需要自己的状态，不加这一条它会矫枉过正。

## AI 在这一章容易错什么

### 只写“有数据”一种状态

**现象**：模板里只有 `v-if="list.length"` 加一个 `v-else`，`v-else` 里写“暂无数据”。请求还在路上时，页面显示的是“暂无数据”。

**原因**：它的样本里，成功路径的代码最多。而且四态模板比单状态模板长，生成时它会往短的那边收敛。

**怎么处理**：**把四态规范写进 AGENTS.md 的代码风格一节。** 这样它每次都会读到，不必你每次重复交代。判断有没有漏，看两个地方：

1. 请求函数调用前后，有没有 `loading` 状态的开关。
2. 错误分支是不是和空数据分支合并了 —— 这是最常见的偷懒。

```vue
<!-- ✗ 偷懒的写法：出错被当成没数据 -->
<div v-if="!list.length">暂无数据</div>

<!-- ✓ 分开写，两种情况的引导动作不同 -->
<div v-else-if="error">
  <p>{{ error }}</p>
  <button @click="load">重试</button>
</div>
<div v-else-if="!list.length">
  <p>还没有活动</p>
  <button @click="goCreate">创建活动</button>
</div>
```

### `v-for` 的 `key` 用数组下标

**现象**：`v-for="(item, index) in list" :key="index"`。

**原因**：这是最省事的写法，`index` 就在手边，不用想“哪个字段唯一”。

**怎么处理**：**只要列表会被增删或排序，就不能用下标。** 现象很好辨认：删掉列表中间的一条，输入框里的内容串到了相邻的行；或者拖拽排序后，某一行的勾选状态跟错了位置。

正确做法是取一个业务上唯一的字段：

```vue
<div v-for="item in list" :key="item.id">
```

如果数据里确实没有唯一字段，让后端加一个 —— 这比在页面上想办法便宜。**别把 `index` 加上字段名凑一个 key**（`item.name + index`），那等于还是用下标。

### 同一份数据既用 `ref` 存又用 `computed` 算一遍

**现象**：`const total = ref(0)` 后面又在某个 `watch` 里 `total.value = list.value.length`。

**原因**：它习惯“先算出来存着”，因为这样在别处用起来不用重复写计算逻辑。

**怎么处理**：判断标准只有一条 —— **这份数据是从别处算出来的，还是用户直接输入的？** 算出来的用 `computed`，输进来的用 `ref`。

```js
// ✗ 两份数据，可能不一致
const approvedCount = ref(0)
watch(list, () => { approvedCount.value = list.value.filter(i => i.status === 'APPROVED').length })

// ✓ 一份数据，不会不一致
const approvedCount = computed(() => list.value.filter(i => i.status === 'APPROVED').length)
```

顺带一个本项目的具体点：**名额只统计审核通过的报名记录**，待审核和已驳回都不占名额。这类过滤条件写在 `computed` 里，比在 `watch` 里维护一个计数更不容易漏改。

### 把 `deep` 和 `immediate` 的语义说反

**现象**：它说 `deep: true` 是“立即执行一次”，或者 `immediate: true` 是“监听对象内部的变化”。

**原因**：两个选项都用来“改变 watch 的默认行为”，它有时会把哪个管哪个说串。它给的代码通常是对的，错的是解释。

**怎么处理**：记清楚各自管什么 ——

| 选项 | 管什么 | 什么时候需要 |
| --- | --- | --- |
| `immediate: true` | 创建时立刻跑一次回调 | 依赖初始化时的值做一次处理 |
| `deep: true` | 对象内部的属性变化也触发 | 监听的是对象或数组，且改的是里面的字段 |

一个实用的提醒：**`deep: true` 有代价**，它会递归遍历对象，层级深的对象上开销不小。能用具体路径代替就别用 `deep`：

```js
// 不如直接监听到字段
watch(() => state.filter.status, () => { /* ... */ })
```

::: details 还有一类错误：把 `v-if` 与 `v-for` 写在同一个元素上
**现象**：`<div v-for="item in list" v-if="item.checked">`。它有时会这么写，还配上“这样写更简洁”。

**原因**：这种写法在 Vue 2 里能跑（`v-for` 优先级高于 `v-if`），所以样本里很多。但在 Vue 3 里 `v-if` 的优先级更高，而 `v-if` 的条件里用不到 `v-for` 的循环变量，直接报错。

**怎么处理**：两种情况，改法不同：

```vue
<!-- 想过滤列表：用计算属性，一步到位 -->
<div v-for="item in checkedList" :key="item.id">

<!-- 想按条件决定整块显不显示：把条件提到外层 -->
<template v-if="showList">
  <div v-for="item in list" :key="item.id">
</template>
```

第二种写法用 `<template v-if>` 包一层，不会多出一个真实标签，这也正是[5.3](/unit05/03-conditional)里讲的那个用法。

顺带说一句：**如果它的模板里出现 `v-for` 和 `v-if` 同元素，说明它这次是按 Vue 2 的优先级在写。** 这与[单元 4](/unit04/ai-collaboration)里那张旧写法表是同一类问题，整段代码都要再审一遍。
:::

## 怎么验收 AI 的产出

这一章的产出是页面模板与派生逻辑。验收时按“状态齐不齐 → key 对不对 → 派生有没有重复”的顺序过：

- [ ] 四种状态都在，顺序是加载中 → 出错 → 空数据 → 有数据
- [ ] 出错态有重试入口，空状态有下一步引导动作
- [ ] 筛选无结果和真的没有数据，两种空状态分开写了
- [ ] 每个 `v-for` 的 `key` 都是业务上唯一的字段，不是下标
- [ ] 模板里没有 `v-for` 与 `v-if` 写在同一个元素上
- [ ] 从别处算出来的数据用的是 `computed`，没有被单独存成 `ref`
- [ ] `deep` 和 `immediate` 的用法与你的初衷一致（不是因为它写了就跟着写）
- [ ] 你手动制造了一次请求失败、一次空结果，两种界面都出现了

最后一条是这个单元的验收里最有用的一条。**四态是没法靠读代码确认的，只能靠真的把每种情况跑出来。** 制造失败最简单的办法是打开浏览器的网络面板，把请求设成离线，或者临时把接口地址改错一个字母。

## 练习

### 拿你自己的列表页，让 AI 找出缺了哪几种状态

**任务**：从本周的练习或案例里挑一个列表页（[案例 02 的可排序筛选表格](/unit05/07-case-grid)是好选择），让 AI 指出缺了哪几种状态，然后补齐，最后**把四种状态各跑出来一次**。

**要求**：记录里必须包含这四项：

| 项 | 要求 |
| --- | --- |
| 改之前的模板 | 完整保留，注明自己判断缺了哪几种 |
| AI 的判断 | 它说缺了哪几种，与你自己的判断对照 |
| 改之后的模板 | 完整保留，四态的顺序要能看出来 |
| 四种状态的复现方法 | 每种写清“怎么让它出现”，并注明实际跑通了没有 |

::: details 验收标准与参考思路
**为什么要“每种写清怎么让它出现”**：因为四态最容易的失败方式是“写了但从来没触发过”。`v-else-if="error"` 这行代码在不在，光看模板看不出来它到底会不会执行 —— 只有真的把请求弄失败一次，才知道 `error` 有没有被赋值。

**思路提示**：

- 制造四种状态的顺序建议是：把网络调成离线看**出错态**；把筛选条件设成一个查不到结果的值看**筛选无结果**；把接口换成返回空数组看**真的没数据**；在请求上加 3 秒延时看**加载态**。这四种里，前两种不需要改代码。
- 让 AI 判断之前，**先把你的判断写下来**。不先写，你就会被它的答案带着走，看不出它漏了什么。
- 如果它只给了一个空状态，回去用第 1 个提示词模板重问一次，把“两种空”明说出来。这正好能验证“提问方式决定输出质量”。
- `key` 那一项也顺手查一遍。列表能被筛选和排序的页面上，`key` 用错很容易在排序时露出问题。

**不合格的写法**：

> 让 AI 把四种状态都补上了，看起来挺完整的。

“看起来完整”不算数。加载态是不是只写了一个“加载中”的文字、出错态有没有重试按钮、两种空状态有没有分开 —— 这些都得具体看到才算。

**合格的写法**：

> 改之前只有“有数据”和“暂无数据”两种。我自己判断缺了加载态和出错态。
> AI 说缺的也是这两个，但它把“没有活动”和“筛选无结果”合成了一条，
> 这一点它没意识到 —— 是我在提示词里明说之后它才分开的。
> 复现方法：网络调成离线看到“加载失败，请重试”；
> 筛选条件填“zzz”看到“没有匹配的活动，试试清空筛选条件”；
> 接口临时返回空数组看到“还没有活动，去创建第一个”；
> 请求加 3 秒延时看到骨架屏。四种都实际跑出来了。
> 另外我发现案例里的 `key` 用的是 `index`，列表能排序，我改成了 `item.id`。

差别在于：后者把每种状态**真的跑出来了**，并且发现了 AI 没看出来的那个问题（两种空被合并）。
:::
