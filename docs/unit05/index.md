## 这一周开始处理“真实业务”

上一单元的代码都很短：显示一个名字、切换一个状态、绑一个颜色。
这一周要处理的，是真实业务里最耗时的那一类需求 ——
**筛选、排序、分页、搜索、条件显示**。

先看一个典型的活动列表页，它要同时满足：

- 关键词搜索（标题里包含关键词）；
- 状态筛选（只看报名中的）；
- 点击表头排序（按报名截止时间，升序 / 降序 / 取消）；
- 分页（每页 10 条）；
- 加载中、出错、空数据、有数据四种状态都要处理；
- 还有“共 37 条，当前显示 1 - 10 条”这样的统计。

如果你按上一单元的写法，很容易写成这样：

```js
// ✗ 一个环节变了，手动去调下一个环节
watch(keyword, () => { applyFilter(); applySort(); applyPagination() })
watch(statusFilter, () => { applyFilter(); applySort(); applyPagination() })
watch(sortField, () => { applySort(); applyPagination() })
watch(page, () => { applyPagination() })
```

这段代码能跑，但它是**脆的**：加一个筛选条件要动四个 `watch`；
某个 `watch` 里漏调一步就出 bug；而且数据在多个变量之间来回赋值，
很难说清“当前列表到底是什么”。

正确的做法是换一个思路：**除了最原始的那几个状态（关键词、筛选值、排序字段、页码），
其他一切（筛选结果、排序结果、分页结果、总条数）都是算出来的。**
算出来的东西用**计算属性**，不存第二份。

```js
// ✓ 每一步都是计算属性，自动跟着源头走
const filtered = computed(() => { /* 筛选 */ })
const sorted = computed(() => filter 之后排序)
const paged = computed(() => sorted 之后切片)
const total = computed(() => filtered.value.length)
```

这就是这个单元的核心：**从“手动同步多份数据”变成“一条派生链”。**

::: tip 一句话概括这个单元的作用
**把重复运算和派生数据交给计算属性，把副作用交给侦听器，把渲染规则写清楚。**

学完这个单元，你已经能独立做出一个带搜索、筛选、排序、分页的数据列表页 ——
这是前端岗位上出现频率最高的一类页面。
:::

::: warning 这次课最容易出问题的地方
**`v-for` 的 `key`。** 用索引当键，在“列表中间删除一项”时会出现
输入框内容错位的现象（具体现象见 [5.4](/unit05/04-list)）。
这个 bug 很难从界面上看出原因，因为代码逻辑完全正确。

建议：**现在起，凡是 `v-for` 一律给一个业务上唯一的 `id`。**
不要用索引，除非列表是纯静态、永不增删的。
:::

## 开始之前：先复习两件事

这个单元大量依赖 JavaScript 的数组方法，以及上一单元的响应式基础。
开始之前请确认下面两件事。

**第一，数组方法要熟练。**

| 方法 | 用途 | 在本单元哪里用 |
| --- | --- | --- |
| `filter` | 筛选出符合条件的项 | 关键词搜索、状态筛选 |
| `map` | 把每一项变成新东西 | 生成表格行数据、格式化 |
| `reduce` | 汇总成一个值 | 统计总名额、已通过人数 |
| `sort` / `toSorted` | 排序 | 点表头排序 |
| `slice` | 截取一段 | 分页 |
| `some` / `every` | 判断是否存在 / 全部满足 | 全选半选状态 |

不会写 `filter` 和 `map`，这个单元会非常吃力。**这两条属于 JavaScript 基础，
不是 Vue 的内容。**

**第二，上一单元的四条结论要能背出来：**

- 脚本里读写 `ref` 要 `.value`，模板里不用；
- `reactive` 不能整体替换、解构会丢响应性；
- 自动解包只在模板顶层生效；
- 遇到“改了数据界面不动”，先查有没有经过响应式对象的读写。

不记得的话，回去翻一遍 [4.4](/unit04/04-reactivity)。

## 这个单元的产出

按课程要求，这次课交两样东西。

**一、待办清单**

一个可运行的增删改查清单应用，包含：新增、行内编辑（带取消）、删除（带撤销）、
按状态筛选、实时计数。完整要求见[案例 01](/unit05/06-case-crud)。

**二、可排序筛选的数据表格**

用校园活动数据做一张表格，包含：关键词搜索、状态筛选、
点击表头三态排序、分页、全选半选。完整要求见[案例 02](/unit05/07-case-grid)。

两样产出都要求**不使用任何 UI 组件库**。这一单元练的是“自己把逻辑写清楚”，
不是“学会调别人的组件”。组件库从[单元 6](/unit06/) 开始引入。

::: details 这两样产出的评分重点
不看界面好不好看（那是 CSS 的事），看三件事：

1. **派生链清不清楚。** 筛选、排序、分页是不是各自一个计算属性，
   而不是靠一堆 `watch` 互相触发。
2. **有没有第二份状态。** 比如“筛选后的列表”是不是被单独存进了一个 `ref`
   并且需要手动维护。
3. **四态齐不齐。** 加载中、出错、空数据、有数据是不是都处理了，
   顺序对不对。

这三点也是工作里代码评审最常提的意见。**现在养成习惯，以后改起来少受罪。**
:::
