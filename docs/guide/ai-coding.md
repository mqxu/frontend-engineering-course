# AI 编程：用之前先知道它的边界

::: tip 这一页要解决什么
这一页不讲怎么按快捷键，讲**什么时候该用、什么时候不该用、用完怎么判断能不能用**。
后面每个单元都有一节“AI 协作”，那是这一页的方法落到具体知识点上的用法。
:::

## 先看一个真实的场面

学期末检查项目，老师指着一处代码问：“这个 `el-table` 的 `row-key` 为什么这么设？”

同学看了半天：“AI 生成的，我没细看。”

再往下问：“那这个页面加载时为什么会闪一下？”

“不知道。”

这段对话里有两个问题。第一个是态度问题，后面会讲。第二个才是关键：**代码是你交的，但你没看懂它。** 到了答辩、到了工作里别人接手、到了线上出故障，能救你的只有“你知道它是怎么跑的”。

这一页的目的就是让你避免走到这一步。

## 这一年发生了什么

AI 编程工具不是新鲜东西，但形态在 2026 年发生了根本变化。

JetBrains 在 2026 年 5 到 7 月做了一次覆盖全球 1.5 万多名专业开发者的调查，几个数字值得记住：

| 指标 | 数据 |
| --- | --- |
| 每周至少用一次 AI 编码工具 | 约 90% |
| 每天使用 | 68% |
| 用它完成完整开发任务（不只是补全） | 已成为主流用法 |

这个比例意味着：**不用 AI 编程，在今天已经不是主流选择。** 但你也要看清下面这件事，它决定了这门课的态度。

### 从“补全”到“代理”

工具的能力分了三层，搞清楚自己在用哪一层，很重要：

| 层次 | 形态 | 它能做什么 | 你要做什么 |
| --- | --- | --- | --- |
| 补全 | 编辑器里的灰色提示 | 补全一行、一个函数体 | 你自己定结构，它帮你打字 |
| 对话 | 侧边栏聊天 | 解释代码、解释报错、改写选中的片段 | 你贴代码、你判断、你复制回去 |
| 代理 | 能读文件、能改文件、能跑命令 | 一次性改多个文件、执行任务、自己验证 | 你写清要求、你审结果 |

第三层是这一年的分水岭。工具从“帮你打字”变成了“替你把事做完”，工具使用率的排名也随之重排：

| 工具 | 2026 年 1 月 | 2026 年 5 - 7 月 |
| --- | --- | --- |
| Claude Code | 18% | 39% |
| GitHub Copilot | 29%（去年同期） | 21% |
| OpenAI Codex | 3% | 16% |
| Cursor | 18% | 12% |

数字背后的信号是：**竞争焦点从“谁的编辑器好用”变成了“谁的代理能真正把事做完”。** 这也是为什么这门课把 AI 协作的落点放在“怎么描述任务、怎么验收结果”，而不是“怎么让补全更快”。

顺带说一句使用范围的变化。同一时期内，AI 在**需求分析与设计**环节的使用率从 2024 年的 45.0% 上升到 2026 年的 70.9%。也就是说，AI 早就不只是写代码的工具了 —— 从拆需求开始它就能参与，这正好对应本课程第 11 周要练的“从需求到页面清单”。

## 工具怎么选

### 三条硬约束

给学生的建议和给企业团队的建议不一样，因为你有三个现实约束：

1. **能不能直接用**：海外工具在中国大陆没有官方的合规服务，存在网络不稳、账号被封、数据出境这几类风险。做课程项目优先用本土工具，不要在这件事上耗时间。
2. **要不要花钱**：学生阶段没必要为工具付费，先用免费额度把方法练熟。
3. **中文语境**：课内所有需求文档、报错截图、答辩材料都是中文，中文理解好的工具省掉大量来回解释。

### 国内主流的四款

2026 年 5 月国内 AI 编程 IDE 的市场份额大致是这样一个格局：

| 工具 | 份额 | 特点 | 适合什么情况 |
| --- | --- | --- | --- |
| 腾讯 CodeBuddy | 28% | 有 IDE 插件、独立 IDE、命令行三种形态；主推 SPEC 规范驱动开发，流程是需求澄清 → 任务拆解 → 代码预审 → 安全拦截 | 想练“先写规格再写代码”这套流程时用它，约束感最强 |
| 阿里 Qoder CN | 26% | 由通义灵码更名而来，支持工程感知、仓库知识库、长上下文 | 项目变大、希望工具能记住整个仓库结构时用它 |
| 字节 Trae | 24% | 基于 VS Code 架构，插件和快捷键通用；有 Agent 模式；基础版免费 | **零基础起步就用它**，上手成本最低，中文理解好 |
| 百度文心快码 | 22% | 面向任务的编程代理 | 已经在用百度系产品时可以顺带试 |

### 怎么决定

不要纠结“哪个最强”，这个问题没有稳定答案，一年内排名就换过一轮。按这个顺序决定：

1. **先选一个能免费用的，装上，用两周。** 不用比较，先有手感。
2. 如果两周后发现“它老是听不懂我要什么”，问题通常不在工具，在**你的描述方式** —— 这时候去看后面每个单元的“提示词怎么写”。
3. 等你能稳定地把一次任务描述清楚，再考虑换工具。**工具换起来很快，描述能力换不掉。**

::: warning 一个常见误区
不要把“装了哪个工具”当成学习成果。这门课考核的是：你能不能把需求描述清楚、能不能判断 AI 给的东西对不对。这两件事在任何工具上都通用。
:::

## 效率是真的，代价也是真的

这部分是这一页最重要的内容。**只看前半段的工具排行，会得出错误结论。**

### 一组来自真实团队的数据

Faros AI 在 2026 年 3 月发布了一份覆盖 22,000 名开发者、4,000 个团队的统计。团队从低 AI 采用率转为高采用率之后：

| 指标 | 变化 |
| --- | --- |
| 代码变更量 | 上升 861% |
| 事故与 PR 的比值 | 上升 242.7% |
| 开发者缺陷率 | 从 9% 升到 54% |
| 代码审查的中位耗时 | 增加 441.5% |
| 零审查直接合并的 PR 占比 | 31.3% |

最后一行是最值得停下来想的一个数字。它不是“有人决定不审查”，而是**审查的人跟不上产出的速度**。代码在没有被人读过的情况下就上线了。

### 代码质量的具体差距

| 研究 | 结论 |
| --- | --- |
| CodeRabbit 分析 470 个 PR | AI 生成代码平均每个 PR 有 10.83 个问题，人工代码是 6.45 个，差 1.7 倍 |
| Sonar 测试各大模型 | 发现的每个模型里，90% 以上的问题属于“代码异味”—— 不立即报错，但长期难维护 |
| Black Duck《2026 OSSRA》 | 代码库平均漏洞数同比上升 107% |
| Software Improvement Group 分析 30,000 个系统 | AI 生成代码的安全风险违规约为人工代码的 2 倍，过半含漏洞；代码规模超过 10 万行后，AI 带来的效率收益基本消失 |
| Sonar 开发者调查 | AI 产出已占已提交代码的 42%（预计 2027 年达 65%）；96% 的开发者不完全信任 AI 生成代码的正确性，但**不到一半的人每次提交前都会检查** |

请重点看最后一行里的对比：**几乎所有人都知道不该全信，但一半以上的人还是直接提交了。** 这个落差有个名字，叫“验证缺口”。

### 一句总结

> 代码产出翻了近十倍，人的阅读速度没变。**瓶颈从“写”转移到了“审”。**

所以这门课对 AI 的态度可以概括成一句话：**用它可以，但你必须具备审它的能力。** 而审的能力，恰恰来自你手写过的那些代码 —— 你写过 `computed`，才知道 AI 写错在哪。

::: danger 三件绝对不要做的事
1. **不要提交你没读过的代码。** 哪怕它能跑。
2. **不要把密钥、token、真实账号密码贴进对话。** 2026 年 3 月已经出现过通过提示注入攻击劫持 AI 编码代理、窃取 API 密钥与访问令牌的案例。
3. **不要把 AI 的判断当成安全结论。** 尤其是权限、鉴权、输入校验这三块，见单元 9 和单元 10。
:::

## 三个概念，知道它们管什么就够

这一年里频繁出现的三个词，你不需要会实现，但需要知道各自的职责，否则读文档时会一头雾水。

| 概念 | 它解决的问题 | 一句话理解 | 你要知道到什么程度 |
| --- | --- | --- | --- |
| AGENTS.md | AI 不知道你的项目约定 | 放在仓库根目录的 Markdown 文件，写明项目的技术栈、目录约定、代码风格、禁止事项 | 会写、会维护。本课程单元 3 讲基础写法，单元 11 讲项目里怎么用 |
| MCP | AI 不知道如何调用你的外部工具 | 一套让 AI 连接外部服务（数据库、接口、内部系统）的协议 | 知道它是什么、什么时候需要，不用自己实现 |
| Agent Skills | 重复的流程每次都要重新交代 | 把一套流程和参考资料打包成可复用的目录，AI 按需加载 | 知道它是什么、怎么判断该不该做 |

### 三者的关系

它们不是互相替代的，是三层不同的东西：

- **AGENTS.md 提供静态的项目上下文** —— 每次对话开始前，AI 就该知道的项目信息。
- **MCP 提供动态的工具调用能力** —— 让 AI 能去问数据库、能去调接口。
- **Agent Skills 提供可复用的专业能力** —— 把“怎么做一次代码审查”这类流程固化下来。

打个比方：AGENTS.md 是给新同事的项目说明文档，MCP 是他手上的系统账号权限，Skills 是“我们公司的代码审查流程手册”。

### AGENTS.md 值得多说两句

因为它是三者里你**现在就能用上、而且立刻见效**的一个。

它最早由 OpenAI 在 2025 年 8 月随 Codex CLI 推出，2025 年 12 月捐赠给 Linux 基金会下的 Agentic AI Foundation 托管。到 2026 年中，已有 28 个以上工具原生支持它，GitHub 上有 6 万多个仓库包含这个文件。

几个实用规则：

- **文件放在仓库根目录**，与代码一起提交，团队成员共享。
- **支持分层**：子目录可以放自己的 AGENTS.md，AI 处理某个目录下的文件时，就近的文件覆盖上层。前端目录可以放一份更细的。
- **社区建议核心文件控制在 100 到 200 行**，只做导航性说明，细节通过链接指向别的文档。这个做法叫“渐进式披露”—— 需要时再展开，不要一次全塞进去。
- 各工具的原生文件另有名字：Claude Code 用 `CLAUDE.md`，Gemini CLI 用 `GEMINI.md`，GitHub Copilot 用 `.github/copilot-instructions.md`，Cursor 用 `.cursor/rules`。但 `AGENTS.md` 是跨工具通用的那个。

一份最小的 AGENTS.md 大概长这样（完整版本见[项目里的 AI 协作规范](/project/ai-collaboration)）：

```md [AGENTS.md]
# 项目约定

## 技术栈
Vue 3.5 + Vite 8 + Vue Router 5 + Pinia 4 + Element Plus 2。

## 目录约定
- 页面组件放 src/views，一个路由一个文件
- 通用组件放 src/components，只有被两处以上复用才移进来
- 接口函数放 src/api，按业务模块分文件

## 接口约定
- 后端响应格式 { code, message, data }，成功码是 0，不是 200
- 前端字段用驼峰，后端返回下划线，在 api 层统一转换

## 禁止事项
- 不要修改 src/utils/request.js 的拦截器逻辑
- 不要在代码里写任何密钥、token
- 不要删除你没有确认过引用位置的代码
```

注意最后三条“禁止事项”。有分析发现，在真实项目的 AGENTS.md 里，最有效的往往就是这类明确的边界说明，而不是冗长的代码风格清单。

## 这门课的三条约定

从第 1 周到第 12 周，AI 协作按这三条来。

### 一、先写清楚，再让 AI 写

不要一上来就说“帮我做个活动管理页面”。先自己把这几件事写下来：

1. 这个页面给谁用，他进来要完成什么。
2. 页面上有哪几块内容，每块显示什么数据。
3. 数据从哪个接口来，返回哪些字段。
4. 加载中、没数据、出错分别显示什么。

写完再交给 AI。看起来多花十分钟，实际上省掉的是后面反复返工的时间。

这套方法有个正式名字叫**规格驱动开发（Spec-Driven Development）**，它的核心主张是：把“要建什么、为什么建”先写成规格，代码是规格的落地。GitHub 官方的 Spec Kit 把这套流程做成了工具（2025 年 9 月发布，2026 年中已超过 13 万 star，支持 38 种 AI 编码工具），流程是：项目原则 → 规格 → 澄清模糊点 → 质量清单 → 技术计划 → 任务清单 → 一致性检查 → 执行实现。

你不必用这个工具，**用几份 Markdown 文件走同样的流程效果一样**。本课程第 11 周会完整走一遍。

### 二、每一段 AI 产出的代码，你都要能解释

给一个可以自己操作的验收动作，就叫“三句话检查”：

> 对着这段代码，不看 AI 的回答，自己回答三个问题：
> 1. **它做了什么？** —— 用一句话说清输入和输出。
> 2. **为什么这么写？** —— 说清关键的那一两个决定，比如为什么用 `computed` 而不是 `watch`。
> 3. **如果这里出错会怎么表现？** —— 说出一个具体的故障现象。

三句话都答得上来，这段代码可以进你的项目。**答不上来就别提交，回去读懂或者换一种写法。**

这个动作听起来简单，但它刚好补上了前面数据里那个“验证缺口”。Sonar 的调查把“审查与验证 AI 代码”列为 AI 时代最关键的开发者技能 —— 它说的就是这个能力。

### 三、诚实声明 AI 参与

课程不禁止用 AI，禁止的是**用了不说**。综合项目要求交一份 AI 参与声明，说明：

- 哪些模块用 AI 生成或辅助过；
- 你为了让 AI 产出可用结果，做了哪些澄清和补充；
- 你发现并修正了 AI 的哪些错误；
- 哪些部分你判断不适合交给 AI，自己写的，为什么。

第三项是重点。**能说出“AI 错在哪、我怎么发现的”，比写出多少代码更能证明你的水平。**

## 哪些活可以交给 AI，哪些必须自己判断

最后给一张对照表，这门课后面每个单元的“AI 协作”节都是这张表在具体知识点上的展开。

| 可以放心交给 AI | 必须自己判断 | 绝对不要交给 AI |
| --- | --- | --- |
| 解释陌生概念、解释报错含义 | 技术选型与方案取舍 | 密钥、账号、真实用户数据的处理 |
| 生成配置文件的初稿 | 配置是否真的生效（要跑一次验证） | 权限与鉴权的最终判定 |
| 把重复代码抽成函数、组件 | 抽出来的边界是否合理 | 删除代码（必须先自己搜引用） |
| 生成校验规则、错误提示文案 | 校验规则的业务含义对不对 | 提交未读过的代码 |
| 解释构建产物体积、性能数据 | 优化前后的对比测量 | 对外发送的正式材料（要自己过一遍） |
| 起草文档、README、答辩提纲 | 内容是否与实际实现一致 | 声称“已经测试通过” |

看这张表会发现一个规律：**AI 擅长“把已经想清楚的事变成代码”，不擅长“替你想清楚”。** 而你的核心竞争力，恰好长在后半段。
