# 单元 11 · AI 协作：走一遍从规格到实现的完整流程

前面十章的 AI 协作，都是“问它一个知识点”或者“让它改一段代码”。这一章不一样 —— 从这一周开始，你要**让它按规格实现一个完整的页面**。

这是 AI 编码真正的主战场，也是最容易失控的地方。失控的方式有两种：一种是它一次生成十几个文件，你没读完就提交了；另一种是它按自己的习惯搭了一套结构和你的项目对不上，等你发现的时候已经有三个页面依赖它了。

这一节要讲的就是怎么把这件事控制在可验收的范围内。方法只有一个：**先把规格写清楚。**

## 这一章哪些活能交给 AI

判断标准：**规格里写明的事可以交给它实现，规格里没写的部分一律不能让它补。**

| 任务 | 能交给 AI 吗 | 为什么 |
| --- | --- | --- |
| 把规格文档整理成给 AI 的任务说明 | 可以 | 整理和改写，机械工作 |
| 按规格实现一个页面 | 可以 | 但要严格限定“只创建哪几个文件” |
| 按 AGENTS.md 逐条自查产出 | 可以 | 有清单的检查它做得快 |
| 解释某个接口字段的用途 | 可以 | 快速确认理解 |
| 起草页面的四态结构 | 可以 | 前面几个单元已经建立了这个习惯 |
| 起草任务清单的条目 | 可以 | 但优先级要你自己排 |
| 判断“这个需求该拆成几个页面” | **不能直接信** | 它倾向一步到位，拆得不够细 |
| 补上规格里没写的接口或字段 | **不能直接信** | 它会按常见命名编一个出来 |
| 决定第一版做哪些功能、不做哪些 | **不行** | 取决于时间与课程要求 |
| 决定页面之间的跳转关系 | **不行** | 取决于业务流程 |

**倒数第三行是这一章最需要提防的。** 它编出来的字段名往往比真的还像真的 —— `activityStatus`、`signupCount`、`createTime` 这种命名挑不出毛病，但它和你们后端的字段可能根本不是一个。

## 提示词怎么写

### 1. 先搞清规格驱动开发在做什么

这一章的用法有个正式名字，叫**规格驱动开发（Spec-Driven Development）**。四个要点：

**一、核心主张：先写规格，再让 AI 实现。** 代码是规格的落地，规格本身是可以被审阅、被讨论、被修改的产物。

**二、为什么需要它。** 因为“一次让 AI 写太多”出来的东西对不上需求，而返工的成本比一开始写清楚更高。更麻烦的是：**返工时你不知道该改哪里，因为整段代码都是它生成的，你只是“觉得不对”。**

**三、流程长什么样。** GitHub 的 Spec Kit 把这套流程做成了工具链（2025 年 9 月发布，2026 年中已超过 13 万 star，支持 38 种 AI 编码工具），它的命令顺序是：

| 顺序 | 做什么 |
| --- | --- |
| 1 | 立项目原则（相当于 AGENTS.md） |
| 2 | 写规格 —— 只写做什么、为什么，**不写技术栈** |
| 3 | 澄清模糊点 |
| 4 | 生成质量清单 |
| 5 | 写技术计划 |
| 6 | 拆任务清单 |
| 7 | 跨产物一致性检查 |
| 8 | 执行实现 |

国内的编码工具也在往同一个方向走 —— 腾讯 CodeBuddy 主打的规范驱动开发就是同一套思路：需求澄清、任务拆解、代码预审、安全拦截。**你不必用这些工具，用手写 Markdown 走同样的流程，效果一样。**

**四、为什么这一章要再讲一次 AGENTS.md。** [单元 3](/unit03/ai-collaboration)讲的是“AGENTS.md 是什么、写什么”；这一章讲的是“**怎么用它**”—— 它是流程里的第 1 步（项目原则），后面所有步骤都建立在它之上。规格里可以不写技术栈，但技术栈必须已经写在 AGENTS.md 里 —— 否则 AI 会自己选一套。

**本项目的规格不用另写。** 你在[项目规格](/project/)里看到的这几份文档本身就构成规格：

```
① 需求规格说明          做什么、为什么做、有哪些字段
        ↓
② 业务规则与状态流转     名额怎么算、冲突怎么判、状态怎么变
        ↓
③ 接口约定              路径、参数、返回结构、错误码
        ↓
④ 目录结构与命名约定     文件放哪、怎么命名
        ↓
⑤ 页面清单与任务清单     拆成一次能做完的小任务
```

前四份是给定的，**第五份要你自己拆。** 这一节练的其实就是第五份怎么写。

### 2. 让它先复述需求确认理解

```text
先读根目录的 AGENTS.md，以及 docs/页面清单.md 里“页面 4 · 活动列表”一节。

不要写代码。先告诉我三件事：
1. 用你自己的话复述一遍这个页面要做什么，包括有哪几块内容
2. 这个页面有哪些状态需要处理（加载中、出错、空数据等）
3. 有哪几处你觉得描述不明确、需要我确认

第 3 项按“会影响实现方式”的程度排序。
```

**为什么这么写**：这一步看起来多花了五分钟，省下的往往是半小时。**理解偏差在写代码之前暴露出来，改的是一句话；在写完之后暴露出来，改的是十几个文件。**

第 3 点最有价值 —— 它列出来的“不明确处”通常正是你没想清楚的地方。你在写规格的时候觉得已经说清了，它一问才发现“筛选条件变化后要不要回到第一页”这种事你根本没写。

### 3. 给它一份规格再让它实现

```text
读 AGENTS.md 和 docs/任务/04-活动列表.md，按里面的要求实现这个页面。

约束：
1. 只创建或修改这两个文件：src/views/activity-list.vue、src/api/activity.js
2. 接口只用 docs/接口清单.md 里已有的，不要新增接口
3. 字段名在 api 层转成驼峰，页面里不出现下划线字段
4. 用 script setup 的组合式写法，不用选项式 API
5. 页面要有四态：加载中、出错、空数据、有数据

完成后按这个格式汇报：
- 改了哪些文件，每个文件做了什么
- 哪些地方是我没写清楚、你自己决定的（逐条列出）
- 有哪些地方你不确定，需要我确认
```

**为什么这么写**：五条约束里，第 1 条和第 2 条最关键，它们把“它可能做的事”框死了。**不限定文件范围，它会顺手改你的请求层、动你的 store、往 `utils` 里加东西** —— 每一处都可能是新的问题源。

汇报格式里的第 2 项是这段提示词的核心：**让它主动列出“你自己决定的部分”**，那些就是你要逐条核实的清单。它自己决定的越少，你的核对成本越低 —— 所以如果这一项列了七八条，说明你的规格写得太粗，回去补。

### 4. 让它按 AGENTS.md 逐条自查

```text
读根目录的 AGENTS.md，把它里的每一条约定都当成一条检查项，
逐条检查你刚才生成的代码。

输出用表格：约定的原文 / 我的代码符不符合 / 在哪一行 / 不符合的话怎么改。

要求：
1. 每一条都要出现，符合的也写出来
2. 不要改代码，只给表
3. 如果有某条约定你判断不了，直接写“判断不了”并说明缺什么信息
```

**为什么这么写**：这一步是把 AGENTS.md 从“写给 AI 看的文件”变成“AI 用的检查清单”。**同一份文件，读一遍和当检查项用一遍，效果差很多** —— 前者它只当背景知识，后者它必须逐条给出结论。

要求“符合的也写出来”和“判断不了的写判断不了”，都是为了堵住偷工减料。少了这两句，它容易只报两三条问题、剩下的一笔带过，让你误以为其余都没问题。

## AI 在这一章容易错什么

### 一次让它生成太多

**现象**：你写“帮我做活动管理模块”，它一次给出五个页面的代码，外加 store、api、路由、以及几个你没想到的组件。文件加起来两千多行。

**原因**：从它的角度，“一次做完”是最省事的方案 —— 不用等你反馈，也不用在多轮之间保持一致。它没有“我要花半天才能读完这些代码”这个视角。

**怎么处理**：**一次只做一个页面，而且只做能在一小时内读完的量。** 判断标准很简单：

> 它给你的代码，你有没有把握**逐行读完并解释**？没有，就说明给多了。

把任务切小的具体做法，就是在规格的“完成标准”里写清边界。比如：

| 切法 | 一次的范围 |
| --- | --- |
| 按页面切 | 一次一个页面，先列表页再表单页 |
| 按功能切 | 先“能显示数据”，再“能筛选”，最后“能分页” |
| 按文件切 | 先 api 层，再页面组件，最后路由与菜单 |

**“不做”这一节比“要做”更能约束范围。** 写清“不做批量操作、不做导出、不做列自定义”，它就不会顺手给你加上。

### 产出不符合项目已有的约定

**现象**：它新建了一个 `src/services/activityService.js`，或者自己写了一个 `request.js`，或者组件里直接 `axios.get`，或者用了 `element-plus` 的另一种写法。每一样单独看都合理，合起来看是另一套项目。

**原因**：它不知道你的项目里已经有什么。你不给它看现有代码，它就只能按“一个典型项目应该长什么样”来搭 —— 而“典型项目”和“你们的项目”不是一回事。

**怎么处理**：三件事一起做。

1. **提示词里限定文件范围**（第 3 个模板的第 1 条）。范围限定死了，它想另起一套也没有地方放。
2. **让它先读 AGENTS.md 和已有的同类文件。** 提示词第一句就写“读 AGENTS.md”，再补一句“参考 `src/views/session-list.vue` 的写法”，效果更好 —— 有现成的例子照着，它不会自己发明。
3. **在 AGENTS.md 的禁止事项里写明。** 本项目的那五条里，“不要引入新的 UI 库或状态管理库”和“不要修改 `src/utils/request.js` 里的拦截器逻辑”正是防这个的。

**判断有没有另起一套，最快的办法是看文件清单。** 它汇报“新建了这几个文件”时，你逐个对一下 `src/` 的目录约定 —— 出现约定之外的目录，就是跑偏了。

### 编造字段与接口

**现象**：它写出来的代码里有 `res.data.signupCount`、`activity.status === 'PUBLISHED'`、`api.getActivityDetail(id, { withStats: true })`。这些字段、状态值、参数，你的接口清单里都没有。

**原因**：这是幻觉依赖在业务层的版本。它按“一个活动管理系统应该有这些字段”来补，因为这些命名在它见过的项目里高频出现。**它补得越合理，你越容易放过。**

**怎么处理**：**接口和字段只能从接口清单里来，不能用它给的。** 两个具体的检查动作：

```bash
# 把代码里用到的字段名抽出来，和后端返回的对照
grep -o "res\.[a-zA-Z]*\.[a-zA-Z]*" src/views/activity-list.vue | sort -u

# 把代码里用到的状态值抽出来，和状态流转文档对照
grep -o "'[A-Z_]\{3,\}'" src/views/activity-list.vue | sort -u
```

本项目的活动状态只有四个：`DRAFT`、`SIGNING`、`SIGNUP_CLOSED`、`FINISHED`。**如果它写出了 `PUBLISHED`、`ONGOING`、`CLOSED` 这类值，说明它是编的** —— 而且这个错很隐蔽，因为状态判断错了往往只是“某个筛选条件不生效”，页面上看不出异常。

顺带说一个本项目里特别容易编错的地方：**下架是独立的布尔标记 `offShelf`，不是一种状态。** 如果它把下架写成了 `status === 'OFF_SHELF'`，那整套状态判断都错了。

::: details 还有一类错误：硬编码假数据，交付时忘了换
**现象**：页面里写着 `const list = ref([{ id: 1, title: '测试活动', status: 'SIGNING' }])`，或者 `// TODO: 接接口` 然后一直没接。

**原因**：这是它“让页面先跑起来”的常用手段 —— 有假数据，界面立刻能看，你能马上判断布局对不对。本身不算错，**错在忘了换。**

**怎么处理**：**允许它用假数据，但要求它把假数据集中在一处并标记出来。**

```js
// ✓ 集中在文件顶部，一眼能看到
// TODO(临时数据): 接口联调后删除，见 docs/任务/04-活动列表.md
const MOCK_LIST = [/* ... */]
const list = ref(MOCK_LIST)
```

这样做有两个好处：一是交付前搜 `MOCK_` 或 `TODO(临时数据)` 就能全找出来，二是它不会散落在十几个地方。

**交付前一定搜一遍这三类东西：**

```bash
# 假数据
grep -rn "MOCK_\|mockData\|测试活动\|张三\|TODO" src/

# 调试输出
grep -rn "console\.log" src/

# 硬编码的地址
grep -rn "localhost\|127\.0\.0\.1\|http://" src/
```

这三条命令[单元 12](/unit12/ai-collaboration)讲部署前检查时还会用到。**把它们写进提交前的自查习惯里，比每次靠记可靠。**
:::

## 怎么验收 AI 的产出

这一章的验收动作要照着规格逐条过，而且必须**在浏览器里真的走一遍**。

- [ ] 规格里的每一条“完成标准”，你都动手验证过了（不是读代码判断的）
- [ ] 规格里的“不做”，它确实没做
- [ ] 它只改了提示词里限定的文件，没有动 request.js、没有加新依赖
- [ ] 代码里用到的字段名，全部在接口清单里能找到
- [ ] 代码里用到的状态值，全部在状态流转文档里能找到（四个状态，下架是独立标记）
- [ ] 它汇报的“自己决定的部分”，你逐条确认过，该改规格的回去改规格
- [ ] 按 AGENTS.md 自查的表里，没有“判断不了”的行留着
- [ ] 没有 `MOCK_`、`console.log`、硬编码地址残留

前两条对应“做完了没、做多了没”，中间三条对应“有没有编东西”，后三条对应“该收的尾收了没”。**这八条过完，这个页面才算是“按规格交付”，不是“碰巧能跑”。**

## 练习

### 用“规格 → 实现 → 验收”走一遍一个新页面

**任务**：从项目的页面清单里挑一个还没做的页面，完整走一遍四个步骤：写规格 → 让 AI 实现 → 验收 → 记录。**记录里要写清它返工了几次、每次是因为什么。**

**要求**：记录里必须包含这四项：

| 项 | 要求 |
| --- | --- |
| 你的规格文档 | 四节齐全：目标、约束、不做、完成标准 |
| 给 AI 的提示词 | 完整保留，包括你限定文件范围的那一段 |
| 验收结果 | 逐条对照完成标准，写清哪几条过了、哪条没过 |
| 返工记录 | 每次返工写清“因为什么、改了规格还是改了提示词” |

::: details 验收标准与参考思路
**为什么重点记“返工因为什么”**：因为返工的原因就是你规格里的漏洞。**同一类漏洞改一次规格就够了，下次不用再返工。** 这才是这一节真正要你带走的东西 —— 不是“学会用 AI 写页面”，而是“学会写一份不用返工的规格”。

**思路提示**：

- 第一次写规格别追求完美，写完就让它实现一遍。**先跑一轮，你才知道自己的规格漏了什么。** 空想是想不到的。
- 验收时严格执行“动手验证”这一条。规格里写“删除最后一页最后一条后，停留在上一页而不是空白页”，那就真的删一次看看 —— 读代码判断出来的“应该没问题”，不算过。
- 返工记录里区分两类：**规格没写清**（回去补规格）、**它没按规格做**（改提示词，把那条约束写得更硬）。这两类的处理方式不同，混在一起就学不到东西。
- 如果它一次生成的文件超过你半小时能读完的量，**不要往下走，回去把任务切小。** 这一步忍住了，后面会省很多事。
- 做完把它当检查项用一遍（第 4 个提示词模板）。**这一步花的时间最少，发现的问题往往最多。**

**不合格的写法**：

> 让 AI 做了活动列表页，改了几次，现在能跑起来了。

“能跑起来”是这一章最低的标准。规格里的“完成标准”写了几条？过了几条？返工了几次、为什么返工？

**合格的写法**：

> 规格我写了目标、约束、不做、完成标准四节，完成标准里列了三条。
> 第一次实现返工了两处：
> 一是它用了 `status === 'PUBLISHED'`，接口清单里没有这个值，是我把状态流转文档贴给它之后改对的；
> 二是筛选条件变化后没有回到第 1 页 —— 这一条我在规格里没写，所以回去补了规格，重新生成了一次。
> 完成后我按三条完成标准逐条验证：筛选项清空能恢复全量（过）、
> 删除最后一页最后一条会跳到空白页（没过，改了两行修好）、
> 后端关掉时显示错误态而不是一直转圈（过）。
> 最后按 AGENTS.md 自查，发现它用了 `.filter` 在模板里做筛选 —— 违反了“派生数据用 computed”这条，
> 改成计算属性了。
> 两条经验：**状态值和分页行为这类东西，规格里不写明它就会自己编；规格里没写的事，一定会返工。**

差别在于：后者不但完成了任务，还把两处返工转成了两条可以复用的规格经验。**下一次写规格，这两条就不会再漏。**
:::
