单元 3

工程规范、质量保障与 Git 协作

模块一 · 工程化认知与工具链4 学时第 3 周
学完这个单元，你应该能够
  • 能配置并解释一套前端代码检查方案，让检查在编辑与提交两个环节自动生效
  • 能按模块化思路组织代码文件
  • 能规范使用 Git 完成一次完整的功能开发与合并
  • 能配置一条自动构建流水线
课堂产出
带校验钩子的工程模板首次合并请求 + 自动构建流水线

这一周要“建仓库” ​

前面两周都在自己的电脑上折腾：装环境、配构建、调依赖。这一周不一样 —— 这一周你要和同学一起，在一个共享的仓库里写代码。

一旦代码不再只有你看，问题就换了一批：

单人开发多人协作
缩进用空格还是 Tab 随意一次提交里混进几百行“格式改动”，评审没法看
变量名随手起别人读不懂你写的 data2、tmp、listNew
提交信息写“改了一下”出了问题想回退，找不到是哪次提交引入的
本地跑通就提交有人提交的代码根本构建不过
直接改主分支上的代码两个人改同一个文件，冲突了不会解

这五条对应本单元的五节内容。它们不是“高级技巧”，而是你从今天开始每天都要用的东西。

这个单元是整门课的转折点

第 1、2 周是“把工具装好”，从这一周开始是“在一个真实的仓库里协作”。

本单元结束时你会有一个工程模板 —— 它包含构建配置、代码检查、提交钩子、流水线。 第 11 周做综合项目时，不是从零开始，而是直接从这个模板开始。

所以这一周的产出不是练习题，是你要一直用下去的东西。认真做。

本单元的知识地图 ​

小节讲什么解决什么问题
3.1 为什么需要代码规范评审成本、格式争论、规范的三层划分为什么这件事必须自动化
3.2 ESLint 与 Prettier 配置扁平配置、规则集、职责划分、编辑器联动、提交钩子怎么让检查自动生效
3.3 模块化与目录组织ES Module、导出方式取舍、按功能分目录、命名约定代码怎么组织才不越写越乱
3.4 Git 协作流程分支模型、提交信息、冲突解决、代码评审、.gitignore两个人怎么安全地改同一份代码
3.5 自动构建流水线四个阶段、本地能过流水线不过的原因、门禁的价值怎么不靠人工自觉
AI 协作 · AGENTS.md 与提交规范AGENTS.md 是什么、写什么、怎么分层，配合提交信息规范让 AI 按项目约定产出，而不是按它自己的习惯
课后练习规范治理、钩子拦截、两人协作评审、流水线跑绿把这些配置真的用起来

五节的顺序是一条链：先有规范意识（3.1）→ 用工具把规范自动执行（3.2）→ 代码本身组织得好（3.3）→ 协作流程规范（3.4）→ 把检查接到流水线上（3.5）。

这次课的 4 学时怎么用 ​

环节时长做什么
检查预习0.3 学时抽问：你遇到过哪些“格式争论”？你现在的提交信息都写成什么样？
讲解1.2 学时重点讲 3.2 的检查链路与 3.4 的冲突解决；3.1、3.3、3.5 以自学 + 答疑为主
现场任务1.9 学时配好检查与钩子，两人一组各自开分支实现一个小功能并合并
复盘0.6 学时展示几组被钩子拦下的提交，对比不同分支的冲突解决方式

这次课最容易卡住的地方

不是配置本身，是提交钩子不生效。

husky 需要在 Git 仓库里初始化；lint-staged 需要和 husky 配合； 配置写完后要真的做一次提交才能验证。三个环节里任何一个没做对， 表现都是“提交居然通过了” —— 而且不报错，你根本不知道它没生效。

验证方法只有一个：故意提交一次不合规的代码，看它有没有被拦下来。 练习里专门有一道题做这件事，不要跳过。

开始之前 ​

三样准备。前两样第 2 周应该已经完成。

  • 一个能构建的项目：练习 1 修好的那个工程，能跑 pnpm build。
  • 一份可用的 vite.config.js：带别名和代理配置。
  • 一个 GitHub 或云效的账号：这一周要建远程仓库、开合并请求。 校内可以统一用学校提供的代码托管平台。

另外找一个搭档。3.4 的冲突场景需要两个人真的改同一个文件才能体会到 —— 一个人自己造冲突，是体会不到“评审时该看什么”的。

text
同学 A：负责活动列表页的活动状态筛选功能
同学 B：负责活动列表页的时间格式化功能
两个人都会改 src/views/ActivityListView.vue —— 冲突就是这样产生的

这个单元的产出 ​

按课程要求，这次课交两样东西。

一、带校验钩子的工程模板

一个可以直接复制用来开新项目的仓库，至少包含：

组成部分要求
构建配置可用的 vite.config.js、环境变量文件
代码检查ESLint 配置 + Prettier 配置，职责不重叠
提交校验husky + lint-staged + commitlint，提交不合规时被拦下
编辑器说明.vscode/settings.json 与推荐扩展列表
说明文档README.md 写清楚怎么装、怎么跑、怎么提交

判断模板合格的三条标准

  1. 新人克隆后能跑起来：不做任何额外确认，照着 README.md 三步内启动。
  2. 不合规的代码提交不上去：格式错误、提交信息不规范都会被拦。
  3. 检查在编辑器里就能看到：不用等到提交才发现问题。

第 3 条最容易被忽略，但它是“规范能不能长期维持”的关键 —— 要等提交才发现问题，人就会想办法绕过检查。

二、首次合并请求 + 自动构建流水线

项目要求
分支从主分支切出一个功能分支，命名规范
提交至少 3 次提交，信息符合约定格式
评审有一次真实的互相评审，留下评论并说明采纳理由
合并合并前流水线跑绿
流水线安装依赖 → 执行检查 → 构建，三个阶段都通过

不要为了“跑绿”而关掉检查

流水线第一次跑，通常会因为一些历史代码的问题失败。这时候有两种处理方式：

  • 把出问题的规则临时关掉 —— 三周后你会发现规则全被关光了。
  • 只修本次改动涉及的文件，其余问题记成待办。

选第二种。门禁的意义是“不让问题变多”，不是“立刻让所有问题归零”。

读完之后 ​

这个单元结束之后，你手上有三样东西：一个能构建的工程、一套自动检查、 一个能跑的流水线。它们就是第 4 周开始写 Vue 代码的工作台。

下一单元（单元 4）开始讲 Vue 3 的模板语法与响应式。到那时候， 你每写一行代码都会被格式化、被检查、被流水线验证 —— 这正是我们想要的状态： 把规范交给工具，把注意力留给业务逻辑。

如果这个单元学得吃力，优先保证 3.2（检查链路）和 3.4（Git 流程）过关。 这两节是后面每周都要用的。
