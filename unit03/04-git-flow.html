3.4 Git 协作流程 ​

两个人改了同一个文件 ​

你和搭档同时在做活动列表页。分工是这样：

谁做什么改哪些文件
你加活动状态筛选ActivityListView.vue、features/activity/api.js
搭档改报名截止时间的显示格式ActivityListView.vue、shared/utils/format.js

两人都从主分支切了功能分支，各自提交，各自推送。你先把分支合并进主分支， 然后搭档去合并他自己的分支时，Git 停下来了：

text
Auto-merging src/views/ActivityListView.vue
CONFLICT (content): Merge conflict in src/views/ActivityListView.vue
Automatic merge failed; fix conflicts and then commit the result.

冲突不是错误，是提示。 它的意思是：Git 发现两个人改了同一个文件的同一段代码， 它不知道应该保留谁的，所以交给你判断。

这一节讲怎么规范地用 Git 协作，重点讲冲突怎么处理。

分支模型：三条规矩 ​

多人协作不需要复杂的分支模型，记住三条就够用：

规矩说明
主分支（main）始终可用主分支上的代码必须能构建、能运行。不直接往主分支提交
一个功能一个分支从主分支切出，做完再合回去，做完就删掉
通过合并请求合并不允许“本地合完直接推主分支”，要有人看过

用一张图表示这个循环：

text
main  ──●────────────●──────────────●──→
         \          / \            /
          \        /   \          /
feature    ●──●──●      ●──●──●──●
           切分支    推送   开合并请求   评审   合并   删分支

常用命令 ​

bash
# 1. 先让主分支是最新的
git switch main
git pull

# 2. 切出功能分支（名字要能看出做什么）
git switch -c feat/activity-status-filter

# 3. 写代码，分多次小步提交
git add src/features/activity/
git commit -m "feat(activity): 活动列表支持按状态筛选"

# 4. 推送并建立追踪关系
git push -u origin feat/activity-status-filter

# 5. 到平台上开合并请求

# 6. 合并之后清理
git switch main
git pull
git branch -d feat/activity-status-filter

不要在 main 上直接改

git switch -c 这一句最关键。很多人图省事，直接在 main 上写代码然后 git push。

后果有两个：一是你的半成品代码会影响所有人；二是万一推上去的代码有问题， 回退要动到所有人共用的分支。

判断方法：git branch --show-current 输出的如果不是功能分支名，先切分支再动手。

分支命名与提交信息 ​

分支命名 ​

text
<类型>/<简短描述>

feat/activity-status-filter     新功能
fix/enroll-deadline-format      修 bug
refactor/api-error-handling     重构
docs/readme-quick-start         文档
chore/upgrade-vite              杂事

要求：全小写、用短横线连接、能看出做什么。避免 dev1、test、zhangsan 这种名字。

提交信息格式 ​

就是 3.2 里 commitlint 检查的那套：

text
<类型>(<范围>): <描述>

feat(activity): 活动列表支持按状态筛选
fix(review): 修复审核通过后名额未更新的问题
docs(readme): 补充本地开发启动步骤
refactor(api): 把请求拦截器抽成独立模块
chore(deps): 升级 element-plus 到 2.14.5

两个常见的写法问题：

✗ 不好的描述✓ 好的描述差别
改了一下feat(activity): 活动列表支持按状态筛选前者三个月后完全没用
修复 bugfix(review): 修复审核通过后名额未更新的问题后者能定位到具体问题
更新代码refactor(api): 把请求拦截器抽成独立模块前者等于没说

判断标准：三个月后你看到这条信息，能想起改了什么吗？ 答不上来的，就重写一遍。

提交的粒度 ​

粒度例子评价
太细每个文件一次提交提交记录几十条，找不到重点
合适一次提交完成一件可描述的事出问题时能精确回退
太粗一次提交改了活动、审核、场地三个模块想回退一半都做不到

“一件可描述的事”是判断标准：如果你写提交描述时要用“顺便”“还有”“另外”， 说明这次提交该拆。

冲突的产生与解决 ​

为什么会冲突 ​

Git 合并两个分支时，逐行比较两边相对共同祖先的改动：

情况Git 怎么处理
A 改了第 10 行，B 没动直接采用 A 的改动
A 改了第 10 行，B 在第 20 行加了一行自动合并，两边都保留
A 改了第 10 行，B 也改了第 10 行冲突，交给人工判断

关键点：冲突只发生在“同一处代码被两边都改了”时。 所以减少冲突的办法不是“不要一起写代码”，而是让改动尽量分散 —— 这也正是 3.3 按功能分目录 带来的好处之一。

一次真实的冲突 ​

你合并进主分支之后，搭档去合并他的分支，Git 报冲突。打开 src/views/ActivityListView.vue，会看到这样的内容：

text
const filteredList = computed(() => {
<<<<<<< HEAD
  return list.value.filter((activity) => activity.status === statusFilter.value)
=======
  return list.value.filter((item) => item.status === currentStatus.value)
>>>>>>> feat/activity-time-format
})

三个标记的含义：

标记含义
<<<<<<< HEAD冲突块开始，下面是当前分支（这里是 main，已经包含了你的改动）
=======分隔线
>>>>>>> feat/activity-time-format冲突块结束，前面是要合并进来的分支的版本

注意 HEAD 指的是“你现在所在的分支”，不是“别人改的”。 这一点最容易搞反。用 git branch --show-current 确认自己现在在哪。

解决步骤 ​

bash
# 第 1 步：看哪些文件冲突了
git status

# 输出里会列出 both modified 的文件
# both modified:   src/views/ActivityListView.vue
text
<<<<<<< HEAD
  return list.value.filter((activity) => activity.status === statusFilter.value)
=======
  return list.value.filter((item) => item.status === currentStatus.value)
>>>>>>> feat/activity-time-format
text
// 两边的意图是：一个改筛选变量名，一个用了更清晰的变量名
// 合并结果：保留“变量名统一为 currentStatus”这个更好的写法
const filteredList = computed(() => {
  return list.value.filter((item) => item.status === currentStatus.value)
})
bash
# 第 2 步：删掉三个标记，把内容改成最终想要的样子
# 第 3 步：告诉 Git 这个文件解决了
git add src/views/ActivityListView.vue

# 第 4 步：确认没有遗漏的冲突文件
git status

# 第 5 步：完成合并提交
git commit

# 第 6 步：验证 —— 这一步不能省
pnpm lint && pnpm build

判断依据：该保留谁 ​

这是冲突解决里唯一需要动脑的地方。按下面的顺序判断：

情况怎么处理
两边改的是同一件事，只是写法不同选更好的那个写法（可读性、一致性优先）
两边改的是不同的事，只是碰巧在同一行两个都保留，手动组合
一边删了这段代码，一边改了这段代码搞清楚“为什么删”，找对方确认
看不懂对方为什么这么改直接问，不要猜

第三种情况最危险。删掉那段代码的人可能是故意的（那段逻辑移到别处了）， 也可能是误操作。猜错的代价是功能悄悄失效，而且可能几周后才发现。

冲突解决里最有用的一句话

看不懂就问，别猜。

问一句“你这里为什么把 deadline 判空也删了”花 30 秒； 猜错导致报名时间显示成 NaN 并在演示时被发现，花一下午。

冲突解决不是考试，不需要独立思考。

中途想撤退 ​

冲突解决到一半发现搞不定，可以撤回去重新来：

bash
# 撤销整个合并，回到合并前的状态
git merge --abort

# 如果已经提交了合并，也可以回退到上一个提交
git reset --hard HEAD~1
bash
# 只想采用某一方的版本（谨慎使用）
git checkout --ours src/views/ActivityListView.vue    # 采用当前分支的
git checkout --theirs src/views/ActivityListView.vue  # 采用对方分支的

--ours / --theirs 会整段丢弃一边的改动

这两个命令是“整文件选择”，不是“逐行选择”。用之前先把那个文件备份一份 （复制成 .bak），或者先看清楚那边的改动是不是完全不需要。

新手用 reset --hard 之前的习惯：先 git stash 或者建一个临时分支。 丢掉的提交是找不回来的。

预防冲突的三条习惯 ​

习惯效果
每天开工先 git pull 拉最新主分支减少分叉长度
功能分支只做一件事，做完尽快合并分支存活时间短，重叠机会少
别在同一个文件里做大范围格式化格式化改动会覆盖整个文件，必然冲突

第三条特别值得注意：如果你在功能分支里顺手格式化了一个文件， 而这个文件别人也在改，冲突就不可避免了。 所以格式化最好单独一次提交，或者在合并前再统一做。

合并与变基怎么选 ​

bash
# 合并：把对方分支的历史接进来，产生一个合并提交
git merge main

# 变基：把自己的提交“移到”对方分支的最新提交之后，历史变成一条直线
git rebase main
对比项mergerebase
历史形态保留分叉，有合并提交一条直线
冲突解决次数一次解决全部可能每个提交都要解一次
是否改写提交哈希不改改写
适合场景合并到主分支、共享分支之间本地整理自己的提交
风险无对已推送的共享分支变基会害别人

本课程的建议：

  • 从主分支更新自己的功能分支 → 用 git merge main（简单、安全）。
  • 合并功能分支进主分支 → 由平台上的合并请求完成。
  • 不要对已经推送、别人可能在用的分支做 rebase。

变基的危险之处

变基会重写提交历史。如果别人已经从你的分支拉过代码， 你一变基，你们的提交哈希就对不上了，他再推就会产生大量重复提交。

判断能不能变基的标准：这个分支只有你一个人在用吗？ 是的话可以，不是就别动。

代码评审看什么，不看什么 ​

评审是协作里最容易被做错的一环。做错的方式有两种：什么都不看，或者什么都看。

应该看不该占用评审时间
逻辑是否正确、边界情况是否处理缩进、引号、分号（工具管）
是否有未处理的错误情况变量该叫什么名字（除非确实含义不清）
是否影响其他模块与本次改动无关的历史代码问题
命名能否表达意图“如果用另一种设计模式会更好”这类偏好
有没有重复实现的逻辑自己习惯的写法 vs 作者习惯的写法
有没有把密钥、调试代码提交进去——

第三行和最后一行是新手最容易踩的：

  • 不要评审历史代码。这次提交只改了活动筛选，你却在评论里说“这个文件三个月前的 一段逻辑写得很乱”—— 这属于“顺手说说”，会打击人的积极性，而且不解决当下问题。
  • 一定要看最后一行。密钥、console.log、注释掉的调试代码、 临时改成 true 的开关，这些都是评审必须看的。

一次好的评审评论长什么样 ​

✗ 不好✓ 好
这里不对第 42 行：status == 0 换成 === 更合适，因为接口返回的 status 是字符串
这样写不好这个筛选逻辑和 features/review/ 里的很像，能不能抽成组合式函数复用
应该加错误处理接口失败时 loading 不会恢复成 false，下次打开页面会一直显示加载中

差别在于：好的评论给出理由和影响，坏的评论只给结论。 给理由对方才能判断该不该改；给影响对方才知道这有多严重。

.gitignore 该写什么 ​

.gitignore 的作用是“哪些文件不进 Git”。它分两类内容：

类别例子为什么
生成物dist/、node_modules/每次都能重新生成，提交只会让仓库变大
个人相关.env.local、.vscode/settings.json 里的个人偏好每台机器不同，提交会造成无意义的冲突
系统文件.DS_Store、Thumbs.db操作系统生成的，和项目无关
日志与缓存*.log、.vite/临时文件

一份完整的配置：

bash
# 依赖目录：几十万个文件，绝对不能提交
node_modules/

# 构建产物：每次 build 都能重新生成
dist/
dist-ssr/

# 本地环境变量：每个人机器上可能不同
.env.local
.env.*.local

# 日志与缓存
*.log
npm-debug.log*
.vite/
*.tsbuildinfo

# 编辑器与系统文件
.DS_Store
Thumbs.db
.idea/

# 测试与覆盖率产物
coverage/

这三个文件一定要提交，别加进 .gitignore

文件为什么必须提交
pnpm-lock.yaml保证所有人装出同样的依赖树（2.2）
.vscode/extensions.json新同学打开项目能看到该装哪些扩展
.vscode/settings.json保证所有人的格式化行为一致

判断标准：这个文件对“所有人应该一致”有帮助吗？ 有就提交； 只有你自己机器才需要的（比如 .env.local）就忽略。

已经提交过的文件再加进 .gitignore 无效

.gitignore 只对还没被跟踪的文件生效。已经提交过的文件要先从索引里移除：

bash
# 从 Git 索引里移除，但保留本地文件
git rm --cached .env.local

# 目录的话加 -r
git rm -r --cached dist

注意 --cached 这个参数不能少 —— 不加会把本地文件也删掉。

小结 ​

  • 三条规矩：主分支始终可用、一个功能一个分支、通过合并请求合并。
  • 分支名格式 <类型>/<简短描述>；提交信息用 feat(scope): 描述。
  • 提交粒度是“一件可描述的事”，出现“顺便”“还有”就该拆。
  • 冲突只发生在“同一处代码被两边都改了”时，是提示不是错误。
  • 解决冲突的步骤：看 git status → 理解两边意图 → 删标记 → git add → 提交 → 跑构建验证。
  • 看不懂对方为什么这么改，直接问，不要猜。
  • 更新自己的分支用 merge；不要对已推送的共享分支做 rebase。
  • 评审看逻辑、边界、影响、命名；格式问题交给工具，历史代码问题不在本次范围内。
  • .gitignore 忽略生成物、个人配置、系统文件；锁文件和 .vscode 配置要提交。

常见坑 ​

坑 1：以为冲突是“谁写错了”

现象：两个人开始互相推责任，觉得是对方改错地方了。

原因：把冲突理解成错误。

换个角度：Git 冲突的完整含义是“这两个改动都合法，但我不知道你要哪个”。 它说明两个人都正常完成了工作，只是改到了同一处。

处理：看两边的意图，做合并判断。冲突次数多，说明的是分工或目录组织有问题， 不是人的问题。

坑 2：git pull 报 “Please commit your changes or stash them”

现象：本地有未提交的改动，git pull 拒绝执行。

原因：拉取下来的改动会覆盖你本地未提交的部分，Git 不敢动。

处理：三选一 ——

bash
# 1. 先提交（推荐，改动确实完成了一部分）
git add . && git commit -m "wip(activity): 筛选逻辑进行中"

# 2. 暂存起来，拉完再恢复
git stash
git pull
git stash pop

# 3. 反转：放弃本地改动（会丢失，谨慎）
git checkout -- .

注意 wip 类型的提交在合并请求里要去掉 —— 它不是一次有意义的提交记录。

坑 3：冲突解决完忘记删标记

现象：构建报 Unexpected token <<<<<<< 之类的语法错误。

原因：<<<<<<<、=======、>>>>>>> 三个标记没删干净。

处理：

bash
# 搜一下还有没有残留
grep -rn "<<<<<<<" src/

顺便也搜 >>>>>>> 和 ======= —— 后者在 Markdown 里是合法的分隔符， 但在 JS 里是语法错误。提交之前跑一次这个搜索，比构建失败后再找省时间。

坑 4：把 node_modules 提交上去了

现象：仓库体积突然涨到几百 MB，克隆要等很久。

原因：.gitignore 没写，或者写之前已经 git add . 过。

处理：

bash
git rm -r --cached node_modules

然后确认 .gitignore 里有 node_modules/，再提交这一次删除。

注意：这只让后续不再跟踪它，历史记录里的那几百 MB 还在。 真要彻底清理需要重写历史，成本很高。所以这件事要在一开始做对。

坑 5：在 main 上写了一半才发现

现象：已经在 main 上改了好几个文件，还没提交。

原因：忘了先切分支。

处理：

bash
# 建一个新分支，改动会跟着过去（因为还没提交）
git switch -c feat/activity-status-filter

# 确认一下当前分支和改动
git status

原理：未提交的改动不属于任何分支，切分支时会跟着走。所以只要还没提交， 随时可以切到正确的分支上。提交之后就要麻烦一些（需要 cherry-pick 或 reset）。

课后练习 ​

练习 1：走完一次完整的分支流程

要求：

  1. 从 main 切一个功能分支，实现一个小组件（比如活动状态标签）。
  2. 至少做 3 次提交，每次只做一件事，信息符合 feat(scope): 描述 格式。
  3. 推送到远程，开一个合并请求。
  4. 找搭档评审，根据评论做至少一处修改。
  5. 合并，删除分支。

验收标准

项目要求
分支命名符合 <类型>/<描述> 格式
提交信息全部符合 commitlint 规则，没有 wip 残留
提交粒度每次提交只做一件事，能各自描述清楚
评审有一条真实的评审评论，并说明采纳或未采纳的理由
合并前流水线跑绿

截图留证：提交记录列表、评审评论、合并后的分支图。

练习 2：制造并解决一次冲突

和搭档配合，人为制造一次冲突：

约定的分工

  • 你改 src/views/ActivityListView.vue 里的 filteredList 计算属性， 把筛选变量的名字改成更清楚的（比如 statusFilter）。
  • 搭档改同一个计算属性，把箭头函数的参数名从 a 改成 activity。

步骤

  1. 两人各自从 main 切分支，各自改，各自提交推送。
  2. 你先合并进 main。
  3. 搭档从 main 拉最新代码（git merge main），触发冲突。
  4. 按本节讲的六步解决。
  5. 把冲突标记的原文和解决后的代码都记录下来。

验收标准

项目要求
记录完整冲突原文、两边意图、最终选择、理由四项齐备
验证解决后 pnpm lint && pnpm build 都通过
反思写一句话：这次冲突本可以怎么避免

参考思路：最后一项的答案通常是“如果先商量好变量名”“如果两次改动分散在不同文件” 或者“如果功能分支存活时间更短”。

练习 3：评审一份真实的合并请求

找一个公开的、你熟悉技术栈的开源项目，看一个已合并的合并请求。

  1. 数一数评审评论有多少条，按类型分类（格式 / 命名 / 逻辑 / 架构建议）。
  2. 找出你认为最有价值的一条评论，说明为什么。
  3. 找出你认为最没必要的一条（如果有），说明为什么。

验收标准：必须给出真实的评论内容（引用原文），不能只说“看了几个”的原理。

参考思路：选 star 数较多、有专职维护者的项目，评审质量通常更高。 按“评论条数 / 改动行数”这个比例看，能感觉出不同项目的评审风格差异。

练习 4：写一份团队 Git 约定

给你们的项目写一份 Git 约定文档（放 docs/git-workflow.md），至少包含：

项目内容
分支命名类型有哪些、怎么描述
提交信息类型清单、范围怎么定、描述怎么写
提交粒度什么算一次提交
合并方式用 merge 还是 rebase，谁来合并
冲突处理什么情况下必须先问对方
评审要求至少几个人看、哪些内容必须看、多久内要给反馈

验收点：每条约定都要能回答“如果违反了怎么发现”。 答不上来的约定，要么写成一条检查规则，要么删掉 —— 不能执行的约定等于没有约定。
