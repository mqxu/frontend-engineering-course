3.1 为什么需要代码规范 ​

一次真实评审现场的记录 ​

下面是一段真实发生过（内容做了整理）的代码评审。评审的是活动列表页的一个改动， 功能本身只有 30 行。

评审人 A：第 42 行这里缩进是 4 个空格，我们前面都是 2 个空格吧？ 作者 B：我编辑器默认 4 个空格，改了。 评审人 A：第 58 行逗号后面没空格。 作者 B：改了。 评审人 A：第 63 行这个函数为什么用 function 声明，前面都是箭头函数？ 作者 B：习惯，改了。 评审人 A：第 71 行字符串用了双引号，我们统一用单引号。 作者 B：改了。 评审人 A：还有个问题，这段代码里 formatDeadline 好像没被用到？是不是漏了什么逻辑。 作者 B：对，我把筛选逻辑删了忘了删这个 import。 评审人 A：还有过滤条件那里，status == 0 用的是双等号，可能有问题。 作者 B：这个确实该用 ===。 评审人 A：好，那就没问题了。

数一下：11 条评论里，前 4 条全是格式问题，占了评审时间的大半； 只有最后 2 条是真正值得讨论的。

更值得注意的是那个“漏了的 import”。它本来应该在更早的位置被发现 —— 如果有一个工具在你保存文件时就说“这个变量声明了但没用到”， 评审时就不用花时间找它。

这一节想说明的就是一件事：规范和格式分歧，应该是机器干的活，不是人干的活。

格式争论为什么特别浪费时间 ​

把上面那 4 条格式评论拆开看，会发现它们有三个共同特点：

特点具体表现后果
没有唯一正确答案4 个空格还是 2 个空格，两种都能写争不出结果，只能靠“谁资历高听谁的”
反复出现每换一个作者就会再来一轮同一个话题被讨论几十次
与代码质量无关缩进不影响程序行为讨论它不产生任何价值

第三点最关键。格式问题不影响正确性，却最容易引发争论 —— 因为它门槛低，人人都能说上两句；又因为它没有客观标准，谁也说服不了谁。

真正的解决办法不是“定一个更严格的规矩”，而是把这件事从讨论里移出去：

让一个工具决定，所有人照着做。工具说了算，人不用争论。

一个判断标准

如果一个问题的答案可以用“是”或“否”机械地判断，它就不该由人来决定。

“这里该缩进几个空格” → 机械可判断 → 交给工具。 “这个筛选条件改用包含还是相等更合适” → 需要理解业务 → 由人讨论。

这一节后面会看到，工具能处理的不止格式 —— 还有一批低级错误也能机械判断。

规范的三层 ​

“代码规范”是一个笼统的说法。分开看，它其实有三层，每层的工具和检查时机都不同：

层次管什么例子由谁负责什么时候检查
格式层它长什么样缩进、引号、分号、换行、排序Prettier、Stylelint保存文件时
语义层它写得对不对未使用的变量、==、v-html、await 漏写ESLint保存 + 提交时
提交层改动怎么记录提交信息格式、一次提交管几件事commitlint提交时

三层的分工很重要：

  • 格式层可以全自动修。因为它不涉及语义，工具改完结果一定等价。
  • 语义层只能自动修一部分。像 == 改 === 可以自动修， 但“这个变量 unused 是删掉还是补充使用”需要人判断。
  • 提交层不检查内容，只检查结构和粒度 —— 提交信息写没写类型、 一次提交是不是同时改了七八件不相关的事。

不要试图用一层工具解决三层问题

两个常见的错误做法：

  1. 只用 ESLint，不管格式规则。ESLint 能做格式，但它做得慢且容易和 Prettier 冲突。
  2. 只看格式，不管语义。代码缩进完美，但里面有一堆 == 和漏掉的 await。

三层的目标不同：格式层求“统一”，语义层求“少犯错”。

语义层能拦下什么 ​

给几个真实的例子，都是校园活动服务平台代码里出现过的。

js
// 1. 用 == 比较，'0' == 0 会通过，但 '草稿' == 0 不会
if (activity.status == 0) { /* ... */ }

// 2. 声明了没用的变量，代码里的死逻辑
import { formatDeadline } from '@/utils/format'  // 全文没用到

// 3. 异步函数漏了 await，报错被吞掉，页面只是“没反应”
function loadActivities() {
  fetchActivities()  // 没有 await，也没有 .catch
}

// 4. 用了 v-html 渲染用户提交的活动描述
<div v-html="activity.description"></div>

这四类问题的共同点是：能跑，但会出问题，而且出问题时很难定位。

问题什么情况下会出问题排查难度
==后台返回来的是字符串 '0'中 —— 需要看接口返回
未使用的 import不会出错，但代码里留着过期逻辑低 —— 但会误导后来的人
漏 await接口失败时没有任何提示，用户只看到列表空着高 —— 报错被吞了
v-html用户提交的活动描述里带脚本时高 —— 安全问题，不一定有人测

第 3 条最典型。loadActivities() 里没有 await， 接口报错时 Promise 变成 rejected 而没人处理，控制台可能只有一行警告。 用户看到的是“列表一直空着”，你排查半天以为是后端挂了。

这类问题靠人眼评审发现不了，因为代码“看起来是对的”。 但 ESLint 可以在保存时就告诉你：Promises must be awaited or handled。

规范能不能长期维持，看三件事 ​

第一周兴致勃勃定了规范，第三周就没人管了 —— 这种事很常见。原因不在“态度”， 而在规范本身的设计。能让规范长期有效的，是三个条件：

条件一：工具要快 ​

如果检查一次要等 40 秒，人的选择一定是关掉它。这条没有商量余地。

实际数字感受一下：

做法检查一次的耗时你会怎么做
每次保存检查整个项目十几秒到几十秒关掉保存检查
只检查当前文件一百毫秒以内一直开着
每次提交检查整个项目半分钟以上想办法绕过提交钩子
每次提交只检查改动文件几百毫秒无感

所以后面配的时候有两个关键词：“只检查被改动的文件” —— 这正是 lint-staged 存在的理由。

条件二：问题要在编辑器里可见 ​

报错出现在终端里，意味着你必须主动去跑一条命令才知道有问题。 没有几个人会主动跑。

反过来，如果问题直接在编辑器里用红色波浪线标出来，你就会顺手改掉 —— 因为它挡住了视线。

text
你在第 42 行敲下 activity.status == 0
编辑器立刻在这一行下面画一条黄色波浪线，悬停显示：
“Expected '===' and instead saw '=='. (eqeqeq)”

条件三：要能一键自动修 ​

再想一下：如果编辑器提示“你少了个分号”，而你只能手动补，50 个文件就是 50 次手动操作。 这种量级的重复劳动，人一定会放弃。

所以工具必须支持自动修复：

bash
# ESLint 自动修复能修的问题
pnpm eslint . --fix

# Prettier 格式化
pnpm prettier --write .

配好之后，这个动作甚至可以完全不用你执行 —— 保存文件时自动完成。

三条条件的检查清单

配置完任何一套规范方案之后，问自己三个问题：

  1. 保存一个文件之后，检查结果出现得够快吗（感受是“立刻”，不是“等一下”）？
  2. 写错的时候，编辑器里有提示吗（不是只在终端里）？
  3. 这个问题能被一条命令自动修掉吗？

三个都答“是”，这套规范才有可能活过这个学期。 有一个答“否”，它就会在三周内被绕过。

规范不是“为了好看” ​

最后澄清一个常见的误解：有人觉得规范就是“让代码好看”“老师要求”。

看两个具体收益，都是可以衡量的：

收益具体表现
评审时间用在刀刃上11 条评论里格式类的从 4 条降到 0 条，讨论集中在业务逻辑
回退和定位变简单提交信息规范之后，git log 能直接看出哪次改了什么

第一条的收益可以算：一次评审 20 分钟，格式类讨论占 8 分钟， 一个学期 10 次评审就是 80 分钟 —— 一个多小时花在“缩进几个空格”上。

第二条在看历史记录时特别明显。对比一下两种提交信息：

text
改了一下
再改
提交
修复 bug

# ✓ 好
feat(activity): 活动列表支持按状态筛选
fix(activity): 修复报名截止时间显示错误
refactor(api): 统一请求层错误处理

三个月后查“报名截止时间为什么显示错了”，第二种可以直接找到那一次提交； 第一种你只能把几十次提交逐个点开看。

小结 ​

  • 格式争论浪费时间，因为它没有唯一答案、反复出现、与代码质量无关。
  • 能用机械规则判断的事，不该由人讨论，交给工具。
  • 规范分三层：格式层（长什么样）、语义层（写得对不对）、提交层（怎么记录）。
  • 语义层能拦下 ==、未使用的变量、漏掉的 await、v-html 这类“能跑但会出问题”的代码。
  • 规范要长期有效，需要三个条件：工具快、问题在编辑器里可见、能一键自动修。
  • 规范的实际收益是可衡量的：评审时间减少、历史定位变快。

常见坑 ​

坑 1：把规范当成“老师的要求”

现象：配置是被动的，做完就忘，后面几周又恢复成随意写。

原因：没意识到规范的第一受益人是你自己。

换个角度想：一个月后你要改今天的代码。如果当时的变量名是 data2、 提交信息是“改了一下”，你排查问题的时间会多出好几倍。

这不是纪律问题，是成本问题。

坑 2：一次性定几十条规则

现象：第一周定了 40 条规则，第二周代码里到处是红色波浪线，第三周全部关掉。

原因：规则太多，改不动。

处理：第一次只定三类，且必须是能自动修的。

  • 格式类全交给 Prettier（人不用管）。
  • 语义类只开最关键的几条（未使用变量、==、漏 await）。
  • 提交信息按格式检查。

让历史代码的问题保持原样，只要求“新写的代码合规”。 这样规则才会被接受。

坑 3：以为“老代码有问题”就必须立刻全修

现象：接进检查之后，终端刷出 800 条警告，当天全用来修告警了，业务一行没写。

原因：把“检查历史”和“检查新代码”混在一起了。

处理：分三步 ——

  1. 先只对改动文件做检查（提交钩子天然就是这样）。
  2. 把全量检查放进流水线，但允许失败（先观察一段时间）。
  3. 每次动到某个文件时顺手把那个文件的问题修掉。

告警数量应该逐周下降，而不是一次性清零。 一次性清零的代价是业务停摆一天。

坑 4：靠“互相提醒”维持规范

现象：评审时反复说“记得用单引号”“记得写类型前缀”。

原因：规则停留在口头，没有工具执行。

判断方法：同一句话说了三遍以上，就该把它变成一条规则。

说三遍以上说明两件事：这个规则确实重要；靠提醒确实记不住。

坑 5：只检查格式，不检查语义

现象：代码缩进完美、引号统一，但接口报错被吞、有一个 == 比较状态值。

原因：以为“格式统一”就等于“规范”。

处理：回顾这一节的“三层”表。格式层只解决“统一”， 语义层才解决“少犯错” —— 而后者对项目质量的影响大得多。

检查顺序：先开格式（让人无感），再逐步开语义（需要人判断）。 两者都要有。

课后练习 ​

练习 1：统计一次评审的评论类型

找一次你参与过的代码评审（课程组的、社团项目的都行）， 把评论按下面的表分类统计：

类型条数占比应该由谁处理
格式类（缩进、引号、分号）
命名类（变量名、函数名）
语义类（逻辑、错误处理）
业务类（需求理解、边界情况）

参考思路：如果格式类加命名类超过一半，说明这个项目的规范全靠人在维持。 写下至少两条可以改成工具执行的条目。

验收点：要给出真实数字，不能凭印象写“大概一半”。

练习 2：找出这段代码里的语义问题

下面这段代码是活动列表页的加载逻辑。找出至少 4 个语义层的问题， 并说明每个问题在什么情况下会出故障。

js
import axios from 'axios'
import dayjs from 'dayjs'
import { ElMessage } from 'element-plus'

const list = ref([])
let loading = false

function loadActivities(status) {
  loading = true
  axios.get('/api/activity/list', { params: { status } }).then((res) => {
    list.value = res.data.data
    loading = false
  })
}

function formatTime(t) {
  if (t == null || t == '') return '-'
  return dayjs(t).format('YYYY/MM/DD')
}

参考思路：从这五个角度找 ——

  1. loading 是不是响应式的？模板里用它会有反应吗？
  2. 请求失败时怎么办？loading 会恢复吗？
  3. list.value = res.data.data 如果 res.data.data 是 undefined 会怎样？
  4. t == null || t == '' 里，== 和 === 的行为区别是什么？
  5. dayjs 和 ElMessage 是不是都用到了？

验收点：每个问题都要写出“什么输入 → 什么现象”，不能只写“这样写不好”。

练习 3：给规范分三层

把下面这些条目分到“格式层 / 语义层 / 提交层”，并写出该由哪个工具管：

  1. 缩进统一用 2 个空格
  2. 不允许出现未使用的变量
  3. 提交信息必须以 feat / fix 等类型开头
  4. 字符串统一用单引号
  5. 不允许用 v-html 渲染用户输入
  6. 一次提交只做一件事
  7. 抛出错误时必须处理（await 或 .catch）
  8. 对象最后一个属性后面要加尾逗号

参考思路：分完之后会发现，格式层的每一条都能自动修， 语义层只有一部分能自动修，提交层完全不能自动修（只能拒绝）。 这个区别决定了后面配置的思路。

练习 4：写下你自己的“三遍规则”清单

想一想你自己在评审或合作中说过三遍以上的话，列出来。

格式：

我常说的话出现场景能不能改成规则

参考思路：如果某条“能不能改成规则”填的是“能”， 就把它记下来 —— 这一单元后面会教你怎么把它变成一条真正的检查规则。

验收点：至少三条，其中至少一条能改成工具规则。
