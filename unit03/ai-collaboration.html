单元 3 · AI 协作：把项目约定写给 AI 看，顺便把提交规范立起来 ​

这一周你第一次要在一个共享的仓库里写代码。规范从这一周起不再是你个人的偏好，而是别人评审你的依据。

AI 在这一章的位置很特殊：它既能帮你把规范写出来，又是最需要被规范约束的那个合作者。因为它默认按训练数据里的习惯写，不按你项目的约定写 —— 你不告诉它，它就按大众写法给你。

这一章要讲的 AGENTS.md，就是为这件事准备的。

这一章哪些活能交给 AI ​

判断标准：把规范写成文字这件事可以交，规范本身定成什么样得由你和搭档一起定。

任务能交给 AI 吗为什么
起草 AGENTS.md 的初稿可以它知道一份约定文件通常要写哪几类内容
按约定格式写提交信息可以格式是机械规则，它不会写累
解释一条检查报错的含义可以规则名和报错文案它见得比教程多
给出修一条检查错误的写法可以但要你自己看一眼修完的行为有没有变
中文提交信息的措辞可以一句话的事
决定用哪套规则集、哪几条规则要关不行这是团队取舍，取决于代码现状
生造一条看起来合理的规则名不能直接信规则名写错，配置不报错，检查静默失效
判断分支该怎么切、谁评审谁不行取决于你们组的分工

最后三行是这一章的重点。配置类文件最麻烦的地方是写错了不报错 —— 规则名拼错、路径写错、插件没装，表现都是“检查通过了”，你以为配好了。

提示词怎么写 ​

1. 先搞清 AGENTS.md 是什么，再动手写 ​

它最早由 OpenAI 在 2025 年 8 月随 Codex CLI 推出，2025 年 12 月捐赠给 Linux 基金会下的 Agentic AI Foundation 托管。到 2026 年中，已有 28 个以上工具原生支持它，GitHub 上有 6 万多个仓库包含这个文件。

四个问题各一句话：

问题答案
是什么放在仓库根目录的一份 Markdown 约定文件，AI 编码工具会自动读它
为什么要你每次要向 AI 重复交代的约定，写一次就够了
写什么技术栈、常用命令、目录约定、接口约定、禁止事项
怎么分层子目录可以再放一份，AI 处理该目录下的文件时，就近的文件覆盖上层

几条实用规则：

  • 和代码一起提交，不是放在你本地的某个角落。它是团队成员共享的。
  • 核心文件控制在 100 到 200 行，只做导航性说明，细节用链接指向别的文档。这个做法叫“渐进式披露”—— 需要时再展开，不要一次全塞进去。
  • 各工具的原生文件另有名字：Claude Code 用 CLAUDE.md，Gemini CLI 用 GEMINI.md，GitHub Copilot 用 .github/copilot-instructions.md，Cursor 用 .cursor/rules。但 AGENTS.md 是跨工具通用的那个。
  • 最有价值的往往是禁止事项那一段。 有分析发现，在真实项目的 AGENTS.md 里，最有效的指令常常就是“不要提交密钥”这类最简单的边界说明。本项目的完整模板见项目 AI 协作规范。

2. 让它起草 AGENTS.md 的初稿 ​

text
这是我的项目：学生会用的校园活动管理后台，Vue 3 单页应用，
技术栈是 Vue 3.5 + Vite 8.3 + Vue Router 5.3 + Pinia 4.0 + Element Plus 2.14，
包管理器统一用 pnpm。

请起草一份 AGENTS.md，包含这几节：常用命令、技术栈、目录约定、
接口约定、禁止事项、提交规范。

要求：
1. 控制在 100 行以内，不要写成教程
2. 接口约定这一节先留空占位，我等下自己填
3. 禁止事项写 5 条，每条后面用括号注明“违反了会出什么问题”
4. 不要写“代码必须无 bug”“性能要最优”这类无法验证的条目

为什么这么写：第 3 点是这份模板真正的价值所在 —— 一条禁止事项如果不写清“违反了会怎样”，它就不会被人当回事。第 4 点是在提前堵住一个常见毛病，见下面“容易错什么”。至于接口约定留空，是因为约定只能从你的后端拿，让 AI 猜出来的字段名是假的。

写完自己过一遍：每一条都要能对上你们项目的实际写法。对不上就改，别留着。

3. 让它按提交规范写提交信息 ​

text
我要提交这些改动，请按 Conventional Commits 格式给我写提交信息：

改动的文件：
- src/views/ActivityListView.vue（加了活动状态筛选）
- src/components/StatusTag.vue（新建，显示活动状态标签）

项目约定：type 取 feat、fix、docs、style、refactor、chore，
格式是 <type>(<scope>): <subject>，subject 用中文简述做了什么。

给我三个候选，并说明每个候选里 type 为什么这么选。

为什么这么写：要求它解释“type 为什么这么选”，是因为提交信息里最容易含糊的正好是 type —— 加一个筛选功能到底算 feat 还是 refactor，取决于算不算新增能力。让它说理由，你才能判断它选得对不对。格式对了但 type 选错，搜索历史记录时照样找不到。

4. 让它解释一条检查报错 ​

text
我的 ESLint 报了这个：

[完整粘贴，包含规则名那一行]

这是我的 eslint.config.js：

[粘贴配置文件]

我看了规则的说明但没看懂它在防什么。
请按这个顺序讲：
1. 这条规则在防什么错误，给一个会触发它的代码例子
2. 我这个文件里具体是哪一行触发的，为什么
3. 两种改法各是什么，改完行为有没有变化

如果这条规则名不存在或者说错了，直接告诉我，不要解释。

为什么这么写：最后那句是这一节最有用的一句。配置类内容里，规则名写错是常态，而写错的表现是没有报错。 明确告诉它“名字不对就直接说”，比让它顺着一个错名字编出一段解释强得多。

AI 在这一章容易错什么 ​

用已经废弃的 ESLint 配置写法 ​

现象：它给你的配置文件叫 .eslintrc.json 或 .eslintrc.cjs，里面有 env、extends: ["eslint:recommended"]、parserOptions 这些字段。文件格式看着很正式，但现在的 ESLint 已经不按这套读。

原因：.eslintrc 那套写法存在了很多年，训练数据里占绝大多数。ESLint 后来改成了扁平配置（eslint.config.js），写法完全不同，但它给老写法更顺手。

怎么处理：以官方文档的 Getting Started 为准，不要以它的回答为准。 判断办法很简单：看它的配置里有没有 export default [...] 这种数组导出 —— 有就是扁平配置，这才是当前的写法。两个写法不要混着用，混用会出现“配置里有这条规则但不生效”这种最难查的问题。

提交信息写成 update code ​

现象：它帮你想的提交信息是 update code、fix bug、修改了一些问题。

原因：这类信息在开源仓库里极其常见，它自然就跟着写了。它不知道你们组要用提交历史做检索。

怎么处理：把格式要求写进 AGENTS.md 的“提交规范”一节，这样它每次都会读到。格式定成 <type>(<scope>): <subject>，type 取 feat、fix、docs、style、refactor、chore。

判断一条提交信息合不合格，有一个很实用的标准：半年后你只看这一行，能不能知道这次改了什么。 update code 显然不行，feat(activity): 活动列表增加状态筛选 可以。

生造一条并不存在的规则名 ​

现象：配置里写着 "no-unused-variable": "error" 或者 "vue/no-lost-var"。名字看着很像真的，但 ESLint 不认识它。

原因：这是幻觉依赖的另一种形态 —— 按命名规则拼一个。规则名通常由“插件名/规则名”两段组成，它拼的时候常常把插件前缀漏掉或多加一个。

怎么处理：配完一定要做一次故意违规的提交。 这是唯一可靠的验证办法，和单元 3 正文里说的同一件事：故意写一个格式错、又有语义问题的文件，提交一次，看它有没有被拦下。被拦下了就说明配置真的生效了；提交居然通过，就说明某个环节是假的。

还有一类错误：起草的 AGENTS.md 里写“不可能被执行的约束”

现象：它给你写下的约定是“代码必须完全无 bug”“性能要尽可能最优”“注释要写得完整清楚”“遵循最佳实践”。

原因：这些话在各类规范文档里高频出现，它顺手就抄进来了。但它们有一个共同问题：无法验证。

怎么处理：一条约定要能被执行，得满足两个条件 —— 有人能判断它有没有被违反，违反了能被指出来。

对照一下：

不合格的约定改成什么样
代码必须无 bug提交前跑 pnpm test，通过才提交
性能要最优列表页首屏请求控制在 3 个以内
注释要完整只给 domain 下的规则函数写注释，说明判断依据
遵循最佳实践组件统一用 script setup，不用选项式 API

右边这些的共同点：能被检查，也能被拒绝。 写完 AGENTS.md 让 AI 审一遍，专门问它“哪几条是你判断不了有没有被违反的”，这个提问能筛掉一大半空话。

怎么验收 AI 的产出 ​

这一章的产出是配置文件，验收动作全部落在“真的生效了吗”上面。逐条过：

  • [ ] 它给的配置文件格式与官方文档一致，没有出现 .eslintrc 这种旧写法
  • [ ] 它提到的每个规则名，都在官方规则列表里查到了
  • [ ] 它提到的每个包名，都用 npm view <包名> version 确认过存在
  • [ ] 配置里的每条规则，你都故意写一段违规代码验证过它真的报错
  • [ ] 提交钩子链路的三个环节都验证过：husky 装上了、lint-staged 配上了、故意提交被拦下了
  • [ ] 它起草的 AGENTS.md 里，每条约定你都能说出“违反了会出什么问题”
  • [ ] AGENTS.md 里的 API 约定，与你后端实际返回的字段逐个核对过
  • [ ] 提交信息按约定格式写过一次，并能在 git log 里看懂

前四条对应“配置真的生效了”，中间两条对应“约定是真的、不是抄的”，最后两条对应“规范已经用起来了”。这八条过完，这个工程模板才能拿去做第 11 周的综合项目。

练习 ​

起草你们的 AGENTS.md，再让 AI 审一遍 ​

任务：为你和搭档的仓库写一份 AGENTS.md，先用 AI 起草，然后逐条核实，最后让 AI 专门找出“判断不了有没有被违反”的条目。

要求：记录里必须包含这四项：

项要求
AI 的初稿完整保留，不要只留你改完的版本
你改掉/删掉的条目逐条写清为什么删（对不上实际？无法验证？）
你补上的条目每条注明依据，比如“因为我们的成功码是 0 不是 200”
二次审查结果让 AI 找“无法验证的约定”，看它找出来的和你自己找的重合多少
验收标准与参考思路

为什么要留 AI 的初稿：只留下你改完的版本，就看不出它在哪几类内容上最容易跑偏。留着初稿对照，你下次就知道该在提示词里提前堵住什么。这是这一节练习的真正收获。

思路提示：

  • 提示词里别让它猜接口约定。字段名、成功码、错误码只能从后端拿。它猜出来的字段名看着合理，联调时会以最难看的方式暴露出来。
  • 专门检查“禁止事项”那一段。本项目的五条禁止事项对应五个真实容易出问题的地方（改拦截器、写密钥、删未确认引用的代码、改规则函数签名、加新依赖），你可以先看项目 AI 协作规范里的对照表，再判断你们组还需要加哪几条。
  • 篇幅自己数一下行数。超过 200 行就说明你没在用“渐进式披露”，细节该用链接指出去。
  • 写完让 AI 审的时候，问题要问具体：不要问“这份文件写得好不好”，要问“哪几条是你判断不了有没有被违反的”。 前一个问题它只会夸你，后一个问题它能给出有用清单。

不合格的写法：

让 AI 写了一份 AGENTS.md，看了看挺全面的，就提交了。

“挺全面”不是标准。一份抄来的、每一条都对不上你们项目实际的约定文件，比没有更糟 —— 因为 AI 会照着它执行，而它执行的是错的。

合格的写法：

AI 的初稿里有个字段名 activityStatus，我查了后端返回的是 status，改过来了。 它还写了“接口统一用 try/catch 包裹”，这条我删了 —— 我们的请求层在拦截器里统一处理错误，页面里 catch 是多余的。 我补了一条“不要在 views 下建二级子目录放同一个模块的组件”，因为上周已经有同学这么干了，评审时才发现。 二次审查时我让它找无法验证的条目，它指出了“代码要写得清晰易懂”这一条，我也删掉了。

差别在于：后者每一条改动都能说出依据，说明这份文件真的对应着他们的项目。
