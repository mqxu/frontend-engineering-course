单元 11 课后练习 ​

这个单元的练习全部围绕综合项目，做完之后的产物可以直接进项目仓库。

练习分两部分：

  • 必做：跟上课程进度走的四道题，做完能保底跑通活动管理模块。
  • 选做：想拿高分的同学做，覆盖更细的边界情况。

每道题下面有验收标准表。自己先跑一遍验收标准，再交。 老师检查时就是按这张表逐项验的。

必做 1：补全页面清单与接口清单 ​

要求 ​

为“场次与场地”和“报名审核”两个模块，各写一份清单文档，包含四张表：

  1. 实体表 —— 有哪些实体、每个实体有哪些关键字段
  2. 动作表 —— 谁能对实体做什么、做完状态怎么变
  3. 页面清单 —— 页面、路由、主要接口、可访问角色
  4. 路由表 —— 直接可以贴进 routes.js 的代码

保存为 docs/design/module-session.md 和 docs/design/module-signup.md（放在你自己的项目仓库里，不是教程站点里）。

验收标准 ​

检查项通过标准
实体判断有依据每个实体的判断理由能说出来（有自己的 id、会被单独查询）
流程和标记分开了状态字段是单向流程，下架 / 启用这类是独立标记
页面职责不重叠不存在两个页面做同一件事
新增和编辑共用组件路由表里两条路由指向同一个组件文件
静态路由在动态路由前面create 写在 :id 前面
清单能互相反推页面清单的每个接口都在接口清单里，接口清单没有孤儿接口
标出了需要跨表判断的动作“占用场地”这类要查别的数据才能判断的动作有标注
参考思路

场次模块的实体：场次（Session）、场地（Venue）。

“场次”是独立实体，不是活动的数组字段 —— 因为它有自己的 id，需要被单独查询（“查今天在体育馆的所有场次”）。

有个容易搞错的地方：“场次时间”是场次的字段，不是实体。 但“时段冲突”这条规则意味着场次之间会互相影响，这在动作表里体现为：“占用场地”这个动作的成功条件包含一次查询，不是简单的字段校验。

场次的动作表：

动作谁做结果状态怎么变
新增场次组织者占用一个场地时段无 → 已安排
修改场次时间 / 场地组织者换时段或换场地，需要重新检查冲突已安排 → 已安排
取消场次组织者、审核员释出时段已安排 → 已取消
开始 / 结束系统（按时间）场次进入进行中 / 已结束已安排 → 进行中 → 已结束

注意“修改场次”这个动作：它不是“改了字段”，而是“换一个时段占用”。这两个动作在冲突检测上的逻辑不同 —— 修改时要排除自己（否则自己和自己冲突）。

这个细节在业务规则里有说明，不排除自己是一个非常经典的 bug。

报名审核模块的实体：报名记录（Signup）、审核记录（AuditLog，可选）。

审核记录要不要单独一张表，取决于需求要不要留痕。先问清需求再决定，不要默认加表。

必做 2：搭出完整的工程骨架 ​

要求 ​

建一个 Vite + Vue 3 工程，达到下面的状态：

  • 目录结构符合 11.2 的规划
  • 路由表覆盖至少“登录 + 活动管理 + 报名审核 + 场次与场地 + 数据看板”五个入口
  • 后台布局能跑起来：侧边栏、顶栏、面包屑、内容区
  • 菜单能点、能高亮（包括详情页和编辑页）
  • 未登录访问后台页面会被跳到登录页
  • 浏览器标签页标题跟着页面变

验收标准 ​

检查项怎么验证
登录页没有侧边栏访问 /login，看不到菜单
后台页面有侧边栏访问 /dashboard，左侧菜单、顶部面包屑都在
菜单能跳转点每个菜单项，地址栏和内容区都跟着变
详情 / 编辑页菜单仍高亮直接访问 /activity/create，侧边栏“活动管理”是高亮的
面包屑跟着变从列表进编辑页，面包屑变成“活动管理 / 编辑活动”
未登录会被拦清掉本地 token，访问 /activity，跳回 /login 且带 ?redirect=
只有内容区滚动把一个页面内容撑长，侧边栏和顶栏固定不动
宽表格不撑破布局表格列数多时，横向滚动条出现在内容区内部
标签页标题跟着变切页面，看标签文字
目录结构符合规划views/ 按业务模块分，api/ 按模块分文件
没有三级以上的相对路径全局搜 ../../，应为 0 结果
没有提交 node_modulesgit ls-files | grep node_modules 应为空
参考思路

最后一个检查项很容易漏。 如果发现已经提交了：

bash
git rm -r --cached node_modules
git rm -r --cached dist
git commit -m "chore: 从仓库移除构建产物与依赖"

--cached 不能漏，漏了会连本地文件一起删掉。

“宽表格不撑破布局”这一项要主动造数据测。 往表格里加 12 列，或者把浏览器窗口缩到很窄。如果没测出来，说明你的测试数据不够极端 —— 加 min-width: 0 这件事，只有在内容真的溢出时才看得出区别。

必做 3：完成活动列表页 ​

要求 ​

按 11.4 的模板做 ActivityList.vue，包含：

  • 查询条件：关键字、状态（两个都要能用）
  • 表格：标题、类型、状态、报名情况、报名截止、操作
  • 行操作：详情、编辑、下架 / 恢复、删除
  • 分页：页码、每页条数
  • 四态齐全
  • 删除有二次确认，成功后自动刷新

数据可以先用 mock（本地假数据或 json-server），接口层按接口约定的真实路径写。

验收标准 ​

检查项怎么验证
查询能生效输入关键字点查询，看请求参数里有没有 keyword
查询后回到第 1 页翻到第 3 页，改状态筛选，点查询，看请求参数里 page 是不是 1
每页条数能改改成 20，回到第 1 页，列表显示 20 条
重置能恢复初始条件点重置，条件清空且列表刷新
加载中有反馈网络面板限速，看有没有 loading 遮罩
无数据状态有引导查一个不存在的关键字，看提示和“立即创建”按钮
失败状态有重试把接口地址改错，看错误信息和“重新加载”按钮
删除有二次确认点删除，看有没有确认弹窗
取消删除不请求接口点取消，看网络面板有没有发请求
删除后自动往前翻页翻到最后一页并删光该页数据，看是否自动回到上一页
下架后状态立刻变点下架，确认后看表格里的标签是否变成“已下架”
操作列按钮跟状态对上造一条“已结束”的活动，看“编辑”按钮是否消失
表格有 row-key检查代码里的 row-key="id"
参考思路

最容易漏的三项：查询后回第 1 页、删除后往前翻页、取消删除不发请求。

“取消删除不请求接口”这一项，需要在 ElMessageBox.confirm 的 catch 里 return：

js
try {
  await ElMessageBox.confirm('确定删除吗？')
} catch {
  return   // ← 用户取消，直接返回，不要往下走
}
await deleteActivity(row.id)

漏了这个 return 的后果是：用户点了取消，删除照样执行。这是最危险的一类 bug —— 用户以为没删，其实删了。

ElMessageBox.confirm 在用户点取消时是 reject，所以 catch 是“用户取消”而不是“出错了”。这个语义容易误解，记住它。

必做 4：完成活动表单页 ​

要求 ​

做 ActivityForm.vue，新增和编辑共用，包含：

  • 字段：标题、类型、名额、报名截止时间、活动说明
  • 校验：必填、长度、名额为正整数、截止时间晚于当前时间
  • 编辑模式下：名额不能小于已通过人数、截止时间只能往后退
  • 提交：submitting 状态、防重复提交、成功提示、失败不跳转
  • 未保存离开提醒

验收标准 ​

检查项怎么验证
新增和编辑是同一个文件views/activity/ 下只有一个 ActivityForm.vue
新增模式字段为空访问 /activity/create，所有字段是空的
编辑模式字段有值从列表点编辑，字段都回填了
必填校验能触发什么都不填点提交，看有没有红字
标题长度校验输入 1 个字符，看是否提示
名额整数校验输入 2.5，看是否被拦
截止时间校验选一个过去的时间（手动输入绕过置灰），看是否报错
提交按钮有 loading点提交，看按钮是否变 loading
连点两次只创建一条快速点两次提交，看列表里是不是只有一条
校验失败不请求接口填错一个字段后提交，看网络面板有没有发请求
提交失败按钮恢复把接口地址改错，提交失败后按钮能再点
提交成功有提示并跳转看是否提示并回到列表
提交成功后列表有新数据回列表，看有没有刚创建的活动
编辑时名额下限生效造一条已有 5 人通过的活动，把名额改成 3，看是否报错
离开未保存表单有提醒填一个字段，点侧边栏菜单，看有没有确认弹窗
提交成功跳转不弹提醒提交成功时不应弹“未保存”提示
参考思路

“校验失败不请求接口”和“提交失败按钮恢复”这两项最容易漏。

校验失败不请求接口 —— 关键是 validate() 要 await 并包 try：

js
try {
  await formRef.value.validate()
} catch {
  return   // ← 校验失败直接返回
}

提交失败按钮恢复 —— 关键是 submitting 放 finally：

js
submitting.value = true
try {
  await createActivity(form)
  // 成功后的跳转
} finally {
  submitting.value = false
}

“编辑时名额下限”这一项需要造数据。 造一条 quota = 10、approvedCount = 5 的活动。如果后端没提供这个数据，可以先在前端临时写死 originalApprovedCount.value = 5 测一遍校验规则，测通了再接接口。

“离开未保存有提醒”测的时候要注意：先填一个字段（触发 dirty），再点菜单。如果直接点菜单，dirty 还是 false，不会弹窗 —— 这不是 bug，是正确行为。

选做 1：把列表和表单抽成可复用的“页面模板” ​

要求 ​

把列表页的标准做法抽成三个通用件：

  • useTable（11.4 已经给了，可以再改进）
  • StateWrapper.vue：统一处理加载中与失败状态
  • useFormPage.js：统一处理新增 / 编辑共用的表单逻辑

然后用这套通用件重写一遍活动列表页和表单页，对比重写前后的代码量。

验收标准 ​

检查项通过标准
三个通用件都有文件存在且能独立说明职责
重写后代码量减少给出前后行数对比（用 wc -l）
通用件有默认行为不传可选配置也能跑
通用件没有写死业务里不出现 activity、Activity 这类业务词
有说明文档写清每个通用件的参数和适用场景
参考思路

“通用件里不出现业务词”是最重要的验收点。

如果你的 useTable 里出现了 activityStatus、signupDeadline 这种字段名，那它就不是通用的，只是把活动列表的逻辑换了个地方放。判断方法：把 useTable 用在报名列表上，需要改它吗？ 需要改就说明抽象失败了。

关于“代码量减少”这一项，注意别为了减行数把代码压成一行 —— 下面这种写法不叫复用，叫炫技：

js
// ✗ 行数少了，但没人能看懂
const { q, l, ld, e } = useTable(f, { q: { k: '', s: '' } })

验收时看的是“新增一个列表页需要写多少行”，不是现有文件多少行。抽完之后，写报名列表页应该只需要写“请求函数”和“列定义”两件事。

选做 2：给列表页加上批量操作 ​

要求 ​

活动列表支持多选，选中后可以：

  • 批量下架
  • 批量删除（只有全为草稿时才允许）
  • 跨页保留勾选

验收标准 ​

检查项怎么验证
能多选勾选几行，看底部/顶部有没有显示选中数量
批量下架生效勾 3 条，点批量下架，看 3 条状态都变了
批量删除有条件限制选中包含“报名中”的活动时，批量删除按钮应禁用并说明原因
跨页保留勾选第 1 页勾 2 条，翻到第 2 页，之前勾的还在
翻页后能正确清空提供一个“清空选择”的入口
全选只选当前页点表头全选，只勾选当前页（不要跨页全选）
参考思路

跨页保留勾选靠的是 row-key + reserve-selection：

vue
<el-table-column type="selection" :reserve-selection="true" width="48" fixed="left" />

reserve-selection 必须配合 row-key 才生效 —— 这就是 11.4 里强调 row-key 是标配的原因。

**“点表头全选只选当前页”**是 el-table 的默认行为。想改成跨页全选需要自己实现（把所有页的数据都拿到前端，但那样就失去了分页的意义）。默认行为是对的，不要改。

批量操作有部分失败怎么办？ 这是这道题真正要思考的地方。三种做法：

做法好处代价
全部成功才提交（事务）数据一致一条失败全部回滚，用户要重来
逐条提交，报告成功 / 失败数能部分完成数据处于“部分完成”状态，要跟用户解释
后端提供批量接口一次请求，后端控制事务需要后端支持

这道题推荐让后端提供批量接口。 如果后端只能逐条处理，前端要等所有请求结束再统一提示：

js
const results = await Promise.allSettled(ids.map((id) => setActivityOffShelf(id, true)))
const failed = results.filter((r) => r.status === 'rejected').length
if (failed === 0) {
  ElMessage.success(`已下架 ${ids.length} 条活动`)
} else {
  ElMessage.warning(`成功 ${ids.length - failed} 条，失败 ${failed} 条，请重试失败项`)
}

Promise.allSettled 和 Promise.all 的区别要记清楚：all 遇到第一个失败就整体 reject，allSettled 会等全部完成并给出每一项的结果。批量操作要用 allSettled。

选做 3：给项目写一份设计文档 ​

要求 ​

在项目仓库里写 docs/design/DESIGN.md，包含：

  1. 项目背景与目标用户
  2. 页面清单与路由表（必做 1 的成果）
  3. 数据模型（实体、字段、关系）
  4. 状态机说明（用文字或图）
  5. 目录结构说明
  6. 关键设计决策（每条写清“选了什么 / 为什么 / 代价是什么”）
  7. 已知限制与后续计划

验收标准 ​

检查项通过标准
设计决策有取舍说明每条决策都写了“代价是什么”
状态机表述无歧义能据此写出 canSignup(activity) 这个函数
数据模型有字段类型不是只写字段名
已知限制诚实至少 3 条，且是真的限制
没有空话不出现“提升用户体验”“架构清晰”这类无法验证的说法
参考思路

这份文档最有价值的部分是第 6 条“关键设计决策”。

举几个这个项目里真实存在的决策：

决策选了什么为什么代价
活动与场次的关系场次独立成实体一个活动多个场次，需要单独查询时段冲突多一张表、多一组接口
下架的表示方式独立字段 offShelf下架与报名状态是两个维度，混在一起会出现状态冲突每个“能不能报名”的判断要检查三个条件
新增 / 编辑共用组件共用一个 ActivityForm.vue字段完全相同，避免重复维护校验规则组件内部要靠 isEdit 分支，逻辑复杂度上升
状态文案的存放统一放 utils/dict.js列表、详情、看板多处使用，改文案只改一处加一个状态要改三个地方（枚举、label、tagType）

“代价”这一列是这份文档的核心。 只写“我选了 A，因为 A 好”，那是宣传不是设计。能说出代价，才说明你真的想过。

第 7 条“已知限制”也要诚实写。 比如“目前报名不支持候补”“场地冲突检测未考虑准备时间”“没有做操作日志”。

把限制写出来不会扣分，藏着才会。 老师一看就知道你有没有从“能跑”想到“能不能用”。

选做 4：挑出一个真实存在的坑并写清楚 ​

要求 ​

在你自己写代码的过程中，至少会遇到一个“现象 - 原因 - 处理”完整的坑。把它写清楚，要求：

  • 现象可以被复现（写清复现步骤）
  • 原因分析到源码或规范层面，不停留在“反正就是这样”
  • 处理方式给出代码
  • 说明同类问题以后怎么避免

验收标准 ​

检查项通过标准
现象可复现步骤写清楚，别人照着能复现
原因有依据引用了官方文档，或给出了自己的验证过程
处理方式给代码不是“注意一下就好”
有预防措施写清下次怎么不踩
参考思路

这个项目里常见的几个坑，可以挑一个验证：

  • el-menu 的 default-active 名字里带 default，但它其实支持响应式更新。为什么？
  • min-width: 0 为什么能让 flex 子项内部的宽内容变成内部滚动？不加时的实际表现是什么？
  • KeepAlive 的 include 为什么要匹配组件的 name 而不是文件名？用 <script setup> 写的组件为什么默认没有 name？
  • :key="route.path" 让组件重建，那 KeepAlive 还有效吗？两个一起用会怎样？

“原因分析到源码或规范层面”这条要求的意思是：不要写“因为 Vue 的设计就是这样”，要写清“因为 computed 的依赖收集发生在求值时，而 route.meta 是一个响应式对象，所以……”。

验证过程可以是这样：

  1. 先写出你的猜测
  2. 设计一个能证伪的测试（改一行代码，看现象是否消失）
  3. 记录结果
  4. 如果猜测错了，把错的那个也写进去 —— 推翻自己的过程比结论更有说服力

最后一条提示：这类“踩坑记录”是技术简历里很值钱的东西。面试官问你“遇到过什么难题”，能讲清楚一个真实的坑，比背十道八股题都管用。
