11.1 从需求到页面清单 ​

一段真实的业务描述 ​

假设学院的老师给你这样一段话：

我们想给学生会做一个活动管理的后台。组织者可以创建活动，填标题、类型、报名截止时间、名额， 发布之后学生就能报名。学生报名了不能直接算数，得组织者审核，通过的才算占名额。 名额满了之后报名入口要关掉，不能再报了。有些活动要办好几场，不同的场次用不同的场地， 但同一个场地同一时段不能冲突。审核员能看到所有人的活动，组织者只能看自己的。 最后有个页面能看整体数据，比如一共多少活动、多少报名在等审核。

这段描述里没有一个技术词，但它是你能拿到的全部信息。 学生看到这段话最常见的反应是：

看懂了。然后呢？我该先建哪个文件？

问题不在理解，在从"业务描述"到"代码结构"中间缺了一步。这一步不写清楚，你会在后面反复推翻自己：做到一半发现“报名审核”既可以放在活动详情里，也可以单独做一个菜单，选哪个？

所以这一节只做一件事：把这段描述变成三份可以照着敲代码的清单。

三步拆解 ​

拆解的顺序是固定的：先找实体，再找动作，最后定页面。

顺序不能换。先想页面，你会拆出一堆职责重叠的页面；先想实体，页面自然就出来了。

第一步：找实体 —— 有哪些"东西" ​

从描述里圈出名词。凡是能单独存一张表、能单独发一个接口的，就是实体。

实体从描述哪里来关键字段
活动 Activity“创建活动，填标题、类型、报名截止时间、名额”标题、类型、组织者、报名截止时间、名额、状态
报名记录 Signup“学生报名了……得组织者审核，通过的才算占名额”学生、学号、关联活动、审核状态、报名时间
场次 Session“有些活动要办好几场”关联活动、开始时间、结束时间、场地
场地 Venue“不同的场次用不同的场地”名称、容量、位置
用户 User“组织者”“审核员”“学生”账号、姓名、角色

判断标准：这个东西有没有自己的身份（需要一个 id）？会不会被单独查询？会 → 是实体。

一个实用的自检

实体表写完之后，问自己：这段描述里，哪些词经常和另一个词一起出现？

“报名记录”总是和“某个学生”和“某个活动”一起出现 —— 它有自己的 id，所以是实体。 “报名截止时间”只跟着活动走，离开活动它没有意义 —— 所以它是活动的字段，不是实体。

这个判断错了会很难受：把“报名截止时间”做成实体，你会多出一张表、一组接口、一个可能不需要的页面。

第二步：找动作 —— 每个实体上发生什么 ​

对每个实体，问三个问题：谁能对它做什么？做的结果是什么？做完之后它的状态变了吗？

以“活动”为例：

动作谁做结果状态怎么变
创建组织者生成一条草稿无 → 草稿
编辑组织者字段被改草稿 / 报名中都可以改
发布组织者学生能看到并报名草稿 → 报名中
下架组织者、审核员学生看不到状态不变，下架标记置为真
报名截止系统（按时间）报名入口关闭报名中 → 报名截止
结束系统（按时间）归档报名截止 → 已结束

这张表有两个用处：

一、它直接决定按钮。 表格里有多少个“人能做的动作”，页面上就有多少个按钮。

二、它暴露了状态机。 把“状态怎么变”那一列连起来，就是活动状态机：

草稿 ──发布──> 报名中 ──到截止时间──> 报名截止 ──活动结束──> 已结束
                 └──── 下架（独立标记，不改状态）────┘

状态机写错，是后台项目最常见的设计错误

新手容易把“下架”当成一个状态，写成：

草稿 → 报名中 → 已下架 → 报名截止 → 已结束

这样写会导致一个问题：下架的活动到截止时间之后，该变成“已下架”还是“报名截止”？ 两个状态冲突了，只能加 if 判断打补丁。

正确的做法是把两件不同的事分开：

维度取值由谁决定
状态 status草稿 / 报名中 / 报名截止 / 已结束由时间和发布动作决定，单向往前，不回退
下架标记 offShelftrue / false由人来决定，随时可以来回切

一个活动的“能不能报名”，等于“状态是报名中”并且“没有被下架”并且“名额没满”。 三个独立条件分开判断，比揉成一个状态清楚得多。

这个思路在很多地方都能用：订单的“已支付”和“已退款”、文章的“已发布”和“已置顶”、用户的“已禁用”和“未实名”—— 一个是流程，一个是标记，不要混在一起。

第三步：定页面 —— 每个动作放哪 ​

现在把动作分配到页面上。分配规则是三条：

规则一：读一个实体，一个页面。 列表、详情各一个。

规则二：写一个实体，一个页面组件，两种用法。 新增和编辑字段完全相同，用同一个组件，靠路由参数区分。

规则三：动作太多就分出去。 如果一个页面上要同时处理活动本身和它的报名记录，说明该拆了。

按这三条规则，“活动管理”模块拆出来是：

页面路由职责动作
活动列表/activity查询、分页、看状态下架 / 恢复 / 删除
活动详情/activity/:id看完整信息跳去编辑、跳去报名列表
新增活动/activity/create填字段并保存存草稿 / 存并发布
编辑活动/activity/:id/edit改字段保存
报名列表/activity/:id/signups看这个活动的报名通过 / 驳回

注意“新增”和“编辑”是两条路由，但共用一个组件。 组件内部靠 route.params.id 有没有值来判断当前是哪种模式：

js
// src/views/activity/ActivityForm.vue
const route = useRoute()
const activityId = computed(() => route.params.id)
const isEdit = computed(() => Boolean(activityId.value))

分工是：“报名列表”虽然属于活动，但它操作的是报名记录，所以它不属于活动模块，归到报名审核模块。判断归属看它操作哪个实体，不看它挂在哪个路由下。

三份清单长什么样 ​

拆完之后输出三份表格。这三份表就是你接下来写代码的全部依据。

清单 A：页面清单 ​

页面路由主要接口可访问角色
登录/loginPOST /api/auth/login未登录
活动列表/activityGET /api/activities组织者、审核员
活动详情/activity/:idGET /api/activities/:id组织者、审核员
新增活动/activity/createPOST /api/activities组织者
编辑活动/activity/:id/editPUT /api/activities/:id，GET /api/activities/:id组织者

清单 B：路由表 ​

页面清单直接翻译成路由表，注意层级关系：

js
const routes = [
  { path: '/login', component: () => import('@/views/login/LoginView.vue') },
  {
    path: '/',
    component: () => import('@/layouts/AdminLayout.vue'),
    redirect: '/dashboard',
    children: [
      {
        path: 'activity',
        children: [
          { path: '', name: 'activity-list', component: () => import('@/views/activity/ActivityList.vue') },
          { path: 'create', name: 'activity-create', component: () => import('@/views/activity/ActivityForm.vue') },
          { path: ':id', name: 'activity-detail', component: () => import('@/views/activity/ActivityDetail.vue') },
          { path: ':id/edit', name: 'activity-edit', component: () => import('@/views/activity/ActivityForm.vue') }
        ]
      }
    ]
  }
]

子路由的顺序有讲究

create 必须写在 :id 前面。

因为 :id 会匹配任意一段路径，如果 :id 在前面，访问 /activity/create 时它会被当成 id === 'create' 的详情页 —— 页面报错，你还得花十分钟才想明白。

规则：静态路径写在动态参数前面。

清单 C：接口清单 ​

方法路径用途请求参数
GET/api/activities活动列表keyword、status、page、pageSize
GET/api/activities/:id活动详情路径参数
POST/api/activities新增活动活动对象
PUT/api/activities/:id编辑活动活动对象
PATCH/api/activities/:id/offshelf下架 / 恢复{ offShelf: boolean }

这份清单和页面清单是双向往返的。 检查方法：页面清单每一行的“主要接口”列，都应该能在接口清单里找到；接口清单里每一个接口，都应该有页面在用它。有孤儿接口，说明你漏了一个页面。

完整的接口约定（含字段名、字段类型、错误码）在综合项目 · 接口约定。

一个例子：把“报名审核”拆一遍 ​

上一节用活动管理演示了完整过程。现在换你自己走一遍，用同样的三步拆“报名审核”。

第一步找实体。 报名记录（已有）、审核记录（要不要单独存？）。这里有个判断：如果只看“最新审核结果”，那审核状态直接放在报名记录上就行；如果要留痕（谁在什么时候批的、改过几次），就要单独一张审核记录表。先问清楚需求再决定，不要默认加表。

第二步找动作。

动作谁做结果状态怎么变
报名学生生成一条待审核记录无 → 待审核
通过组织者、审核员占掉一个名额待审核 → 已通过
驳回组织者、审核员释放名额，可填驳回理由待审核 → 已驳回
撤销报名学生记录作废待审核 / 已通过 → 已取消

第三步定页面。

页面路由职责
报名列表/signup跨活动的报名查询，按状态筛
某活动的报名/activity/:id/signups单个活动的报名，审核操作更密集
报名详情/signup/:id看学生信息与历史

注意“通过”这个动作和名额的联动：通过之后要判断名额是否已满，满了就把活动的报名入口关掉。 这个逻辑放在前端只是提示，真正的判断必须在后端做 —— 两个组织者同时点“通过”，前端拦不住。这一点在业务规则里有完整说明。

小结 ​

  • 从需求到代码的第一步不是建文件，是拆清单。 顺序固定：找实体 → 找动作 → 定页面。
  • 实体判断标准：有自己的 id、会被单独查询。满足两条就是实体，不满足就是别人的字段。
  • 动作表直接决定按钮，状态流转直接决定状态机。 状态机是后台项目最容易出错的地方。
  • 流程和标记要分开。 状态是单向的流程，下架 / 置顶 / 禁用是随时可切的标记，不要混成一个字段。
  • 页面拆分三条规则：读一个实体一个页面；写一个实体一个组件两种用法；动作太多就分出去。
  • 新增和编辑共用组件，靠路由参数区分，不要写两份几乎一样的表单。
  • 三份清单要能互相反推。 页面清单 → 路由表 → 接口清单，任何一份对不上，说明拆的时候漏了东西。

常见坑 ​

页面拆得太细，做完发现有一半页面没人进

现象：拆出十几个页面，做到后面发现“活动标签管理”“活动模板”这些页面自己都不想去写。

原因：拆页面时按“可能有的字段”而不是“确实要做的动作”拆。描述里没提过的功能，不应该出现在你的清单里。

怎么处理：拆完清单后做一次削减 —— 对每个页面问“删掉它，主线还能跑通吗？”能跑通的先标成“可选”。先做能跑通主线的页面，剩下的有空再说。课程项目的评分看的是主线完整度，不是页面数量。

新增和编辑写了两个几乎一样的组件

现象：ActivityCreate.vue 和 ActivityEdit.vue 各两百行，除了初始化数据的方式不同，其余完全重复。改一个校验规则要改两处。

原因：一开始觉得“新增和编辑是两件事”，于是建了两个文件。

怎么处理：合并成一个 ActivityForm.vue。区别只有两处：① 进页面时是否要先拉详情回填；② 提交时调 POST 还是 PUT。用 const isEdit = computed(() => Boolean(route.params.id)) 判断，两处各写一个三元表达式就够了。

js
// 初始化：编辑模式才拉详情
onMounted(async () => {
  if (isEdit.value) {
    const { data } = await getActivityDetail(activityId.value)
    Object.assign(form, data)
  }
})

// 提交：编辑用 PUT，新增用 POST
const submit = async () => {
  await formRef.value.validate()
  isEdit.value
    ? await updateActivity(activityId.value, form)
    : await createActivity(form)
}
路由写好了，但刷新页面 404

现象：在应用内点菜单跳转正常，直接刷新 /activity/create 就 404。

原因：开发服务器需要 history 模式的回退配置。Vite 自带这个能力，多数情况下不用管；但如果部署到 Nginx 或静态托管，就必须配 try_files 把未知路径回退到 index.html。

怎么处理：本地开发先确认 createWebHistory() 用的是默认配置；部署时的配置见12.3 部署上线。这个问题不要在单元 11 纠结，先记下来。

面包屑显示的是 id，不是标题

现象：/activity/42/edit 的面包屑显示“活动 / 42 / 编辑”，42 是什么完全看不出来。

原因：面包屑直接用 route.params.id 拼字符串。

怎么处理：面包屑要能读到实体的标题。两种做法：① 详情接口返回后在组件里用 provide 把标题传上去；② 路由 meta 里给一个通用的名字（比如统一显示“编辑活动”）。课程项目用第二种就够了，第一种留着以后需要时再加。具体写法见 11.3 布局骨架与嵌套路由。

清单里的接口，后端说“没有这个接口”

现象：照着自己拆的清单写完了，交给后端同学，对方说“这个接口我没打算做”。

原因：拆清单时没和后端对过。前端拆出来的页面清单，和后端拆出来的接口清单，几乎不可能一次对上。

怎么处理：清单是沟通工具，不是单方面产出。拆完第一时间去对一遍，重点问三个问题：① 列表接口的分页参数叫什么；② 状态字段用的是数字还是字符串；③ 下架这种小动作，是一个独立接口还是一个通用更新接口。

这份确认下来的结论就是接口约定，定完之后不要自己偷偷改，改一处要通知对方。

课后练习 ​

练习 1：为“场次与场地”模块拆三份清单

按这一节的三步法，拆出“场次与场地”模块的实体表、动作表、页面清单、路由表、接口清单。

思路提示：

  • 实体至少有“场次”和“场地”。想清楚场次和活动的关系 —— 一个活动有多个场次，所以场次是独立的实体，不是活动的数组字段。
  • 动作里有一个是“占用场地”，它的成功条件不是字段合法，而是时段不冲突。这类“需要查别的数据才能判断”的动作，要在接口清单里标出来。
  • 页面清单里，“场地管理”和“场次安排”是两个不同的入口，不要合成一个。
  • 时段冲突的完整规则（边界相接算不算冲突）见业务规则，照着写就行。
练习 2：找出下面这份清单的三个问题

某同学为“数据看板”拆出的清单：

页面路由主要接口
看板首页/dashboardGET /api/stats
活动统计/dashboard/activityGET /api/stats/activity
报名统计/dashboard/signupGET /api/stats/signup
场地使用统计/dashboard/venueGET /api/stats/venue
统计详情/dashboard/detail/:typeGET /api/stats/:type/detail

思路提示：先数一下描述里对看板的原始要求是什么（“一个页面能看整体数据，比如一共多少活动、多少报名在等审核”）。然后想三个问题：① 一个页面的需求拆成四个页面，是变好了还是变复杂了？② 路由参数 :type 用来切换统计类型，那么类型有哪些、每种类型的展示方式一样吗？③ 这四个页面共用一套布局和筛选条件，那它们应该是页面还是组件？

没有唯一正确答案。 这道题练的是“能说出为什么这么拆”，不是“拆得对不对”。

练习 3：把活动状态机的边界情况补全

业务规则里给的状态是“草稿 → 报名中 → 报名截止 → 已结束”。请补出下面这些情况该怎么处理，并说明理由：

  1. 报名中的活动，组织者点“下架”，状态变成什么？
  2. 报名的截止时间到了，但这条活动被下架了，状态该不该变？
  3. 已结束的活动，组织者想再开放一次报名，可以吗？
  4. 草稿状态的活动，能直接跳到“已结束”吗？

思路提示：回到这一节的核心判断 —— 哪些属于“流程”，哪些属于“标记”。第 1、2 题考的就是这个区分。第 3 题想一下“已结束”是终态还是可以回退的状态，如果允许回退，那“报名截止时间已过”这个约束还要不要再校验一次。第 4 题想一下“跳过中间状态”会不会让某些页面出现意料之外的数据（比如从未发布过的活动出现在“已结束”列表里）。
