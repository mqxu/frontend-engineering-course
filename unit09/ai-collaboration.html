单元 9 · AI 协作：前端的权限判断不是安全边界 ​

这一章讲登录与鉴权。AI 在这里能帮你不少 —— 守卫的骨架、退出登录要清哪些东西、401 之后怎么处理，它都能给出来。但有件事它容易说错，而且说错了后果不小：

它倾向于把前端的路由守卫说成“安全措施”。

路由守卫解决的是体验问题 —— 未登录的人不该看到后台界面，该被送到登录页。但它拦不住任何一个会发请求的人。你在浏览器控制台里敲一行代码就能绕过它，或者干脆不用浏览器直接调接口。

这一章要建立的判断是：守卫管界面，服务端管权限。 这两件事都做，不是因为“多做一层更保险”，是因为它们解决的根本不是同一个问题。

这一章哪些活能交给 AI ​

判断标准：整理和检索可以交；凡是“这算不算安全”的判断，一律自己下。

任务能交给 AI 吗为什么
检查守卫有没有漏处理边界情况可以边界情况有限，它能列全
搜索代码里有没有把 token 打印或拼进 URL可以检索类工作它做得快
解释四种守卫的执行顺序可以顺序是确定的，它讲得清
起草守卫的骨架可以当起点，具体规则要你填
起草退出登录的清理清单可以但要你对照项目实际情况增删
解释 afterEach 适合做什么可以这也是它容易建议错的地方，见下
判断“加了这个守卫就安全了吗”不能直接信它倾向把前端守卫说成安全措施
决定权限规则的具体内容不行取决于业务，而且要和后端对齐
决定 token 存在哪里不行涉及服务端能力与安全取舍

倒数第三行是这一章唯一必须记住的一句。 你不需要记住守卫有哪四种，翻文档就有；但你需要知道它在整体安全里处在什么位置，这个判断错了，后面写的代码全是错的。

提示词怎么写 ​

1. 让它审守卫的逻辑，重点是漏掉的边界 ​

text
这是我的路由守卫：

[粘贴完整代码]

请检查这几类边界情况分别处理了没有，没处理的给改法：
1. 未登录访问需要登录的页面
2. 已登录却访问登录页
3. 登录成功后回到原来想去的页面
4. 没有权限访问某个页面（登录了但角色不对）
5. 访问不存在的地址
6. 退出登录后，动态加进去的路由有没有被清掉

输出用表格：边界情况 / 处理了没 / 在哪一行 / 没处理的话会怎样。
另外单独说明：这些判断里，哪些属于“体验”，哪些真的挡住了什么。

为什么这么写：第 2 点是最常被漏的 —— 大部分人的守卫只写“未登录跳登录页”，忘了已登录的人点回登录页时会看到一个登录表单。这个边界不难处理，但不提醒就想不起来。

最后那句是这一章的核心追问。要求它把每一条判断归类成“体验”还是“真的挡住了什么”，它就没法笼统地说“这样写很安全”。你在读它的回答时，重点看它有没有把“跳转”当成“拦截”。

2. 让它检查 token 的存储与传递 ​

text
这是一段涉及 token 的代码：

[粘贴相关文件]

请逐项检查：
1. 有没有把 token 打印到控制台（console.log 及各种变体）
2. 有没有把 token 拼进 URL、写进 HTML、或者塞进不需要它的请求
3. 有没有把 token 硬编码在代码里（包括测试代码和注释）
4. token 的读写是不是集中在一个文件里，还是散落在各处

每一项给出：有 / 没有 / 在哪一行。没有问题的项也要写出来。
最后说明：这段代码里 token 存在哪，XSS 能不能读到它。

为什么这么写：第 4 点很实用。token 散落在各处时，将来换存储方式要全局搜索替换，一定会漏。集中的话只改一个文件。要求“没有问题的项也要写出来”，是为了避免它只报问题 —— 那样你会不知道剩下几项它是查了还是没查。

最后一句问“XSS 能不能读到”是刻意的。这是你想让它说清楚的事，而不是让它替你判断安全性。它回答“能读到，因为存在 localStorage”就够了，至于这个取舍能不能接受，是你和服务端一起决定的。

3. 让它讲清守卫能防到什么程度 ​

text
关于前端路由守卫，请回答两个问题：

一、它能拦住哪些人？（举三种，说明每种在什么情况下会被拦住）
二、它拦不住哪些人？（举三种，说明为什么拦不住，以及他们能直接做什么）

要求：不要用“前端守卫只是辅助”这类笼统说法，给具体的例子。
最后说清一件事：如果一个用户绕过守卫直接调接口，真正拦住他的是谁。

为什么这么写：这个问题值得单独问一次，因为它能一次性把“前端守卫 = 安全措施”这个误解拆掉。要求给三种具体的绕过方式 —— 比如在控制台里直接改内存状态、直接请求接口、把本地存的 token 换掉 —— 它就没办法只给一句“它只是辅助”。

最后的追问是收口：绕过守卫直接调接口的人，拦住他的是后端。 这句话是整个单元的落点。

AI 在这一章容易错什么 ​

把路由守卫当成权限控制的全部 ​

现象：你问它“这样写安全吗”，它回答“已经加了路由守卫，未登录用户无法访问后台页面，是安全的”。

原因：它评估的依据是“用户从界面走流程时能不能过去”。界面流程它看得见，直接发请求这件事它看不见 —— 它没有运行的客户端，也就没有“绕过”这个概念。

怎么处理：把这个误解拆成两半，各归各处：

问题谁解决
未登录的人不该看到后台界面路由守卫（体验）
未登录的人不能拿到数据服务端校验 token（安全）
角色不对的人不该看到某些菜单路由与菜单过滤（体验）
角色不对的人不能改数据服务端校验角色（安全）

左边这一列全都属于“体验”—— 做不好会让人困惑、点错、白跑一趟，但不会造成损失。右边才是真正拦住人的地方。

所以正确的说法是：守卫必须做，服务端校验也必须做，而且服务端那份是主，前端这份是辅。 前端的守卫漏了，用户会看到一个转圈然后报错；服务端的校验漏了，才是真出事。

答辩时怎么讲这一条

如果老师问你“你的权限控制怎么做的”，答“我加了路由守卫”是半句话。完整的答法是：

前端用路由守卫控制界面可见性，未登录跳登录页、角色不符跳 403 页面； 但前端的判断只是体验优化，真正拦住非法请求的是后端 —— 每个接口都会校验 token 和角色，前端传什么参数都不影响后端的判断。

这段话里的关键是最后半句。能主动说出“前端拦不住”，比把前端说得多严密更能证明你懂。

token 处理不当 ​

现象：代码里出现这些：

你看到的问题
console.log(token) 或 console.log(res.data) 打印了整个响应调试信息留在提交里，token 进了控制台历史
axios.get('/api/x?token=' + token)token 进了 URL，会被写进服务器日志和浏览器历史
const TOKEN = 'eyJhbGciOi...'硬编码，无法轮换，也可能进了版本库
把 token 写进 <meta> 或全局 HTML页面脚本能读到，等于放大了 XSS 的影响面

原因：前者是调试习惯，后三者都是“顺手”，功能上都能跑。

怎么处理：三条规矩。

  1. token 的读写集中在一个文件里（本项目是 src/utils/token.js）。这样将来换存储方式只改一处，也方便统一检查有没有泄漏。
  2. token 只走请求头。 本项目在请求拦截器里统一注入，页面代码里不出现 token 这个词。
  3. 调试时打印结构，不打印值。 想看返回结构就打印 Object.keys(res.data)，别打印整个响应。

顺便说清一个取舍（这条答辩时会用到）：本项目把 token 存在 localStorage，是教学上的简化，因为它简单直观、便于调试。更安全的做法是服务端写进 HttpOnly Cookie，那样 JavaScript 读不到、XSS 偷不走，代价是要处理 CSRF。知道这个取舍并且说得清，比盲选一个更值。

守卫漏掉两个边界 ​

现象：守卫只写了“未登录跳登录页”。已经登录的人点回登录页，看到一个登录表单；登录成功后停在首页，而不是原来想去的那个页面。

原因：它写守卫时以“防未登录”为主线，其余边界都不在主线里。

怎么处理：两个边界各一行代码，但都需要你记得加。

js
router.beforeEach((to) => {
  const token = getToken()

  // 边界一：已登录还去登录页，直接送回首页
  if (to.name === 'login' && token) return { name: 'home' }

  // 未登录且目标需要登录，带着目标地址去登录页
  if (to.meta.requiresAuth && !token) {
    return { name: 'login', query: { redirect: to.fullPath } }
  }
})

登录页里再用这个 redirect：

js
const route = useRoute()
router.replace(route.query.redirect || { name: 'home' })

第二个边界有个细节要注意：redirect 的值要校验，不能直接拿来做跳转目标。 万一它是 //evil.com，就会跳到站外去。至少判断它以 / 开头、且不以 // 开头。这个判断“该不该做”你去想一遍，比记结论有用 —— 它的道理和“前端校验不等于安全”是同一个。

退出登录没清动态路由 ​

现象：退出登录只清了 token 和用户信息，路由表里那些按权限动态加进去的页面还在。退出后用地址栏直接访问，界面能打开（数据请求会失败，但页面壳子还在）。

原因：动态加路由这件事是“加”，它想不到要“减”。

怎么处理：注销的时候，除了 token 和用户信息，还要把动态加进去的路由移除，并清掉菜单数据。本项目用的做法是记下移除函数并逐个调用：

js
// 加的时候记下来
const removeHandles = []
addRoutes.forEach(r => removeHandles.push(router.addRoute(r)))

// 退出时逐个摘掉
removeHandles.forEach(remove => remove())
removeHandles.length = 0

判断该清哪些东西，问一句就行：“下次换个账号登录，这些残留会不会让他看到不该看的？” 会，就要清。

还有一类错误：把什么都塞进 beforeEach

现象：它起草的守卫里，beforeEach 同时干了这些事：判断登录、检查角色、设置页面标题、上报页面埋点、开关顶部的加载条。守卫函数写了七八十行，里面还发了一次请求验证 token。

原因：beforeEach 是“每次跳转都会跑”的那个钩子，最显眼，所以什么都往里放。

怎么处理：按“什么时候该跑”分开放。

要做的事放哪为什么
判断能不能进这个页面beforeEach要在跳转前决定，可以取消跳转
设置页面标题、上报埋点、关进度条afterEach跳转已经完成，不需要影响跳转结果
需要等异步结果才能决定放不放行beforeEach 里 async 加 await但要小心，每次跳转都等一个往返

第三行有个实际代价：守卫里每发一次请求，每次跳转都要多等一个来回。 判断该不该这么做，看这个请求能不能缓存 —— 用户信息这类在一次会话里不会变的东西，登录时拿一次存起来，守卫里读内存就够了，不必每次都问后端。

把“设置标题”这类事挪出 beforeEach，不只是代码整洁的问题：写在 beforeEach 里，如果守卫在中途 return 了，后面的语句就不会执行，标题就漏设了。 这类 bug 只在特定跳转路径上出现，很难复现。

怎么验收 AI 的产出 ​

这一章的产出涉及安全边界，验收动作要比前面几章更硬。逐条过：

  • [ ] 守卫处理了六个边界：未登录、已登录访问登录页、登录后回跳、角色不符、404、退出清路由
  • [ ] 代码里没有 console.log 打印 token 或整个响应
  • [ ] token 没有出现在 URL、HTML、硬编码里
  • [ ] token 的读写集中在 src/utils/token.js 一个文件里
  • [ ] 回跳用的 redirect 参数做了校验，不会跳到站外
  • [ ] 退出登录清掉了 token、用户信息、动态路由、菜单数据
  • [ ] 把权限判断写在模板里的地方，你都确认过它只是“体验”，后端也做了校验
  • [ ] 你能用一句话说清：如果绕过守卫直接调接口，拦住他的是谁

前六条是“有没有做”，第七条是“有没有摆对位置”，最后一条是“你有没有真的理解”。最后一条过不了，前面七条做得再全也说明不了什么。

练习 ​

给自己的守卫写一份“能防什么、不能防什么”，让 AI 挑错 ​

任务：为你写的路由守卫写一份说明，分两栏：能防什么（谁会被拦住、被拦之后看到什么）和不能防什么（谁会绕过去、绕过去之后能做什么）。写完之后让 AI 挑错。

要求：记录里必须包含这四项：

项要求
你写的说明完整保留原文
AI 挑出的错逐条记录，注明它说得对不对
你不认同的部分写清为什么不认同
修改后的说明把最终版本单独写一遍
验收标准与参考思路

为什么用“让 AI 挑错”而不是“让它写”：这份说明要考的是你有没有把“体验”和“安全”摆对位置。让它写，你拿到的是一段漂亮的通用说法，学不到东西；你先写它再挑错，它挑出来的每一条都在检验你的理解。而且这次会有反向收获 —— 它挑的错里一定有它自己判断错的地方。

思路提示：

  • “不能防什么”这一栏最容易写空。至少写三条：在控制台里直接改内存中的状态；不走界面直接请求接口；把 localStorage 里的 token 换成一个别的值。
  • “能防什么”这一栏要写清“拦住之后用户看到什么”。这能检验你是不是真的想过这个界面的表现，还是只想着“拦住了”。
  • AI 挑错时大概率会说“建议在后端也做校验”—— 这是对的但不够，你在写的时候就该写上。如果它挑出来的错全是你已经写过的，说明它没认真读，换个问法再试一次。
  • 可以再追问它一句：“我这份说明里有没有哪一句是听起来对、但实际做不到的？” 这个问法比“帮我挑错”更能逼它找真问题。

不合格的写法：

让 AI 看了我的说明，它说写得比较全面，就是建议后端也做校验，我加上了。

“比较全面”是个没有信息量的评价。这份说明里最该写清的三条绕过方式，你有没有写到？

合格的写法：

我写的“不能防什么”里有三条：改内存状态、直接请求接口、换掉本地 token。 AI 的反馈是两点：建议补上“用户可以直接改 URL 里的参数”，以及 “建议后端也做校验”。第二点我已经写了，它没读到； 第一点我认同，但改写了一下 —— 改 URL 参数本身不是绕过守卫， 绕过的是“用参数控制界面”这种做法，所以我把这条改成了 “通过改查询参数让界面显示不需要权限的内容，属于界面层的问题， 但数据层面后端仍会拦”。 另外它提出了一个我不认同的观点：说“前端做严格校验可以减少后端压力”—— 这个说法有问题，压力和安全是两件事，我没有采纳。

差别在于：后者不只是接受反馈，而是判断了每条反馈对不对。它甚至发现 AI 的一条建议本身有逻辑问题 —— 这才是这一节想要的水平。
