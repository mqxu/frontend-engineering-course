10. AI 协作：跨端代码最容易想当然 ​

这一章哪些活能交给 AI ​

先给判断标准：能靠“大量相似代码”解决的活可以交给 AI，需要判断“这个 API 在端上存不存在”的活不能。

写用户端时，AI 的处境和管理端不一样。管理端是纯 Web 环境，AI 见过的代码量极大；用户端多了一层平台约束，而 AI 不知道你跑在哪一端 —— 它默认按浏览器的规则给你写代码，出来能用才怪。

任务能交给 AI 吗为什么
写页面骨架（卡片、列表、表单布局）能结构相似，样式写法通用
写状态判断的 computed能纯逻辑，不依赖平台
写工具函数（日期格式化、字典映射）能和管理端是同一件事
解释一个陌生的报错能，但要核实它可能给出平台不对的解法
推荐组件库与用法不能直接信组件库换过名字，它的知识可能停在上一个版本
写请求封装能，但要审它习惯用 axios，会写成浏览器那套
写页面跳转不能直接信它习惯 vue-router 的写法
决定页面结构（哪些页、怎么分）不能这是设计判断
判断某段代码能否跨端不能它给不出可信答案，只能你自己在两个端跑一遍

最后一行是这一篇的核心。 前面 9 篇里反复出现的“两个端都要跑一遍”，对 AI 生成的东西更加必要 —— 它写出来的代码通常在 H5 端能跑，在小程序端才暴露问题。

提示词怎么写 ​

模板一：让它先认版本，再写代码 ​

text
我要在 uni-app 项目里加一个活动列表页。

动手之前先确认这几件事，不要凭记忆假设：
1. 这是 uni-app 的 Vue 3 + Vite 版本，不是 uni-app x
2. UI 组件库是 @wot-ui/ui（注意不是旧名 wot-design-uni），
   组件通过 pages.json 的 easycom 自动引入，前缀是 wd-
3. 项目已经有一个封装好的请求层，用法是 http.get(url, params)，
   路径不带 /api 前缀，返回值已经是业务 data，错误对象上带 code

确认之后按这些约束写：
- 用 script setup，生命周期钩子从 @dcloudio/uni-app 导入
- 不要用 window、document、localStorage、axios
- 样式用 rpx，细线用 px
- 需要跨端差异的地方用条件编译，注释掉不需要的那一端

输出就是这一个 vue 文件的完整代码，不要解释。

为什么这么写： 三条“先确认”对应三类它最容易错的地方 —— 框架版本、组件库名称、项目已有的约定。尤其第二条，组件库换过名字，如果不点名，它很可能给你写出 wot-design-uni 的引入路径。

最后一句“不要解释”也是有意的：解释会占掉一半输出，而你要的是代码。 需要解释时单独再问。

模板二：让它审查跨端兼容性 ​

text
这是我写的 uni-app 页面代码：
（贴代码）

帮我逐个标出这些写法在微信小程序端会发生什么：
- 哪些 API 在小程序里不存在
- 哪些 CSS 属性小程序不支持或表现不同
- 哪些地方需要条件编译

按“行号 → 问题 → 建议改法”的表格输出。
不确定的地方标出来，不要猜。

为什么这么写： 直接让它“检查代码质量”，它会给你一堆命名建议；指定“跨端兼容性”这个角度，它才会往平台差异上想。最后一句“不确定的标出来”很重要 —— 跨端的具体支持情况它常常拿不准，宁可让它承认不确定，也别让它编一个看起来合理的答案。

模板三：给它两端的行为，让它定位差异 ​

text
同一份代码，H5 端正常，微信小程序端出现下面的现象：
（贴小程序端的报错或截图描述）

相关代码是：
（贴代码）

可能是哪几类原因？按可能性从高到低列出来，每类给我一个验证办法。
不要直接给修改后的完整代码，先让我确认是哪一类。

为什么这么写： 只报一个端的现象，AI 倾向于猜一个原因然后大改一通。要求“先给分类和验证办法”，你就有了自己判断的机会 —— 跨端问题里，猜错方向比改错代码浪费更多时间。

AI 在这一章容易错什么 ​

用已经改名的组件库 ​

现象： AI 给你的代码里出现 pnpm add wot-design-uni 或者 "^wd-(.*)": "wot-design-uni/components/wd-$1/wd-$1.vue"。

原因： 这个组件库 2026 年把包名换成了 @wot-ui/ui。AI 的训练数据里旧名字的语料更多，它会自然地给出旧的那个。旧包在 npm 上依然存在（停在 1.14.0），所以照着装也能装上 —— 不会报错，只是用的是一个不再更新的版本。

怎么处理： 两个办法。

一是在提示词里点名（上面模板一的做法）。二是养成核实包名的习惯：

bash
# 查包存不存在、最新版本是多少
curl -s https://registry.npmjs.org/@wot-ui%2Fui/latest | head -c 200

# 对照旧包名，看它停在哪个版本
curl -s https://registry.npmjs.org/wot-design-uni/latest | head -c 200

第二条命令更有价值 —— 看到旧包版本号停在一年前、而新包还在持续更新，就知道该用哪个了。

官方文档里的路径也要注意

组件库的官方文档默认按 uni_modules 安装方式写例子，导入路径是 @/uni_modules/wot-ui。你的项目是 npm 安装的，路径是 @wot-ui/ui。

照抄文档例子会报“找不到模块”，这不是 AI 的错，也不是文档的错，是安装方式不同。看到这个路径就手动换掉。

把 Web 的 API 写进来 ​

现象： 代码里出现 window.localStorage.setItem(...)、document.querySelector(...)、axios.get(...)、new FormData()。

原因： AI 见过的 Web 代码远多于跨端代码，这些是它的默认写法。H5 端这些全都能跑，所以你不容易发现。

怎么处理： 记住这张替换表，审查时逐条对照：

AI 会写的换成什么
window.localStorageuni.setStorageSync / uni.getStorageSync
document.querySelector用 ref 拿组件实例，或者 uni.createSelectorQuery
axios项目封装好的 http
new FormData()uni.uploadFile
window.location.hrefuni.navigateTo / uni.switchTab
fetchuni.request
alert / confirmuni.showToast / uni.showModal
window.setTimeout直接用 setTimeout（这个能用）

最后一行说明不是所有 Web API 都不能用 —— setTimeout、Promise、Math、Date 这些语言层面的东西在哪个端都有。要用条件编译或者换 API 的，是那些依赖浏览器环境的对象。

用 vue-router 的写法做跳转 ​

现象： 代码里有 router.push('/activity/1')、useRouter()、<router-link>。

原因： AI 把 Vue 生态的路由习惯直接套过来了。用户端根本没有 vue-router，路由是 pages.json 配置加 uni.navigateTo 这套。

怎么处理： 换成 uni 的 API，并且注意 tabBar 页面的区别：

js
// ✗ AI 常写的
router.push('/pages/activity/detail?id=' + id)

// ✓ 换成 uni 的 API
uni.navigateTo({ url: '/pages/activity/detail?id=' + id })

特别要检查 switchTab。 AI 即使知道用 uni.navigateTo，也常常对 tabBar 页面用错 —— 而这类错误只在真正点到那个按钮时才暴露，编译和构建都不报错。

生命周期钩子从 vue 导入 ​

现象： 代码写的是 import { onLoad, onShow } from 'vue'，或者干脆用了 onMounted 来接收路由参数。

原因： 在 Vue 3 Web 项目里，所有钩子都从 vue 导入。AI 会延续这个习惯，而 uni-app 的页面钩子来自另一个包。

怎么处理： 分清两套钩子的来源：

js
// ✓ 页面级钩子：从 @dcloudio/uni-app 导入
import { onLoad, onShow, onPullDownRefresh, onReachBottom } from '@dcloudio/uni-app'

// ✓ 组件级钩子：从 vue 导入
import { onMounted, onUnmounted, ref, computed } from 'vue'

从 vue 导入 onLoad 不会报错，它只是一个普通的导出（undefined），调用时会报“不是一个函数”，但这个报错出现的位置和真正的问题隔了很远。

新加了页面但不改 pages.json ​

现象： AI 给了你一个完整的新页面 .vue 文件，你放进 src/pages/，跳转时报“页面不存在”。

原因： 在 Web 项目里，新建一个组件文件就完事了；在 uni-app 里页面必须在 pages.json 里登记。 AI 生成单文件时经常漏掉这一步。

怎么处理： 每次让 AI 新增页面，在提示词里明确要求它同时给出 pages.json 要加的那一段：

text
新建页面时，除了给出 .vue 文件，还要给出 pages.json 里需要添加的配置片段，
包括 path、style 里的标题，以及如果这个页面在 tabBar 里，说明该用哪个跳转 API。

这个习惯能省掉一类反复出现的小麻烦。

怎么验收 AI 的产出 ​

  • [ ] 两个端都跑过一遍了吗？H5 通过不算通过
  • [ ] 代码里有没有 window / document / localStorage / axios 这四个词
  • [ ] 有没有出现 router.push / useRouter / router-link
  • [ ] 生命周期钩子的导入来源对不对（页面钩子来自 @dcloudio/uni-app）
  • [ ] 新增的页面，pages.json 里登记了吗
  • [ ] 涉及跳转的地方，跳的是不是 tabBar 页面，用的是 switchTab 吗
  • [ ] 请求有没有走项目封装好的 http，有没有自己拼 uni.request
  • [ ] 用到的组件名能不能在你装的组件库版本里找到（wd- 开头的去 node_modules/@wot-ui/ui/components/ 下看一眼）
  • [ ] 时间处理有没有直接用 new Date(后端字符串)（iOS 会挂）
  • [ ] rpx 和 px 的使用场合对不对（细线用了 px 吗）

这十条里，第 1 条和第 2 条能拦住大部分问题。 剩下的按出现频率排：跳转方式、生命周期导入、pages.json 漏登记。

最后那两条（时间处理和 rpx）不是 AI 特有的问题，但因为它生成的代码量比你手写大得多，这类小问题的出现次数会被放大。

练习 ​

让 AI 写一个用户端的活动详情页，然后找出它写错的地方，改对并记录。

任务要求：

项要求
提示词用本篇模板一的结构，包含三条“先确认”和四条约束
产出一个完整可跑的详情页 .vue 文件
排查逐条对照上面那份验收清单，记录发现的每一处问题
修改每处问题都要在两个端验证过
记录按下表格式写一份记录
序号AI 写了什么为什么不行怎么改在哪一端暴露的
1
验收标准与参考思路

验收标准：

项要求
记录条数不少于 4 条
覆盖类型至少包含：Web API、跳转方式、生命周期导入、pages.json 这四类各一条
暴露端每条都要写清是在哪一端、什么操作下暴露的
两个端修改后的代码在两个端都验证过
结论最后写两三句：哪类问题最容易漏，为什么

不合格的记录：

| 1 | 用了 localStorage | 小程序不支持 | 改成 uni.setStorageSync | 小程序 |

只写“不支持”等于没记录。 要说清是哪一步暴露的 —— 是编译时报错，还是运行时白屏，还是点到某个按钮才出问题。这决定了你今后在哪个阶段检查它。

合格的记录：

| 1 | window.localStorage.setItem('token', ...) | 小程序没有 window 对象 | 换成 uni.setStorageSync('token', ...) | H5 端完全正常；小程序端编译不报错，进页面时白屏，控制台报 window is not defined |
| 2 | router.push('/pages/signup/form?id=' + id) | 用户端没有 vue-router | 换成 uni.navigateTo | 编译期就报错，这一条好发现 |
| 3 | import { onLoad, onShow } from 'vue' | 页面钩子要从 @dcloudio/uni-app 导入 | 拆成两行导入 | 编译不报错，进页面时 onLoad 不是函数，整个页面逻辑不执行 |
| 4 | 新页面没有登记到 pages.json | 没登记的页面跳不过去 | 补上 path 与 style | 点击跳转时提示页面不存在 |

参考思路：

三个地方值得注意：

一是“在哪一端暴露”这一列最有价值。 你会发现规律：编译期报错的问题都好解决（改完就过），运行时才暴露的才是麻烦的（第 1、3 条都是）。而第 3 条的报错位置和真实原因隔得很远 —— 这类问题要多花时间定位，记录时把定位过程也写下来。

二是同一份提示词跑两次，比较两次的结果。 同一个 AI 两次给出的代码，错误位置不一定相同，但它容易犯哪几类错是稳定的。 摸清这个规律，比记住某一次的具体错误有用。

三是把这份记录留下来。 答辩时可以放进“开发生成记录”里 —— 单元 11 的 AI 参与声明里有一栏是“发现的错误”，这种有现象、有原因、有改法的记录，比“用了 AI 提效”这种空话有说服力得多。
