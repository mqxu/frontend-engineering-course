1. 为什么是 uni-app ​

一个具体的场面 ​

管理端上线了。你兴冲冲把地址发到班群，配了一句“同学们可以在上面报名了”。

十分钟后，群里陆续冒出这些话：

  • “在哪儿点啊，字好小”
  • “我手机上打开了，按钮点不到”
  • “要注册吗？我懒得注册”
  • “能不能直接发个二维码，扫一下就报名的”

你打开手机看了下自己做的页面：表格横向溢出，侧边栏占了半屏，按钮得放大三倍才点得到。这个界面从设计的那天起就不是给手机用的。

于是问题变成：学生这一端，用什么做？

三条路，选哪条 ​

方案优点代价
给管理端加媒体查询，做成响应式不用写新代码桌面后台的表格、侧边栏、弹窗在手机上很难改造，改完两边都别扭
单独写一个手机版 Web完全自由学生还是得每次输网址或收藏；发布一个 H5 也要自己处理各种浏览器差异
用 uni-app 写，编译成多端一套代码出 H5、小程序、App要学一套新的页面配置与 API 用法，部分 Web 写法在端上不可用

我们选第三条。理由不是“多端听起来厉害”，而是小程序这个入口的学习成本最低 —— 学生扫码就能用，不用注册账号、不用记网址、不用装 App。

uni-app 是怎么做到一套代码多端的 ​

关键要理解一件事：uni-app 不是运行时，是编译器。

你的代码（Vue 3 单文件组件 + uni 的 API）
        ↓
   uni-app 编译器（在你机器上跑）
        ↓
 ┌──────────┬──────────┬──────────┬──────────┐
 │  H5      │ 微信小程序 │ 支付宝小程序│  App     │
 │ HTML+css │ wxml+wxss│ axml+acss│ 原生渲染   │
 └──────────┴──────────┴──────────┴──────────┘

编译期就完成了转换，所以：

  • 你写的 <view> 在小程序里变成 wxml 的 view 标签，在 H5 里变成 <div>
  • 你写的 uni.request() 在小程序里调用 wx.request，在 H5 里用 XMLHttpRequest
  • 你写的样式会被转成各平台认识的形式

这也解释了后面所有“为什么不行”的问题。 凡是编译期无法转换的东西都不能用 —— DOM 操作、window 对象、浏览器专有 API，都是这个道理。

先分清：uni-app 和 uni-app x 是两个东西 ​

搜索“uni-app 教程”时，你会同时看到 uni-app 和 uni-app x 这两种说法，容易混。

uni-app（经典版）uni-app x
主语言JavaScript / TypeScriptUTS（带类型约束的语言）
App 端渲染WebView 加原生混合原生渲染，没有 WebView
小程序与 H5支持，生态成熟不是主攻方向
样式完整 CSS，支持各种选择器以 flex 为主，很多高级 CSS 特性不支持
npm 生态绝大多数前端 npm 包可用App 端大量 JS 包不可用，要用 UTS 版本
plus 对象有，用于调用原生能力没有，改用 UTS 直接调系统 API
组件库数量多、成熟需要用适配过的 UTS 版本
适合谁项目以小程序、H5 为主项目以 App 为主，追求原生性能，需要上架鸿蒙

这门课用经典版。 三个理由：

  1. 我们的目标是 H5 加微信小程序，这正是经典版的强项
  2. 教学要能在浏览器里直接看到结果，uni-app x 的调试链路更长
  3. 经典版用的还是 JavaScript 和 Vue 3 那套东西，你在前 10 个单元学到的东西全部作数

别在项目里混用

两个版本的项目结构看着像，但底层完全不同。不要把经典版的项目直接当 uni-app x 项目打开，也不要在教程里跳着用两边的写法。这一栏从头到尾只说经典版（下文提到“uni-app”都指经典版）。

和管理端的 Vue 项目差在哪 ​

这是最该记住的一张表。左边你都会，右边是新东西。

项管理端（Vue 3 Web）用户端（uni-app）
工程入口index.html + main.jsmain.js 导出 createApp，入口由编译器生成
页面注册路由表写在 router/index.js页面写在 pages.json 的数组里
路由跳转router.push('/activity/1')uni.navigateTo({ url: '/pages/activity/detail?id=1' })
路由守卫router.beforeEach没有全局守卫，用页面生命周期或 uni.addInterceptor
根元素组件可以多根页面必须能落到 view 等内置组件上
DOM 操作document.querySelector 随便用没有 document，也没有 window
本地存储localStorageuni.setStorageSync / uni.getStorageSync
网络请求axiosuni.request（回调式，要自己包成 Promise）
样式单位px / remrpx（750rpx 等于屏幕宽度）
点击事件@click@click 也行，但官方推荐 @tap
页面生命周期onMounted / onUnmounted额外有 onLoad / onShow / onPullDownRefresh / onReachBottom
生命周期导入从 vue 导入页面钩子从 @dcloudio/uni-app 导入
富文本v-html<rich-text :nodes="html" />
页面跳转传参路由参数，任意对象URL 查询串，只能传字符串

最需要当心的是第四行和第五行。 你在管理端习惯的 document、window、localStorage、axios，在小程序里一个都不存在。编译不会报错到让你一眼看出问题，而是运行时白屏或者报 document is not defined。

什么时候不该用 uni-app ​

工具没有绝对的好坏，说清适用边界：

场景该不该用
要出微信小程序用，这就是它的主场
要出手机 App 且能接受 WebView 性能用
要出手机 App 且追求原生流畅度、要上架鸿蒙看 uni-app x，或者直接原生
只在浏览器里跑的桌面管理后台不要用。选 Element Plus 那套更省事
需要大量操作 DOM、和第三方 JS 库深度集成慎用。小程序环境不给你 DOM

小结 ​

  • uni-app 是编译器，不是运行时，一套代码在编译期分别转成各平台的产物
  • 经典版和 uni-app x 是两套技术，这门课用经典版：Vue 3 + JS，主攻 H5 与小程序
  • 与管理端最大的差异在四处：路由变成配置、没有 DOM、请求换成 uni.request、单位换成 rpx
  • 编辑器的自动补全帮不了你识别“这个 API 在小程序里没有”，要靠你自己记住哪些写法不能用
  • 工具链版本比管理端旧，这是跨端框架的固有代价，不是写错了

常见坑 ​

装了浏览器插件试 uni-app，结果什么都没看到

现象： 在浏览器里直接打开 src/pages/index/index.vue，页面一片空白。

原因： .vue 文件不是浏览器能直接执行的东西，它必须经过 uni-app 编译器处理。管理端的 Vite 项目也一样，只是你习惯了在 localhost 上通过开发服务器看，忘了这一步。

怎么处理： 永远通过 pnpm dev:h5 启动的开发服务器访问，不要直接双击文件。记住这条，后面也就不会再犯。

在脚本里用了 window.localStorage，小程序端报错

现象： H5 端一切正常，切到微信小程序后白屏，控制台报 window is not defined 或者 localStorage is not defined。

原因： 小程序的运行环境里没有浏览器对象模型，window、document、localStorage、navigator 都不存在。H5 端有，所以问题只在某一端暴露 —— 这也是为什么两个端都要跑一遍，不能只看 H5 通过就提交。

怎么处理： 换成 uni 的 API：uni.setStorageSync() / uni.getStorageSync()。如果确实需要一段只在 H5 生效的代码，用条件编译把它圈起来：

js
// #ifdef H5
window.someThirdPartyThing()
// #endif
搜到的 uni-app 教程是用 new Vue() 写的

现象： 照着搜索到的文章写，代码里出现 new Vue({ el: '#app' })、Vue.use(...)、this.$refs.xxx，项目跑不起来。

原因： 网上大量 uni-app 文章是 2020 年前后写的，那时候默认是 Vue 2。搜索结果不会告诉你它过期了。

怎么处理： 看文档只认官方地址 uniapp.dcloud.net.cn，并确认页面上的“Vue 3”标识。判断一段代码是不是 Vue 2 写法，看有没有这些特征：new Vue()、Vue.prototype、this.$set、选项式里的 data() 返回对象、beforeDestroy 生命周期名。碰到就丢掉换一篇。

课后练习 ​

拿管理端的一个页面对照一遍，只做纸上分析，不写代码。

任选一个页面（推荐选活动列表页，它的元素最多），完成下面这张对照表：

管理端用到的写法在用户端换成什么属于哪一类问题
例：router.push('/activity/' + id)uni.navigateTo({ url: '/pages/activity/detail?id=' + id })路由方式不同
例：localStorage.setItem('token', t)uni.setStorageSync('token', t)没有浏览器对象
例：<el-table>换成列表卡片，没有等价组件桌面组件不适合触屏

表格要求写满 8 行，其中至少 2 行是“用户端没有等价写法，要换一种设计”，而不是简单换 API 名字。

验收标准与参考思路

验收标准：

项要求
行数不少于 8 行
分类每行标注属于哪一类：路由方式、浏览器对象、单位换算、组件不可用、请求方式、生命周期
至少有 2 行属于“没有等价写法，要改设计”，并说明改成什么设计
结论最后写两三句：这个页面照搬到手机上，最别扭的是哪一处

不合格的写法：

| 用了 px | 改成 rpx | 单位换算 |

只写“改成 rpx”等于没分析。真实情况是：表格的列宽在手机上无论如何都摆不下，你得决定显示哪几列、剩下的挪到详情页 —— 这是设计问题，不是换算问题。

合格的写法：

| `<el-table>` 的 6 列布局 | 手机上摆不下 6 列，改成卡片列表：只显示标题、类型标签、报名进度；其余字段放详情页 | 组件不可用，要改设计 |
| 表格的“操作”列放 4 个按钮 | 改成卡片底部的 1 到 2 个主按钮，其余收进“更多”菜单 | 触屏点击区不够，要改设计 |
| `el-pagination` 分页 | 换成触底自动加载下一页 | 手机上不该让人点页码 |

参考思路： 拿活动列表页分析，通常能凑出这些条目 —— 路由跳转、分页组件、表格组件、px 单位、localStorage 存 token、axios 请求、document 相关的第三方库、el-message 提示、onMounted 里发请求（用户端要在 onLoad 里发）、日期格式化库（有些依赖 Intl，小程序支持情况不一）。其中“要改设计”的至少有分页、表格、操作列这三处。
