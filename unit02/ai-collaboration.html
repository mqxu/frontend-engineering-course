单元 2 · AI 协作：依赖与版本，别交给 AI 记 ​

这一章的内容有个共同点：全是事实型知识。 Node 有哪些 LTS 版本、engines 字段怎么写、^ 和 ~ 差别在哪、镜像源地址是什么、某个包该放 dependencies 还是 devDependencies —— 这些问题的答案不是"想"出来的，是"查"出来的。

而 AI 恰恰不擅长这一类知识。它可以跟你讲清 package.json 里每个字段的设计意图，但它给你写出来的版本号，很可能在 npm 上根本不存在，或者早就过了维护期。

这一章的两个产出，依赖排查单和 vite.config.js，都属于"照抄就会踩坑"的东西。所以这一节的用法和上一章不同：让 AI 讲清原理，让官方仓库定事实。

这一章哪些活能交给 AI ​

判断标准：能帮你把看不懂的东西看懂，这类活可以交；凡是涉及具体版本号、包名、命令取值的，必须自己查一遍。

任务能交给 AI 吗为什么
解释一条依赖报错在说什么可以报错原文是给包管理器看的，它翻译得比你好
讲清 package.json 某个字段的作用可以它见过大量真实项目里的用法
给一份"安装失败的可能原因"清单可以有价值的是排序，不是结论
帮你把 vite.config.js 翻译成人话可以但每条配置都要你跑一遍才算数
对比两个依赖的取舍可以当起点用，最终由你的项目决定
写出具体的版本号不能直接信它的知识有截止时间，前端工具以月为单位迭代
报一个包名让你装不能直接信见下面的"幻觉依赖"
决定删不删锁文件不行这是团队协作层面的决定

中间那两行是这一章的重点。版本号和包名是最容易被照抄进项目、又最容易被发现是错的两类信息。

提示词怎么写 ​

1. 让它解释一条依赖报错 ​

text
我在 pnpm install 时遇到这个报错：

[完整粘贴，从 ERR_ 开头那一行到最后一行]

环境：Node v24.9.0，pnpm 12.4.1，Windows 11。
在此之前我刚把 registry 换成了 [镜像地址]。

请按这个顺序回答：
1. 这条报错在描述哪一层出了问题（网络 / 镜像 / 版本 / 权限 / 缓存 / 锁文件）
2. 给出排查顺序，每步一条能直接跑的命令，以及"看到什么说明是这一层"
3. 你确定的地方直接说结论，不确定的地方明确说不确定

为什么这么写：第 1 点把问题限定在"哪一层"，正好对上 2.2 的排查顺序。第 2 点要求"每步给出预期现象"，因为依赖排查最耗时间的不是不知道原因，是不知道跑完这条命令该看到什么。最后一句让它敢说"不确定" —— 排查过程中，一个诚实的"我不确定"比一个笃定的错误方向省时间得多。

2. 让它审 package.json，并标出它不确定的地方 ​

text
这是我的 package.json：

[粘贴完整内容]

请逐个字段解释它在这里的作用，用表格：字段 / 作用 / 取值范围 / 我这个值合不合适。

另外单独列一节“我不确定的地方”：凡是涉及具体版本号是否存在、
某个包该放 dependencies 还是 devDependencies、某个字段的默认值，
如果你不能确定，直接写出来，不要给一个看起来合理的答案。

为什么这么写：一次问"这个文件有问题吗"，它多半回"整体看起来合理"。拆成逐字段，它才必须给出具体判断，你才好逐条核实。后半段那句是关键 —— 明确告诉它"不确定可以写出来"，能挡掉相当一部分编造。你拿到的"不确定清单"就是你的核实待办。

3. 让它审 vite.config.js，每条配置都要给验证办法 ​

text
这是我的 vite.config.js：

[粘贴完整内容]

请回答三件事：
1. 每条配置解决什么问题，用一句话
2. 每条配置我怎么确认它真的生效了，给一条能直接跑的命令或一个可观察的现象
3. 有哪些配置是我写了但实际没起作用的

不要评价"配置是否规范"，只回答"有没有生效"。

为什么这么写：配置文件最麻烦的地方是写错了不报错。别名写错一个路径，构建时才发现；代理配错端口，请求静默 404。要求"每条给验证办法"，就把一份静态配置变成了一份可执行的检查清单。最后那句是在堵它用"配置规范，符合最佳实践"这类话敷衍过去。

AI 在这一章容易错什么 ​

版本号凭记忆写 ​

现象：它给你的安装命令是 pnpm add vue@3.6.0，或者写进 package.json 的依赖是 "vite": "^7.2.0"。格式完全正常，但装上去不是版本不存在，就是和其他依赖对不上。

原因：它的知识有截止时间。前端工具链的版本迭代以月为单位，它记住的是训练数据里的那一段，而它无法判断那一段是不是已经过期。

怎么处理：版本号只从两个地方取 —— npm registry 或官方文档。 一条命令的事：

bash
# 查一个包的最新版本
curl -s https://registry.npmjs.org/vue/latest | head -c 200

# 包名带斜杠的，斜杠转义成 %2F
curl -s https://registry.npmjs.org/@vue%2Fuse%2Fcore/latest | head -c 200

返回 {"error":"Not found"} 说明这个包不存在（不是版本不存在）。要看某个包的全部版本，去掉 /latest：

bash
curl -s https://registry.npmjs.org/vite | python3 -m json.tool | grep '"latest"'

本课程用到的基线版本记在工具链与版本清单里，写完配置回头核一遍。

报一个并不存在的包名 ​

现象：pnpm install 报 ERR_PNPM_FETCH_404 或 404 Not Found。它给你的那个包名，格式、大小写、作用域都挑不出毛病。

原因：这种行为叫幻觉依赖。它不是查了仓库发现没有，而是根据见过的包名按命名规则拼了一个出来 —— vue-router-lite、@vue/sortable 这类听起来很合理的名字，都是常见的编造结果。

怎么处理：装之前先确认存在，别先改 package.json 再 install。

bash
# 有版本号输出就是存在
npm view vue-router version

# 想看这个包的详细信息（作者、描述、最近发布时间）
npm view vue-router

要判断一个包是不是"真在用"，可以顺带看一眼最近发布时间 —— 三年没更新的包放进新项目要谨慎。

建议你删掉锁文件 ​

现象：安装冲突时它说"删除 pnpm-lock.yaml 再重装就能解决"。

原因：这是它见过最多的"通用解法"，但它不知道你的项目是团队协作、有 CI 流水线。

怎么处理：锁文件记录了整棵依赖树的精确版本，删掉等于让每个环境重新解析一遍版本范围。"我这能跑、CI 上跑不起来"的问题，多半就是这么来的。 只在极少数情况才删（比如刚换了包管理器、或锁文件确实损坏）。正常的问题回到 2.2 的排查顺序 逐层排除，一次只改一个变量，然后记进排查单。

把 dependencies 和 devDependencies 放反 ​

现象：它把 vite、eslint、vitest 写进 dependencies，或者把 element-plus 放进 devDependencies。

原因：它的判断依据是"这个包看起来像不像开发工具"，而这个词的边界很模糊 —— vite 算是工具，那 vite 的插件呢？

怎么处理：判断标准只有一条 —— 这个包会不会被打进最终产物。 打包工具、检查工具、测试工具、类型定义放 devDependencies；被页面代码 import 进来、运行时要用到的放 dependencies。拿不准就用一个动作验证：pnpm build 之后看产物里有没有它。

还有一类错误：改 type 或升大版本，却不提影响面

现象：它说"把 "type" 改成 "module" 就能解决"，或者"升级到最新大版本就好了"。你照着改了，别的文件开始报错。

原因：这类改动的影响面不在它拿到的上下文里。它只看到你贴的那一个文件，看不到还有哪些地方依赖了旧行为。

怎么处理：凡是动到 type、engines、packageManager 或主版本号的建议，都先追问一句："这个改动还会影响哪些文件？" 然后自己搜一遍引用位置：

bash
# 看还有哪些文件要求了某种模块格式
grep -rn "require(" src/ vite.config.js

# 看有没有地方写死了 Node 版本
grep -rn "engines\|node -v" package.json .github/

type 字段这类全局设置，改错的表现往往是一部分文件正常、一部分文件报错的语法错误，很难第一眼看出根因。所以宁可先问清影响面，也不要直接改。

怎么验收 AI 的产出 ​

这一章的产出是配置和依赖清单，验收动作比上一章更硬 —— 大部分都能用运行结果判定。逐条过：

  • [ ] 它给的每个版本号，都在 registry.npmjs.org 上查到了
  • [ ] 它提到的每个包名，都用 npm view <包名> version 确认过存在
  • [ ] 它判断的 dependencies / devDependencies 归属，你按"会不会进产物"复核过
  • [ ] 它给的每条 vite.config.js 配置，你都跑过 pnpm dev 或 pnpm build 确认生效
  • [ ] 它没有建议你删锁文件；如果有，你问清了理由并记进了排查单
  • [ ] 它给的镜像源地址你现在访问得通
  • [ ] 动到 type、engines、主版本号的建议，你搜过影响面
  • [ ] 改完能跑通 pnpm install 与 pnpm build && pnpm preview

前三条对应"事实对不对"，中间三条对应"配置真的生效了没"，最后两条对应"改动的影响面控制住了"。这八条过完，这一章的配置就可以提交了。

练习 ​

用 AI 审一遍自己的 package.json ​

任务：拿第 1 周建好的练习工程，让 AI 逐个字段解释一遍，然后逐条核实它说的每一个事实，最后交一份分歧清单。

要求：记录里必须包含这四项：

项要求
字段解释逐个字段问，把它给的解释和自己的理解对照着记
它标出的"不确定项"完整保留，这条清单就是你的核实待办
你的核实动作每个版本号怎么查的、每个包名怎么确认的，写清命令和输出
分歧清单它说错的地方，写清它错在哪、正确是什么、你怎么发现的
验收标准与参考思路

为什么要"逐个字段问"：一次问"这个文件有没有问题"，它多半回"整体看起来合理"。把问题拆小，它才必须给出具体判断，你才抓得住漏洞。这是这一节最实用的一个技巧。

思路提示：

  • 优先核三类字段：engines、packageManager、每个依赖的版本范围。这三类最容易出错，也最容易造成"本地能跑、别人报错"。
  • 让它解释一遍 ^ 与 ~ 的差别，然后拿 2.3 package.json 逐字段精讲 里的说法对照。有分歧就以文档为准，别以它的回答为准。
  • 如果它报出来的版本比你实际装的还新，别急着升。先确认这个版本存在，再查它有没有破坏性改动（大版本号变了通常就有）。
  • 分歧清单是这次练习的重点。一条分歧都找不出来，通常说明你没真核，而不是说明 AI 全对。

不合格的写法：

让 AI 看了一下 package.json，它说没什么问题，我就没改。

这句话里没有任何可验证的信息：它看的哪个字段？"没问题"的标准是什么？有没有可能它只是没看出来？

合格的写法：

我问 AI 逐字段解释。到 engines 时它说写成 "node": ">=18" 就行。 我查了 Node 官网的版本列表，18 已经不在维护期，而本课程从第 4 周起的 Vue 项目要求 20.19 以上。 我把字段改成 "node": ">=20.19"，再跑一遍 pnpm install，没有 EBADENGINE 警告。 分歧点：它按"能跑就行"给建议，而项目还要考虑课程后续单元的要求。

差别在于：后者把"它为什么这么建议"和"项目实际要求是什么"摆在了一起做判断。这类判断没法让 AI 替你做，因为它不知道你的项目接下来要往哪走。
