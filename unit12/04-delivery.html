12.4 交付材料与答辩 ​

代码写完了，但你还没"交出去" ​

想象一下这个场景：你交了一个 Git 仓库给老师。老师打开一看，根目录有 src、package.json、还有一堆配置文件。他克隆下来，跑 npm install，报错；看 README，只有一行“# my-project”。他问你“怎么跑？”，你说“要先装 pnpm，然后……”。

这不是交付，这是把自己的电脑镜像发给别人。

交付的标准是：别人不看你的代码，也能把它跑起来、知道它做了什么、明白你为什么这么设计。

这一节讲三件事：README 怎么写、交付文档包含什么、答辩怎么讲。

第一份材料：README.md ​

README 是别人打开你仓库看到的第一个文件。它决定别人愿不愿意继续看下去。

一份合格的 README 有八个部分：

md
# 校园活动服务平台 · 管理端

面向学生会与社团的活动管理后台。组织者创建活动并审核报名，审核员维护场地与场次安排。

## 在线预览

https://activity.example.edu.cn

测试账号：`organizer / 123456`（组织者）、`auditor / 123456`（审核员）

## 功能

- **活动管理** —— 创建、编辑、发布、下架活动，查看报名情况
- **报名审核** —— 按活动查看报名记录，通过或驳回（可填驳回理由）
- **场次与场地** —— 为活动安排场次，系统自动检测同时段同场地的冲突
- **数据看板** —— 活动总数、待审报名数、名额使用率

## 技术栈

| 类别 | 选型 |
| --- | --- |
| 框架 | Vue 3.5（组合式 API + `<script setup>`） |
| 构建 | Vite 8.3 |
| 路由 | Vue Router 5.3 |
| 状态 | Pinia 4.0 |
| UI 库 | Element Plus 2.14 |
| 请求 | axios 1.20 |

## 本地运行

环境要求：Node >= 20.19，pnpm >= 9

```bash
# 1. 克隆
git clone <仓库地址>
cd activity-admin

# 2. 装依赖
pnpm install

# 3. 配置接口地址（可选，默认指向 /api）
cp .env.example .env.development

# 4. 启动
pnpm dev
```

打开 http://localhost:5173

> 第一次启动会自动生成 `src/auto-imports.d.ts` 和 `src/components.d.ts`，
> 在此之前编辑器可能报“找不到 ref”，启动一次即可消除。

## 构建与部署

```bash
pnpm build      # 产物在 dist/
pnpm preview    # 本地预览生产构建
```

部署步骤见 [docs/deploy.md](docs/deploy.md)。

## 目录结构

```
src/
├── api/          接口函数，按业务模块分文件
├── assets/       样式与图片
├── components/   跨模块复用的组件
├── composables/  组合式函数
├── layouts/      布局组件
├── router/       路由表与守卫
├── stores/       Pinia
├── utils/        格式化、字典
└── views/        页面，按业务模块分子目录
```

## 已知问题

- 报名不支持候补队列，名额满后学生无法登记意向
- 时段冲突检测未考虑场次之间的准备时间（布置、清场）
- 数据看板的统计未做缓存，每次进入页面都重新请求

## 开发说明

提交前会跑 ESLint 与 Prettier（husky + lint-staged），提交信息遵循 Conventional Commits。

README 里最容易漏的三件事

一、测试账号。 老师打开线上地址，看到登录页，但没有账号。这一条漏了，前面的部署全白做。

二、.env.example。 你说“要配接口地址”，但别人不知道要配哪些变量。给一个示例文件，里面写清每个变量的作用，值留空或填示例值。

bash
# 接口基础路径。开发时走 Vite 代理，生产时走 Nginx 转发
VITE_API_BASE_URL=/api

# 页面标题，显示在浏览器标签栏
VITE_APP_TITLE=校园活动服务平台

注意 .env.example 可以提交，.env.local、.env.production 里如果含真实配置就不该提交。 判断标准：含密钥的不提交，只含地址的可以提交。

三、已知问题。 很多同学不敢写，怕扣分。恰恰相反：写出已知问题是加分项，藏着才是减分项。 它说明你清楚自己的项目边界在哪。

而且这道题是有比较的 —— 一个说“功能都实现了”的项目，老师一测发现三个 bug，可信度归零。一个说“候补功能没做、冲突检测没考虑准备时间”的项目，老师发现这两处确实没做，其他功能都能用 —— 可信度很高。

第二份材料：交付文档 ​

README 是入口，交付文档是细节。建议放在 docs/ 目录下：

docs/
├── design.md        设计文档：需求、数据模型、状态机、关键决策
├── api.md           接口约定：统一响应、错误码、逐接口定义
├── deploy.md        部署文档：环境、步骤、Nginx 配置
├── dev-notes.md     开发记录：联调问题表、踩坑记录
└── optimization.md  优化记录：前后对比数据

四份文档各有各的用处：

文档回答什么问题谁会看
design.md这个系统是怎么设计的？为什么这么设计？老师、接手的同学
api.md接口怎么调？出错了怎么办？后端同学、测试同学
deploy.md怎么把它跑起来？怎么更新？运维同学、未来的你
dev-notes.md开发中遇到什么问题？怎么解决的？老师（考察过程）、面试官
optimization.md做了什么优化？效果如何？老师（考察工程能力）

design.md 的写法 ​

按 选做 3 的要求写。核心是第 6 部分“关键设计决策” —— 每条写清选了什么、为什么、代价是什么。

判断标准：读完这份文档，另一个人能不能在你的基础上继续开发？能，就合格。

dev-notes.md 的写法 ​

这份文档在答辩时最有用。结构很简单，就是一张表加几段分析：

md
## 联调问题记录

| 编号 | 现象 | 排查过程 | 定位 | 处理 |
| --- | --- | --- | --- | --- |
| 1 | 登录成功但刷新页面就退回登录页 | 先看 Local Storage，token 在；再看 Network，刷新后的请求头里没有 Authorization | 请求拦截器在模块顶层调用了 useUserStore()，此时 Pinia 还没安装，拿到了空 store | 改成在拦截器回调内部调用，或直接读 localStorage |
| 2 | 活动列表总数显示为 0 | 看 Response，后端返回的是 totalCount | 字段名对不上 | 在 api 层的转换函数里统一成 total |

## 一个值得展开的问题：为什么刷新后 token 会丢

（详细分析，包含代码、官方文档依据、验证过程）

为什么这份文档值钱：它证明你真的做过，而且想过。面试官问“你遇到过什么难题”的时候，能讲清楚一个真实的坑，比背十道八股题管用。

optimization.md 的写法 ​

一页表格加几句结论：

md
## 首屏加载优化记录

测试条件：生产构建 + 浏览器缓存禁用 + Slow 4G 限速，取三次平均值。

| 步骤 | dist 总大小 | 首屏 transferred | 首屏请求数 | FCP |
| --- | --- | --- | --- | --- |
| 基线（完整引入 Element Plus） | 2.1 MB | 1.42 MB | 4 | 3.8 s |
| + 路由懒加载 | 2.1 MB | 412 KB | 6 | 1.6 s |
| + Element Plus 按需引入 | 1.3 MB | 218 KB | 6 | 1.1 s |
| + 分包 | 1.3 MB | 218 KB | 9 | 1.0 s |
| + gzip | 1.3 MB | 96 KB | 9 | 0.8 s |

结论：首屏传输量从 1.42 MB 降到 96 KB（降低 93%），FCP 从 3.8 秒降到 0.8 秒。
其中贡献最大的是路由懒加载与按需引入两项。分包对首次加载无影响，但它让后续更新只需重新下载 12 KB。

最后那句结论很重要。 它说明你不仅会做，还知道每一项的作用是什么 —— 包括分包对首次加载没有帮助这个容易被误解的点。

第三份材料：答辩 PPT ​

答辩 PPT 5 到 8 页就够。页数多不等于讲得好。

推荐的页面结构 ​

页内容讲多久
1封面：项目名、姓名、学号10 秒
2项目简介：做什么用、给谁用30 秒
3功能演示：3 到 5 张关键截图，或者直接在线演示2 分钟
4技术架构：一张图说清前后端怎么配合1 分钟
5一个技术难点：问题 → 排查 → 解决 → 收获3 分钟
6工程实践：优化数据、部署方式、代码规范1.5 分钟
7已知问题与改进方向30 秒
8总结20 秒

第 5 页是重点。 老师最想知道的是你有没有真正解决过问题。

第 5 页怎么写 ​

选一个你真的踩过、真的搞懂了的问题。推荐从这三个里挑：

候选为什么适合讲
名额与报名数的并发问题涉及业务规则、前后端职责划分，能展开到“为什么前端拦不住”
时段冲突检测（边界相接不算冲突）涉及算法思考和边界条件，能展示严谨性
首屏从 1.4 MB 降到 96 KB有数据、有方法、有取舍

这一页的四步结构：

第一步：问题。 用一句话说清楚。

两个组织者同时审核同一个活动的最后两个名额，结果通过了三个人，超出名额上限。

第二步：排查。 说清你是怎么找到原因的。

一开始以为是前端的判断有问题，加了 loading 和禁用。用两个浏览器同时操作，还是能复现。后来发现前端的检查是在“点通过”的那一刻做的，两个请求在服务端是并发的，两边都读到“还剩 2 个名额”，都通过了。前端的检查只能减少误操作，不能保证正确。

第三步：解决。 说清最终怎么改的。

在后端把“检查名额 + 更新报名状态”放进同一个数据库事务，并对活动行加行锁。前端的检查保留，但它只是体验优化。

第四步：收获。 说清你从中学到什么。

我原来以为“前端校验 + 后端校验”是重复劳动。现在明白它们是两件事：前端校验是为了让用户少犯错，后端校验是为了保证数据正确。只要涉及多个用户同时操作，前端的判断就一定是不可靠的。

讲技术难点的四个不要

一、不要讲“API 不会用，查了文档”。 这不是难点，是正常开发过程。

二、不要讲只有你遇到、别人无法复现的问题。 比如“我的 Node 装不上，重装系统好了”。这种讲完大家只能沉默。

三、不要只讲结论不讲过程。 “我用 Promise.allSettled 解决了批量操作的问题”—— 为什么不用 Promise.all？两者差在哪？不讲这些等于没说。

四、不要超过 3 分钟。 讲得长不等于讲得好。能把一个复杂问题讲清楚，才是能力。

一个检验方法：讲完之后，如果你的同学能把这个问题的“现象、原因、解决”复述出来，说明你讲清楚了。如果他只能说“他做了个优化”，那就是没讲清楚。

在线演示的注意事项 ​

如果要在答辩现场打开线上地址演示，提前做三件事：

准备为什么
提前 30 分钟打开一遍确认服务还活着、数据还在
准备好测试数据演示时列表里有内容、有几个不同状态的活动
准备一份录屏现场网络出问题时能立刻切换

第三件最重要。 现场网络、服务器、投影仪任何一个出问题，演示就废了。录屏是保底方案，成本只是花两分钟录一次。

演示的默认路径（不要现场自由发挥）：

登录（组织者）→ 活动列表 → 新增活动 → 列表里看到新活动
→ 切到报名审核 → 通过一条报名 → 回到活动列表，看报名数变化

这条路径覆盖了：鉴权、列表、表单、状态联动、跨模块数据一致。 五件事，两分钟讲完。

不要演示的时候现场输入长文本。 提前把要输入的内容准备好，用剪贴板粘贴。现场打字容易出错，会让你紧张。

评分标准 ​

课程项目的评分通常看这五个维度。对照它检查你的交付材料：

维度权重看什么
功能完整度30%主线功能能不能跑通，边界情况处理了没有
工程质量25%目录结构、代码组织、命名规范、有没有重复代码
工程化实践20%版本控制、代码规范、构建优化、部署上线
文档质量15%README 能不能让人跑起来，设计文档有没有取舍分析
答辩表现10%能不能讲清一个技术难点，能不能回答提问

注意“工程质量”占 25%，比你想的高。 这不是看你的功能多不多，是看代码是不是能给别的人看。

常见的扣分点 ​

扣分点怎么避免
没有线上地址这是硬性要求，练 1 到 2 小时就能搞定
README 只有项目名按这一节的八部分写一遍
一个文件几百行超过 300 行的组件就要考虑拆
大量重复代码列表页和表单页抽成模板
满屏 console.log提交前搜一遍清掉
提交信息是“修改”“更新”用 Conventional Commits，见 3.4
没有 .gitignore检查 git ls-files | grep node_modules
演示时子路由刷新 404部署时测一遍，见 12.3
文档里说“功能都实现了”写清已知问题

答辩常见提问 ​

老师常问的六类问题。提前想一遍答案。

关于业务规则

活动名额满了之后，学生在手机上会看到什么？如果两个学生同时点报名呢？

答的思路：前端的表现是什么（入口置灰、提示文案），后端怎么保证正确性（事务 + 行锁）。能说清“前端拦不住并发”是关键。

下架的活动，到报名截止时间之后状态该是什么？

答的思路：这是一个“流程 vs 标记”的问题。下架是标记，状态是流程，两者独立。能说清为什么不能把下架做成一个状态，是加分项。

关于技术选型

为什么用 Pinia 而不是直接把数据放在组件里？ 为什么用 Element Plus 而不是手写组件？

答的思路：不要答“因为流行”或“老师让用的”。说清具体解决了什么问题。比如“组织者信息要在侧边栏、表单、看板三处用到，放在组件里要层层传递”。

关于工程化

你更新了代码，用户要做什么才能看到新版本？ 前端怎么知道后端接口的地址？ 为什么刷新页面不会 404？

答的思路：这三题都在 12.3 里。“更新后如何看到新版本”考的是 index.html 不缓存 + 资源带哈希这套机制 —— 这一题答不上来很吃亏，因为它是部署的核心原理。

关于优化

你做了什么优化？效果怎么样？

答的思路：用数据回答。“首屏从 1.42 MB 降到 96 KB”。不要只说“做了懒加载和按需引入”，没有数据的优化等于没做。

那分包对首次加载有帮助吗？

答的思路：没有。 分包减少的是后续更新的下载量。能诚实说出“这一项对首屏没帮助”比把它吹成优化手段强得多。

关于安全

token 存在 localStorage 里安全吗？

答的思路：不安全（能防 CSRF，但防不住 XSS）。说清前端能做的缓解措施（不用 v-html 渲染用户输入、设置短过期时间），以及真正的解法（httpOnly Cookie + CSRF token）。

关于不足

这个项目如果还要继续做，你会优先做什么？

答的思路：不要说“没什么可做的了”。 说清你知道的缺口，并给出优先级判断。比如“先做报名的候补队列（真实场景里名额满是最常见的诉求），再做操作日志（现在审核记录没有留痕，出了问题无法追溯）”。

项目复盘 ​

答辩完之后，花半小时写一份给自己的复盘。这部分不用交，但价值很高。

问题你的回答
哪一部分花的时间最多？和最初的估计差多少？
哪个 bug 花了最长时间？原因是什么？下次怎么更快定位？
有哪段代码，现在回头看想重写？为什么？
如果重做一遍，你会改变哪个决定？
这门课里哪个知识点你当时觉得没用，后来发现很有用？
下一个项目你想用什么技术？为什么？

最后两个问题最重要。 第一个是检验你对课程的判断，第二个是给你下一步定方向。

把这份复盘存起来。 实习面试的时候，如果面试官问“你从这个项目里学到什么”，你能拿出的不是一段即兴回答，而是一份写过的分析。

小结 ​

  • 交付的标准是“别人不看你的代码也能跑起来、看明白”。 不是把自己的电脑镜像发给别人。
  • README 要八件事：项目说明、在线地址与测试账号、功能、技术栈、本地运行、构建部署、目录结构、已知问题。
  • 测试账号和 .env.example 最容易漏，漏了前面的部署就白做。
  • 已知问题要诚实写。 写出来是加分，藏着被发现是减分。
  • 交付文档五份：设计、接口、部署、开发记录、优化记录。各有各的读者。
  • 开发记录（dev-notes.md）最值钱，它证明你真的做过，也是面试时的素材。
  • 答辩 PPT 5 到 8 页，第 5 页“一个技术难点”占 3 分钟，是全场重点。
  • 讲技术难点的四步：问题 → 排查 → 解决 → 收获。少了“排查”就没有说服力。
  • 演示要提前准备：提前打开确认、准备好数据、准备录屏兜底。
  • 工程质量占 25%，不是看功能多少，是看代码能不能给别人看。
  • 优化要用数据回答。 “首屏从 1.42 MB 降到 96 KB”比“做了懒加载”强一百倍。
  • 能诚实说出“分包对首屏没帮助”这种话，会让老师对你评价更高。
  • 复盘是给自己的。 它决定你从这个项目里真正拿到了什么。

常见坑 ​

老师在现场打不开线上地址

现象：答辩前自己试过是好的，老师打开是 404 或者一直转圈。

原因：三种。

一、服务器上的服务停了。 进程崩了，或者服务器重启后服务没自启。每次答辩前重新确认一遍。

二、内网地址。 部署在自己宿舍的电脑上，用的是内网 IP。在教室连不上。

三、校园网限制。 某些端口（比如 8080、3000）被校园网封了。

怎么处理：

  • 必须有录屏兜底。 这是唯一可靠的保底方案。
  • 提前 30 分钟在答辩教室的网络上测一遍（如果条件允许）。
  • 用 80 / 443 端口，不要用非常规端口。

根本建议：部署到云服务器或者静态托管平台，别用宿舍的电脑。

演示时列表是空的，说明不了问题

现象：打开活动列表，显示“还没有活动”。老师问“你这个能新增吗？”你现场创建，结果校验出错，卡住了。

原因：没有提前准备演示数据。

怎么处理：答辩前跑一次数据准备脚本，或者手工造好数据：

需要的数据：

数据为什么至少几条
各种状态的活动演示状态标签和筛选4 条（草稿、报名中、报名截止、已结束各一）
已下架的活动演示下架标记1 条
有名额的、名额快满的、名额已满的演示名额管控各 1 条
待审核的报名演示审核操作3 到 5 条

写一个脚本准备这些数据，比现场手敲快得多，也不容易出错。

bash
# 用 curl 批量创建
for i in 1 2 3 4 5; do
  curl -X POST http://localhost:8080/api/activities \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer $TOKEN" \
    -d "{\"title\":\"演示活动 $i\",\"type\":\"LECTURE\",\"quota\":50}"
done
PPT 写成了功能清单

现象：PPT 有 20 页，每页都是“功能点：xxx”，讲的时候照着念。

原因：把 PPT 当成了功能说明书。

怎么处理：删掉一半。 功能不需要一页一个，一张截图加一行说明就够了。

PPT 的篇幅分配原则：

  • 讲事实的部分（功能、架构）：占 30%
  • 讲思考的部分（难点、取舍、优化）：占 60%
  • 讲展望的部分（不足、计划）：占 10%

为什么思考占这么多：功能做完了大家都能看到（一演示就知道），但你脑子里想过什么，不写不说不出来。

具体做法：把“功能清单”四页压缩成一页（一张带编号标注的界面截图），把省下的三页用来讲那个技术难点。

被问到一个不会的问题

现象：老师问“你的接口为什么用 PATCH 不用 PUT？”你答不上来，沉默了十秒。

原因：没准备，或者确实不知道。

怎么处理：不要瞎编。

正确的回答方式有三种：

一、承认不知道，但给出你能推到的部分。

PATCH 和 PUT 的具体区别我没查过。我当时的判断是下架只是改了一个字段，不是替换整个资源，所以用了 PATCH。如果是替换整个对象应该用 PUT。这个理解如果有问题，我回去查一下。

这个回答比瞎编好得多。 它展示了你的推理过程，也承认了边界。

二、当场推到答案。

PUT 从名字上是“放置”，应该是整体替换；PATCH 是“补丁”，改一部分。语义上 PATCH 更贴合。另外我记得 PUT 在规范里要求幂等，PATCH 不强制。

三、反问澄清。

您是想问语义上的区别，还是想问实际项目里怎么选？

最忌讳的是：编一个听起来对但错的答案，然后被追问两句就露馅。那比直接说不知道的损失大得多。

提前准备：把这一节“答辩常见提问”的六类问题，每题写三句话的答案，背下来。六类问题覆盖了 80% 的提问。

讲超时了，被老师打断

现象：PPT 讲到第 6 页，老师看表说“时间到了”。

原因：没有排练，或者内容贪多。

怎么处理：

  • 提前掐表练三遍。 三遍是必要的 —— 第一遍一定会超时，第二遍能压到差不多，第三遍才能稳住。
  • 准备一个“可裁剪”的版本：如果时间不够，哪几页可以跳过（通常是架构图和优化数据这两部分说一句话带过）。
  • 把时间留给第 5 页那个技术难点。 那一页如果被压缩掉，这次答辩就失去重点了。

一个实操技巧：在每页 PPT 的备注里写下必须说出口的那一句话。紧张的时候容易忘了讲到哪，看到那句话就能接上。

md
<!-- 备注：这一页必须说清的是“前端的检查只能减少误操作，不能保证正确” -->
提交的仓库里有一堆不该有的文件

现象：老师克隆仓库，发现有 .DS_Store、.vscode/settings.json、dist/，甚至有一份 备份/ 目录。

原因：.gitignore 没写全，或者用了“全选添加”的提交方式。

怎么处理：

bash
# 依赖
node_modules

# 构建产物
dist
dist-ssr

# 编辑器与系统
.DS_Store
.idea
.vscode/*
!.vscode/extensions.json

# 自动生成
src/auto-imports.d.ts
src/components.d.ts

# 本地配置
*.local
.env.local
.env.*.local

# 日志
*.log
npm-debug.log*

已经被提交的怎么清理：

bash
# 从索引里移除（保留本地文件）
git rm -r --cached dist node_modules
git rm --cached .DS_Store
git commit -m "chore: 清理不该提交的文件"

# 再加一条：全仓库搜一遍大于 1 MB 的文件
git ls-files | xargs -I{} du -k "{}" | sort -rn | head -10

最后那条命令很有用。 仓库里如果有几百 MB 的二进制文件（比如误提交的安装包、录屏文件），克隆会非常慢，也会被扣分。

课后练习 ​

练习 1：按八部分写一份 README

给项目写一份完整的 README，然后找一个没参与项目的同学，让他照着 README 在你的电脑上跑一遍。

思路提示：

  • 记录他卡住的每一个地方。每一个卡点都说明 README 漏了一条信息。 这是最有效的验证方式。
  • 常见的卡点：不知道要装 pnpm、不知道要先配 .env、启动后不知道该访问哪个地址、没有测试账号。
  • 改完之后再找第二个人试一次。第二个人卡住的地方会比第一个人少很多 —— 但如果还有，那一定是最隐蔽的问题。
练习 2：写一份 dev-notes.md

把这次开发过程中踩过的坑整理成一份文档，至少 5 条。

思路提示：

  • 每条按“现象 → 排查过程 → 定位 → 处理”写。“排查过程”最有价值 —— 它记录了你试过什么、排除了什么。
  • 从这五类里各挑一条：
类型例子
环境问题Node 版本不对
工具配置别名配了但编辑器标红
框架机制KeepAlive 的 include 不生效
接口联调字段名对不上、token 不生效
部署子路由刷新 404
  • 至少挑一条深入展开，写成一篇小分析（包含代码、官方文档依据、验证过程）。这一条会在答辩时用上。
练习 3：做一份答辩 PPT 并排练三遍

按 5 到 8 页的结构做一份 PPT，然后掐表排练三遍。

思路提示：

  • 第一遍：一定会超时，别慌。记下超时的部分。
  • 第二遍：砍掉超时的内容，再看时间。
  • 第三遍：应该能稳定在 10 分钟内。这时候重点是看有没有说清第 5 页那件事。
  • 找一个同学当观众听一遍。问他一个问题：“我刚才讲的那个技术问题，你能复述一遍吗？” 如果他复述不出来，说明你讲得不清楚，回去改。
  • 把每一页必须说出口的那句话写进 PPT 备注，防止紧张时忘词。
练习 4：写一份项目复盘

按这一节“项目复盘”的六个问题，写一份给自己的复盘。

思路提示：

  • 不用交，所以可以写得更真实。 比如“时间管理失败，前两周在纠结 UI 细节，最后一周疯狂补功能”—— 这种话写给自己看才有价值。
  • 最后两个问题（哪个知识点当时觉得没用、下一个项目想用什么技术）要认真答。它们决定你下一步学什么。
  • 把这份复盘存到一个你能找回来的地方。 实习面试前拿出来看一遍，比临时回忆强得多。
练习 5：把项目发布成一个可分享的作品

把它从“作业”变成“作品”。

思路提示：

  • 仓库设为公开（如果内容不涉及隐私），加一个清晰的仓库描述和主题标签。
  • 在 README 顶部加一张项目截图或 GIF 动图。有图的仓库和没图的仓库，观感差别很大。
  • 把“已知问题”改成“后续计划”，并列出你想做的功能。
  • 在 GitHub 上给自己建一个 Profile 仓库，把这个项目放进去。
  • 做完之后，这个项目就变成了你简历里能放链接的东西。 面试官点开能看到代码、能访问线上地址、能读到设计文档 —— 和“熟悉 Vue 3”这几个字完全不是一个量级。
