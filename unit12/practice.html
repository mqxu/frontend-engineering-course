单元 12 课后练习 ​

这是这门课最后一次练习。目标不是学新东西，是把已有的成果交付出去。

练习分三部分：

  • 必做：交付的四个硬性要求，缺一个都会影响最终评分。
  • 选做：让项目从“作业”变成“作品”的加分项。
  • 长期：课程结束后可以继续做的事。

必做 1：完成一次前后端联调并记录 ​

要求 ​

把前端接到真实后端（或同学写的后端、或 json-server 等模拟服务），跑通下面这条链路：

登录 → 活动列表 → 新增活动 → 列表里看到新活动 → 下架活动 → 状态变化

写一份联调记录表，保存为 docs/dev-notes.md 的一部分。

验收标准 ​

检查项通过标准
链路完整跑通五步都能操作成功
记录表至少 5 条每条包含现象、排查过程、定位、处理
“排查过程”有内容写清了试过什么、排除了什么，不是直接写结论
至少一条用的是工具复现记录里能出现 curl 命令或 Postman 的请求信息
记录了字段核对的结果统一响应结构、分页字段、时间格式三件事都有结论
记录了 token 的处理方式存哪里、怎么带、401 怎么处理
参考思路

没有后端怎么办？ 三种替代方案：

方案一：json-server（最省事）

bash
npx json-server --watch db.json --port 8080 --middlewares auth.js
json
{
  "activities": [
    { "id": 1, "title": "校园歌手大赛", "type": "COMPETITION", "quota": 100, "approvedCount": 42, "status": "SIGNING", "offShelf": false },
    { "id": 2, "title": "程序设计竞赛", "type": "COMPETITION", "quota": 60, "approvedCount": 0, "status": "DRAFT", "offShelf": false }
  ],
  "signups": [
    { "id": 1, "activityId": 1, "studentName": "张三", "studentNo": "2023010101", "status": "PENDING" }
  ]
}

注意 json-server 返回的分页信息和你的接口约定不同（它返回的是 X-Total-Count 响应头，不是响应体里的 total）。这正好是一个练“字段名对不上怎么处理”的机会 —— 在 api 层的转换函数里适配它。

方案二：写一个最小的 Express 服务。 二三十行就能提供几个假接口，而且你能完全控制返回结构。

方案三：用 vite-plugin-mock。 在开发环境拦截请求返回假数据，配置更简单，但它不经过真实的网络请求，练不到跨域和网络层的问题，所以不如前两个方案。

关于记录表，一条合格的记录长这样：

编号现象排查过程定位处理
1登录成功，但刷新页面就退回登录页① 看 Application → Local Storage，token 在；② 看 Network，刷新后的请求头里没有 Authorization；③ 在拦截器里打日志，发现拿不到 tokenrequest.js 在模块顶层调用了 useUserStore()，此时 Pinia 还没被 app.use() 安装，拿到的是空对象改成在拦截器回调内部调用 useUserStore()，或直接读 localStorage

注意“排查过程”里的 ①②③。 这三个动作本身就是能力 —— 它说明你知道该看哪里。只写结论的记录表没有价值。

必做 2：完成构建优化并给出对比数据 ​

要求 ​

按 12.2 的优先级顺序逐项优化，每做一项测一次数据，填进对比表。

验收标准 ​

检查项通过标准
有基线数据优化前的 dist 大小、首屏 transferred、请求数都有
至少做了 4 项优化从路由懒加载、按需引入、分包、压缩、图片优化里选
每项都有独立数据不是只给“优化前”和“优化后”两行
测试条件一致都用了生产构建 + 禁缓存 + 固定限速，并写明了条件
首屏传输量下降 50% 以上如果没达到，分析原因
有结论说清哪项贡献最大、哪项没效果
参考思路

“每项都有独立数据”是最重要的要求。

很多同学的做法是：把懒加载、按需引入、分包、压缩一起改完，然后构建两次，得到一个“1.42 MB → 96 KB”的数字。

这样做的价值少了一半。 因为你不知道哪一项贡献了多少 —— 而这恰恰是答辩时会被问的。

正确的做法：改一项 → 构建 → 测一次 → 填一行。

步骤dist 总大小首屏 transferred首屏请求数FCP
基线2.1 MB1.42 MB43.8 s
+ 路由懒加载
+ 图标按需引入
+ Element Plus 按需引入
+ 分包
+ gzip
+ 图片转 WebP

测试条件必须写清：

md
测试条件：`pnpm build` + `pnpm preview`，Chrome 开发者工具勾选 Disable cache，
网络限速 Slow 4G，取三次刷新的平均值。

“分包”那一行会很有意思 —— 你会发现 dist 总大小没变、首屏传输量也没变。这不是失败。 分包减少的是“用户第二次访问、而你更新了代码”时的下载量。

把你对这件事的理解写进结论。 这比数字本身更能说明你真的懂了。

如果首屏下降不到 50%，检查这几件事：

  • 有没有做路由懒加载（这一项通常贡献最大）
  • 有没有 import * as ElementPlusIconsVue 这种全量引入
  • 有没有把首屏用不到的库（比如 echarts）打进首屏 chunk
  • 第一屏的图片有没有转格式、有没有加 loading="lazy"

参考思路

没有服务器怎么办？ 三个选择：

方案成本说明
Vercel / Netlify / Cloudflare Pages免费自动 HTTPS、压缩、SPA 回退，最省事
学校或云厂商的学生服务器免费或低价能练到真实的 Nginx 配置
内网服务器可能受限教室可能访问不到，慎用

推荐用静态托管平台。 它把 HTTPS、压缩、SPA 回退都自动处理了，你能把时间花在真正的功能上。

但如果你想练 Nginx 配置（这也是一项能写进简历的技能），就找一台服务器做一遍。

关于“子路由刷新不 404”这一项：

用静态托管平台的话，要确认平台识别出了这是单页应用。Vercel 通常会自动识别，但如果识别失败，需要自己加配置：

json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }]
}

注意这条规则会覆盖所有路径，包括 /api/*。如果有接口转发需求，要把它放在前面：

json
{
  "rewrites": [
    { "source": "/api/(.*)", "destination": "https://api.example.com/api/$1" },
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

规则是按顺序匹配的，接口规则必须写在前面。

关于“手机能访问”，最容易出问题的是接口地址：

  • 如果 .env.production 里写的是 http://localhost:8080，手机上会去连手机自己的 8080 端口。
  • 如果写的是内网 IP（192.168.x.x），用流量访问时连不上。

用相对路径 /api + Nginx 转发不会有这个问题。 这也是推荐这种配置的原因之一。

参考思路

“已知问题”这一条，写什么好？

三到五条真实的问题。可以从这些角度找：

角度例子
没做的功能报名不支持候补队列
简化了的实现时段冲突检测未考虑准备时间
性能上的取舍数据看板每次都重新请求，未做缓存
边界情况活动标题没有做敏感词过滤
权限粒度目前只有两个角色，没有细到按钮级
移动端管理端只做了桌面端适配，手机端体验一般

不要写这种：

  • “界面还可以更美观”（这不是问题，是感受）
  • “代码可以更规范”（空话，没说哪里不规范）
  • “功能还可以更完善”（同义反复）

判断标准：每一条都应该能对应到一个具体的、可以动手做的改进项。比如“报名不支持候补队列”可以直接变成一个任务；“界面还可以更美观”没法变成一个任务。

关于“关键设计决策”的代价怎么写，举两个例子：

决策为什么代价
下架用独立字段 offShelf，不做成状态下架和时间驱动的状态是两个维度，混在一起会出现“下架的活动到截止时间变成什么”这类冲突判断“能不能报名”要同时检查三个条件（状态、下架标记、名额），不能只看状态一个字段
新增与编辑共用一个表单组件字段和校验规则完全相同，避免维护两份组件内部要通过 isEdit 分支处理回显与提交，逻辑复杂度上升；且必须靠路由 :key 强制重建，否则切换时数据会残留

注意“代价”那一列说的都是真实的、可验证的后果。 这就是合格与不合格的分界线。

选做 1：写一个自动部署脚本 ​

要求 ​

把部署过程写成一个脚本，一条命令完成。要求：

  • 有前置检查（工作区是否干净、构建是否成功）
  • 有备份机制（出问题能回滚）
  • 失败时立即退出，不带着错误继续

验收标准 ​

检查项通过标准
一条命令完成部署执行脚本后线上自动更新
有工作区检查有未提交改动时会阻止部署并提示
有备份部署前备份了当前线上版本
有失败退出中间任何一步失败都会停下来
有回滚方法文档里写了怎么用备份恢复
脚本里有注释每一步在做什么能看懂
参考思路

核心是 set -euo pipefail 这一行。

bash
#!/usr/bin/env bash
set -euo pipefail

三个参数各自的作用：

参数作用不加的后果
-e任何命令返回非零就退出构建失败了，脚本继续往下跑，传上去的是旧产物
-u用未定义变量时报错拼错变量名时得到空字符串，命令执行出意外结果
-o pipefail管道中任何一环失败都算失败pnpm build | tee log 里构建失败会被 tee 的返回值掩盖

-o pipefail 这一条最容易被忽略。 它的作用是：管道命令的返回值取最后一个非零值，而不是最后一个命令的返回值。

bash
# 没有 pipefail：即使 pnpm build 失败，整个管的返回值是 tee 的 0
pnpm build | tee build.log
echo $?   # 0，看起来成功了

关于备份，最简单的做法是在服务器上留一份上一版：

bash
# 部署前先备份
ssh "$SERVER" "rm -rf $REMOTE_DIR.prev && cp -r $REMOTE_DIR $REMOTE_DIR.prev"

# 出问题时回滚
ssh "$SERVER" "rm -rf $REMOTE_DIR && mv $REMOTE_DIR.prev $REMOTE_DIR"

注意备份目录不能放在站点根目录下，否则会被 Nginx 当成静态资源提供出去，别人可以直接访问到你的旧代码。

关于“工作区检查”，这一条看起来多余，但它能避免一类很烦的问题：

bash
if [ -n "$(git status --porcelain)" ]; then
  echo "工作区有未提交的改动："
  git status --short
  echo "请先提交或暂存后再部署"
  exit 1
fi

为什么重要：部署脚本通常是“在服务器上拉代码 + 构建”，拉到的是已提交的代码。如果本地有未提交的改动，你测的是 A 版本，服务器构建的是 B 版本 —— 排查这类不一致会花掉很多时间。

选做 2：给项目加上持续的代码质量保障 ​

要求 ​

在仓库里加上自动检查，让问题在提交时就暴露。

  • 提交前跑 ESLint 和 Prettier（只检查改动过的文件）
  • 提交信息符合 Conventional Commits
  • 推送后自动跑一次构建，构建失败会有通知

验收标准 ​

检查项通过标准
提交前自动检查故意写一行不合规范的代码，提交被拦下
只检查改动的文件提交时不会因为别人文件的旧问题被拦
提交信息有校验写“update”这样的信息会被拒绝
推送后有自动构建在仓库的 Actions 页面能看到构建记录
构建失败有反馈故意推一个语法错误的提交，能看到失败记录
参考思路

这套东西在 3.5 自动构建流水线 里讲过基础。 这里是把它真正接到项目上。

配置的关键点：

json
{
  "scripts": {
    "lint": "eslint . --fix",
    "format": "prettier --write src/",
    "prepare": "husky",
    "build:check": "vite build && node scripts/check-size.mjs"
  },
  "lint-staged": {
    "*.{js,vue}": ["eslint --fix", "prettier --write"],
    "*.{css,scss}": ["stylelint --fix", "prettier --write"],
    "*.{json,md}": ["prettier --write"]
  }
}

“只检查改动的文件”这一条靠 lint-staged。 它只把本次提交涉及的文件传给 ESLint，而不是整个项目。

为什么要这样：全项目跑 ESLint 可能会报出几百条历史遗留的警告，于是大家都用 --no-verify 跳过检查 —— 钩子就形同虚设了。

“从改动文件开始”是让规范真正生效的关键。 老代码的规范可以慢慢补，但新代码必须干净。

关于“故意写错代码测试钩子”，这个动作很重要：

bash
# 1. 写一行不合规范的代码（比如用双引号、少分号、变量未使用）
echo 'const a = "x"' >> src/utils/format.js

# 2. 尝试提交
git add src/utils/format.js
git commit -m "test: 测试钩子"

# 3. 观察是否被拦下，以及报了什么错

# 4. 撤销测试改动
git checkout -- src/utils/format.js

如果没被拦下，检查 .husky/pre-commit 文件有没有执行权限：

bash
ls -l .husky/pre-commit
chmod +x .husky/pre-commit   # 没有执行权限的话加上

这一步很容易漏，尤其是在 Windows 上克隆下来的仓库 —— Git 默认不保留文件的执行权限（core.filemode 配置）。在 .husky 目录里加一个 .gitattributes 或者在文档里写明“克隆后要执行 chmod”，能避免团队成员都踩一遍。

选做 3：给项目写一份使用手册 ​

要求 ​

站在使用者（活动组织者、审核员）的角度写一份操作说明，不是技术文档。

验收标准 ​

检查项通过标准
按角色组织分成“组织者怎么用”“审核员怎么用”两部分
用截图说明每个关键步骤有截图
覆盖完整流程从创建活动到审核报名，走完整条主线
说明了业务规则名额怎么算、什么情况下不能报名、时段冲突怎么判断
有常见问题至少 5 条，都是使用层面的问题
没有技术术语不出现“接口”“组件”“部署”这类词
参考思路

这份文档的训练价值在于“换视角”。

你写了两周代码，脑子里的模型是“数据、接口、组件”。但使用者的模型是“我要办一个活动，怎么让同学报名”。

这个转换很难，但它是产品能力的核心。

几个具体的改写例子：

技术视角的说法使用者视角的说法
活动状态为 SIGNING 且 offShelf = false 且 approvedCount < quota 时才可报名活动在报名期内、没有被下架、名额还没满，学生才能报名
提交后调用 POST /api/signups 接口点击“提交报名”按钮
校验失败会返回 400 与错误码如果必填项没填，会提示“请填写…”

“常见问题”要写使用者真的会问的：

  • 学生报名了但我没审核，会占名额吗？（不会，只有通过审核才占）
  • 名额满了之后还能改大吗？（可以，改大后报名入口会重新打开）
  • 我不小心下架了活动，学生已经看到的报名还在吗？（还在，下架只是不让新报名）
  • 两个场次安排在同一个场地，中间不留时间可以吗？（可以，边界相接不算冲突）
  • 审核错了能改吗？（已通过的记录可以撤销，撤销后名额会释放）

每一条问题都应该对应到一条真实的业务规则。 写不出来，说明你对规则的理解还不够清楚。

做完之后回答一个问题：写这份文档的过程中，有没有发现规则设计上的漏洞？（提示：很多人在这一步才发现“名额满了之后报名入口该不该关”“驳回的报名能不能重新提交”这类问题当时没想清楚）发现了就补进设计文档。

选做 4：做一次完整的故障演练 ​

要求 ​

故意制造六种故障，逐个排查，记录现象和定位方法。

编号制造什么故障
1注释掉 Nginx 的 try_files
2把 .env.production 的接口地址改成 http://localhost:8080
3把 base 改成 '/wrong/'
4注释掉 index.html 的不缓存配置
5去掉 axios 的超时配置，把后端停掉
6在 proxy_pass 后面加一个斜杠

验收标准 ​

检查项通过标准
六种故障都复现了每种都有现象记录
记录了控制台报错不是只写“打不开”
记录了 Network 表现Status、请求地址、响应头
有定位方法看到什么现象能推出是哪个问题
有排查时间记录第一次多久，之后多久
都改回来了确认线上恢复正常
参考思路

这个练习的价值在“建立症状与原因的对应关系”。

做完之后你应该形成这样的直觉：

现象第一反应
子路由按 F5 才 404，点菜单正常history 回退配置（try_files）
白屏，资源请求路径里有 /wrong/base 配错
接口请求地址里出现 localhost打包时的环境变量没配对
更新部署后用户还看到旧版index.html 被缓存了
接口 404，但地址看起来对proxy_pass 的斜杠，或后端没监听
一直转圈不停，最后超时后端挂了，或地址不通

“更新部署后用户还看到旧版”这一条特别值得做。 它不像白屏那么明显，很容易被误判成“用户没刷新”。

正确的验证方法：

  1. 部署版本 A
  2. 用普通刷新（F5，不用 Ctrl+Shift+R）打开页面
  3. 部署版本 B（改一行界面上看得见的文案）
  4. 再用普通刷新打开，看是不是还是 A 的文案

如果还是 A，就是 index.html 被缓存了。

记录“排查时间”这一项很有意思。 第一次可能需要半小时，做完六种之后再遇到同样的现象，几分钟就能定位。这个时间差就是这次练习的收获。

最后提醒：一定要改回来并确认线上正常。 演练的目的是学习，不是真的把项目搞坏。
