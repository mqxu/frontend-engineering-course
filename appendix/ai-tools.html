AI 编程工具速查 ​

这一页是 AI 协作的工具区。正文讲方法与边界，这里按“你此刻要解决的问题”来查。

  • 不知道选哪个工具 → 看第一节的工具速查表。
  • 要让 AI 先读懂你的项目 → 抄第三节的 AGENTS.md 模板。
  • 知道要什么但说不清 → 翻第四节的提示词句式库。
  • 拿到 AI 的代码不知道从哪审起 → 用第五节的审查清单。
  • 想确认 AI 说的包和版本是真的 → 跑第六节的核实命令。

一、工具速查表 ​

先给结论：学生阶段按“能直接用、不花钱、中文好”三条选，不要比参数。 一年内工具排名就换过一轮，比较工具型号的收益很低，练描述能力与审查能力的收益很高。

国内工具 ​

工具形态费用适合的场景注意点

这些工具在中国大陆没有官方的合规服务，存在网络不稳、账号被封、数据出境这几类风险。做课程项目优先用本土工具，不要在这件事上耗时间。

别做的事

不要为了用某个工具去借账号、买代充、装来路不明的东西。课程考核的是能力，不是工具型号。

二、选工具的三步 ​

  1. 装上能免费用的那一个，用两周。 不用比较，先有手感。
  2. 两周后如果觉得“它老听不懂我要什么”，先别换工具。 问题通常在描述方式上，去翻第四节的句式库。
  3. 等你能稳定把一次任务描述清楚，再考虑换。 工具换起来很快，描述能力换不掉。

三、AGENTS.md 模板 ​

最小可用版 ​

放在仓库根目录，与代码一起提交。先从这个版本开始，遇到新问题就往上加：

md
# 项目约定

## 常用命令
- 装依赖：pnpm install
- 开发：pnpm dev
- 构建：pnpm build
- 检查：pnpm lint

改完先跑 lint 再提交。

## 技术栈
Vue 3.5（组合式 API + script setup）+ Vite 8 + Vue Router 5 + Pinia 4 +
Element Plus 2，包管理用 pnpm。

## 目录约定
- src/views      页面组件，一个路由一个文件
- src/components 通用组件，被两处以上复用才放进来
- src/api        接口函数，按业务模块分文件
- src/stores     Pinia store，一个模块一个文件

## 接口约定
- 响应格式 { code, message, data }，成功码是 0，不是 200
- 前端字段用驼峰，后端返回下划线，转换在 api 层做

## 禁止事项
- 不要写任何密钥、token、真实账号密码
- 不要删除你没有确认过引用位置的代码
- 不要引入新的 UI 库或状态管理库

几个写作要点 ​

要点说明
命令放最前面AI 最常见的错误之一是编造命令，写在最前面能明显减少
禁止事项要具体“不写密钥”“不删未确认引用的代码”这类边界说明，比冗长的风格清单更有效
控制在一两百行只做导航性说明，细节用链接指向别的文档。这个做法叫“渐进式披露”
每条都要能对上项目写“成功码是 0”之前确认你们的后端真是这样，写错了比不写更糟
支持分层子目录可以再放一份更细的，AI 处理该目录文件时就近的覆盖上层的

完整的项目级模板（含业务规则、提交规范、代码风格）见综合项目的 AI 协作规范。

四、提示词句式库 ​

提示词的效果差异，八成来自三件事：给了多少上下文、约束写没写清、要什么格式的输出。

下面按用途分组，方括号里是要你自己填的部分。

4.1 解释类 ​

text
用一句话解释 [概念] 是什么、解决什么问题、什么时候不该用它。
不要展开，不要举例，我要的是判断标准。
text
这段代码是做什么的？请按三部分回答：
1. 输入是什么、输出是什么
2. 关键的那一两个设计决定，以及为什么这么做
3. 如果这里出错，会表现出什么现象

为什么这么写：加上“按三部分回答”，输出的结构就固定了，你不用在散乱的文字里找重点。最后一句问“出错会怎么表现”，其实是在帮你准备验收动作。

4.2 生成类 ​

text
先读仓库根目录的 AGENTS.md 和 [文档路径]，按照 [任务文档路径] 的要求实现。

要求：
1. 只创建 [文件列表]，不要修改其他已有文件
2. 接口只用 [接口清单路径] 里列出的，不要新增接口
3. [项目特定约束，例如：成功码是 0]

先不要写代码，先把实现计划讲一遍，包含你打算改哪些文件、
每个文件做什么、有哪些地方你不确定。我确认后你再写。

为什么这么写：四个约束分别防四类问题 —— 改超范围、编造接口、违反项目约定、想错方向。“先讲计划”这一条最省时间：看错计划只要一分钟就能纠正，代码写错了要重来。

4.3 排查类 ​

text
报错原文：
[完整粘贴，不要删减]

我的操作：[做了什么触发的]
已经试过：[试过什么，结果如何]
相关文件：[涉及的文件路径]

请回答：
1. 这个报错最可能的原因是什么，按可能性排序，给出判断依据
2. 为了确认是哪一种，我下一步应该看什么、跑什么命令
3. 每种原因对应的改法

不确定的地方直接说不确定，不要给猜测性的结论。

为什么这么写：“已经试过”这一段能省掉大量来回。最后一句很关键 —— 不写这句，AI 倾向于给一个听起来确定的答案，而不是说“我不确定”。

4.4 审查类 ​

text
请审查 [文件路径] 的这段改动，重点看：
1. 有没有违反 AGENTS.md 里的约定
2. 加载中、空数据、出错三种状态处理了吗
3. 有没有硬编码的假数据、密钥、调试用的输出
4. 有没有改动这段代码不该改的地方

每条问题请给出：文件与位置、为什么是问题、怎么改。
没有问题就说没有问题，不要为了凑数硬找。

为什么这么写：最后一句必要。不写这句，它经常为了让输出“看起来有价值”而挑一些不重要的小毛病，你会被淹没在无关建议里。

4.5 让它承认不确定 ​

这三句可以随时追加，很实用：

text
这条结论你有把握吗？如果没有，直接说没有把握，不要猜。
text
这个包名和版本号，你确定在官方仓库里存在吗？如果不确定，告诉我怎么核实。
text
你刚才建议我删除这个文件，请先给出检索它是否被引用的命令，我自己跑一遍。

五、AI 代码审查清单 ​

5.1 通用清单 ​

按类别过，比从头读一遍快，也不容易漏。

接口与数据

  • [ ] 成功码用的是 0，不是 200
  • [ ] 错误分支有处理，错误码被挂到了 Error 对象上（err.code = code）
  • [ ] 页面里没有出现后端下划线字段，转换在 api 层做了
  • [ ] 用到的接口都在接口清单里，没有编造的接口
  • [ ] 没有硬编码的假数据残留

状态与渲染

  • [ ] 加载中、空数据、出错三种状态都有对应界面
  • [ ] v-for 用了稳定的业务 id 作 key，不是数组下标
  • [ ] 没有把能算出来的值另存一份状态
  • [ ] 解构响应式对象时没有切断响应式
  • [ ] 没有在子组件里修改 props 或 props 对象的内部属性

边界与异常

  • [ ] 空数组、空字符串、null 时页面不报错
  • [ ] 数字为 0、字符串为空时判断逻辑仍然正确
  • [ ] 提交类按钮有防重复点击
  • [ ] 组件卸载时清理了定时器、事件监听、watch

安全

  • [ ] 没有密钥、token、真实账号密码
  • [ ] 没有用前端判断当权限控制的唯一手段
  • [ ] 没有把不可信内容直接当 HTML 渲染
  • [ ] 没有 token 出现在日志或地址栏里

可维护

  • [ ] 没有 console.log 残留
  • [ ] 命名与项目其他部分一致
  • [ ] 没有重复实现项目里已有的工具函数或组件
  • [ ] 改动范围与预期一致（git diff --name-only 看一眼）

5.2 AI 代码的六种典型问题 ​

这类问题的共同点是：看起来对，但不一定对。 人工代码的典型错误是命名不规范、边界漏判、逻辑写反；AI 的典型错误不是“明显写错”，是“补全了你没说清的地方”。有统计显示 AI 生成代码平均每个 PR 的问题数是人工代码的 1.7 倍，其中九成以上属于不立即报错但长期难维护的问题。

下面六种按出现频率排，每种给出识别方法。

一、编造的依赖

现象：package.json 里出现一个命名完全符合规范、版本号也合理的包，但仓库里没有。

识别：装之前先在浏览器打开 https://www.npmjs.com/package/[包名] 确认存在。或跑：

bash
curl -s https://registry.npmjs.org/[包名]/latest | head -c 200

如果返回 {"error":"Not found"}，这个包不存在。

二、默认约定写错

现象：按行业最常见的方式写，而不是按你们项目的约定写。典型是成功码写成 200，而项目约定是 0。

识别：把 AGENTS.md 里的约定逐条对照生成的代码。这类问题单靠读代码看不出来，因为两种写法看起来一样合理。

三、把错误信息丢掉

现象：拦截器里写 Promise.reject(new Error(message))，业务码 code 丢失，页面里 e.code === 2005 永远不成立。

识别：搜一遍项目里所有判断业务码的地方，看它们依赖的字段是不是真的传到了。

四、只写成功路径

现象：函数只有正常返回的分支，没有失败处理；页面只有“有数据”这一种显示。

识别：对着每个请求问一句“如果这个请求失败了，页面会显示什么”。答不出来就是漏了。

五、状态放错位置

现象：组合式函数把状态定义在模块作用域（写在 export function 外面），所有用到它的组件共享同一份数据。两个列表页互相影响，且只在同时打开时才复现。

识别：看组合式函数里 ref / reactive 定义在函数体内还是函数体外。定义在体外就是在共享。

六、建议删除“看起来没人用”的代码

现象：AI 判断某个文件或函数没有被引用，建议删掉。但这个文件可能是路由懒加载或动态导入进来的。

识别：任何删除建议都先让它给出检索命令，自己跑一遍确认。 例：

bash
grep -rn "组件名" src --include="*.vue" --include="*.js"

搜不到不等于没人用 —— 动态导入的路径往往是以变量拼出来的。

六、核实命令 ​

AI 给的版本号和包名一律要核。三个常用命令：

bash
# 查包的最新版本
curl -s https://registry.npmjs.org/vue/latest | head -c 200

# 包名里带斜杠的，斜杠要转义成 %2F
curl -s https://registry.npmjs.org/@vue%2Fuse%2Fcore/latest | head -c 200

# 查某个命令行工具是否存在
command -v pnpm

Node 各版本的 LTS 名称与发布时间：

bash
curl -s https://nodejs.org/dist/index.json | head -c 600

为什么必须自己核

AI 的训练数据有截止时间，它给出的版本号一定会过期，而且它有时会把版本号和包名“拼”出来。这类错误的识别成本很高，因为它看起来完全合理。

七、AI 相关术语 ​

术语一句话解释常见误解
编码代理 Coding Agent能读文件、改文件、跑命令的 AI 工具，不只是补全以为它和补全是同一类东西。补全帮你打字，代理替你把事做完
上下文工程 Context Engineering决定往对话里放哪些信息，让产出更准以为提示词越长越好。无关信息会稀释重点
AGENTS.md放在仓库根目录、告诉 AI 项目约定的 Markdown 文件以为它是某个工具的专有配置。它是跨工具的通用格式
渐进式披露 Progressive Disclosure主文件只放导航性信息，细节按需展开以为把所有内容塞进一个文件更好
MCP让 AI 连接外部服务（数据库、接口、内部系统）的一套协议以为要自己实现。知道它是什么、什么时候需要就够
Agent Skills把一套流程和资料打包成可复用的能力，AI 按需加载以为要写代码。它就是一个目录加一份 Markdown
规格驱动开发 SDD先写清“要建什么、为什么”，再让 AI 按规格实现以为要多写一堆文档。规格就是需求、规则、接口这几份
提示注入 Prompt Injection把恶意指令藏在 AI 会读到的地方，让它执行不该执行的操作以为只在安全领域才需要关心。2026 年 3 月已出现针对编码代理的真实攻击
验证缺口 Verification Gap多数人知道 AI 代码不能全信，但不到一半的人每次提交前真的检查以为“看着跑通了”就等于验证过
代码异味 Code Smell不立即报错、但让代码越来越难维护的写法以为只有报错的问题才算问题。有研究显示 AI 代码九成以上的问题属于这一类
幻觉依赖 Hallucinated DependencyAI 编出来的、仓库里不存在的包名或坐标以为名字符合规范就一定是真的

更完整的通用术语见术语表。

怎么用这一页 ​

不要通读。它是遇到问题时来查的。

一个建议的用法是：每次让 AI 产出代码后，用第五节的清单过一遍，把踩到的问题记在自己的开发记录里。 前两次会花十几分钟，三五次之后就变成条件反射了 —— 这时候你审 AI 代码的速度，会比手写快得多。
