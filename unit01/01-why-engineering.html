1.1 前端是怎么走到工程化的 ​

一个真实的问题 ​

打开任何一个成熟互联网产品的前端页面，按 F12，切到 Sources 面板，你会看到几百万行压缩过的代码。 但你去看这个产品的前端仓库，它是这样的：

text
src/
├── api/              接口定义，一个业务模块一个文件
├── assets/           图片、字体等静态资源
├── components/       通用组件，跨页面复用
├── composables/      组合式函数，把可复用的逻辑抽出来
├── layouts/          布局组件
├── router/           路由配置
├── stores/           全局状态
├── styles/           全局样式与变量
├── utils/            纯工具函数
├── views/            页面组件
├── App.vue
└── main.js

几十个人同时改这个仓库，还要保证每周发一次版。 靠什么？靠的就是这一节要讲的东西 —— 工程化。

要理解它是什么，最好的办法是回头看：这些东西是怎么一步步长出来的。

第一阶段 · 静态页面时代 ​

时间：大致是 1995 到 2005 年。

工作方式：写好 HTML 文件，用 FTP 传到服务器。要改一处文字，就重新上传一次文件。

html
<!DOCTYPE html>
<html>
  <head>
    <title>公司首页</title>
  </head>
  <body>
    <h1>欢迎光临</h1>
    <p>联系电话：025-8888xxxx</p>
  </body>
</html>

这个阶段没有"前端工程师"这个岗位。做页面的人往往同时会写后端，页面只是后端模板的一部分（比如 JSP、ASP）。

痛点：页面上的任何一点变化，都要刷新整个页面。用户点一个"查看更多"，浏览器就白屏一下再重新加载。 交互体验现在看起来不能忍，但在当时没有更好的办法。

第二阶段 · jQuery 时代 ​

时间：大致是 2006 到 2013 年。

转折点：Ajax 技术普及，大家发现"不刷新页面也能取数据"；同时浏览器之间的兼容性差异成了噩梦 （写一个事件监听要判断五种浏览器）。jQuery 出现了，它把兼容性差异抹平，用一句 $('#id').on('click', fn) 解决了原来要写十几行的事。

js
// 用 jQuery 做一个"点击显示更多"
$('#more-btn').on('click', function () {
  $.get('/api/list', { page: 2 }, function (res) {
    var html = ''
    for (var i = 0; i < res.data.length; i++) {
      html += '<li>' + res.data[i].title + '</li>'
    }
    $('#list').append(html)
  })
})

注意这段代码里最重要的那个词：append —— 我们在手动操作 DOM。数据变了，我们得自己找到页面上的元素， 然后手动把它改掉。

痛点在两三年后开始显现：

  • 页面一复杂，代码里全是 $('#xxx')，谁也不知道哪个元素被谁改过。
  • 数据在 JS 变量里有一份，在页面上还有一份。改了变量忘了改页面，页面就不更新；改了页面没改变量， 下次操作又对不上。两份数据要人工保持同步，这是 bug 的温床。
  • 一个页面上千行 jQuery 代码，函数之间互相调用，没人敢删任何一个函数。

第三阶段 · 工程化起步 ​

时间：大致是 2013 到 2018 年。

这个阶段的起点是一个看起来跟前端无关的事：Node.js 出现了。

Node 让 JavaScript 可以脱离浏览器运行。这件事的意义是：前端终于能在自己的电脑上跑工具了。 于是各种工具开始出现：

工具类型代表解决什么
包管理npm、yarn、bower依赖不用手动下载、手动复制粘贴
模块化打包Browserify、Webpack、Rollup把几百个源文件打包成浏览器能加载的几个文件
任务自动化Grunt、Gulp压缩、编译、监听文件变化，自动跑
语法转换Babel提前用还没普及的新语法
CSS 预处理Sass、Less变量、嵌套、函数
框架Angular、React、Vue不再手动操作 DOM，改为描述"数据变化后页面应该长什么样"

这一堆工具带来的变化是根本性的：前端从"写页面"变成了"做工程"。

但代价也很直接 —— 一个 2016 年的 Vue 项目，光配置文件就有：

text
build/
├── build.js
├── check-versions.js
├── utils.js
├── vue-loader.conf.js
├── webpack.base.conf.js
├── webpack.dev.conf.js
├── webpack.prod.conf.js
└── webpack.test.conf.js
.babelrc
.eslintrc.js
.editorconfig
.postcssrc.js
package.json

八个 webpack 配置文件，光看懂 base / dev / prod 三者的关系就要花半天。这就是为什么后来的工具都在追求"零配置"。

第四阶段 · 组件化与全链路 ​

时间：2018 年至今。

这一阶段的主题是收敛：工具变少了，配置变短了，但能做的事更多了。

变化前后对比
构建工具Webpack 八个配置文件 → Vite 一个配置文件，启动从 30 秒到 1 秒
代码组织按文件类型分目录 → 按功能分目录，一个功能的模板、逻辑、样式放在同一个文件里
语言JavaScript 自由类型 → TypeScript 全程类型检查
复用复制粘贴组件 → 组合式函数、组件库、私有 npm 包
交付手工传到服务器 → 提交代码自动构建、自动部署

"组件化"是这一阶段最核心的变化。 以前一个按钮的样式在 CSS 文件里、结构在 HTML 里、点击逻辑在 JS 里， 三者分散在三个文件。现在它们都在同一个 .vue 文件里：

vue
<script setup>
defineProps({
  status: { type: String, required: true }
})

const MAP = {
  draft: { text: '草稿', color: '#8b95a5' },
  open: { text: '报名中', color: '#42b883' },
  closed: { text: '已截止', color: '#e6a23c' },
  ended: { text: '已结束', color: '#909399' }
}
</script>

<template>
  <span class="tag" :style="{ color: MAP[status]?.color }">
    {{ MAP[status]?.text || '未知' }}
  </span>
</template>

<style scoped>
.tag {
  font-size: 12px;
  padding: 2px 8px;
  border-radius: 4px;
  border: 1px solid currentColor;
}
</style>

一个文件里同时看到了结构、逻辑、样式，而且 scoped 保证样式不会影响别的组件。 这就是现在前端工程的基本单元。

工程化到底在解决什么：六类问题 ​

把上面的二十多年压缩一下，前端工程化要解决的问题其实就六类。这六类问题，正好对应本课程的六个部分。

#问题不解决的后果主要手段对应单元
1模块化所有代码塞在一个文件里，或者靠全局变量互相调用，改一处崩一片ES Module、按功能分目录单元 3
2依赖管理手动下载第三方库、手动复制到项目里，版本混乱、无法复现pnpm、package.json、锁文件单元 2
3编译转换浏览器不认识 .vue、不认识 Sass、不认识新语法Vite、Babel、PostCSS单元 2
4质量保障拼写错误、未使用变量、格式混乱，靠人眼在代码评审里找ESLint、Prettier、Stylelint、提交钩子单元 3
5自动化每次提交都手动跑检查、手动打包、手动发布npm scripts、CI 流水线单元 3、12
6协作交付三个人改同一个文件互相覆盖；新人拉下代码跑不起来Git 分支模型、提交规范、README单元 3、12

这六类问题要背下来

不是为了考试。当你在后面某个单元觉得"为什么要搞这么麻烦"的时候，回来看这张表 —— 你正在解决的问题一定在里面。知道自己在解决哪一类问题，学习才不会变成背命令。

反例：没有工程化的项目会是什么样 ​

假设你现在接一个需求："做一个活动报名页面，要能增删改查。" 如果没有工程化，很可能写成这样：

text
<!DOCTYPE html>
<html>
  <head>
    <script src="jquery.min.js"></script>
    <script src="bootstrap.min.js"></script>
    <link rel="stylesheet" href="bootstrap.min.css">
    <link rel="stylesheet" href="my-style.css">
  </head>
  <body>
    <div id="app">
      <table id="list"></table>
      <button id="add-btn">新增</button>
    </div>
    <script src="app.js"></script>
  </body>
</html>

看起来挺简单，但两周后问题会接连出现：

时间点出现的问题
需求改成"列表要支持搜索和分页"app.js 从 200 行变成 800 行，找到改哪里要花十分钟
第二个页面也要用同样的表格复制粘贴一份，两份代码各自演化，改一个 bug 要改两处
同事加入他拉下代码，发现少了 jquery.min.js，你忘了告诉他版本号
上线手动把文件传到服务器，传了一半网络断了，线上是半新半旧的版本
三个月后回来看完全想不起来 #app 上绑了几个事件

这五种问题，工程化都有对应的解法。 后面 11 个单元就是在逐个解决它们。

一个容易搞混的点 ​

"工程化"不等于"框架"

很多同学把"学 Vue"和"学前端工程化"当成一回事。其实两者解决的是不同问题：

  • 框架（Vue） 解决的是"怎么把数据变化反映到界面上"—— 属于写代码的层面。
  • 工程化 解决的是"代码怎么组织、依赖怎么管、质量怎么保证、怎么交付"—— 属于做项目的层面。

所以你会看到一个现象：框架用得很熟的人，仍然做不出一个能交付的项目。 因为他缺的是后半部分。 这门课的模块一（工具链）占了 12 学时，比任何一个 Vue 模块都不少，原因就在这里。

小结 ​

  • 前端经历了四个阶段：静态页面 → jQuery 手动操作 DOM → 工程化工具爆发 → 组件化与全链路收敛。 每一步都是被具体痛点推着走的。
  • 工程化要解决六类问题：模块化、依赖管理、编译转换、质量保障、自动化、协作交付。
  • 框架解决"怎么写代码"，工程化解决"怎么做项目"。 两者都要会。
  • 后面每个单元对应其中某一类或几类问题，遇到困惑时回来看第一节的对照表。

常见坑 ​

坑 1："工具太多了，学不过来"

工具确实多，但它们不是平级的。先分清哪些是"必须会"、哪些是"知道有这个东西就行"：

层次内容要求
必须会pnpm 装依赖、package.json 字段、Vite 基本配置、ESLint 报错定位、Git 提交要能独立操作
会用就行Stylelint、husky、lint-staged、commitlint按教程配好，知道它拦住了什么
知道就行Rollup、esbuild、SWC、Babel 的细节听说过，需要时再查

按照这个分层，真正"必须会"的东西其实不多。

坑 2："为什么要用 Node？前端不是浏览器的事吗"

Node 在我们这门课里不是用来写后端服务的，它是给工具链用的运行环境。

Vite、ESLint、Prettier 这些都是用 JavaScript 写的程序，需要一个 JavaScript 运行环境才能跑起来 —— 就像 .exe 需要 Windows、.jar 需要 JVM 一样。Node 就是这个角色。

坑 3："我看别人项目里没有 webpack.config.js，是不是不用学构建工具"

那个人大概率在用 Vite。Vite 把绝大多数配置都预设好了，所以配置文件很短甚至没有 —— 但这不是"不需要构建工具"，而是"构建工具的默认值变好了"。 一旦要配代理、配别名、拆包， 还是得知道配置写在哪。

课后练习 ​

练习 1：找一个真实项目的前端仓库

到 GitHub 上找一个人气较高的 Vue 3 项目（搜索 vue3 admin 之类），把它的 src 目录结构截图， 标出下面几项分别在哪个目录：

  1. 页面组件
  2. 通用组件
  3. 接口定义
  4. 全局状态
  5. 工具函数

参考思路：先从 main.js 或 main.ts 看入口引入了什么，再顺着 router 找到页面组件的位置。 不同项目的命名习惯不一样（比如 stores 和 store、api 和 apis），不要只看目录名，要打开看内容。

练习 2：给自己列一份"痛点清单"

回忆你做过的最大一个网页作业（课设、比赛、实习项目都行），从下面六个方面各写一条你遇到过的问题：

  • 模块化：有没有出现过"所有 JS 写在一个文件里"？
  • 依赖管理：有没有出现过"换台电脑跑不起来"？
  • 编译转换：有没有想要用 Sass 但不知道怎么用？
  • 质量保障：有没有过因为一个拼写错误查了半小时？
  • 自动化：有没有过"每次改完手动压缩文件"？
  • 协作交付：有没有过和同学互相覆盖代码？

参考思路：这些清单不是作业任务。写完之后你会发现，这门课后面每个单元都在解决你清单里的一条。 把它们留着，学到对应单元时回来对照，感受会不一样。

练习 3：画出你的"前端发展时间线"

用一页纸（或思维导图工具）画出四个阶段的演进：每个阶段写清三件事 —— 当时怎么干活、遇到了什么痛点、催生了什么工具。

参考思路：不要照抄本节内容。尝试用自己的话描述，特别是"痛点"那一栏 —— 能用自己的语言讲清痛点，说明你真的理解了为什么会有这些工具。
