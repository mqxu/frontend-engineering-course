10.5 错误分层处理 ​

一个具体的场景 ​

活动列表页上线第一天，审核员点了"加载更多"，出现了这样一幕：

屏幕右上角一个接一个弹出五条一模一样的红色提示：

text
网络连接失败，请检查网络
网络连接失败，请检查网络
网络连接失败，请检查网络
网络连接失败，请检查网络
网络连接失败，请检查网络

同时列表区域是一片空白，没有"重试"按钮，也没有任何说明。 用户不知道该等还是该刷新，只能一遍遍点"加载更多"，然后继续被五条提示砸。

这五条提示来自五个组件各自写的 catch。 问题不在"提示了错误"，而在没有一个统一的分工：谁该提示、谁该只改状态、谁该安静地失败。

这一节把错误分成四层，每一层定好"在哪里处理、给用户看到什么"。

先用四个问题把错误分堆 ​

拿到一个错误，先问四个问题：

  1. 是请求根本没发出去吗？（断网、域名解析失败）
  2. 是请求发出去了但超时吗？
  3. 是服务器响应了，但 HTTP 状态码表示失败吗？（4xx / 5xx）
  4. 是 HTTP 状态码正常，但业务码说失败吗？（200 但 code: 4001 名额已满）

前两个属于网络层，第三个属于HTTP 层，第四个属于业务层。 再加一层权限层（401 / 403），因为它们有专门的处理方式。

四层错误各在哪里处理 ​

层次典型表现在哪里处理用户看到什么
网络层断网、超时、ERR_CONNECTION_REFUSED请求层拦截器识别，页面显示错误态列表区显示"网络连接失败，点击重试"；toast 只弹一次
HTTP 层404 / 500 / 502请求层统一提示，页面按需显示错误态一条 toast 说明 + 页面错误态
业务层HTTP 200，code 非成功请求层统一提示并抛错；表单类错误由页面展示一般 toast；表单校验类错误显示在对应字段下
权限层401 未登录 / 403 无权限请求层统一处理：401 清登录态跳登录页，403 提示无权限401 提示"登录已过期"并跳登录页；403 提示"没有权限"

四条处理原则：

  • 能统一处理的就不要在页面里重复处理。网络层、HTTP 层、权限层都在拦截器里统一办。
  • 页面层只做"界面状态"：加载中、出错、空、有数据，四态里的一态。
  • 同一个错误只提示一次。拦截器提示过了，页面 catch 就不要再弹。
  • 能恢复的错误给用户一个动作入口（重试按钮），不能恢复的说清楚原因。

在拦截器里统一处理 ​

10.4 里的 request.js 已经做了大部分工作。 这里补两个细节。

网络层与超时的区分 ​

axios 抛出的错误里，error.response 不存在表示请求根本没到达服务器， error.code === 'ECONNABORTED' 表示超时：

js
function classifyError(error) {
  // 1. 请求被取消（用户主动取消或竞态取消），不提示
  if (axios.isCancel(error)) return { silent: true }

  // 2. 超时
  if (error.code === 'ECONNABORTED') {
    return { message: '请求超时，请检查网络后重试', retryable: true }
  }

  // 3. 请求没发出去（断网 / 域名解析失败）
  if (!error.response) {
    return { message: '网络连接失败，请检查网络', retryable: true }
  }

  // 4. HTTP 状态错误
  const status = error.response.status
  if (status === 401) return { needLogin: true }
  if (status === 403) return { message: '没有权限执行这个操作', retryable: false }
  if (status === 404) return { message: '请求的资源不存在', retryable: false }
  if (status >= 500) return { message: '服务器出错了，请稍后再试', retryable: true }

  return { message: error.message || '请求失败', retryable: true }
}

retryable 这个标记有什么用

它告诉页面"这个错误值不值得给一个重试按钮"。 网络超时、5xx 通常是暂时的，重试可能成功； 403、404 重试一百次也没用，就不该给按钮误导用户。

业务层的错误码 ​

业务错误码是后端定义的，常见的有：

业务码含义谁该处理
200成功——
4001名额已满报名页面弹窗说明，不跳转
4002时段冲突（同场地时段重叠）表单页在时段字段旁提示
4003报名已截止页面提示并刷新活动状态
4010手机号格式不对表单字段错误，显示在该输入框下

一般业务错误用 toast 就够；表单校验类错误应该显示到对应字段上。 这需要请求层把错误码一起抛出去，让页面能按码区分：

js
if (res.code !== 0) {
  const err = new Error(res.message || '操作失败')
  err.code = res.code // ✓ 把业务码带上，页面可以按码分支
  // 表单类错误交给页面展示，通用错误在这里提示
  if (!FORM_ERROR_CODES.includes(res.code)) {
    ElMessage.error(err.message)
  }
  return Promise.reject(err)
}

错误提示用哪种呈现方式 ​

三种主要方式，各有各的场合：

呈现方式用在什么错误上例子
全局 toast与当前操作相关、用户无法自己修复的错误保存失败、服务器出错
页面级错误态页面主体数据加载失败，页面无内容可显示活动列表加载失败，整个列表区换成重试按钮
表单级字段错误具体某个输入项不合法，用户改一下就能通过"名额必须大于 0"、"截止时间不能早于现在"

怎么选 ​

  • 页面主体的数据加载失败 → 页面级错误态。 因为列表是空的，光弹 toast 用户什么都看不到， 需要一个"重试"按钮占在列表的位置。
  • 一次操作（保存、删除、提交）失败 → toast。 页面上原来的内容还在，弹一条说明即可。
  • 表单字段错误 → 字段下方红字。 让用户知道改哪里。

不要用 toast 显示表单校验错误

"名额必须大于 0" 弹成一条右上角的 toast，用户看着表单不知道是哪一个字段错了。 表单错误要贴着字段显示，这是用户能直接修复的错误。

同一个错误只提示一次 ​

这是最容易违反的一条。约定好分工：

  • 拦截器负责提示（网络层、HTTP 层、通用业务层）。
  • 页面 catch 只负责改状态（把 error 字段设上、显示重试按钮），不再弹 toast。
js
async function load() {
  try {
    await activityStore.fetchList()
  } catch (e) {
    // ✓ 拦截器已经提示过了，这里只改界面状态
    pageError.value = e.message
  }
}

如果某个页面确实需要"自定义提示、不要拦截器的默认提示"， 应该在接口函数上打一个标记（比如自定义 header X-Silent: 1），让拦截器跳过提示， 而不是把 toast 弹两遍。

五条一样提示的根因

上一幕里五个组件各自弹了一次，是因为把"提示"的责任放在了页面， 而一次故障会同时影响五个请求。

统一放到拦截器后，只要你不在页面里再弹，故障时最多一条提示。 如果还有重复，检查是不是同一个接口被 watch 反复触发了 —— 那是请求重复发送的问题， 见 常见报错附录。

静默失败：有些错误不该打扰用户 ​

不是所有错误都要让用户知道。下面这几类应该安静地失败：

场景为什么不提示怎么处理
埋点上报用户不关心，失败了也不影响使用直接 catch 吞掉，最多 console.warn
心跳 / 轮询偶尔失败很正常，下个周期会重试不提示，连续失败 N 次再考虑提示
预取数据用户还没用到，失败了到时候重试不提示
已取消的请求是程序主动取消的，不是错误axios.isCancel 判断后直接返回
js
// 埋点失败不打扰用户
export function reportEventApi(data) {
  return request.post('/track', data, { silent: true })
}

在请求拦截器里读 config.silent，如果为真就给 config 打标记， 响应拦截器里看到这个标记就不弹提示。

静默不等于不记录

静默失败也要留下痕迹 —— console.warn 一条，或者上报到错误监控。 "用户不知道"和"开发不知道"是两回事，排查线上问题时这些记录很有用。

重试策略 ​

网络抖动很常见，有些请求值得自动重试。

哪些能重试 ​

请求类型能不能重试原因
GET 查询✓ 能幂等，重复执行不会改变数据
PUT 全量更新✓ 一般能幂等，重复执行结果一样
DELETE✓ 一般能幂等，删两次和删一次结果一样
POST 新建✗ 不能非幂等，重试可能创建两条记录
POST 动作（通过审核）✗ 不能重试可能重复扣名额

"幂等"是关键判断词：同一个请求执行多次，对服务器的影响是否和执行一次一样。 是，才能自动重试。

重试几次、怎么等 ​

js
/**
 * 带指数退避的重试
 * @param {Function} fn 返回 Promise 的请求函数
 * @param {number} maxRetries 最多重试几次
 */
export async function withRetry(fn, maxRetries = 2) {
  let lastError
  for (let i = 0; i <= maxRetries; i++) {
    try {
      return await fn()
    } catch (e) {
      lastError = e
      // 不可重试的错误直接抛出（比如 403）
      if (!e.retryable) throw e
      if (i === maxRetries) break
      // 指数退避：1 秒、2 秒、4 秒……
      const delay = 1000 * 2 ** i
      await new Promise((resolve) => setTimeout(resolve, delay))
    }
  }
  throw lastError
}

要点：

  • 重试 2 到 3 次就够。次数太多会把用户的等待时间拖得很长。
  • 等待时间要递增（指数退避）。服务器正忙时，立刻重试只会加重负担。
  • 只重试幂等请求，新建、动作类接口不要自动重试。
  • 重试失败后要落到"页面错误态 + 重试按钮"，把决定权交给用户。

自动重试要小心副作用

"通过报名审核"如果自动重试了三次，可能把一条报名通过了三次（后端没做幂等的话）， 名额直接被多扣。凡是会改变数据的接口，重试一律由用户手动触发。

实战：把活动列表页的错误处理补全 ​

假设活动列表页有三个请求源：列表、筛选条件对应的选项、页面统计。 按分层补齐。

vue
<script setup>
import { ref, onMounted } from 'vue'
import { storeToRefs } from 'pinia'
import { useActivityStore } from '@/stores/activity'

const activityStore = useActivityStore()
const { list, loading, total } = storeToRefs(activityStore)

// 页面级错误：只处理"列表加载失败"这一种
const pageError = ref('')
// 统计失败是次要信息，静默处理
const stats = ref(null)

async function loadList() {
  pageError.value = ''
  try {
    await activityStore.fetchList()
  } catch (e) {
    // ✓ 拦截器已提示，这里只负责让页面显示错误态
    pageError.value = e.message
  }
}

async function loadStats() {
  try {
    // 统计是次要内容，失败不影响主流程，不提示用户
    stats.value = await getActivityStatsApi()
  } catch {
    stats.value = null // 静默失败
  }
}

onMounted(() => {
  loadList()
  loadStats()
})
</script>

<template>
  <div class="page">
    <!-- 页面级错误态：占据列表的位置，给一个重试入口 -->
    <div v-if="pageError" class="error-state">
      <p>{{ pageError }}</p>
      <button @click="loadList">重新加载</button>
    </div>

    <!-- 四态的正常分支 -->
    <p v-else-if="loading">加载中…</p>
    <p v-else-if="list.length === 0">还没有活动</p>
    <ul v-else>
      <li v-for="item in list" :key="item.id">{{ item.title }}</li>
    </ul>
  </div>
</template>

这段代码体现了四条分工：

  1. 主数据的错误 → 页面错误态 + 重试按钮。
  2. 次要数据的错误 → 静默失败（统计不显示就行）。
  3. 页面里不弹 toast，提示由拦截器统一负责。
  4. 错误态和加载态是并列的四态之一，不会和加载中同时出现。

别让错误态和加载态打架

上面用 v-if="pageError" 放在最前面，是为了出错时不要继续显示"加载中"。 如果顺序写反，用户会看到错误提示下面还有一个转不完的圈。

小结 ​

  • 错误分四层：网络层、HTTP 层、业务层、权限层，各自有固定的处理位置与呈现方式。
  • 网络层、HTTP 层、权限层在拦截器统一处理；页面只负责界面状态。
  • 呈现方式三选一：全局 toast（操作失败）、页面错误态（主体数据加载失败）、 表单字段错误（字段不合法）。
  • 同一个错误只提示一次，拦截器提示过页面就不要再弹。
  • 埋点、心跳、取消的请求要静默失败，但仍要留日志。
  • 只有幂等请求（GET / PUT / DELETE）能自动重试，重试 2 到 3 次并用指数退避。

常见坑 ​

坑 1：页面里既弹 toast 又显示错误态，用户看到两层提示

现象：列表加载失败，右上角弹一条，列表区又显示一条。

原因：提示责任分散在拦截器和页面两处。

怎么处理：约定拦截器负责提示，页面只改状态。 页面里的 catch 不再调 ElMessage。

坑 2：表单错误弹成 toast

现象：提交活动表单，名额填了 -1，弹出一条 toast 说"名额必须大于 0"， 用户不知道该改哪个框。

原因：把字段级错误当成了操作级错误。

怎么处理：字段错误显示在字段下方。用 Element Plus 的 el-form 校验规则， 或在字段组件上绑 error 属性。

坑 3：取消请求被当成错误提示

现象：用户快速切页，控制台/界面弹出"请求已取消"。

原因：竞态防护里调用了 AbortController.abort()， 拦截器把这个当成网络错误提示了。

怎么处理：拦截器里先判断 axios.isCancel(error)，是就直接 silent 返回。

坑 4：重试把 POST 请求执行了多次

现象：点击"提交报名"后网络抖动，用户看到失败又点了两次，结果报了三次名。

原因：要么是自动重试了非幂等接口，要么是按钮没做防重复点击。

怎么处理：扣住 Submit 按钮（提交中禁用），非幂等接口不自动重试。 详见 常见报错附录 里的"请求重复发送"。

坑 5：401 后提示"网络连接失败"

现象：登录过期，用户看到的是"网络连接失败，请检查网络"，而不是"登录已过期"。

原因：拦截器里 401 分支没写，落到了默认的网络错误分支。

怎么处理：把 401 判断放在最前面，别的分支都不要抢它。

坑 6：500 错误把后端返回的堆栈直接显示给用户

现象：页面上出现一长串英文报错和技术细节。

原因：直接把 error.message 展示出来了。

怎么处理：给用户看人话，技术细节写日志。 500 统一显示"服务器出错了，请稍后再试"，把原始信息 console.error 出去。

练习 1：给一个页面的每个请求定好错误层次

请求属于哪一层可能出错出错怎么提示是否给重试入口

参考思路：填完检查有没有重复提示，以及有没有该静默的接口（比如统计、埋点）在弹 toast。

练习 2：给"报名"表单做字段级错误

报名表单有学号、姓名、手机号三个字段。服务端会对学号重复、手机号格式做校验， 返回不同的业务码。让这些错误显示到对应字段下方。

参考思路：请求层把业务码抛出，页面按码把消息写进对应字段的 error。 关键是建立业务码与字段的映射，别用一堆 if 硬编码在模板里。

练习 3：实现幂等判断的重试

写一个 withRetry(fn, maxRetries)，只在错误标记 retryable 为真时重试， 并且等待时间按 1 秒、2 秒、4 秒递增。用两个假请求测试： 一个前两次失败第三次成功，一个每次都失败。

参考思路：重点是"可重试"的判定放在哪里 —— 放在错误对象上（拦截器打标记），而不是在重试函数里猜。
