单元 10 · AI 协作：接口约定最容易走偏的地方 ​

这一章讲全局状态与请求层。这两块都是“约定密集型”的 —— 成功码是几、错误码怎么带、字段用驼峰还是下划线、分页参数叫什么，全部是约定，而且每一条约定都有两种以上常见的做法。

AI 的问题就出在这里：它会按行业里最常见的那种做法写，而不是按你们项目的约定写。 成功码是最典型的例子 —— 它默认写成 200，而本项目的约定是 0。

麻烦的是这类错误不会报语法错。它表现为“所有请求都进了错误分支”，或者“某个按错误码分支的判断永远不成立”—— 现象和原因离得很远，要查一阵子。

这一节的用法和前面几章有个明显不同：你必须在提示词里把约定写清楚，不能让它猜。

这一章哪些活能交给 AI ​

判断标准：约定由你提供、它负责实现，这个分工没问题；一旦让它去“补上”约定，就会出问题。

任务能交给 AI 吗为什么
按你给的约定起草接口函数可以拼地址、给参数，机械工作
起草 Pinia store 的骨架可以写法有固定套路
检查错误分支有没有把业务码带出去可以它对着清单核对比人快
检查页面里有没有出现下划线字段可以检索类工作它做得快
解释持久化插件的配置项可以配置项的含义它讲得清
起草错误提示的文案可以一句话的事
判断“成功码是几”不能直接信它默认按行业最常见的方式写 200
判断“这条错误该不该提示用户”不能直接信它容易把每一类错误都提示一遍，用户会被打扰
决定哪些状态要持久化不行涉及安全与体验的取舍
决定字段名怎么定不行要和后端一起定

倒数第三行是这一章的核心。 约定这件事不存在“它应该知道”—— 你不写进提示词，或者不写进 AGENTS.md，它就只能猜，而猜错的概率不低。

提示词怎么写 ​

1. 把约定贴在提示词里，让它按约定写 ​

text
请按下面的约定，帮我写一个活动列表的接口函数和对应的 store。

【接口约定】
- 响应格式 { code, message, data }，成功码是 0，不是 200
- 业务错误码是四位数字：2005 名额已满，2006 已过报名截止时间
- 分页参数是 page 与 pageSize，返回结构 { list, total, page, pageSize }
- 后端返回下划线字段，前端用驼峰，转换在 src/api 层做，页面里不出现下划线

【目录约定】
- 接口函数放 src/api/activity.js
- store 放 src/stores/activity.js，用 setup 写法
- 请求实例已经封装好，从 @/utils/request 引入，不要改它的拦截器

【要求】
- 错误分支要把业务码挂到错误对象上，页面里要用到
- store 的 action 要有加载中与失败两种状态，不要只写成功路径
- 写完之后，把你用到的每条约定逐条列出来，标注“约定里写明的”还是“你自己决定的”

为什么这么写：最后一条要求是这段提示词的关键。让它把“哪些是约定、哪些是自己决定的”标出来，你就能一眼看到它猜了哪些地方 —— 而那些地方就是你下一步要核实的重点。

注意请求实例那一条。本项目的拦截器已经处理了业务码和登录失效，AI 很容易“顺手优化”把它改掉，改完之后页面里 e.code === 2005 这类判断全部失效。把“不要改拦截器”写进提示词和 AGENTS.md，能省掉这类问题。

2. 让它审 store 的 action 有没有覆盖失败路径 ​

text
这是我的 store：

[粘贴完整代码]

请逐个 action 检查，用表格输出：
| action 名 | 有没有置 loading | 成功时会改哪些状态 | 失败时会改哪些状态 | 失败后 loading 会不会被重置 |

要求：
1. 每一行都要写，不要只列有问题的
2. 特别检查：请求失败时 loading 会不会一直是 true
3. 特别检查：连续调用两次时，第一次的失败会不会覆盖第二次的成功

为什么这么写：loading 永远是 true 是这一章最典型的一个 bug —— 它出现在 try 里没有 finally 的时候。现象是“点了一次按钮之后，界面一直在转圈，再点也没反应”。这类错误靠读代码很容易漏，因为它看起来“挺完整的”。

第 3 点是给连续请求准备的。列表页翻页、搜索框边输边查都会触发连续请求，这一条能提前把竞态问题暴露出来。

3. 让它检查错误分支有没有丢掉信息 ​

text
这是我的请求层和一处调用方代码：

[粘贴 request.js 的响应拦截器]
[粘贴一个调用方的 catch 分支]

请回答：
1. 拦截器 reject 出来的错误对象上，有哪些字段？（逐个列出来）
2. 业务码有没有被带出来？如果只带了 message，说明调用方会遇到什么
3. 调用方现在靠什么判断错误类型？够不够用？
4. 如果要让调用方能按业务码分支处理，拦截器该怎么改？给改法

为什么这么写：这一段的核心是“错误对象上有什么”。写 Promise.reject(new Error(message)) 的时候，Error 身上只有 message —— 业务码、数据全都丢了。第 2 点让这个问题具体化：调用方会遇到什么。答案就是它只能显示一句文案，没法按码做不同的处理。

比如“名额已满”和“已过报名截止时间”这两条，用户该做的事不同（一个去看别的活动，一个什么都不用做），但如果拦截器只带出 message，页面里就没法分开处理。这个后果说出来，改动理由才成立。

AI 在这一章容易错什么 ​

默认成功码是 200 ​

现象：拦截器里写着 if (res.code === 200)，或者判断写成 if (res.code !== 200) throw new Error(...)。整段代码读起来毫无破绽。

原因：200 是 HTTP 状态码里最常见的成功码，也是很多后端框架的默认约定。它的训练数据里这个数字出现频率最高，所以它默认写这个。

后果很好辨认：所有请求都进了错误分支。 接口明明返回成功，界面却弹一句“操作失败”或者其他奇怪提示。你去看后端返回，code 是 0；再看前端判断，是 200。

怎么处理：两条一起做。

  1. 把约定写进 AGENTS.md 的接口约定一节。 这一条属于“写一次永久生效”的约定：成功码是 0，不是 200。写进去之后它每次都会读到。
  2. 改完之后核对一遍代码里所有判断成功的地方。 一个项目里可能有多处判断（拦截器、单独的下载函数、某个绕过拦截器的调用），改一处不等于改完。
js
// ✗ 按行业默认写
if (res.code === 200) { return res.data }

// ✓ 按项目约定写
if (res.code === 0) { return res.data }

顺便说一个“找出来的办法”：这类问题的现象是“所有接口都失败”，所以排查时先看第一个请求的响应体，别急着看页面代码。响应体里 code 是什么值，一眼就能确认是哪边错了。

reject 的时候把业务码丢了 ​

现象：拦截器里写 return Promise.reject(new Error(res.message))。页面里写 catch (e) { if (e.code === 2005) {...} }，这个分支永远不进去。

原因：new Error(message) 只接受一个字符串参数。业务码 res.code 和 res.data 都没地方放，就丢了。它给的这个写法看起来没问题 —— 错误确实被抛出来了，message 也有。

怎么处理：把码和数据挂回错误对象上。

js
// ✗ 信息丢了
return Promise.reject(new Error(res.message || '操作失败'))

// ✓ 把码和数据带上
const err = new Error(res.message || '操作失败')
err.code = res.code       // 页面可以按码分支处理
err.data = res.data       // 有些错误码会带数据（比如当前剩余名额）
return Promise.reject(err)

判断有没有漏掉这件事，用一句话自查：“页面里的 catch 除了 e.message，还能读到什么？” 如果只能读到 message，那就是漏了。

顺带一个相关的坑：HTTP 错误分支（网络断了、超时、状态非 2xx）也要按同样的方式处理。那种情况下业务码在 error.response.data.code 里，容易被忘掉。两处都处理好了，页面里才有一套统一的错误处理方式。

字段名没做转换，页面里漏出下划线 ​

现象：页面里出现 row.signup_count、item.created_at、activity.start_time。

原因：后端返回下划线是数据库的习惯，前端用驼峰是 JavaScript 的习惯。转换这一步 AI 很容易忘 —— 因为不转换代码也能跑，只是字段名看着别扭。

怎么处理：本项目约定“转换在 src/api 层做，页面里不出现下划线字段”。这样做的好处是：页面代码只和一种命名风格打交道，转换只发生在一个地方。

检查办法是检索，让 AI 做比你自己搜快：

bash
# 在页面和组件目录里搜下划线字段
grep -rn "_[a-z]\{2,\}" src/views src/components

搜出来之后要判断是不是误报 —— 有些下划线不是字段名（比如 CSS 类名、v-model 修饰符）。别一键替换，逐条看。

顺带一条关于转换位置的经验：转换放在 src/api 层意味着每个接口函数都要写一遍转换。接口多了之后容易漏，可以考虑写一个统一的转换函数，在拦截器里做一次。哪种更好取决于你们的接口数量 —— 接口少的时候分散写更直观，多的时候集中做更省心。

store 只定义了成功路径 ​

现象：store 的 action 大致是这样 ——

js
// ✗ 只写成功路径
async function load() {
  const res = await getActivityListApi(query)
  list.value = res.list
  total.value = res.total
}

原因：写成功路径是“让功能跑起来”的最短路径。loading、error、finally 都是“另外还要处理的”，它不会主动补。

怎么处理：要求它给每个 action 都补上三样：加载中、失败、重置。最常见的漏法是 loading 没有被重置 ——

js
// ✓ 三样都补上
async function load() {
  loading.value = true
  error.value = ''
  try {
    const res = await getActivityListApi(query)
    list.value = res.list
    total.value = res.total
  } catch (e) {
    error.value = e.message || '加载失败'   // 失败也要落到状态上
  } finally {
    loading.value = false                    // 这一句最容易漏
  }
}

判断有没有漏，看现象：loading 永远是 true，界面一直转圈。 原因就是请求失败时直接跳出了函数，finally 里那句被漏掉（或者根本没写 finally）。

还有一类错误：持久化存太多

现象：它给的持久化配置是“把整个 store 都存起来”，或者 persist: true 一把梭，所有状态进 localStorage。

原因：全量持久化写起来最省事，一行配置就完事。

怎么处理：持久化要挑着存，不是越多越好。 三条判断标准：

判断说明
这份数据重新拿一次贵不贵不贵就别存，进页面重新请求就行
存下来会不会有安全风险token、手机号、身份证这类要格外小心
存下来会不会“过期”列表数据存三天再打开，看到的是旧的，用户会困惑

按这三条过一遍，本项目里值得持久化的其实只有少数几样：token、用户的基本信息、界面偏好（比如侧边栏折叠状态、每页显示多少条）。

最不该全量存的是列表数据。 存进 localStorage 之后，用户下次打开看到的是一份可能已经过期的数据，而他不知道这件事。数据该由接口给，不该由缓存给。

另外提醒一句：localStorage 里的内容页面上任何脚本都能读。凡是你不想被 XSS 偷走的东西，都不该放进去。 这条在单元 9里讲过，判断标准是一样的。

怎么验收 AI 的产出 ​

这一章的产出是请求层和 store。验收动作的核心是约定的一致性，因为不一致不报错。

  • [ ] 代码里所有判断成功的地方，用的都是 0 而不是 200
  • [ ] 拦截器 reject 出来的错误对象上带业务码和 data，不只是 message
  • [ ] HTTP 错误分支也同样挂了业务码
  • [ ] 页面和组件目录里搜不到下划线字段
  • [ ] 每个 store 的 action 都有加载中、失败、重置三样，finally 里有重置
  • [ ] 连续触发两次请求时，先返回的那次不会覆盖后返回的
  • [ ] 持久化只存了该存的几样，列表数据没有进去
  • [ ] 拦截器没有被改动（你没让它“顺手优化”，它也没擅自改）

前四条对应“约定对不对”，中间两条对应“不顺利的路径写了没”，后两条对应“边界”。这八条过完，请求层就可以给整个项目用了。

练习 ​

写一个故意丢掉业务码的请求函数，让 AI 找出来 ​

任务：把拦截器里的错误处理改成 Promise.reject(new Error(res.message))（也就是丢掉业务码），然后在页面里写一个按 e.code === 2005 分支处理的逻辑，让它变得永远不生效。再让 AI 找出来。

要求：记录里必须包含这四项：

项要求
埋的问题写清改了哪一行
现象描述写清触发了什么、界面显示了什么
AI 有没有找出来找出来了就粘它的定位过程；没找出来就写你换了什么问法
改法与验证写清改完之后怎么确认它已经生效
验收标准与参考思路

为什么这个 bug 值得专门埋一次：它的现象和原因离得太远 —— 你看到的是“名额已满的提示没有出现”，要往回查三层才能找到拦截器里 new Error(message) 那一行。在练习里花二十分钟，比在综合项目联调时花两小时划算。

思路提示：

  • 制造这个 bug 需要一个会返回业务错误的接口。本项目的 2005（名额已满）正好合适 —— 报名一个已经满员的活动就能触发。
  • 第一次问它“这个页面有什么问题”，它多半会在页面代码里找。这是预期结果，记下来。 它看不到拦截器，因为错误的对象上没有码，这个因果关系需要你把两段代码一起给它。
  • 再换第 3 个提示词模板（把拦截器和调用方一起贴给它，问“错误对象上有哪些字段”）。对比两种问法的结果。
  • 改完的验证要注意：不能只看“提示出现了”，要确认页面真的走到了按码分支 —— 在分支里加一句不同的显示（比如显示“换一个活动试试”），能区分出来才算验证成功。
  • 顺手检查一下别处：项目里还有没有别的 catch 也在读 e.code？改一处不够。

不合格的写法：

让 AI 看了一下，它说这里应该把 code 带上，我改了就好了。

“改了就好了”没说明怎么确认好了。而且它没提 HTTP 错误分支 —— 那条也丢码，但触发条件不同（要断网或者让后端返回 4xx），不检查就发现不了。

合格的写法：

我把拦截器里业务失败的分支改成了 Promise.reject(new Error(res.message))。 触发办法：报名一个满员的活动。现象是页面只弹了“操作失败”， 本来该出现的“换一个活动试试”没有出现 —— 因为 e.code 是 undefined。 第一次问“这个页面有什么问题”，它说“catch 分支里缺少对错误类型的判断”，没找到根因。 换成把拦截器和调用方一起贴给它之后，它列出了错误对象上只有 message 一个字段， 定位到了。 改法是把 err.code = res.code 和 err.data = res.data 加回去。 验证时我在分支里加了一句不同的文案，重新触发，看到文案变了才算确认。 另外我发现 HTTP 错误分支也没带码，一起改了 —— 触发办法是把接口地址改错，看 404 的提示。

差别在于：后者不但改了业务错误分支，还主动检查了 HTTP 错误分支，并且把“怎么确认改对了”做成了一个能观察的动作。
