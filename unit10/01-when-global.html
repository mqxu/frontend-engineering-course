10.1 什么时候需要全局状态 ​

一个具体的场景 ​

校园活动服务平台的管理端有三个页面要用到"当前登录用户"：

  • 顶部导航栏要显示"张审核员"和角色标签。
  • 活动列表页要根据角色决定"新建活动"按钮显不显示（只有组织者能建）。
  • 报名审核页要把审核人记在审核记录里。

按你目前会的方法，最直接的写法是把用户信息从登录组件一层层传下去：

vue
<template>
  <TopNav :user="user" />
  <RouterView :user="user" @update-user="user = $event" />
</template>

然后每一层页面组件都要在自己的 props 里声明一遍 user， 用到的地方再往下传一层。这就是 props 逐层传。

问题很快出现：

  1. 报名审核页是 /review 路由，它上面隔了布局组件、侧边栏组件， 用户信息要穿过三层才到。
  2. 导航栏里改了用户名（比如用户改了昵称），怎么通知到别的页面？ 需要 emit 一路往回传。
  3. 有一个页面是自己刷新用户信息的（refreshUser）， 它要 emit 上去、父组件再往下传、再传给导航栏。

结构一复杂，"谁负责改、谁负责传"就说不清楚了。这就是全局状态要解决的问题。

一句话判断

一份数据如果被多个不相邻的页面/组件共用，而且需要跨路由跳转保留， 那它就是全局状态。否则，先考虑留在组件里。

先看三种方案 ​

在学 Pinia 之前，你已经有三种办法在组件之间共享数据。它们不是替代关系，各管一段。

方案数据流向适用场景不适用场景
props / emits父 → 子传递，子 → 父通知父子直系关系；数据只在这一小块界面里用跨越三层以上；多个页面共用
provide / inject祖先 → 后代，跳过中间层某个子树范围内的共享，比如一个多步表单的所有步骤数据要跨路由存在；全局都要用
全局状态（Pinia）任何组件都可以读写登录用户、权限、全局通知、跨页面缓存只在一个页面用的临时数据

props 逐层传：什么时候够用 ​

如果数据只在一棵不深的树里流动，props 反而是最清楚的做法。 比如一个活动筛选组件，把筛选条件从父页面传给筛选子组件：

vue
<template>
  <ActivityFilter :keyword="keyword" @change="keyword = $event" />
</template>

父子直接相邻，谁改的值、谁接收，一眼能看出来。不要为了用 Pinia 而把这种数据搬进全局。 判断依据很简单：中间有没有被迫传一个自己根本用不到的属性。

provide / inject：中间层无关的场合 ​

单元 8 讲过的依赖注入适合"某个子树范围内共享"。 比如报名审核向导分三步，三步组件都需要知道"当前审核的是哪条报名记录"， 但它们之间隔着一个步骤容器：

js
import { provide, ref } from 'vue'

const reviewId = ref(null)

// 提供出去，所有后代用 inject 都能拿到，中间的步骤容器不用管
provide('reviewId', reviewId)

provide / inject 解决不了跨路由的问题

provide 的数据只在这个组件及其后代的生命周期内有效。 一旦路由跳走、组件被卸载，provide 的值就没了。

所以它不能用来存登录用户 —— 用户登录后跳到别的路由，provide 那棵子树早就销毁了。

全局状态：跨页面、跨路由、跨组件树 ​

登录用户就是典型例子：导航栏、列表页、审核页、路由守卫都要读它， 它们既不是父子关系，也不一定在同一棵子树里，而且要在路由跳转后一直保留。 这种数据才应该交给全局状态。

判断标准 ​

遇到一份数据，按下面这三步问自己：

第一步：这份数据被几个地方用？

  • 只有一个组件用（哪怕它是个大页面）→ 留在组件里。
  • 父子两三个组件用，且结构简单 → props 或 provide/inject。
  • 多个不相邻的页面/组件都要读 → 全局状态。

第二步：它需要在路由跳转后还保留吗？

  • 跳走就丢掉无所谓 → 可以留在组件里。
  • 跳到别的页面还要用，甚至刷新浏览器还要在 → 全局状态（可能还要持久化）。

第三步：它需要被多处修改吗？

  • 只有一处会改，其他地方只看 → 先考虑放在最近的公共父级。
  • 多个地方都会改（登录页写、退出按钮清、拦截器刷）→ 全局状态， 因为只有集中管理才能保证"改的时候只有一个入口"。

把这三步写成一张决策表：

问题答案 → 选择
只在一个组件里用？是 → 组件内部状态（ref / reactive）
父子直系，中间没人挡着？是 → props / emits
只在某个子树里共享？是 → provide / inject
多个不相邻的页面共用一个值？是 → Pinia
需要跨路由或跨刷新保留？是 → Pinia（可能加持久化）
多个地方都会修改它？是 → Pinia

用最少的工具解决问题

上表从上往下，能停在前面的就不要往后走。 用 props 能解决的硬塞进 Pinia，会让数据流从"看得见"变成"看不见" —— 改一个值，你不知道还有谁会受影响。

不该放进全局的东西 ​

初学 Pinia 最常见的错误是"开了新玩具就想到处用"，把组件里所有变量都搬进 store。 下面这几类明确不该放全局。

表单里的临时输入 ​

登录表单的账号、密码输入框，活动表单的标题、名额：

js
// ✓ 留在组件里
const username = ref('')
const password = ref('')

// ✗ 不要这样
// const authStore = useAuthStore()
// authStore.loginForm.password = ''   // 密码进了全局状态，还能被持久化，风险更大

理由：表单输入是"这个页面正在编辑的草稿"，跟别的页面无关。 放进全局状态后，用户填了一半切走、再切回来，会看到残留的半截内容，反而更困惑。 更重要的是，密码这类值一旦进全局状态，就很容易被一起持久化到 localStorage。

弹窗的开关 ​

"新建活动"弹窗的 visible、确认删除弹窗的 show：

js
// ✓ 弹窗归它所在的页面管
const createDialogVisible = ref(false)

理由：弹窗状态只影响"这一小块界面显示不显示"，没有任何别的页面需要知道。 唯一值得放全局的例外是全局通知队列（一次登录后全站都要弹同一个提示）—— 那属于工具性质，见案例 06。

只在单页面用的列表数据 ​

活动列表页从接口拿到的活动数组：

  • 如果只有列表页用这一份数据，详情页是自己另外调的接口，那列表可以留在页面里。
  • 如果详情页、编辑页、审核页都要读同一个活动对象，才把它放进全局状态。

判断这句就够：别的页面会不会来读它？

可以重新算出来的数据 ​

"筛选后的活动列表"这种可以从"原始列表 + 筛选条件"算出来的值， 应该用 computed 算，而不是存一份全局状态再手动同步：

js
// ✓ 派生数据用 computed，不占全局状态
const filteredList = computed(() =>
  list.value.filter((item) => item.status === filterStatus.value)
)

理由：存两份就会有一份忘记同步。原始数据变了、派生数据没更新， 这类 bug 最难查。

什么都往全局塞会怎样

  • 数据流难以追踪：你改了一个 store 字段，不知道有哪些页面会跟着变； 排查 bug 时要在十几个文件里搜这个字段名。
  • 调试变复杂：Vue DevTools 里 store 的状态一直在变，你分不清是哪次操作引起的。
  • 热更新变迟钝：改一个 store 文件，依赖它的组件全都要重新加载。
  • 容易误持久化：localStorage 里躺着一堆本该是临时的数据，刷新后行为诡异。

小结 ​

  • 三种共享方案各管一段：props/emits 管父子，provide/inject 管子树，Pinia 管跨页面跨路由。
  • 判断三步：被几个地方用、要不要跨路由保留、有几个地方会改。三问有一问成立，才考虑全局。
  • 能停在 props 或 provide/inject 的，不要往后走到 Pinia。
  • 表单临时输入、弹窗开关、单页面数据、可派生的数据，都不该进全局状态。
  • 放错位置的代价是数据流不可追踪、调试变难、误持久化。

常见坑 ​

坑 1：把所有接口数据都塞进一个 store

现象：写了个 useDataStore，里面有活动、报名、场地、用户……几百行， 改任何一个模块都要在这个文件里找。

原因：没有按业务边界拆分。全局状态不是为了"统一管理所有数据"， 而是为了"共享的数据有唯一来源"。

怎么处理：一个业务模块一个 store 文件，useAuthStore、useActivityStore、 useSignupStore 各自独立。跨模块需要的数据通过跨模块调用拿， 不要合并成一个巨型 store。

坑 2：把只在一个页面用的数据放进全局，结果页面切换后数据还在

现象：用户从活动列表筛选出"报名中"，跳到详情页再返回， 发现筛选条件还在，但他以为自己重进了一个新页面。

原因：把筛选条件放进了全局状态（还持久化了）。

怎么处理：先想清楚"返回列表时保留筛选条件"是不是产品要的行为。 如果是，这样做没问题，但要把行为写进注释说明这是有意为之； 如果不是，筛选条件就应该留在列表页组件里，页面卸载时自然重置。

坑 3：派生数据也存一份进 store

现象：store 里有 list 和 filteredList 两个字段， 某次修改 list 后忘了同步 filteredList，页面上显示的条数对不上。

原因：把 computed 能算的东西存成了 state。

怎么处理：能算的不要存。store 的 getters 就是干这个的：

js
export const useActivityStore = defineStore('activity', () => {
  const list = ref([])
  // ✓ 派生值用 computed，永远跟着 list 走
  const count = computed(() => list.value.length)
  return { list, count }
})
坑 4：以为 provide/inject 也能当全局状态用

现象：在 App.vue 里 provide('user', userRef)， 路由跳到子页面后发现注入的是 undefined。

原因：路由组件默认不在同一棵 provide 子树里（除非它们共享同一个布局组件）， 而且 provide 的值随组件卸载而失效。

怎么处理：真要全局且跨路由，用 Pinia。provide/inject 留给"一个子树范围内的共享"。

课后练习 ​

练习 1：给下面这些数据选位置

校园活动服务平台里有这些数据，逐个判断该放组件内部、props、provide/inject 还是 Pinia， 并说明理由。

  1. 登录成功后拿到的 token 与用户信息
  2. 活动列表页的关键词搜索框内容
  3. "删除活动"二次确认弹窗的显示状态
  4. 报名审核向导三步组件共用的"当前报名记录 ID"
  5. 从活动列表派生的"当前页显示的活动数量"
  6. 顶部导航栏的折叠状态（侧边栏展开/收起）

参考思路：对每一项套用三步判断。注意第 2 题和第 6 题容易答错 —— 搜索框内容如果是"输入中"的草稿，属于组件内部；如果是"已提交的筛选条件"且返回时要保留，才可以进全局。 第 6 题要看它是不是跨页面 —— 如果每个页面都有侧边栏且状态要一致，那它算全局。

练习 2：改造一个真实页面的数据分布

打开你上一单元做的活动列表页，把它用到的所有变量列成一张表， 逐个标注"放哪一层"，然后动手改：该下沉的从 store 里拿回来，该上移的从组件里搬进 store。

参考思路：完成后再问自己一遍 —— "如果我改 store 里这个字段，会有哪几个文件跟着受影响？" 如果答不上来，说明数据放的位置有问题。

练习 3：找出一个"过度全局化"的反例

找一个你写过的（或网上看到的）把大量数据放进全局状态的项目， 列出其中至少三个不该放全局的例子，说明它会导致什么具体问题。

参考思路：可以从这几个角度找证据 —— localStorage 里有没有不该在的字段、页面切换后有没有残留状态、 改一个字段要在多少文件里搜索。具体到"改了哪个字段、影响了哪个页面"才算合格。
