业务规则与状态流转 ​

这一页是项目的规则手册。所有涉及状态判断、名额计算、冲突检测的代码，都要以这里为准。

动手写代码之前先读完这一页。 状态相关的 bug 是最难改的 —— 一旦数据写错了，已经产生的记录没法追溯。

一、活动状态机 ​

状态定义 ​

状态值含义
草稿DRAFT已创建，学生看不到，可随意编辑
报名中SIGNING学生可以报名
报名截止SIGNUP_CLOSED超过报名截止时间，不再接受新报名，但活动还没办
已结束FINISHED活动已办完，归档

状态流转 ​

        ┌──────────── 编辑 ─────────────┐
        │                               │
        ▼                               │
    ┌───────┐  发布   ┌─────────┐  到报名截止时间  ┌───────────────┐  活动结束  ┌──────────┐
    │ DRAFT │ ──────> │ SIGNING │ ─────────────> │ SIGNUP_CLOSED │ ────────> │ FINISHED │
    └───────┘         └─────────┘                 └───────────────┘           └──────────┘
从到触发方式谁能触发
DRAFTSIGNING发布动作组织者（仅限自己的活动）
SIGNINGSIGNUP_CLOSED时间到达系统（后端定时任务或查询时惰性判断）
SIGNUP_CLOSEDFINISHED活动办完组织者手动点“结束”，或系统按活动结束时间判断

三条不可违背的规则 ​

规则一：状态只能向前，不能回退。

SIGNING 不能改回 DRAFT，FINISHED 不能改回 SIGNUP_CLOSED。

为什么：状态回退会让已经产生的数据变得没有意义。一个已结束的活动回退成报名中，那些已经通过审核的报名算什么？已经安排的场次算什么？

如果组织者确实需要重新开放：新建一个活动。这是刻意加的摩擦 —— 它逼着用户意识到“重新开放”是一个有后果的操作，而不是随手改个状态。

规则二：只有 DRAFT 的活动能被删除。

SIGNING、SIGNUP_CLOSED、FINISHED 的活动只能下架，不能删除。

为什么：只要有过一条报名记录，这条活动就承载了学生的数据。删掉它，学生的报名记录就成了孤儿数据。

规则三：编辑权限按状态区分。

字段DRAFTSIGNINGSIGNUP_CLOSEDFINISHED
标题可改可改可改只读
类型可改可改可改只读
活动说明可改可改可改只读
名额可改只能调大只读只读
报名截止时间可改只能往后推只读只读
状态可发布不可改不可改不可改

“名额只能调大”的原因：已经有 approvedCount 个人通过审核了。如果把名额改到比这个数小，数据就不一致 —— 到底是这些人的审核作废，还是名额上限失效？两个选择都很糟糕，所以干脆不允许。

“截止时间只能往后推”的原因：提前截止会让已经看到“还有 3 天截止”的学生觉得被坑了。往后推是善意的（比如场地延期），可以接受。

二、下架：一个独立标记，不是一个状态 ​

这是整个项目里最容易设计错的地方，单独拿出来讲。

错误的设计 ​

有人会把“下架”做成状态机里的一个状态：

DRAFT → SIGNING → OFF_SHELF → SIGNUP_CLOSED → FINISHED

这个设计会在两个地方出问题：

问题一：状态冲突。 一个活动下架了，然后报名截止时间到了。它的状态该是 OFF_SHELF 还是 SIGNUP_CLOSED？

如果改成 SIGNUP_CLOSED，那“下架”这件事就丢了 —— 组织者恢复上架时，系统不知道该恢复到哪。 如果保持 OFF_SHELF，那“报名期已过”这件事就丢了 —— 列表里看不出这个活动已经不能报名了。

问题二：恢复上架时状态不确定。 一个 SIGNING 的活动下架，三天后恢复。这三天里报名截止时间已经过了 —— 恢复后应该是 SIGNING 还是 SIGNUP_CLOSED？代码里得写一堆 if 判断。

正确的设计 ​

状态和下架是两件独立的事，分别用两个字段。

字段类型取值由谁决定
status枚举DRAFT / SIGNING / SIGNUP_CLOSED / FINISHED由时间和发布动作决定，单向
offShelf布尔true / false由人决定，随时可切换
ts
interface Activity {
  id: number
  title: string
  type: ActivityType
  organizerId: number
  quota: number              // 名额上限
  approvedCount: number      // 已通过审核的人数，由后端维护
  signupDeadline: string     // 报名截止时间
  status: ActivityStatus     // 流程状态
  offShelf: boolean          // 下架标记，默认 false
  description: string
  createdAt: string
  updatedAt: string
}

这样设计之后，前面两个问题都消失了：

  • 下架的 SIGNING 活动，报名截止后 status 自然变成 SIGNUP_CLOSED，offShelf 仍然是 true。两件事都记得住。
  • 恢复上架时只需要把 offShelf 改回 false，status 一直是准确的。不需要任何 if 判断。

下架的限制 ​

情况能不能下架说明
DRAFT不能还没发布过，没有什么可下架的
SIGNING能最常见的场景
SIGNUP_CLOSED能活动还没办，临时取消
FINISHED不能已经结束了，下架没有意义

下架之后，已存在的报名记录不受影响。 已经通过审核的学生仍然可以参加（如果活动照常办），只是不再接受新报名。

这句话要写进使用手册。 组织者最常问的就是这个。

三、名额与报名数的联动 ​

三个数字 ​

数字含义谁维护
quota名额上限组织者编辑
approvedCount已通过审核的人数后端在审核通过 / 撤销时更新
pendingCount待审核的人数后端在报名 / 审核时更新

关键规则：只有“已通过”的报名才占用名额。 待审核的不占。

为什么：如果待审核也占名额，会出现这种情况 —— 100 个人报名，其中 80 个明显不合格，但名额已经被占满了，组织者审核驳回一个才能通过一个。这会让审核变成一件很别扭的事。

“能不能报名”的完整判断 ​

一个学生能不能报名，需要同时满足四个条件：

ts
function canSignup(activity: Activity): { ok: boolean; reason?: string } {
  if (activity.status !== 'SIGNING') {
    return { ok: false, reason: '活动当前不接受报名' }
  }
  if (activity.offShelf) {
    return { ok: false, reason: '活动已下架' }
  }
  if (new Date(activity.signupDeadline).getTime() <= Date.now()) {
    return { ok: false, reason: '报名已截止' }
  }
  if (activity.approvedCount >= activity.quota) {
    return { ok: false, reason: '名额已满' }
  }
  return { ok: true }
}

注意这四个条件是“与”的关系，任何一个不满足都不能报名。

名额满了之后要做什么 ​

按课程要求，名额满了就关闭报名入口。做法有两种：

做法怎么做优点缺点
改状态SIGNING → SIGNUP_CLOSED状态一眼可见语义混淆：“报名截止”本来是时间概念
保持状态，靠判断status 不变，前端和后端都按上面的 canSignup 判断语义清晰，撤销一条审核后自动恢复可报名每次判断要查多个条件

推荐第二种。 理由：状态 SIGNUP_CLOSED 的语义是“报名期结束了”，而名额满了是“报名期还在，但进不来了”。两件事不一样。

而且第二种有个实际好处：组织者撤销一条审核，名额空出来，报名入口自动就恢复可用了。 用第一种做法的话，还得再把状态改回去。

如果用第一种做法，必须保证“撤销审核”时状态能回到 SIGNING。这个往返很容易写漏。

前端算出来的名额一定不准

approvedCount 必须由后端在事务里维护，前端只负责显示。

为什么：考虑这个顺序：

  1. 活动还剩 1 个名额
  2. 组织者 A 在电脑上点“通过”，组织者 B 在手机上同时点“通过”
  3. 两个请求几乎同时到达后端

如果后端是“先查 approvedCount，判断小于 quota，然后更新”，两个请求都会读到 approvedCount = 99（假设 quota = 100），都判断为通过，都执行更新 —— 结果是 101 个人通过审核。

这就是并发问题。 前端的任何检查都拦不住它，因为两个请求在前端是各自独立的。

后端必须做的：把“检查名额”和“写入审核结果”放进同一个数据库事务，并对活动行加锁（悲观锁 SELECT ... FOR UPDATE，或者用乐观锁的版本号）。具体实现由后端同学决定，但前端要知道这必须是后端保证的。 这一条是答辩时的重点问题。

四、时段冲突检测 ​

场次的定义 ​

一个活动可以有多个场次（比如初赛、复赛、决赛）。每个场次占用一个场地的一段时间。

ts
interface Session {
  id: number
  activityId: number
  venueId: number
  startTime: string        // 2026-04-10 14:00:00
  endTime: string          // 2026-04-10 17:00:00
  status: 'SCHEDULED' | 'ONGOING' | 'FINISHED' | 'CANCELLED'
}

冲突的判定规则 ​

两条规则：

规则一：同一个场地，两个场次的时间不能重叠。

规则二：边界相接不算冲突。

这第二条是重点。举例：

已有场次新场次冲突吗为什么
14:00 - 17:0015:00 - 18:00冲突15:00 到 17:00 重叠
14:00 - 17:0017:00 - 20:00不冲突边界相接，17:00 这一个瞬间
14:00 - 17:0013:00 - 14:00不冲突边界相接
14:00 - 17:0014:00 - 17:00冲突完全相同
14:00 - 17:0013:00 - 15:00冲突14:00 到 15:00 重叠

判断逻辑：两个区间 [a1, a2) 和 [b1, b2) 不重叠的条件是 a2 <= b1 或者 b2 <= a1。

ts
/** 判断两个时段是否冲突。边界相接不算冲突。 */
function isTimeConflict(
  aStart: Date, aEnd: Date,
  bStart: Date, bEnd: Date
): boolean {
  // 不冲突的两种情况：a 在 b 之前结束，或 b 在 a 之前结束
  if (aEnd.getTime() <= bStart.getTime()) return false
  if (bEnd.getTime() <= aStart.getTime()) return false
  return true
}

注意 <= 不能写成 <。 用 < 的话，14:00-17:00 和 17:00-20:00 会被判定为冲突 —— 因为 17:00 < 17:00 是 false，于是走到最后 return true。

这个 = 号就是“边界相接不算冲突”这条规则的实现。

修改场次时要排除自己 ​

这是一个非常经典的 bug。

场景：一个场次是 14:00 - 17:00，组织者想把开始时间改成 15:00，变成 15:00 - 17:00。

错误的实现：查询“这个场地在这个时段有没有冲突的场次”，结果查到了自己（因为自己就在这个场地上），于是报告冲突，改不了。

正确的实现：检测冲突时把自己排除掉。

ts
async function checkConflict(session: Session, excludeId?: number) {
  const existing = await getSessionsByVenue(session.venueId, session.startTime, session.endTime)
  return existing.filter((s) => {
    if (s.id === excludeId) return false          // 编辑时排除自己
    if (s.status === 'CANCELLED') return false    // 已取消的场次不占时段
    return isTimeConflict(
      new Date(session.startTime), new Date(session.endTime),
      new Date(s.startTime), new Date(s.endTime)
    )
  })
}

两个排除条件都不能少：

  • excludeId：编辑场景
  • 已取消的场次不占时段：一个场次被取消了，那个时段就应该空出来

“已取消的场次不占时段”这一条很容易漏。 漏了的后果是：组织者取消了一个场次想重新安排，结果系统说冲突。他会很困惑 —— 我明明取消了。

前端检测与后端检测 ​

前端检测的价值：让用户在填写表单时就得到反馈，不用等提交。

前端检测做不到的事：

  • 两个人同时抢占同一个时段
  • 别人刚创建的场次，你的页面还没刷新

所以后端必须再检测一次。 前端检测是为了体验，后端检测是为了正确性。这和名额问题是同一类问题。

不用前端检测行不行

行。把检测完全交给后端，前端只负责把后端返回的冲突信息展示出来。

好处：逻辑只有一份，不会出现“前端说不冲突、后端说冲突”的不一致。

代价：用户要提交才知道冲突，体验差一些。

推荐的做法：前端做检测，但把后端的冲突错误码也处理掉。这样两边都覆盖了 —— 常规情况前端即时反馈，并发情况后端兜底。

如果时间紧张，只做后端检测也完全可以接受。 这不是扣分项。

五、报名状态 ​

状态定义 ​

状态值含义
待审核PENDING学生已提交，等组织者处理
已通过APPROVED审核通过，占用一个名额
已驳回REJECTED审核不通过，附驳回理由
已取消CANCELLED学生自己撤销了报名

流转 ​

                    ┌── 通过 ──> APPROVED ──┐
                    │                       │
PENDING ────────────┼── 驳回 ──> REJECTED    ├── 撤销 ──> CANCELLED
                    │                       │
                    └───────────────────────┘
从到谁触发副作用
无PENDING学生报名pendingCount 加 1
PENDINGAPPROVED组织者、审核员pendingCount 减 1，approvedCount 加 1
PENDINGREJECTED组织者、审核员pendingCount 减 1
PENDINGCANCELLED学生pendingCount 减 1
APPROVEDCANCELLED学生、组织者approvedCount 减 1，释放一个名额
REJECTED无—终态，不能改成通过

最后一行要特别注意：REJECTED 是终态。被驳回的报名不能直接改成通过，学生需要重新报名。

为什么：驳回时有理由记录。直接改成通过，那条驳回理由就没有意义了，而且审核记录会变得混乱。保持终态的不变性，比提供便利更重要。

例外情况：如果组织者发现驳错了，正确做法是撤销驳回（把记录标记为 CANCELLED），然后让学生重新报名。这个过程会留下痕迹。

驳回必须填理由 ​

驳回时 rejectReason 必填，长度 5 到 100 字。

为什么强制：学生收到“你的报名被驳回”但不知道原因，只能来找组织者问。这条规则把沟通成本前移到了审核的时候。

字数下限 5 个字，是为了防止组织者随便填“不行”“没空”这种没有信息量的理由。

六、权限规则 ​

操作组织者审核员
看活动列表只看自己的看全部
看活动详情只看自己的看全部
创建活动能不能
编辑活动只看自己的不能
下架 / 恢复活动只看自己的能（全部）
删除活动只看自己的 DRAFT不能
审核报名只看自己活动的能（全部）
维护场地不能能
安排场次只看自己活动的能（全部）
看数据看板只统计自己的全部

这张表是“前端做界面控制 + 后端做真实校验”的依据。

前端要做的事：

  • 菜单按角色显隐
  • 按钮按角色和状态显隐
  • 路由守卫拦掉无权访问的页面

后端要做的事（真正的权限控制）：

  • 每个接口都校验当前用户有没有权限操作这条数据
  • 组织者请求别人的活动 id，返回 403

前端的权限控制只是体验优化

前端藏起来一个按钮，不等于用户不能做这件事。

用户完全可以在浏览器控制台里改掉 v-if，或者直接用 curl 调接口。如果后端没有校验，数据就被改了。

判断方法：把前端代码里的 v-if 全部去掉，看后端会不会拦住。拦得住，说明权限控制是真的；拦不住，说明只是装饰。

这句话要写在你的设计文档里。 它是答辩时的常见提问。

七、规则速查 ​

写代码时可以对着这一页快速查。

要判断的事规则
学生能不能报名status === 'SIGNING' 且 !offShelf 且未过截止时间 且 approvedCount < quota
活动能不能编辑status !== 'FINISHED' 且（组织者只能改自己的）
名额能不能改小只在 DRAFT 且 approvedCount === 0 时能
活动能不能删除status === 'DRAFT'（且只能删自己的）
活动能不能下架status !== 'DRAFT' && status !== 'FINISHED'
场次时段会不会冲突同场地、两个区间有交集（边界相接不算）、排除自己和已取消的
报名能不能改成通过当前状态必须是 PENDING
通过审核要改什么pendingCount 减 1、approvedCount 加 1，且在同一个事务里
撤销通过要改什么approvedCount 减 1（名额被释放）
能不能给已下架的活动排场次不能

八、这些规则怎么落到代码里 ​

规则不写在代码里，就会散落在各个页面里，改一次漏三处。

推荐的做法：把规则集中到一个模块。

ts
// src/domain/activity-rules.ts
export function canSignup(activity) { /* ... */ }
export function canEdit(activity, user) { /* ... */ }
export function canDelete(activity, user) { /* ... */ }
export function canOffShelf(activity, user) { /* ... */ }
export function canChangeQuota(activity, newQuota) { /* ... */ }

然后页面里只做一件事：

vue
<el-button v-if="canDelete(row, userStore.userInfo)" link type="danger" @click="handleDelete(row)">
  删除
</el-button>

这样改的好处：

  • 规则只有一份，列表页、详情页、看板的判断不会不一致
  • 规则可以单独测试（写几个用例断言 canDelete 的返回值）
  • 答辩时可以说“业务规则集中在 domain 目录，页面只负责展示”

代价：多了一层文件。而且规则变化时要同时改 domain 和页面（如果页面用了硬编码的话）。

这个取舍值得。 这一节列的规则有十来个，散在五个页面里，改一个规则要搜遍全项目。

小结 ​

  • 状态只能向前，不能回退。 回退会让已产生的数据失去意义。
  • 下架是独立标记，不是状态。 状态是单向流程，标记随时可切。混在一起会出现状态冲突。
  • 只有“已通过”的报名占名额，待审核的不占。
  • “能不能报名”要同时检查四个条件：状态、下架标记、截止时间、名额。
  • 名额满了不改状态，靠判断。 这样撤销审核后报名入口会自动恢复。
  • 并发问题前端拦不住，approvedCount 必须由后端在事务里维护。
  • 时段冲突：边界相接不算冲突。 实现上是 <= 而不是 <。
  • 修改场次要排除自己，否则自己和自己冲突，改不了。
  • 已取消的场次不占时段，漏了这一条，取消后重新安排会说冲突。
  • 驳回必须填理由（5 到 100 字），把沟通成本前移到审核时。
  • REJECTED 是终态，不能直接改成通过。驳错了要撤销后重新报名。
  • 前端权限控制只是体验优化，真正的权限必须后端做。
  • 规则集中到一个 domain 模块，不要散在页面里。
