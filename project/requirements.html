管理端需求规格 ​

这一页把管理端要做的东西写清楚：有哪些功能、每个功能包含什么字段、界面大概长什么样。

它不涉及技术实现。技术方案见接口约定和目录结构。 用户端（学生手机端）的规格不在这里，单独写在用户端需求规格。

一、项目目标 ​

一句话：让校园里的活动从“发通知、收名单、手工统计”变成“线上发布、在线报名、系统审核”。

要解决的问题（真实存在的三个痛点）：

痛点现在怎么做的做完之后
报名靠人工统计群里发通知，学生接龙，组织者手工数学生在线上报名，系统自动计数
名额管不住报满了还在报名，只能靠组织者喊停名额满了报名入口自动关闭
场地会撞车两个活动约了同一个场地同一个时间系统检测时段冲突，提交时就拦下

项目的边界（明确不做的）：

  • 管理端不做学生端页面（学生端是独立的一栏，见用户端需求规格）
  • 不做消息通知（短信、微信推送）
  • 不做活动签到
  • 不做多校区、多学校支持

把“不做什么”写清楚，比写“做什么”更重要。 它决定了你遇到新需求时该不该动手。

二、功能清单 ​

按模块列出所有功能。每一项都要有明确的验收标准，否则“做完了”和“没做完”只能靠感觉判断。

模块一：登录鉴权 ​

编号功能验收标准
A1账号密码登录输入正确的账号密码能进入后台；错误的给出明确提示
A2登录态保持登录后刷新页面仍停留在原页面，不需要重新登录
A3token 失效处理token 过期后请求会被拦下并跳回登录页，不会一直转圈
A4路由拦截未登录直接访问后台地址会被跳转到登录页，登录后回到原地址
A5角色区分组织者和审核员看到不同的菜单和按钮
A6退出登录点退出后清理登录态并回到登录页；再访问后台会被拦

模块二：活动管理 ​

编号功能验收标准
B1活动列表支持按标题关键字、状态查询；支持分页；四种状态（加载中 / 有数据 / 无数据 / 失败）都能正确显示
B2新增活动填写标题、类型、名额、报名截止时间、活动说明；保存后出现在列表里
B3编辑活动字段回填正确；保存后列表和详情同步更新
B4发布活动草稿状态的活动发布后变成报名中；报名截止时间已过的不能发布
B5下架 / 恢复下架后列表显示已下架标记；恢复后标记消失；草稿和已结束的不能下架
B6删除活动只有草稿能删除；删除有二次确认
B7活动详情显示完整信息、报名统计（已通过 / 待审核 / 已驳回）、场次数量
B8状态标签四种状态有不同颜色的标签，一眼能区分

模块三：报名审核 ​

编号功能验收标准
C1报名列表支持按活动、按审核状态、按学生姓名或学号查询；支持分页
C2单活动报名视图从活动详情能跳到该活动的报名列表，且已按该活动筛选
C3审核通过二次确认后状态变为已通过；活动名额减一
C4审核驳回必须填写驳回理由（5 到 100 字）；状态变为已驳回
C5撤销审核已通过的撤销后释放名额，报名入口恢复可用
C6名额提示名额已满时通过操作被拦下并提示；列表里显示出“42 / 100”这样的进度
C7关联信息列表里直接显示活动标题和学生姓名，不用点进详情

模块四：场地与场次 ​

编号功能验收标准
D1场地列表显示名称、容量、位置、启用状态
D2新增 / 编辑场地名称必填且唯一；容量必须是正整数
D3启用 / 停用场地停用的场地不出现在新增场次的选项里
D4场次列表支持按活动、按日期范围查询
D5新增 / 编辑场次选择活动、场地、开始与结束时间；结束后必须晚于开始
D6冲突检测同一场地同一时段重叠时提示冲突，并说明和哪个场次的哪段时间冲突；边界相接不算冲突
D7取消场次取消后该时段被释放，可以安排新的场次

模块五：数据看板 ​

编号功能验收标准
E1数量指标活动总数（按状态分布）、报名总数、待审核数、已通过数
E2名额使用率显示整体名额使用率，含算法说明
E3近期活动显示最近更新的几条活动，点击能进详情
E4待办提醒显示待审核报名数、48 小时内截止报名的活动
E5权限差异组织者只统计自己的活动，审核员统计全部

三、页面清单 ​

“一个页面一个职责”的拆分结果：

页面路由模块可访问角色
登录/login登录鉴权未登录
无权限/403登录鉴权全部
页面不存在/404登录鉴权全部
数据看板/dashboard数据看板组织者、审核员
活动列表/activity活动管理组织者、审核员
活动详情/activity/:id活动管理组织者、审核员
新增活动/activity/create活动管理组织者
编辑活动/activity/:id/edit活动管理组织者
报名列表/signup报名审核组织者、审核员
某活动的报名/activity/:id/signups报名审核组织者、审核员
场地列表/venue场地与场次审核员
场次列表/session场地与场次组织者、审核员

共 12 个页面。 注意三条拆分依据：

依据一：读和写分开。 “活动详情”和“编辑活动”是两个页面。合并的话权限判断和状态清理都会变复杂。

依据二：新增和编辑共用组件，但占两条路由。 它们字段相同，组件是一个；但用户需要能直接打开其中任意一个，所以路由是两条。

依据三：同一份数据的两个入口，共用一个组件。 /signup 和 /activity/:id/signups 用的是同一个列表组件，后者通过路由参数固定了活动筛选条件。

为什么要有两个入口：从活动详情进报名列表时，用户的心智是“看这个活动的报名”；从侧边栏进时，心智是“看所有待审核的报名”。两种场景需求不同，但界面完全一样，所以共用一个组件。

四、数据字段 ​

活动（Activity） ​

字段类型必填说明
idnumber系统生成主键
titlestring是标题，2 到 50 字
typeenum是类型：LECTURE 讲座 / COMPETITION 比赛 / PERFORMANCE 演出 / SPORTS 体育 / VOLUNTEER 志愿服务 / OTHER 其他
organizerIdnumber系统生成组织者 id，取自登录用户
organizerNamestring系统生成组织者姓名，列表展示用
quotanumber是名额上限，正整数，1 到 2000
approvedCountnumber系统维护已通过审核的人数，只读
pendingCountnumber系统维护待审核人数，只读
signupDeadlinestring是报名截止时间，yyyy-MM-dd HH:mm:ss
statusenum系统维护DRAFT / SIGNING / SIGNUP_CLOSED / FINISHED
offShelfboolean系统维护下架标记，默认 false
descriptionstring否活动说明，最多 500 字
createdAtstring系统生成创建时间
updatedAtstring系统生成最后更新时间

标“系统维护”和“系统生成”的字段，前端不能提交。 想改也改不了 —— 后端会忽略或报错。

报名记录（Signup） ​

字段类型必填说明
idnumber系统生成主键
activityIdnumber是关联的活动
activityTitlestring系统生成活动标题，列表展示用
studentIdnumber是学生 id
studentNamestring系统生成学生姓名
studentNostring是学号，10 位
studentClassstring否班级
statusenum系统维护PENDING / APPROVED / REJECTED / CANCELLED
remarkstring否学生填写的备注，最多 200 字
rejectReasonstring驳回时必填驳回理由，5 到 100 字
auditorNamestring系统生成审核人姓名
auditedAtstring系统生成审核时间
createdAtstring系统生成报名时间

场地（Venue） ​

字段类型必填说明
idnumber系统生成主键
namestring是名称，2 到 50 字，全局唯一
capacitynumber是容量，正整数
locationstring否位置，最多 100 字
remarkstring否备注，最多 200 字
enabledboolean是是否启用，默认 true

用 enabled 停用，不用删除。 删掉场地，历史场次就显示不出场地名了。

场次（Session） ​

字段类型必填说明
idnumber系统生成主键
activityIdnumber是关联的活动
activityTitlestring系统生成活动标题
venueIdnumber是关联的场地
venueNamestring系统生成场地名称
startTimestring是开始时间
endTimestring是结束时间，必须晚于开始时间
statusenum系统维护SCHEDULED / ONGOING / FINISHED / CANCELLED
remarkstring否备注（比如“初赛”），最多 100 字

用户（User） ​

字段类型说明
idnumber主键
usernamestring登录账号
realNamestring姓名
roleenumORGANIZER 组织者 / AUDITOR 审核员
departmentstring所属部门（校学生会、社团联合会等）

角色只有两个。 不做细到按钮的权限，也不做动态角色配置。这两个角色已经足够覆盖需求，多加一层会显著增加复杂度。

五、界面要求 ​

不要求做视觉设计稿，但有几个地方要有明确的呈现方式。

活动列表 ​

列呈现方式
活动标题可点击，进详情页
类型纯文字
状态彩色标签。草稿灰色、报名中绿色、报名截止橙色、已结束默认色；已下架另加一个灰标签
报名情况显示“42 / 100”；名额已满时用红色加粗
报名截止格式化的日期时间；已过期的时间用灰色
操作详情、编辑、下架 / 恢复、删除；按状态和角色显隐

报名列表 ​

列呈现方式
学生姓名纯文字
学号等宽字体（方便核对）
班级纯文字
活动标题长标题用省略号，鼠标悬停显示完整
报名时间格式化的日期时间
状态彩色标签。待审核橙色、已通过绿色、已驳回红色、已取消灰色
审核人纯文字，未审核时显示“—”
操作通过、驳回（仅待审核时可用）；撤销（已通过或待审核时可用）

状态与提示文案 ​

统一在 utils/dict.js 里维护。不要在页面里写死中文，否则同一个状态在不同页面的文案会不一致。

场景文案要求
下架确认“确定要下架‘活动标题’吗？下架后学生将无法报名，已有报名不受影响。”
删除确认“确定要删除‘活动标题’吗？删除后不可恢复。”
名额已满“名额已满，无法再通过新的报名。如需继续，请先调大名额或撤销已有的通过记录。”
时段冲突“与‘活动标题’在 2026-04-10 15:00 到 18:00 的场次冲突，请调整时间或更换场地。”
无数据（活动）“还没有活动。发布第一个活动，学生就能在手机上看到并报名了。”
无数据（报名）“这个活动还没有收到报名。”

这几条文案的共同点：说清“发生了什么”并且给出“下一步怎么办”。

对比一下不合格的文案：“操作失败”“名额不足”“数据为空”。它们都没有告诉用户接下来该做什么。

空状态与错误状态 ​

每个列表页都要区分这两种情况（见 5.5 四态页面规范）：

状态提示提供的动作
成功但无数据说明为什么没有数据“立即创建”或“去发布一个活动”
请求失败说明是网络问题还是服务器问题“重新加载”

这两种不能合并。 合并的后果是后端挂了的时候，用户以为是自己操作有问题。

六、非功能要求 ​

性能 ​

要求标准
首屏加载量生产构建下不超过 400 KB（gzip 后）
首屏时间Slow 4G 限速下 FCP 不超过 2 秒
列表响应换页、查询有 loading 反馈，不出现无响应的空白期
大列表每页最多 50 条，不一次性拉取全部数据

这些数字是优化的目标基线，也是 12.2 构建优化里要测的指标。

兼容性 ​

目标标准
桌面浏览器Chrome / Edge 最近两个大版本
屏幕宽度最小 1280 px 可用；1024 px 下可横向滚动，不破版
移动端管理端不要求适配。学生用的那一端是独立的 uni-app 工程，不共用这套样式

明确写上“不要求移动端适配”是有意义的。 不做这个声明的话，会有人问“手机上怎么是乱的”，而做适配要花掉大量时间在本来就不重要的场景上。

学生要用的手机端不在这个工程里 —— 它是一个单独的 uni-app 工程，有自己的页面、 自己的样式单位（rpx）和自己的组件库，规格见用户端需求规格。

可用性 ​

要求标准
危险操作删除、下架、驳回等操作必须二次确认
表单防重复提交中按钮置为不可点
离开提醒表单有未保存内容时，离开要提醒
错误可恢复请求失败时给出重试入口，不要只提示一句

安全 ​

要求标准
传输必须使用 HTTPS
token 存储localStorage。要明白它的 XSS 风险，见 12.1
权限校验必须在后端做，前端只做界面控制
敏感信息不把密钥写进 VITE_ 环境变量（会被打包进产物）

最后一条要强调：前端代码里的所有东西，用户都能看到。前端没有秘密。

七、验收方式 ​

项目结束时按这份清单逐项验收。每一项都要在线上环境验证，不是本地。

编号验收项怎么验证
1用组织者账号能登录输入账号密码，进入看板
2未登录访问后台被拦清掉本地存储，直接访问 /activity，跳登录页
3登录后刷新不丢登录态在活动列表页按 F5，仍在活动列表页
4能创建一个活动填写表单保存，列表里看到它
5能发布活动草稿活动点发布，状态变成报名中
6能修改活动改标题保存，列表里的标题变了
7已发布的活动不能把名额改小于已通过人数造一条有通过记录的活动，把名额改小，被拦下
8能下架和恢复活动下架后标签出现，恢复后消失
9草稿之外的活动不能删除报名中的活动，删除按钮不显示或点击被拦
10能审核通过一条报名状态变已通过，活动的报名数加一
11驳回必须填理由不填直接提交，被拦下
12撤销通过会释放名额撤销后活动的报名数减一
13能新增场地保存后出现在场地列表
14场地重名被拦用已存在的名称新增，提示重复
15能给活动安排场次选活动、场地、时段，保存成功
16冲突的场次被拦同一个场地安排重叠时段，提示冲突并说明和谁冲突
17边界相接不算冲突安排 14:00-17:00 和 17:00-20:00，应该成功
18看板数字和列表一致看板的活动总数等于活动列表的总数
19组织者看不到别人的数据用组织者账号，看活动列表只有自己的
20界面按角色区分组织者账号看不到“场地管理”菜单
21子路由刷新不 404在 /activity 页面按 F5，页面正常
22手机能打开线上地址用手机浏览器访问

第 17 项要单独强调。 “边界相接不算冲突”是一条容易被忽略的规则，也是区分“做完”和“做对”的地方。

第 18 项容易出问题。 看板和列表用的是两个接口，如果统计口径不一致（比如看板没按角色过滤），数字会对不上 —— 这种不一致用户一眼就能看出来，会严重影响可信度。

小结 ​

  • 先写清“不做什么”，它决定了你遇到新需求时该不该动手。
  • 每个功能都要有可验证的验收标准。 “实现了活动管理”不是验收标准，“能创建、能发布、能修改、能下架”才是。
  • 12 个页面，拆分依据是“读和写分开、新增编辑共用组件、多入口共用页面”。
  • approvedCount、pendingCount、status、offShelf 都是只读字段，前端不能提交。
  • 场地用 enabled 停用，不删除，否则历史场次会丢场地名。
  • 角色只有两个，够用就好。多加一层会显著增加复杂度。
  • 提示文案要给“下一步怎么办”，不能只说“操作失败”。
  • 无数据和失败必须分开，它们引导用户做的事完全不同。
  • 明确声明不做移动端适配，避免在不重要的场景上花时间。
  • 权限必须后端校验，前端只做界面控制。前端没有秘密。
  • 验收要在线上做，不是本地。 本地能跑不等于交付成功。
  • “边界相接不算冲突”和“看板与列表数字一致”是最容易漏的两项。
