综合项目 · 校园活动服务平台 ​

这一部分是综合项目的规格文档。它不是教程，是你们做项目时要照着执行的约定。

这是什么项目 ​

校园活动服务平台 —— 给学生会、社团、学院教务处使用的活动管理平台，有两个端：

端谁用形态
管理端组织者、审核员电脑上的 Web 后台
用户端学生手机上的 H5 / 微信小程序

学生用手机报名，组织者在电脑上发布活动、审核报名、安排场次。系统负责三件事：

  1. 让活动从创建到结束有一个清晰的状态流程
  2. 让名额和报名数之间保持一致
  3. 让同一个场地在同一个时段不出现冲突

两个端共用一套后端接口。 管理端是 12 周课时的主体；用户端不占课时，是管理端跑通之后的第二个端，规格见用户端需求规格，做法见用户端 · uni-app 实战。

谁在用 ​

角色日常做什么系统里的权限
活动组织者发布活动、看报名情况、审核报名、安排场次只能看和管理自己的活动
审核员审核所有活动的报名、维护场地信息能看所有活动，能审核任何报名
学生在手机上浏览活动、报名、查看审核结果登录用户端；只能看到自己的报名记录，只能取消自己的报名

学生的报名数据由后端提供。管理端只读这些数据（在列表里看到学生信息、报名记录）， 用户端负责产生这些数据（提交报名、取消报名）。

主线流程 ​

整条业务主线只有三步：

① 活动发布            ② 报名审核              ③ 场次安排
组织者创建活动         学生报名后组织者审核      通过审核的学生参加
设置名额与截止时间      通过则占用一个名额        安排时段与场地
发布后学生可报名        驳回则释放名额            检测时段冲突

这条主线必须在项目里完整跑通。 其余功能（数据看板、场地维护）是围绕主线的辅助功能。

五个功能模块 ​

管理端按业务拆成五个模块：

模块主要页面涉及角色依赖
登录鉴权登录页全部无
活动管理活动列表、详情、新增、编辑组织者、审核员登录鉴权
报名审核报名列表、某活动的报名组织者、审核员活动管理
场次与场地场地列表、场次安排组织者、审核员活动管理
数据看板看板首页组织者、审核员上述全部

用户端拆分方式不一样，它按学生的一次完整动作来分，只有 5 个页面：

页面学生在这一页干什么
活动列表找活动，支持搜索和下拉刷新
活动详情看活动的完整信息与剩余名额
报名表单填联系方式与备注，提交报名
我的报名看自己所有报名的审核状态，能取消
个人中心登录、退出、看个人信息

两边的拆分依据为什么不同，见用户端需求规格的“页面清单”一节。

技术约束 ​

规格文档不规定技术选型，但课程有一条基线，不符合的要提前说明理由。

管理端：

类别基线
框架Vue 3.5，组合式 API
构建Vite 8.3
路由Vue Router 5.3
状态Pinia 4.0
UI 库Element Plus 2.14
请求axios 1.20
包管理pnpm

用户端：

类别基线
跨端框架uni-app（经典版，不是 uni-app x）
脚手架CLI 方式，基于 Vite（uni-preset-vue#vite）
构建Vite 5.2（官方模板锁定，不要手动升到 8）
框架Vue 3.4（同上，模板锁定）
路由pages.json 配置式，用 uni.navigateTo 等 API，不用 vue-router
状态不引入 Pinia，用 uni.storage + 工具函数
UI 库Wot UI（@wot-ui/ui）
请求uni.request 自封装（沿用管理端的五个设计）

用户端的版本看起来比管理端旧，这不是配置失误 —— uni-app 官方模板锁定了 Vite 5 与 Vue 3.4， 跨端编译器与其版本是绑定的，手动升级会直接编译失败。原因见用户端总览。

完整的版本清单见工具链与版本清单。

为什么要有这条基线：全班用同一套技术栈，遇到问题时同学之间能互相帮忙，老师也能快速定位。如果你的项目有特殊理由要用别的技术（比如你们组已经熟悉 Ant Design Vue），提前说明即可，不是硬性要求。

做了用户端的话，多交两样

前端工程化开发 48 学时不要求做用户端，它是延伸内容。如果你们组做了，把下面两项一起交：

  • 用户端的访问方式：H5 线上地址，或小程序的体验版二维码（答辩演示用体验版就够）
  • README 里补一段用户端的运行方式：pnpm dev:h5 与 pnpm dev:mp-weixin 分别是做什么的

不做用户端不影响上面那几项的评分。做了的话，答辩时能多讲一个技术难点（跨端适配），是加分项。

三阶段节奏 ​

阶段对应单元交付什么
阶段一 · 立项与骨架单元 1 到 3页面清单、接口清单、工程骨架、代码规范配置
阶段二 · 功能实现单元 4 到 10各模块页面与逻辑，单元 5 到 10 的案例直接对应项目模块
阶段三 · 交付单元 11 到 12完整主线功能、优化数据、线上地址、交付文档
（延伸）用户端阶段三之后5 个页面 + H5 或小程序发布，不占课时

详细的阶段划分和每周检查点见三阶段交付。

评分维度 ​

维度权重看什么
功能完整度30%主线三步能不能完整走通，边界情况处理了没有
工程质量25%目录结构、代码组织、命名、有没有大量重复代码
工程化实践20%版本控制、代码规范、构建优化、部署上线
文档质量15%README 能不能让人跑起来，设计文档有没有取舍分析
答辩表现10%能不能讲清一个技术难点，能不能回答提问

“工程质量”占 25%，比多数人预期的高。 它不是看你的功能多不多，是看代码能不能给别的人看。
