单元 4 · AI 协作：别让它把 Vue 2 的写法带进来 ​

从这一章开始你写的是真正的 Vue 代码。AI 在这里能帮你很多 —— 它见过的 Vue 代码比你多几百倍，解释概念、改写写法、排查响应式失效，它都拿手。

但它也有一个很具体的短板：它见过的 Vue 2 代码同样比你多几百倍。 Vue 2 存在了七年，Vue 3 的组合式写法是后来才普及的，训练数据里两者的比例并不偏向新的那一方。所以它给你的代码里，经常混着几处早就该淘汰的写法。

这一节的目标不是“怎么让它写 Vue 代码”，而是怎么一眼认出它写的是哪一版的 Vue。

这一章哪些活能交给 AI ​

判断标准：解释和改写可以交，判断“这算不算 Vue 3 写法”不能交 —— 因为这事它自己就常出错。

任务能交给 AI 吗为什么
把选项式 API 改写成组合式 API可以改写本身是机械工作，但你要逐行核对
解释一个响应式为什么没生效可以它见过的失效场景比教程列的全
列出 Vue 3 里已经不再推荐的旧写法可以当检查清单用，比你自己回忆省事
讲清 Proxy 与 Object.defineProperty 的差别可以讲到能判断对错这一层就够
对比 ref 与 reactive 的取值场景可以但最终按项目的约定来
判断“你写的这段是不是 Vue 3 写法”不能直接信它常把自己混进去的 Vue 2 写法当成正确的
决定用不用某个新 API不行取决于项目的 Vue 版本下限，它不知道
让它直接改你 src/ 下的文件不行改完你还是得逐行读，不如自己写一遍

中间那行是这一章的核心矛盾：你请它帮你检查有没有 Vue 2 残留，而它自己就是残留的来源。 所以检查这件事必须你自己会做。

提示词怎么写 ​

1. 让它把选项式 API 改写成组合式 API ​

text
把下面这段选项式 API 的组件改写成 <script setup> 的组合式写法：

[粘贴完整组件]

要求：
1. 改完把“改了哪些地方”列成一个对照表，左列原写法，右列新写法
2. 特别注意这几处：data、computed、methods、watch、
   生命周期钩子、this 的引用方式
3. 如果某处你没有把握，单独列出来，不要改

为什么这么写：第 1 点的对照表是关键 —— 改写本身它做得不错，但改写理由它通常不写。有了对照表，你就能逐行核对“它为什么这么改”，而不是看一遍“像那么回事”就收下。第 3 点给它留了退路，宁可它标一个“没把握”，也好过它猜一个看起来合理的写法。

2. 让它给你一份旧写法对照清单 ​

text
请列一份对照表：Vue 2 里的写法 / Vue 3 里对应的写法 / 为什么改。

覆盖这些方面：创建应用、注册插件、数据声明、定义方法、注册全局组件、
生命周期钩子的名字、数组和对象的更新方式、模板里的过滤器、事件修饰符。

要求：
1. 只列确实变了的部分，不要凑数
2. 每一项给一小段代码，能直接看出新旧差别
3. “为什么改”用一句话说清，我要的是判断依据，不是原理

为什么这么写：这份对照表是一次性投入、长期用的东西 —— 把它存进自己的笔记，以后审 AI 产出的代码时对着扫一遍就行。要求“只列确实变了的部分”是因为它很容易把没变的也列进来凑数，那样清单就没用了。要求“一句话说清为什么改”，是为了让你能判断出它有没有把某两件事的因果关系说反。

3. 让它帮你排查响应式失效 ​

text
我改了数据，界面不更新。这是相关代码：

[粘贴 script setup 部分和模板部分]

我期望的行为是：[说清什么操作之后界面应该变成什么样]
我实际看到的是：[说清实际是什么样]

请回答：
1. 按可能性排序，列出可能导致不更新的原因
2. 每个原因对应的验证办法，要具体到“看哪一行 / 加什么输出”
3. 你从这个片段里能直接确认的原因是什么，直接说结论

不要建议我换一种写法重写，我要先知道现在为什么不行。

为什么这么写：响应式失效是一类“现象相同、原因各不同”的问题 —— 可能是解构丢了响应性，可能是改了对象里新增的属性，可能是模板里用了没在 setup 里暴露的变量。让它排序给原因，比让它直接给一段新代码有用得多。最后一句是在拦它“别管为什么了，我给你重写一版” —— 那样你学到了零。

AI 在这一章容易错什么 ​

混进 Vue 2 的写法 ​

现象：它给的代码里出现这些东西：

你看到的问题在哪
new Vue({ ... })创建应用现在用 createApp()
Vue.use(SomePlugin)现在写成 app.use(SomePlugin)
filters: { ... } 和模板里的 {{ x | fmt }}过滤器已经被移除，改用计算属性或函数
this.$set(obj, 'key', value)响应式换成 Proxy 之后不再需要它
beforeDestroy / destroyed钩子改名为 onBeforeUnmount / onUnmounted
在 setup 里写 this.xxx组合式 API 里没有 this

原因：Vue 2 存在的时间长，代码总量比 Vue 3 多。它在生成代码时，按“见过的频率”加权，而不是按“哪一版更新”。

怎么处理：记住上面这张表，扫一遍它给的代码。 出现任何一个，就说明它这次是按 Vue 2 的记忆生成的，整段代码都要重新审 —— 不是只改这一处，而是它这一版的其他地方也可能有同类问题。

解构之后失去响应性，它却说没问题 ​

现象：你写了 const { count } = state 或 const { title } = props，然后发现改了 state.count 界面不动。你问它，它说“写法正确”。

原因：解构拿到的是当时那一刻的值，不是那个响应式引用本身。它判断“对不对”的依据是语法有没有错，而这里的语法完全没问题 —— 这是运行时行为的问题，它看不出来。

怎么处理：记住这条规则 —— 从 props 或 reactive 对象里取值时，不要解构基本类型。 需要解构时用 toRefs 或 toRef：

js
import { toRefs, toRef } from 'vue'

// props 解构：用 toRef 保住那一项的响应性
const { title } = toRefs(props)          // 全部解构
const title = toRef(props, 'title')      // 只取一项

// reactive 对象解构同理
const { count, list } = toRefs(state)

注意 toRefs 之后拿到的是 ref，脚本里读写要带 .value，模板里不带。这正好是下面那条。

把 .value 的规则说反 ​

现象：它说“ref 在模板里要写 .value，在脚本里不用写”，或者反过来。

原因：这两条规则方向相反，很容易说串。而且它给的代码有时自己也不一致。

怎么处理：记死一句话 —— 脚本里要 .value，模板里不要。

js
const count = ref(0)

count.value++                              // 脚本里：要 .value
vue
<!-- 模板里：不要 .value -->
<span>{{ count }}</span>

为什么会这样：模板里的顶层 ref 会被自动解包。但自动解包只对顶层生效 —— 如果 ref 是某个对象的一个属性，模板里照样要 .value。这一条边界它常讲错，也是4.4里那个“自动解包的规则与边界”专门讲的。

用 reactive 装基本类型 ​

现象：它写 const count = reactive(0)，或者 const name = reactive('')。

原因：reactive 和 ref 的功能有重叠，它有时不分场景地混用。

怎么处理：一句话判断 —— reactive 只接受对象和数组，基本类型一律用 ref。 写 reactive(0) 不会报错，但返回的东西不是你要的，改它界面也不会动。这个错比语法错更难查，因为控制台是干净的。

还有一类错误：在插值表达式里写语句或复杂运算

现象：它给你写 {{ list.filter(i => i.status === 'SIGNING').length }}、{{ price.toFixed(2) * count }}，甚至 {{ count = 10 }}。

原因：模板里能写表达式，但只能写表达式，不能写语句，也不适合做复杂运算。它对这条边界通常不敏感，因为语法上大多数情况确实能跑。

怎么处理：三条判断标准，扫一眼它的模板就能用：

  1. 里面有没有赋值（=）？有就是语句，模板里不合法。
  2. 里面有没有循环或条件分支的完整逻辑？有就该抽成计算属性。
  3. 同一段运算在模板里出现两次以上？抽成计算属性，顺便拿到缓存。

按4.2里的说法，插值表达式只该放“一眼能看出结果”的东西。改法就是抽出来：

js
// 模板里改成 {{ signingCount }}
const signingCount = computed(
  () => list.value.filter(i => i.status === 'SIGNING').length
)

多写一行，换来的是模板还能读懂，以及这段运算不会每次渲染都重算一遍。

怎么验收 AI 的产出 ​

这一章的产出是 Vue 组件代码。验收动作分两层：先扫旧写法，再验运行时行为。

  • [ ] 代码里没有 new Vue、Vue.use、filters、this.$set、beforeDestroy、this.xxx
  • [ ] 没有从 props 或 reactive 对象里直接解构基本类型；需要解构时用了 toRefs 或 toRef
  • [ ] ref 的取值写对了：脚本里带 .value，模板里不带
  • [ ] 没有用 reactive 装基本类型
  • [ ] 插值表达式里没有赋值，没有复杂运算，重复的运算已经抽成计算属性
  • [ ] 三句话检查能过：说得出它做了什么、为什么这么写、出错会怎么表现
  • [ ] 你自己在浏览器里点一遍，界面按预期更新了
  • [ ] 控制台没有报错和警告

前五条对应“先是 Vue 3 的写法”，第六、七条对应“真的能跑”，最后一条对应“别把问题留给下周”。Vue 的很多错误只在控制台提示，界面上看不出来 —— 一定要开着控制台看一遍。

练习 ​

给 AI 一段 Vue 2 的代码，让它改写，然后逐行核对 ​

任务：自己找一段 Vue 2 的选项式 API 代码（可以从旧教程、旧项目里找，也可以按4.1的字段自己写一段），让 AI 改写成组合式 API，然后逐行核对，记录它改对了哪几处、漏了哪几处。

要求：记录里必须包含这四项：

项要求
原始代码完整保留，注明它用了哪几处 Vue 2 的写法
AI 的改写结果完整保留，不要只留你改完的版本
逐行核对表三列：原写法 / 它改成了什么 / 对不对
漏改与错改清单每一条写清你是怎么发现的、正确写法是什么
验收标准与参考思路

为什么要“逐行核对”而不是“跑一下看看”：因为改写错误的代码经常能跑起来。beforeDestroy 改成 onBeforeUnmount 漏了，表现只是卸载时的清理没执行 —— 页面上看不出异常，直到某天定时器越来越多。这类问题只能靠读代码发现。

思路提示：

  • 原始代码里至少要故意放 4 处 Vue 2 写法：new Vue、filters、this.$set、beforeDestroy。这样才有足够的机会看出它漏没漏。
  • 核对时对着上面那张旧写法表逐个搜关键词，比从头读到尾可靠。
  • 如果它顺手把 filters 改成了 computed，检查一下改完的行为一样不一样 —— 过滤器可以接收参数、可以用在多个地方，改成计算属性时这些地方容易走样。
  • 如果它改对了，也把“改对”记下来。 知道自己哪类问题不需要盯，同样是收获。

不合格的写法：

让 AI 把 Vue 2 的代码改成 Vue 3 了，跑起来没问题。

“跑起来没问题”这句话里没有任何可验证的信息。它漏掉了哪几处？漏掉的那几处会不会在特定操作下才暴露？

合格的写法：

原始代码里有 4 处 Vue 2 写法。AI 改对了 new Vue → createApp、 this.$set → 直接赋值，两处漏改：filters 保留了原样、 beforeDestroy 没改成 onBeforeUnmount。 漏掉 filters 是我搜 filters 关键词发现的； 漏掉 beforeDestroy 是我对着钩子对照表逐一比出来的 —— 页面上看不出问题，因为它只在卸载时执行。 我改成 onBeforeUnmount 之后，在钩子里加了一句输出， 切换路由时能看到它被执行了，才算确认。

差别在于：后者把“怎么发现的”和“怎么确认改对了”都写清楚了。这份记录里最值钱的是那两条漏改 —— 它告诉你该盯哪几类地方。
